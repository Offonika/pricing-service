# Integration Contract Draft: `1С Экспертиза` -> `expertise_case`

Дата фиксации: `2026-04-02`

Статус: `draft for alignment from screenshots + configurator + MSSQL`

## 1. Что уже подтверждено по UI `1С`

По предоставленным скриншотам документа `Экспертиза` уже можно считать подтвержденными такие бизнес-поля:

### 1.1. Журнал документов

- `Дата`
- `Номер`
- `Контрагент`
- `Ответственный`

### 1.2. Шапка документа

- `Номер`
- `Дата`
- `Организация`
- `Подразделение`
- `Контрагент`
- `Ответственный`
- `Договор контрагента`

### 1.3. Вкладка `Товары`

По строке товара видны:

- `Номенклатура`
- `Единица измерения`
- `Качество`
- `Цена`
- `Количество`
- `Сумма`
- `Причина возврата`
- `Решение`
- `Список причин`

Дополнительно видны отдельные поля документа:

- `Комментарий менеджера`
- `Причина1`
- `Причина2`
- `Причина3`
- `Причина4`
- `Причина5`
- `Комментарий отдела брака`

### 1.4. Вкладка `Заявление`

Видны:

- поле `Удостоверение`
- контактная информация контрагента
- телефоны
- печатные формы:
  - `Печать заявления`
  - `Печать Акта передачи`

Практическое уточнение по процессу:

- поле `Удостоверение` существует в форме, но по текущему бизнес-процессу паспортные данные фактически не заполняют;
- для MVP это поле не должно участвовать ни в обязательном extraction contract, ни в модели `expertise_case`.

### 1.5. Вкладка `Отказ`

Видны печатные формы:

- `Печать бланка отказа ФЛ`
- `Печать бланка отказа ЮЛ`

### 1.6. Подчиненность документа

Подтверждена цепочка:

- `Реализация товаров и услуг -> Экспертиза -> Возврат товаров от покупателя`

Это значит, что документ `Экспертиза` не изолирован, а встроен в учетный lifecycle продажи и возврата.

## 2. Предлагаемый mapping в backend

### 2.1. Уровень кейса `expertise_case`

Предлагаемый mapping:

- `external_id`
  - источник: технический `Ref` документа `Экспертиза`
  - статус: подтвержден через `_Document9868._IDRRef`
  - внешний формат `Wave 1`: `hex string` `0x...`
- `onec_expertise_ref`
  - источник: технический `Ref`
  - статус: подтвержден через `_Document9868._IDRRef`
  - внешний формат `Wave 1`: `hex string` `0x...`
- `onec_expertise_number`
  - источник: поле `Номер`
- `created_at_source`
  - источник: поле `Дата`
- `organization_ref`
  - источник: `_Fld9870RRef`
  - статус: подтверждено как link на `_Reference66`
  - внешний формат `Wave 1`: `hex string` `0x...`
- `store_name`
  - источник: поле `Подразделение`
- `customer_name`
  - источник: поле `Контрагент`
- `customer_phone`
  - источник: контактная информация на вкладке `Заявление`
  - статус: технический контур хранения уже локализован до `_InfoRg6402`, рабочее правило выбора primary phone подтверждено SQL-статистикой
  - правило `Wave 1`:
    - сначала `Телефон контрагента`
    - затем `Рабочий`
    - затем `Доп. телефон для переноса`
    - если телефонов нет, кейс все равно создается, а телефон дозаполняют вручную
- `owner_user_external_id`
  - источник: поле `Ответственный`
  - статус: стабилен как `_Fld9875RRef` / `_Reference69._IDRRef`
- `contract_ref`
  - источник: `_Fld9876RRef`
  - статус: подтверждено как link на `_Reference37`
  - внешний формат `Wave 1`: `hex string` `0x...`
- `linked_sale_ref`
  - источник: `_Fld9878RRef`
  - статус: подтверждено как link на документ-основание `Реализация`
  - внешний формат `Wave 1`: `hex string` `0x...`
- `linked_customer_order_ref`
  - источник: `_Fld9909RRef` в строке `Товары`
  - статус: подтверждено как link на `_Document132 = Заказ покупателя`
- `linked_customer_order_number`
  - источник: номер связанного `_Document132`
  - статус: подтверждено, рекомендуется вынести в отдельное поле для Wave 1
- `problem_summary`
  - источник: `Комментарий менеджера` и/или первая причина дефекта
  - правило `Wave 1`:
    - если заполнен `Комментарий менеджера`, берем его;
    - иначе берем первую непустую `return_reason_name` из строки товара;
    - если нет ни комментария, ни причины возврата, поле остается `null`
- `decision_code`
  - источник: поле `Решение` в строке товара
  - статус: `_Enum9869`, уже подтверждены значения `Принято` и `Отказано`
  - нормализация для Wave 1:
    - `Принято` -> `approved`
    - `Отказано` -> `rejected`
    - иное / пустое -> `null`
- `decision_comment`
  - источник: `Комментарий отдела брака` и/или `Комментарий менеджера`
  - правило `Wave 1`:
    - если заполнен `Комментарий отдела брака`, берем его;
    - если он пустой, поле остается `null`;
    - `Комментарий менеджера` не используем как замену для `decision_comment`
- `payload`
  - источник: сырой snapshot документа и связанных сущностей

### 2.2. Уровень строк / предмета экспертизы

Важный вопрос: в документе есть табличная часть `Товары`, значит нужно подтвердить доменную гранулярность.

Варианты:

1. `1 документ Экспертиза = 1 expertise_case`, а табличная часть хранится в `payload`.
2. `1 строка товара = 1 expertise_item` внутри одного кейса.

Для Wave 1 рекомендуется:

- считать `1 документ = 1 expertise_case`;
- табличную часть пока сохранять целиком в `payload`;
- даже если в документе несколько строк товара, в Wave 1 это все равно один `expertise_case`;
- если позже появится реальная потребность разносить строки по отдельным решениям, во Wave 2 выделять `expertise_case_item`.

## 3. Что уже можно считать почти решенным

На основании формы `1С` уже можно уверенно сказать:

- подразделение действительно есть в документе;
- ответственный действительно есть в документе;
- контрагент действительно есть в документе;
- телефон, скорее всего, можно брать из вкладки `Заявление` / контактной информации;
- решение по экспертизе уже есть в учетной форме;
- есть связь документа с продажей и возвратом;
- есть печатный контур заявления, акта передачи и отказа.

На основании прямого чтения SQL уже можно добавить:

- физическая таблица документа `Экспертиза` найдена точно: `_Document9868`;
- физическая табличная часть `Товары` найдена точно: `_Document9868_VT9886`;
- физическое поле документа-основания подтверждено: `_Fld9878RRef`;
- физические поля комментариев подтверждены:
  - `_Fld9884`
  - `_Fld9885`;
- строка товара реально хранит цену, количество и сумму;
- уже расшифрованы ключевые object tables:
  - `_Reference66` = организация;
  - `_Reference68` = подразделение;
  - `_Reference54` = контрагент;
  - `_Reference69` = ответственный;
  - `_Reference37` = договор;
  - `_Reference80` = склад;
  - `_Reference62` = номенклатура;
  - `_Reference41` = единица измерения;
  - `_Reference48` = качество;
  - `_Reference25` = виды контактной информации;
  - `_Reference8913` = справочник причин возврата;
  - `_Reference9867` = справочник причин отказа / `Причина1..5`;
  - `_Enum9869` = перечисление `осиРешение`;
  - `_Enum376` = верхний тип контактной информации;
  - `_Document203` = документ-основание `РеализацияТоваровУслуг`;
  - `_Document132` = `Заказ покупателя`;
- локализован базовый контур контактной информации:
  - `_InfoRg6402._Fld6403_RTRef/_Fld6403_RRRef` = объект-владелец КИ;
  - для контрагентов используется `RTRef = 0x00000036`;
  - `_InfoRg6402._Fld6405_RRRef` = вид КИ (`_Reference25`);
  - `_InfoRg6402._Fld6406` = строковое представление значения;
  - `_InfoRg6402._Fld6404RRef` = enum `_Enum376`, где:
    - order `1` используется для телефонов;
    - order `0` используется для адресов;
- по статистике контрагентов, реально участвующих в экспертизах:
  - `142` контрагентов имеют хотя бы один заполненный телефон;
  - `122` имеют только `Телефон контрагента`;
  - `14` имеют только `Рабочий`;
  - `6` имеют `Телефон контрагента` плюс дополнительный телефонный вид;
  - `Доп. телефон для переноса` без других телефонов в экспертизах не встретился;
- практическое правило выбора `primary phone` можно фиксировать так:
  - сначала `Телефон контрагента`;
  - затем `Рабочий`;
  - затем `Доп. телефон для переноса`.
  - если телефон не найден ни в одном виде КИ, `expertise_case` все равно создается, а номер дозаполняют вручную на операционном этапе.
- модель `1 документ = 1 шапка + 1..N строк товара` подтверждена на уровне SQL.

То есть главный вопрос уже не в том, есть ли эти бизнес-сущности, а в том, как именно технически их читать из `1С`.

## 4. Что еще не подтверждено технически

Для реальной интеграции все еще нужны:

- техническое значение `_Fld9909RRef`:
  - link на `_Document132` уже подтвержден;
  - тип `_Document132` уже подтвержден как `Заказ покупателя`;
  - для Wave 1 согласовано поднимать этот link в отдельные backend-поля;
- нужно ли вообще тащить `_Fld9910` во внешний payload, если он остается константным technical blob;
- есть ли отдельное физическое поле строки под UI-элемент `СписокПричин`, или это действительно только форма поверх `Причина1..5`.

Уже согласованные решения для Wave 1:

- `1 документ Экспертиза = 1 expertise_case`, даже если строк товара несколько;
- если по строкам товара решения различаются, кейс все равно остается одним, а источником истины считаются item-level значения в `payload.items[]`;
- `linked_customer_order_ref` и `linked_customer_order_number` храним отдельными backend-полями;
- `decision_code` нормализуем до двух значений:
  - `approved`
  - `rejected`
- поля НДС в Wave 1 не нужны как часть бизнес-модели и могут оставаться только в сыром payload либо быть пропущены адаптером.
- `_Enum363` и `_Enum364` отдельно сейчас не расшифровываем, потому что для MVP они не нужны.
- `organization_name`, `contract_name`, `return_reason_name` в Wave 1 остаются display-данными внутри `payload`, без отдельных top-level полей кейса;
- `linked_return_ref` отдельной backend-колонкой в Wave 1 не заводим; если ссылка появится в extraction contract, сначала сохраняем ее в `payload`, а в отдельное поле выносим только при явной операционной необходимости.

## 7. Практический вывод

Скриншоты уже закрыли значимую часть бизнес-неопределенности.

Теперь задача уже не в согласовании модели, а в аккуратной реализации read-only extraction contract и его адаптера.

Следующий правильный шаг:

- не спорить уже про состав бизнес-полей;
- взять read-only SQL/метаданные `1С`;
- зафиксировать точный extraction contract для адаптера sync.
