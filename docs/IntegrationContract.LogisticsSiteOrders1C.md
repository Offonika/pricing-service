# Integration Contract: Site Orders / RTU -> Logistics

Документ фиксирует отдельный поток логистики для заказов интернет-магазина,
которые в 1С проходят не как `ПеремещениеТоваров`, а как связка:

```text
Заказ покупателя с сайта -> Реализация товаров и услуг -> сборка РТУ -> физическая доставка/выдача
```

Этот контракт относится к волне пилота после foundation-сценария
передачи/приемки `ПеремещениеТоваров`. В `pricing-service` поток реализуется
read-only синхронизацией РТУ из SQL `1С` через существующий `ONEC_DATABASE_URL`:
новые секреты и отдельные подключения не нужны.

Этот поток связан с документами:

- [Transition_Status_Layer_Between_1C_and_B24_2026-04-02.md](order_flow/Transition_Status_Layer_Between_1C_and_B24_2026-04-02.md)
- [ONEPAGE_Unclaimed_Site_Orders_2026-04-03.md](order_flow/ONEPAGE_Unclaimed_Site_Orders_2026-04-03.md)
- [LogisticsTransportAsIs.md](LogisticsTransportAsIs.md)

## 1. Почему Это Отдельный Поток

Для заказов сайта нельзя считать готовность к логистике только по
`ЗаказПокупателя`.

В текущем процессе:

- сайт создает `Заказ покупателя`;
- на основании заказа создается `Реализация товаров и услуг` (`РТУ`);
- собирается уже `РТУ`, а не исходный заказ;
- физическое перемещение/выдача должно стартовать только после готовности `РТУ`.

Это совпадает с уже зафиксированным архитектурным решением: не двигать внешние
статусы по "сырым" документам 1С, а считать derived operational status во
внешнем backend.

## 5. Как Определять Склад Получателя

Для потока заказов сайта в MVP не нужна отдельная доработка поля `ПВЗ / пункт
выдачи`: склад получателя определяем через способ доставки и адрес самовывоза.

Правило для `Самовывоз`:

1. Берем `Способ доставки с сайта` из `_Document132._Fld9266`.
2. Если значение = `Самовывоз`, берем адрес из:
   - `_Document132._Fld2422` (`Дополнение к адресу`), приоритетно;
   - `_Document132._Fld2395` (`Адрес доставки`), fallback;
   - `_Document203._Fld4965` / `_Document203._Fld4952`, если в заказе пусто.
3. Ищем ровно один активный склад/точку в `logistics_warehouse`, где адрес
   совпадает с `payload.address_aliases`, `payload.aliases`, `payload.addresses`,
   `payload.address`, `payload.pickup_address`, названием или `external_id`.
   `payload.address_aliases` заполняется повторяемым read-only sync из
   `_Reference68._Fld9249 -> _Reference80`, а matching допускает не только
   полное вхождение строки, но и уверенное совпадение адресных токенов
   `улица/шоссе + дом + павильон`. Город, бренд и часы работы не считаются
   достаточным совпадением; если павильон указан в обеих строках и различается,
   документ уходит в `manual_review`.
4. Фактический склад-получатель берем из найденной записи
   `logistics_warehouse`.

Если адрес не сопоставился однозначно, документ должен попадать в
`manual_review`, а не в автоматическую логистическую очередь.

Подтвержденное бизнес-правило для локальной выдачи: если способ доставки -
внутренний `Самовывоз`, но все адресные поля пустые, либо однозначно найденный
склад получателя совпадает со складом РТУ, отдельная логистическая единица не
создается. РТУ остается в ТЗП исходного подразделения. Sync увеличивает счетчик
`local_pickup_skipped`, закрывает ставший неактуальным открытый `manual_review`
этой РТУ и не создаёт `logistics_transfer`.

ОТМЕНЕНО (2026-08-28): массовое исключение РТУ со способами доставки `СДЭК`,
`Почта России`, `Доставка курьером` в `rtu_external_carrier_unmapped`, а также
автоматический перевод таких РТУ в `with_external_carrier` системным событием
`handed_to_external_carrier` с `source = 1c_sync`. Причина: до внешнего
перевозчика заказ проходит физическое плечо нашего водителя, которое должно
подтверждаться сканированием, а не read-only синхронизацией.

Решение 2026-08-28: РТУ со способами доставки `СДЭК`, `Почта России` и
`Доставка курьером` после прохождения readiness gate создаются как
логистические единицы на исходном складе в состоянии `at_warehouse`.
Передача нашему водителю подтверждается только сканированием и событием
`handed_to_driver`.

ОТМЕНЕНО (2026-08-28): передачу внешнему перевозчику вручную подтверждает
водитель, логист либо сотрудник точки сдачи. Причина: сильный факт приемки
должен приходить от самой внешней службы доставки по API.

ОТМЕНЕНО (2026-08-28): `pricing-service` напрямую принимает API-события
перевозчика, создает `handed_to_external_carrier` с `source = carrier_api` и
сам переводит сделку в `IN_DELIVERY`. Причина: адаптеры СДЭК/Почты уже
подключены к Bitrix24 и действующие роботы CRM двигают сделки по их событиям.

Пока наш водитель везет заказ до СДЭК/Почты, логистическая единица находится в
`in_transit`, а CRM-сделка остается в `FINAL_INVOICE` / `Готов к отгрузке`.
После приемки внешней службой существующая интеграция Bitrix24 самостоятельно
ведет внешние стадии сделки. `pricing-service` не подключается к API
перевозчиков повторно и не создает дублирующий outbox. Внешние статусы не
зеркалируются в логистический монитор: пользователь видит их только по стадиям
сделки Bitrix24. Технический readback, если он потребуется для закрытия
внутреннего водительского плеча, не создает внешний пользовательский статус и
ничего не записывает обратно в CRM. Read-only синхронизация `1С` не создает ни
одно из этих физических событий.

Способ доставки однозначно определяет тип внешнего перевозчика. Если точка
сдачи/терминал для этого перевозчика еще не настроены, РТУ остается доступной
для распознавания QR, но ее отправка блокируется через `manual_review` до
настройки точки. Такой случай не считается неизвестным QR.

В `manual_review` логист выбирает склад/точку вручную. Решение должно
сохраняться как аудит с исходной строкой адреса, выбранной точкой и
пользователем, чтобы последующие правила сопоставления можно было улучшать на
фактах.

Дополнительный подтверждающий источник для aliases точек выдачи - публичная
страница `https://master-mobile.ru/contacts/`. Адреса с сайта можно применять
как `logistics_warehouse.payload.address_aliases` через
`tasks/apply_logistics_warehouse_alias_overrides.py`, сохраняя причину
`official master-mobile.ru contacts page`.

## 6. Readiness Gate РТУ Для Логистики

Бизнес-правило следующей волны пилота для готовности `РТУ` к логистической
передаче:

1. РТУ не помечена на удаление.
2. РТУ проведена.
3. В истории РТУ есть событие `Распечатан`.
4. В истории РТУ есть событие `Собран`.

Пометка удаления - технический фильтр безопасности. Три бизнес-признака
готовности для пилота: РТУ проведена, распечатана и собрана. На текущей базе
признак печати для РТУ берем из истории `_InfoRg9448` по действию
`Распечатан`, пока отдельный флаг печати РТУ не подтвержден.

Это правило отличается от `ПеремещениеТоваров`, где раньше обсуждалось событие
`Отсканирован`.

Техническое наблюдение по текущей живой базе:

- для `_Document203` сейчас найдены события `Начата сборка`, `Выставлен сборщик`,
  `Собран`, `Распечатан`;
- событие `Сборка через РМ закончена` по `_Document203` сейчас не найдено;
- в выгрузке конфигурации событие `Сборка через РМ закончена` найдено в форме
  проверки `ПеремещениеТоваров`.

Практическое решение для пилота: 1С ради события `Сборка через РМ закончена` не
дорабатываем, используем текущее событие `Собран` как source of truth для РТУ.

## 7. Черновой SQL Для Текущей Базы

SQL ниже использует согласованное для этой волны событие `Собран`.
Перед production-кодом нужно подтвердить `_Fld9449_RTRef` для
`Документ.РеализацияТоваровУслуг` и добавить его в оба `EXISTS`, как это
сделано для `ПеремещениеТоваров`.

```sql
SELECT
    CONVERT(varchar(34), rtu._IDRRef, 1) AS rtu_external_id,
    rtu._Number AS rtu_number,
    rtu._Date_Time AS rtu_date,
    CONVERT(varchar(34), ord._IDRRef, 1) AS site_order_external_id,
    ord._Number AS onec_order_number,
    ord._Date_Time AS site_order_date,
    ord._Fld2425 AS site_order_number,
    ord._Fld9266 AS site_delivery_method,
    CAST(ord._Fld2422 AS nvarchar(max)) AS site_delivery_addition,
    CAST(ord._Fld2395 AS nvarchar(max)) AS site_delivery_address,
    CAST(rtu._Fld4965 AS nvarchar(max)) AS rtu_delivery_addition,
    CAST(rtu._Fld4952 AS nvarchar(max)) AS rtu_delivery_address,
    CONVERT(varchar(34), rtu._Fld4940RRef, 1) AS source_warehouse_external_id,
    wh._Code AS rtu_warehouse_code,
    wh._Description AS rtu_warehouse_name
FROM dbo._Document203 AS rtu WITH (NOLOCK)
JOIN dbo._Document132 AS ord WITH (NOLOCK)
    ON ord._IDRRef = rtu._Fld4939_RRRef
LEFT JOIN dbo._Reference80 AS wh WITH (NOLOCK)
    ON wh._IDRRef = rtu._Fld4940RRef
WHERE rtu._Marked = 0x00
  AND rtu._Posted = 0x01
  AND EXISTS (
      SELECT 1
      FROM dbo._InfoRg9448 AS print_event WITH (NOLOCK)
      WHERE print_event._Fld9449_RRRef = rtu._IDRRef
        AND print_event._Fld9454 = N'Распечатан'
  )
  AND EXISTS (
      SELECT 1
      FROM dbo._InfoRg9448 AS assembled_event WITH (NOLOCK)
      WHERE assembled_event._Fld9449_RRRef = rtu._IDRRef
        AND assembled_event._Fld9454 = N'Собран'
  );
```

## 8. Как Это Ложится В Логистику

Для внешнего сервиса это не `transfer` из документа `ПеремещениеТоваров`, а
отдельный тип логистической единицы:

- `source_document_type = rtu`;
- `external_id = _Document203._IDRRef`;
- `origin_order_external_id = _Document132._IDRRef`;
- `site_order_number = _Document132._Fld2425`;
- `lookup_code = MMLOG1|rtu|<rtu_external_id>|<site_order_number>`;
- `barcode = lookup_code` для совместимости старых scan endpoints;
- `source_warehouse_id` берется из склада РТУ
  `_Document203._Fld4940RRef -> _Reference80`;
- до production-развертывания отдельного реквизита точки
  `target_warehouse_id` определяется через адрес самовывоза и карточку
  `logistics_warehouse`;
- production-based candidate отдельного реквизита
  `ЗаказПокупателя.осиТочкаСамовывоза` принимает `PICKUP_POINT = XML_ID` склада
  и описан в связанной задаче Codex
  [«Уточнить поле точки самовывоза»](codex://threads/01a0499c-af7c-78d0-8bea-64a994831eb5)
  и [спецификации 1С](../../1C_Dev_Workflow/docs/specs/ut103-task-107-pickup-point-field-candidate-2026-08-28.md);
  candidate пока не установлен в рабочую 1С, поэтому текущий адресный fallback
  сохраняется до отдельного разрешения, установки и readback;
- сканирование выполняется по печатному штрихкоду/QR на форме РТУ; значение,
  которое возвращает сканер, должно однозначно находить одну РТУ;
- движение дальше идет тем же state machine: передача водителю, транзит,
  внешняя служба доставки, приемка в подразделении.

РТУ не должна двигать CRM/заказ как "выдано клиенту" только по факту создания
или проведения. Для клиента и Bitrix24 нужен derived status, например
`ready_for_dispatch`, пока физическая логистика не завершена.

Сервисный слой:

- extractor находится в `app/services/logistics_onec.py`;
- запуск из cron/ручной проверки: `tasks/sync_logistics_rtu_from_onec.py`;
- кандидат cron находится в `infra/cron/logistics_rtu_sync.sh` и
  `infra/cron/logistics_rtu_sync.cron`; shell по умолчанию выполняет dry-run,
  использует `flock`, а запись включается только явным `LOGISTICS_RTU_SYNC_APPLY=1`;
- адресные aliases точек из `1С` подтягиваются командой
  `tasks/sync_logistics_warehouse_aliases_from_onec.py`;
- без `--apply` команда делает dry-run и возвращает отчет `fetched`,
  `synced_planned`, `manual_review_planned`, `skipped`;
- с `--apply` команда пишет изменения и возвращает `synced_created`,
  `synced_updated`, `manual_review_created`, `manual_review_resolved`,
  `skipped`;
- ОТМЕНЕНО (2026-08-28): флаг `--external-carriers`, который сразу переводит
  РТУ в `with_external_carrier`, не разрешен для production. До доработки sync
  он считается legacy-механизмом, потому что пропускает внутреннее плечо
  водителя и создает неподтвержденное физическое событие;
- с `--apply` сервис вызывает общий `logistics.sync_units`, поэтому повторный
  sync обновляет существующую РТУ, а не создает дубль.
- открытый ручной разбор, который стал неактуальным после успешного sync той же
  РТУ, закрывается автоматически со статусом `resolved`;
- отчет для логистов:
  `tasks/report_logistics_rtu_manual_review.py --review-type rtu_target_warehouse_unresolved`.
- подтвержденные aliases применяются только явным JSON-файлом через
  `tasks/apply_logistics_warehouse_alias_overrides.py`; без `--apply` команда
  показывает dry-run, с `--apply` пишет `address_aliases` и историю
  подтверждения в `payload.alias_override_history`.

Возврат принятой межточечной РТУ в ТЗП выполняется read-only endpoint:

- `GET /api/logistics/rtu/ready-for-pickup`;
- обязательный фильтр `warehouse_code`, опциональные `date_from` и
  `format=json|xml`;
- код склада сопоставляется с `logistics_warehouse.external_id`,
  `payload.code` и `payload.onec_departments[].code`;
- возвращаются только РТУ, у которых исходный и целевой склады различаются,
  state находится на конечном складе, а последнее событие равно
  `accepted_at_point`;
- ТЗП использует XML-ответ и добавляет найденную РТУ в «Готов к выдаче»
  получателя; endpoint ничего не записывает в 1С.

Подтверждения физической логистики не записываются обратно в production `1С`:

- `handed_to_driver` для внутренней РТУ создает сильное событие
  `pickup_moving_to_point` и DB-outbox стадии `PICKUP_TRANSIT`;
- `accepted_at_point` на однозначно ожидаемом складе создает сильное событие
  `pickup_stored_at_point` и DB-outbox стадии `PICKUP_WAITING`;
- outbox применяется только для pilot allowlist, строго по порядку событий
  заказа, с повторным чтением и readback сделки Bitrix24;
- повторный scan/confirm является идемпотентным и не создает второй переход;
- внешний carrier flow не использует эту внутреннюю цепочку стадий.

## 9. Решения Пилота И Остаточные Проверки

- `ПВЗ / пункт выдачи` в 1С для MVP не дорабатываем.
- Отдельный реквизит внутреннего самовывоза
  `ЗаказПокупателя.осиТочкаСамовывоза` подготовлен в другой задаче; до его
  production-развертывания логистический sync продолжает адресное
  сопоставление. СДЭК-ПВЗ с внутренней точкой самовывоза не смешивается.
- Source of truth по готовности РТУ: `не помечена на удаление` + `Проведена` +
  событие `Распечатан` + событие `Собран`.
- Адреса, которые не сопоставились с одним подразделением, отправляются в
  `manual_review`; логист выбирает подразделение вручную.
- Отдельный barcode для РТУ-пакета на старте не создаем, используем печатный
  штрихкод/QR с расходной накладной.
- QR/lookup в backend закреплен как
  `MMLOG1|rtu|<rtu_external_id>|<site_order_number>`.
- Если generated lookup не уникален, документ отправляется в `manual_review`.
- Локальная РТУ не создает логистическую единицу и остается в ТЗП своего склада.
- Межточечная РТУ возвращается в ТЗП получателя только после
  `accepted_at_point` на конечном складе.
- Для `_InfoRg9448` по РТУ нужно подтвердить и зафиксировать RTRef документа,
  чтобы события других типов документов не попадали в gate по совпавшей ссылке.
