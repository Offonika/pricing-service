Onepage v0.1 — «Контур экспертиз MVP»

1. Цель
Убрать полуручной учет экспертиз между магазином, `ОКК`, `1С` и `Bitrix24`, не углубляясь в тяжелую доработку старой `1С УТ 10.3`.

Решение:
- оставить `1С` системой учета документа `Экспертиза`;
- вынести операционный lifecycle экспертизы во внешний backend-контур;
- использовать `Bitrix24` как кейсовый и обзорный слой, а не как единственное место хранения состояния.

2. Что меняется
`1С` продолжает вести:
- документ `Экспертиза`;
- номер экспертизы;
- дату документа;
- организацию;
- подразделение;
- контрагента;
- ответственного;
- договор контрагента;
- товарную часть экспертизы;
- печатные формы заявления / акта передачи / отказа;
- список причин возврата и результат по товару;
- учетные связи с возвратом, реализацией и другими документами;
- печатный бланк, если он нужен в операционной работе.

Новый внешний сервис начинает вести:
- единый `expertise_case` (карточка кейса экспертизы);
- owner (ответственный за кейс) и SLA (контрольный срок);
- текущий операционный статус кейса;
- историю этапов;
- отметку `клиент оповещен`;
- audit trail (журнал действий) по всем действиям;
- вложения и служебные данные, если они нужны вне `1С`.

`Bitrix24` используется для:
- очереди кейсов;
- контроля просрочки;
- обзора по owner (ответственным) и подразделениям;
- производных задач только там, где реально нужно действие;
- будильников по сроку нахождения экспертизы в `ОКК` и по сроку принятия решения;
- автоматического информирования подразделения-инициатора о результате экспертизы и необходимости уведомить клиента.

3. Как это работает
Базовый поток MVP:
- из `1С` во внешний backend приходит документ `Экспертиза`;
- backend создает или обновляет `expertise_case` (карточку кейса);
- backend через интеграционный слой `Bitrix24` создает или обновляет карточку smart-process `Экспертиза`;
- кейс получает owner (ответственного), дедлайн текущего этапа и начальный статус `created` (`создано`);
- дальнейшие этапы фиксируются как события во внешнем контуре.

Что уже подтверждено технически:

- документ `Экспертиза` физически хранится в SQL-таблице `1С` `_Document9868`;
- табличная часть `Товары` физически хранится в `_Document9868_VT9886`;
- link на документ-основание (`Реализация`) реально хранится в шапке документа;
- `Комментарий менеджера` и `Комментарий отдела брака` реально хранятся в шапке документа;
- телефон клиента не хранится прямо в документе, а подтягивается из контактной информации контрагента;
- поле с паспортными данными исторически завязано на отдельный регистр, но в текущем процессе эти данные фактически не заполняют и для MVP их можно игнорировать.
- контур контактной информации уже локализован до `_InfoRg6402` + `_Reference25`.

Минимальные статусы MVP:
- `created` — кейс создан, находится в этапе доставки до `ОКК`
- `received_by_okk` — нормативный срок доставки истек и кейс автоматически считается поступившим в `ОКК`; в пользовательском UI `Bitrix24` показывается как стадия `В работе ОКК`
- `under_review` — экспертиза находится на рассмотрении; в пользовательском UI `Bitrix24` показывается как та же стадия `В работе ОКК`
- `decision_ready` — решение по экспертизе уже принято и зафиксировано
- `client_notified` — подразделение подтвердило, что клиент оповещен
- `returned_to_central_defect` — по положительному решению оформлен возврат в центральный брак
- `returned_to_store` — по отказному решению результат возвращен в подразделение / магазин
- `manual_review` — нужен ручной разбор нестандартного случая

Короткая расшифровка терминов в этом документе:
- `owner` — ответственный за кейс на текущем этапе
- `SLA` — контрольный срок текущего этапа, а не один общий срок на весь кейс
- `smart-process` — карточка процесса в `Bitrix24`, где виден статус, сроки и служебные действия
- `payload` — сырой набор данных, пришедший из `1С` и связанных сущностей
- `sync` — синхронизация данных между системами
- `Wave 1` — первая волна внедрения, то есть минимально полезный первый этап

4. Что получает бизнес
- единый реестр экспертиз;
- прозрачный owner (ответственного) по каждому кейсу;
- двухэтапный SLA:
  - доставка до `ОКК`: `moscow = 2`, `spb = 8`, `other = 8` календарных дней;
  - ответ `ОКК`: `moscow = 3`, `spb = 14`, `other = 14` календарных дней;
- будильники ответа `ОКК` идут ежедневно по лестнице:
  - `moscow`: `2` дня -> менеджер `ОКК`, `4` дня -> Омар / Арсен / Максим, `12` дней -> Эльдар;
  - `spb` / `other`: `13` дней -> менеджер `ОКК`, `15` дней -> Омар / Арсен / Максим, `23` дня -> Эльдар;
- усиленный контроль `ОКК` за сроком проведения экспертизы и сроком принятия решения;
- понятные статусы вместо чатов и бумажных отметок;
- автоматическую постановку задачи на уведомление клиента сотрудникам подразделения, из которого оформлена экспертиза;
- отдельный шаг `клиент оповещен`;
- контроль факта оповещения клиента;
- история действий по каждой экспертизе;
- максимально роботизированный smart-process с минимальным ручным участием;
- основу для дальнейшего barcode/QR и Telegram-сценариев.

Операционное правило `Wave 1`:

- решение по экспертизе принимает `ОКК`;
- клиента уведомляет подразделение-инициатор экспертизы;
- `ОКК` не становится call-центром по всем кейсам, а контролирует срок и факт уведомления;
- одна notify-task в `Bitrix24` создается на кейс: постановщик — система, основной исполнитель — руководитель подразделения-инициатора, соисполнители — сотрудники подразделения, fallback — координатор `ОКК`;
- автоматическая `SMS` клиенту через `Bitrix24` не входит в `Wave 1` и рассматривается как следующий шаг роботизации.

5. Что видит руководитель
По каждому кейсу:
- номер экспертизы;
- дата экспертизы;
- подразделение;
- контрагента;
- клиент и телефон;
- краткое описание проблемы;
- текущий статус;
- дедлайн;
- ответственный;
- решение;
- признак `клиент оповещен`;
- историю событий.

Отдельно:
- список открытых кейсов;
- список просроченных кейсов;
- очередь по owner (ответственным);
- историю спорных кейсов.

6. Что нужно от 1С
Минимум, без глубокой переделки:
- read-only (только на чтение) доступ к документу `Экспертиза`;
- стабильный идентификатор документа:
  - предпочтительно строковый `Ref` в формате `hex` `0x...`;
  - номер документа сам по себе недостаточен как технический ключ;
- дата создания документа;
- номер экспертизы;
- `organization_ref` как стабильный ссылочный идентификатор организации;
- организация;
- подразделение;
- клиент;
- ответственный;
- `contract_ref` как стабильный ссылочный идентификатор договора;
- договор контрагента;
- `linked_sale_ref` как link на документ-основание продажи;
- телефон клиента из вкладки `Заявление` / контактной информации контрагента;
- товарная часть документа:
  - номенклатура;
  - единица измерения;
  - качество;
  - цена;
  - количество;
  - сумма;
  - причина возврата;
  - решение;
  - список причин;
- комментарий менеджера;
- причины `1..5`, если они реально сохраняются как отдельные поля;
- комментарий отдела брака;
- учетная связь с исходной `Реализацией`;
- учетная связь с документом `Возврат от покупателя`, если он создается по результату;
- учетные ссылки на связанные документы, если они важны для контекста.

Важно:
- `1 документ Экспертиза в 1С = 1 expertise_case` (одна карточка кейса);
- внешний backend не должен угадывать структуру документа, нужен явный source contract;
- если часть полей живет не в самом документе, а в связанных справочниках/регистрах, это нужно отдельно зафиксировать.

Что уже подтверждено по форме документа визуально:
- в журнале документов видны колонки:
  - `Дата`
  - `Номер`
  - `Контрагент`
  - `Ответственный`
- в карточке документа есть верхний блок:
  - `Номер`
  - `Дата`
  - `Организация`
  - `Подразделение`
  - `Контрагент`
  - `Ответственный`
  - `Договор контрагента`
- есть вкладки:
  - `Товары`
  - `Заявление`
  - `Отказ`
- на вкладке `Заявление` видна контактная информация, включая телефоны;
- есть печатные формы:
  - `Печать заявления`
  - `Печать акта передачи`
  - `Печать бланка отказа ФЛ`
  - `Печать бланка отказа ЮЛ`
- документ встроен в цепочку подчиненности:
  - `Реализация -> Экспертиза -> Возврат от покупателя`.

Что уже подтверждено по конфигуратору и SQL:

- объект документа в конфигурации:
  - `Документ.осиЭкспертиза`

  - `осиДокументОснование`
- физическая SQL-таблица шапки документа:
  - `_Document9868`
- физическая SQL-таблица табличной части `Товары`:
  - `_Document9868_VT9886`
- физические поля комментариев:
  - `_Fld9884` = `КомментарийМенеджера`
  - `_Fld9885` = `КомментарийОтделаБрака`
- уже расшифрованы ключевые таблицы-справочники:
  - `_Reference66` = организация
  - `_Reference68` = подразделение
  - `_Reference54` = контрагент
  - `_Reference69` = ответственный
  - `_Reference37` = договор контрагента
  - `_Reference80` = склад
  - `_Reference62` = номенклатура
  - `_Reference41` = единица измерения
  - `_Reference48` = качество
  - `_Reference25` = виды контактной информации
- причины `1..5` реально живут в шапке документа как отдельные ссылочные поля;
- причины `1..5` указывают на отдельный справочник `_Reference9867` (`осиПричиныОтказа`);
- `ПричинаВозврата` по строке товара указывает на `_Reference8913` (`Справочник Причины возврата`);
- по строке товара уже подтверждаются SQL-значения:
  - количество
  - цена
  - сумма
- `Решение` по строке управляется через перечисление `осиРешение` / `_Enum9869`;
- верхний тип контактной информации хранится в `_Enum376`:
  - order `1` используется для телефонов
  - order `0` используется для адресов
- для `_Enum9869` уже подтвержден mapping:
  - order `0` = `Принято`
  - order `1` = `Отказано`
- `_Fld9912RRef` в строке `Товары` соответствует `ПричинаВозврата`, а не `СписокПричин`;
- `СписокПричин` пока выглядит не отдельным SQL-полем строки, а UI-действием формы над документными полями `Причина1..5`;
- `_Fld9910` в строке `Товары` существует физически как `IMAGE`, но почти во всех строках содержит один и тот же 18-байтный technical blob, поэтому пока не выглядит полезным бизнес-полем;
- `_Fld9909RRef` в строке `Товары` стабильно бьется в `_Document132`;
- `_Document132` уже подтвержден локальными SQL-исследованиями проекта как `Заказ покупателя`;
- значит `_Fld9909RRef` сейчас нужно трактовать как link на связанный `Заказ покупателя`, а не на `Возврат от покупателя`;
- для Wave 1 эту связь имеет смысл хранить отдельно в backend, а не только внутри сырого `payload`;
- `_InfoRg6402` выглядит как основной регистр контактной информации:
  - `_Fld6403_RTRef/_Fld6403_RRRef` = объект-владелец
  - `_Fld6405_RRRef` = вид КИ
  - `_Fld6406` = строковое представление
- по текущему примеру `Мамедов Акпер` в `_InfoRg6402` заполненных строк не найдено, что согласуется с пустыми значениями на форме `Заявление`;
- по статистике контрагентов, участвующих в экспертизах:
  - `142` контрагентов имеют хотя бы один заполненный телефон;
  - `122` имеют только `Телефон контрагента`;
  - `14` имеют только `Рабочий`;
  - `6` имеют `Телефон контрагента` плюс еще один телефонный вид;
- практическое правило выбора `primary phone` уже можно фиксировать так:
  - сначала `Телефон контрагента`
  - затем `Рабочий`
  - затем `Доп. телефон для переноса`
  - если телефона нет ни в одном виде КИ, кейс все равно создается, а телефон дозаполняют вручную в процессе
- `Причины отказа` выбираются из справочника `осиПричиныОтказа`.

7. Что пока не делаем
- тяжелую доработку формы и логики старой `1С УТ 10.3`;
- Telegram UX;
- глубокую синхронизацию с `Bitrix24`;
- обратную запись жизненного цикла кейса в `1С`;
- автоматическое закрытие всех кейсов через сложную матрицу решений;
- полноценный barcode/QR контур.

8. MVP-периметр
В первую очередь запускаем:
- backend-модель `expertise_case` (карточки кейса);
- историю событий `append-only` (журнал, который только дополняется, без перезаписи прошлого);
- sync (синхронизацию) кейсов из `1С`/адаптера;
- list/get/history API (методы просмотра списка, карточки и истории);
- actions:
  - `receive` — принять кейс в `ОКК`
  - `start-review` — начать рассмотрение
  - `decision` — зафиксировать решение
  - `client-notified` — подтвердить, что клиент оповещен
  - `complete` — завершить кейс с одним из исходов: `returned_to_central_defect` или `returned_to_store`

Не входит в MVP:
- UI в Telegram;
- сложные роботы `Bitrix24`;
- загрузка вложений из нескольких источников;
- автоматическая классификация дефекта;
- barcode scanning.

9. Основной архитектурный принцип
Рекомендуемый путь:
- не моделировать экспертизу как обычную задачу `Bitrix24`;
- не тащить весь lifecycle обратно в старую `1С`;
- использовать внешний backend как anti-corruption layer (прослойку-адаптер, изолирующую бизнес-модель) между `1С` и `Bitrix24`.

То есть:
- `1С` = система учета документа;
- backend = источник истины для статуса кейса, owner (ответственного), SLA (контрольного срока) и event history (истории событий);
- `Bitrix24` = слой обзора, координации и производных задач.

10. Что уже зафиксировано до боевой интеграции
До реального запуска концепт уже переведен в набор конкретных решений.

Зафиксировано:
- внешний ключ интеграции — `hex`-представление `0x...`;
- `customer_phone_primary` выбираем в таком порядке:
  - `Телефон контрагента`
  - `Рабочий`
  - `Доп. телефон для переноса`
  - если телефона нет, кейс все равно создается;
- `_Fld9909RRef` в строке `Товары` трактуем как link на связанный `Заказ покупателя`;
- цифровые вложения для `Wave 1` живут в `Bitrix24`:
  - каноническое место хранения — связанная папка `Bitrix Disk`;
  - smart-process хранит ссылку на нее и обзорные поля;
- минимально обязательные поля для создания `expertise_case`:
  - `external_id` / `onec_expertise_ref`
  - `onec_expertise_number`
  - `created_at_source`
  - `owner_user_external_id`
- `sync update` выполняем при изменении бизнес-полей шапки, item-level полей и выбранного телефона клиента;
- `_Fld9910`, поля НДС, печатные формы и прочие технические поля не считаем основанием для business-sync.

Для `Wave 1` дополнительно фиксируем:

- как отдельные поля кейса выносим `organization_ref`, `contract_ref`, `linked_sale_ref`;
- `return_reason_ref` и `decision_ref` оставляем в `payload.items[]`;
- внешний `decision_code` нормализуем только в `approved` (`принято`) / `rejected` (`отказано`), остальные значения считаем `null` (`не определено`).

Что уже решено:

- даже если в документе `Экспертиза` несколько строк товара, в Wave 1 это все равно один кейс;
- если по строкам товара решения различаются, кейс все равно остается одним, а item-level решения живут в `payload.items[]`;
- связь со связанным `Заказом покупателя` храним отдельно в backend, а не только в `payload`;
- `decision_code` в backend для Wave 1 нормализуем так:
  - `Принято` -> `approved` (`принято`)
  - `Отказано` -> `rejected` (`отказано`)
- поля НДС для Wave 1 не нужны.
- `organization_name`, `contract_name`, `return_reason_name` не поднимаем в отдельные top-level поля кейса;
- `linked_return_ref` в отдельное поле `Wave 1` не выносим;
- для `Bitrix24 Wave 1` разделяем два финальных исхода:
  - `returned_to_central_defect` — возврат оформлен в центральный брак
  - `returned_to_store` — возвращено в подразделение

12. Управленческое решение
Рекомендуемый путь:
- утвердить внешний `expertise_case` как отдельный bounded context;
- считать `1С` системой учета документа `Экспертиза`;
- не стартовать боевую sync-интеграцию, пока не зафиксирован source contract документа;
- после согласования source contract запускать следующую волну:
  - адаптер `1С`;
  - точный mapping полей;
  - правила решений и закрытия;
  - затем `Bitrix24`-слой и производные задачи.

Это дает быстрый и безопасный MVP-каркас, не ломает старую `1С` и снижает риск сделать контур экспертиз на неполных предположениях.
