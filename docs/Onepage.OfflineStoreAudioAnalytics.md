# OnePage: офлайн-запись разговоров менеджер-клиент у стойки

Дата обновления: `2026-05-14`

Статус: рабочий контекст для переносного пилота.

Исходный OnePage из `Openclaw B` импортирован в
`docs/imports/openclaw-b-offline-dialog-recording-onepage.md`
(`sha256: 9f09269f3a55120177bf07b010288ef17767edd1b8e05821d8560530b2c27716`).

## Зачем Это Нужно

Нужно организовать стабильную запись живых диалогов у стойки продаж в магазинах
так, чтобы дальше можно было:

- автоматически получать файлы на центральный сервер;
- делать транскрибацию;
- сохранять результаты в PostgreSQL;
- строить отчеты и речевую аналитику по аналогии с уже работающим контуром по
  звонкам.

На первом этапе главная цель не аналитика, а надежное получение качественных
записей. Пилот делаем не сразу на все магазины: используем один переносной
комплект и по очереди тестируем точки по неделям.

## Что Показал Тест

Тестовая схема:

- микрофон `Aceline AMIC-11`;
- программа записи `Snooper`;
- расстояние до говорящего примерно `30-40 см`.

Результат:

- общий смысл части диалогов распознается;
- для грубой проверки гипотезы схема подходит;
- для стабильной речевой аналитики качество недостаточное.

Основные проблемы:

- один бюджетный микрофон рядом с менеджером плохо пишет клиента;
- нет раздельной записи менеджера и клиента по каналам;
- в расшифровке теряются модели, цены, артикулы и отдельные фразы;
- в шумной рознице качество будет еще хуже.

Вывод:

- `Aceline AMIC-11 + Snooper` можно использовать только как временный черновой
  пилот;
- как стандартное решение для rollout на `12` магазинов этот вариант не подходит;
- для следующего этапа нужен компактный специализированный микрофон, который
  можно быстро переставлять между магазинами.

## Как Идем По Этапам

### Этап 1. Переносной Пилот

На пилоте используем один компактный переносной комплект:

- один специализированный микрофон;
- крепление на монитор;
- подключение к ПК;
- запись на одной стойке;
- перенос комплекта между магазинами по очереди.

Этот этап нужен, чтобы:

- быстро проверить качество записи в реальных магазинах;
- не закупать сразу оборудование на все точки;
- понять, достаточно ли одного микрофона для первичной транскрибации.

Минимальная цель пилота:

- один магазин за раз;
- `30` тестовых диалогов суммарно;
- проверка качества записи и транскрибации в реальных условиях.

Предпочтительный кандидат комплекта после проверки оборудования:

- `SpRecord MIC4` как аппаратный edge-recorder с внутренним накопителем, Web UI,
  сетевой выгрузкой и мониторингом;
- `STELBERRY M-1105HD` как специализированный микрофон для сценария
  клиент-кассир;
- `Snooper` остается fallback-вариантом только если аппаратный рекордер не
  успеваем получить или настроить.

Важное ограничение: один `STELBERRY M-1105HD` дает более подходящую mixed-запись
диалога, но не честное stereo-разделение "менеджер слева / клиент справа".
Для rollout это можно решать только после пилота: либо оставляем mixed-запись на
рабочее место, либо ищем актуальную не-EOL схему раздельных каналов у другого
поставщика/класса оборудования.

По итогам проверки каталога и звонка поставщику: у этого вендора сейчас не
закладываем сценарий "миниатюрный однонаправленный одноканальный микрофон" как
доступный закупочный стандарт. EOL-модели не используем для планирования.

### Этап 2. Контур Транскрибации И Отчетов

- загрузка файлов на сервер;
- запись метаданных в PostgreSQL;
- ASR worker;
- сохранение транскриптов;
- ежедневные отчеты по аналогии со звонками.

### Этап 3. Rollout

Если пилот подтверждает эффект, переходим к целевой схеме:

- базовый rollout-кандидат: `1` mixed-канал на рабочее место, если качество
  пилота достаточно для ASR и отчетов;
- upgrade-кандидат: раздельные каналы менеджер/клиент только если mixed-записи
  не хватает и найден актуальный не-EOL комплект;
- целевой формат для своего recorder/upload agent: `WAV PCM 16 bit, 16 kHz`;
- для раздельной записи роли каналов фиксируются явно: менеджер и клиент.

Это даст:

- лучшее качество записи;
- более точную транскрибацию;
- возможность анализировать реплики отдельно без сложного разбора говорящих.

## Рекомендации По Микрофонам

### Для Пилота

Требования:

- компактный;
- крепится на монитор;
- быстро снимается и переносится между магазинами;
- дает более качественную запись, чем бытовой настольный микрофон.

Базовый приоритет для пилота:

- `SpRecord MIC4 + STELBERRY M-1105HD`, если подтверждаются стабильная выгрузка,
  формат записи и достаточное качество ASR;
- `STELBERRY M-1100HD` или `M-1050HD` как близкие актуальные замены, если
  `M-1105HD` не подходит по корпусу/монтажу;
- `Snooper` и простой микрофон оставляем только как fallback для чернового теста.

Если нужен больший упор именно на запись диалога сотрудник-клиент:

- рассмотреть `STELBERRY M-1100HD` или аналогичный двунаправленный микрофон, но
  это менее простой вариант подключения.

Не использовать как основной стандарт:

- `Aceline AMIC-11`;
- `STELBERRY M-75`;
- EOL-модели `STELBERRY M-1200`, `M-1300` и аналоги, снятые с производства;
- гипотетическую схему "миниатюрный однонаправленный 1 канал", пока нет
  доступной актуальной модели и подтверждения поставщика;
- одиночные дешевые настольные USB/3.5 мм микрофоны.

### Для Rollout

Базовый вариант после успешного пилота:

- `1` mixed-микрофон на рабочее место;
- стоимость считать от текущей оценки `~20-22.5 тыс. руб.` на рабочее место;
- для `2` менеджеров ориентир `40-45 тыс. руб.`.

Раздельные каналы:

- рассматривать только если пилот показывает, что mixed-запись не вытягивает
  ASR/аналитику;
- не завязывать решение на EOL-модели;
- искать актуальный комплект у другого вендора или recorder-схему с двумя
  микрофонами на рабочее место;
- ожидаемо это дороже и ближе к `x1.5+` от базовой схемы, точную цену считать
  после выбора доступных микрофонов.

## ПО На Рабочем Месте

На пилоте можно временно оставить `Snooper` только как рекордер, если он стабильно
пишет файлы. Это допустимо именно потому, что пилотный комплект будет переносным
и использоваться по очереди, а не сразу на `12` точках.

Для rollout нужен свой локальный Windows-агент/служба на каждом ПК, который:

- пишет 2-канальный звук;
- режет запись на диалоги по тишине;
- хранит локальный буфер `3-7` дней;
- автоматически отправляет файлы на сервер;
- повторяет отправку при сбоях;
- контролирует, что оба канала живы;
- шлет статус и ошибки.

Практически для пилота:

- если можно писать в обычную папку, пишем сразу в локальный spool;
- если рекордер требует FTP/SFTP-сервер, поднимаем его только локально на Windows
  как технический адаптер;
- наружу FTP не открываем;
- если аппаратный recorder поддерживает только `FTPS`, допускаем его как
  защищенный pilot-adapter в закрытой сети/VPN/allowlist, с отдельными учетными
  данными на устройство;
- для v1 с `SpRecord MIC4` отправляем на центральный сервер по `FTPS` в
  защищенную landing-zone;
- `SFTP` оставляем fallback-вариантом для программного Windows-uploader;
- для собственного агента в rollout целевой вариант - `HTTPS API` с токеном,
  идемпотентностью и подтверждением приема.

## Что Готовим До Выезда

Программную часть нужно подготовить заранее, чтобы на месте остались только
монтаж, настройка громкости/чувствительности и подбор положения микрофона.

До выезда:

- поднять central landing-zone для `FTPS`/ручной загрузки пилотных записей;
- подготовить ingest job, который забирает новые файлы, проверяет размер,
  длительность, checksum и формат;
- поддержать manifest или fallback-метаданные из имени файла/папки, если
  SpRecord не отдает полноценный JSON;
- завести draft PostgreSQL-таблицы/миграцию для карточки офлайн-диалога;
- подключить существующий ASR worker к offline-audio candidate queue;
- сделать dry-run на тестовых WAV/MP3 без выезда;
- подготовить daily status/quality report: сколько файлов пришло, сколько прошло
  ingest, сколько ушло в ASR, какие ошибки качества;
- подготовить чеклист выезда: место установки, уровень громкости, тестовая фраза
  менеджера/клиента, запись 5-10 пробных диалогов, контроль клиппинга и тишины.

## Целевая Архитектура

### На ПК Менеджера В Пилоте

- один компактный микрофон на мониторе;
- локальный рекордер пишет файлы;
- локально хранится буфер на случай обрыва сети;
- комплект можно перевезти в другой магазин и быстро подключить заново.

### На ПК Менеджера В Rollout

- 2 микрофона подключены к одному 2-канальному аудиоинтерфейсу;
- локальный recorder/upload agent пишет и сегментирует диалоги;
- локально хранится буфер на случай обрыва сети.

### На Центральном Сервере

- принимаем файлы по `FTPS` для аппаратного пилота, далее целевой вариант для
  собственного агента - `HTTPS`, fallback для Windows-uploader - `SFTP`;
- raw audio храним как файлы в storage, не в PostgreSQL;
- PostgreSQL хранит карточку диалога, статус загрузки, статус транскрибации,
  транскрипт и результаты аналитики.

### На ASR-Сервере

- отдельный worker выполняет транскрибацию;
- результат пишет в PostgreSQL;
- затем отдельный analysis worker строит summary, флаги и отчеты.

Рекомендуемая роль серверов:

- текущий центральный сервер: API, PostgreSQL, отчеты, orchestration;
- более мощная Windows-машина `Ryzen 7600 / 64 GB`: ASR worker;
- storage: файловое хранилище raw audio с retention.

## Что Сохраняем

В PostgreSQL:

- карточку диалога;
- транскрипт;
- summary;
- quality flags;
- аналитические поля и статусы.

Raw audio:

- храним отдельно как файлы;
- рекомендуемый retention для старта: `14-30` дней;
- после успешной транскрибации и проверки можно удалять по политике хранения.

## Минимальные Проверки

- файл не пустой;
- корректная длительность;
- на пилоте есть сигнал на активном микрофоне;
- в rollout есть сигнал на обоих каналах;
- доля тишины и клиппинга не превышает согласованный порог;
- файл доехал на сервер и получил карточку без ручного копирования;
- алерт, если нет новых записей более `2` часов;
- алерт, если в rollout один канал постоянно молчит;
- алерт, если есть очередь неотправленных файлов;
- алерт, если ASR не отрабатывает в SLA.

## Важные Ограничения

- Перед пилотом нужно согласовать правила уведомления сотрудников и клиентов о
  записи, доступ к аудио и retention с ответственными за безопасность/HR/юристами.
- В отчетах не публиковать raw transcript целиком, если он содержит персональные
  данные; для управленческого контура использовать summary, flags и ссылки с
  ограниченным доступом.
- Пилот оценивает не только распознавание речи, но и надежность доставки файлов:
  локальный буфер, повторную отправку и отсутствие ручного копирования.

## Что Нужно Согласовать

1. На первом этапе используем один переносной комплект, а не закупаем сразу все
   магазины.
2. Для пилота подтверждаем один компактный микрофон на монитор как временное
   решение.
3. `Snooper` допускается только как временное пилотное решение.
4. Для rollout планируем переход на 2-канальную схему записи.
5. Для rollout планируем собственный локальный Windows-агент.
6. Raw audio храним отдельно от PostgreSQL.
7. Retention raw audio на старте принимаем `14-30` дней.
8. Правила уведомления о записи, доступ к аудио и порядок удаления raw audio.
