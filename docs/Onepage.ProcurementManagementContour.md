## 0. Шапка для решения

Нужно строить не "одну формулу закупки", а управляемый контур закупок по
папкам, свойствам, ассортиментным статусам и расчетным профилям. Папка
номенклатуры остается верхним уровнем управления и понятной рамкой для людей,
но не единственной единицей расчета. Где возможно, программа должна управлять
закупкой через свойства, характеристики, `предмет`, `tag`, поставщика,
логистику, спрос, цену, ассортиментный статус и риск.
У `АКБ`, `дисплеев`, `шлейфов`, `стекол` и других групп могут быть разные
графики заказа, сроки поставки, правила расчета, страховой запас, документы и
стоп-сигналы.

Что утверждаем:

- программа сама готовит проект заказа поставщику: что купить, сколько купить,
  у кого купить и почему;
- опасные решения программа не проводит сама: человек видит объяснение и
  подтверждает, меняет, запрещает или отправляет строку на разбор;
- `1С` остается учетной системой, единственная запись в `1С` идет через файловый
  обмен и только как непроведенный черновик `ЗаказПоставщику`;
- жизненный статус товара живет в `pricing-service` и в `1С` не выгружается:
  выгрузка статусов и служебных свойств отменена `2026-08-05`;
- рабочее место закупщика - приложение Bitrix24 `Формирование заказа`; карточка
  смарт-процесса `Закупка/Заказ` начинается только после появления документа в
  `1С` и ведет оплату, логистику, приемку;
- WeChat/Disk превращаются из "памяти в переписке" в доказательства: цена,
  срок, счет, чек, скрин, запись, кто подтвердил и когда;
- контур управления ассортиментом строим так, чтобы при переходе на `1С КА`
  типовой модуль "Управление ассортиментом" получил уже очищенную
  классификацию, статусы и правила, а не хаос в справочнике;
- контур сначала запускаем на пилоте, а не сразу на всех товарах.

### Принятые решения

| Вопрос | Решение |
| --- | --- |
| Единица управления | Не весь каталог одной формулой. Верхний уровень - папка номенклатуры, рабочий уровень расчета - расчетная единица закупки по SKU, `предмету`, `tag`, свойствам, характеристикам, поставщику, логистике, спросу и риску. Автоматическая консолидация группы аналогов в одного победителя отменена `2026-07-26` и удалена из кода `2026-07-31` после сверки количества: каждая карточка считается и заказывается независимо |
| Рабочая поверхность | Приложение Bitrix24 `Формирование заказа`: разделы `Витрина`, `Помощник`, `Заказы`, `Свойства`, `История` |
| Автоматическое формирование | Расчёт сам создаёт внутренние проекты по поставщикам в приложении; предварительное совпадение с человеческим решением для их создания не требуется |
| Проверка количества | Закупщик проверяет и при необходимости исправляет количество в приложении |
| Строки с блокерами | Не пропадают и не отменяют весь расчёт: сохраняются в проекте с пометкой для проверки; передать такой проект в 1С нельзя до устранения проблем |
| Где хранится жизненный статус | Только в `pricing-service`. Выгрузка статуса, причины, даты и утвердившего в свойства `УТ 10.3` отменена `2026-08-05` и запрещена в коде |
| Единственный канал записи в 1С | Файловый обмен |
| Что создает программа в 1С | Непроведенный черновик `ЗаказПоставщику`, только после подтверждения количества ответственным |
| Кто подтверждает перед созданием черновика | Любой сотрудник закупки с действующим доступом к приложению: кто открыл проект и взял его в работу, тот проверяет количество и выполняет ручное подтверждение. Очередь общая; назначения по папке, постоянного заместителя и таймера переключения нет. Система сохраняет фактического пользователя действия |
| Кто может ставить `не закупать` | Отдел закупки, с причиной, автором и датой |
| Кто ставит `Эксклюзив` | Омар как старший отдела закупки, но это коммерческий признак товара, а не замена жизненного статуса ассортимента |
| Ручной минимальный остаток | Общего дефолта нет: для эксклюзивных товаров вручную задают Омар и ответственный менеджер по папке; поле оставляем общим |
| Пересмотр `Эксклюзив` | Каждые 30 дней, подтверждают Омар и ответственный менеджер по папке |
| Какие склады считать для продаж | Все склады, откуда товар продается систематически, кроме центрального склада и складов брака/несистемных продаж |
| Какие склады учитывать по остатку | Активные точки продаж, центральный склад, транзитные склады и склады перемещений |
| Как не исказить среднюю продажу | Центральный и транзитные склады учитывать по остатку, но не как торговые точки по дням наличия |
| Закупка или перемещение | Закупку считать по потребности сети; дефицит отдельной точки сначала закрывать кандидатом перемещения, а покупать только непокрытый остаток |
| Возраст и границы истории | Дата рождения карточки, первое поступление, `date_min/date_max` хранятся с источником и определяют надёжность расчёта; они не включают жёсткую дорисовку продаж |
| Как отмечать дорогие товары | Верхние 25% цены/себестоимости внутри группы; профиль `Дорогой быстрый` или `Дорогой медленный` ставится из заказа поставщику либо вручную ответственным за папку |
| Как показывать эксклюзив | Выделять на сайте как эксклюзивный продукт, а не прятать внутри служебного статуса |
| Резкий скачок цены поставщика | Больше или меньше `10%` в течение двух заказов, с учетом графика папки |
| Выбор поставщика | Сначала допустимость, затем прозрачная лестница: успеть до дефицита → нет блокера качества → полная известная стоимость → при разнице `≤3%` скорость и стабильность → MOQ, оплата и исполнение. При разнице `>3%` выигрывает меньшая полная стоимость среди успевающих кандидатов. Фиксированных весов нет; при ничьей показываются 2–3 кандидата и требуется подтверждение перед 1С |
| Источник правил по дисплеям | Пилотные видео 37976/37992, помощник закупок, заказы поставщику и свойства карточек |
| Сезонность | Считать по 3 годам, отдельно по номенклатурным группам и с учетом количества SKU в периоде |
| Потребности магазинов | Учитывать как отдельный сигнал спроса из РММЗ, например `Потребности Савелова` |
| Что двигает товар по лестнице статусов | Ранние ступени - закупочные события (первый заказ, передача в карго), дальше только спрос: продажи за окна `30/90/180` дней и дни наличия. Правило `5 поступлений за 180 дней` и подтверждение ответственного отменены `2026-08-05` |
| План/прогноз продаж | Включать в формулу, но показывать источник и риск расхождения. На `2026-08-09` в расчете этого еще нет |
| Целевой выбор метода расчета спроса | Выбирать автоматически по профилю: средняя по доступным дням, сезонная средняя, один из проверенных методов редкого спроса, потребность магазина или ручная проверка. BRT, Croston/SBA/TSB и min/max пока только кандидаты для теневого сравнения |
| Управление ассортиментом сейчас | В `pricing-service` строим аналитический слой: паспорт товара, статус ассортимента, рекомендации ввода/вывода, BCG/ABC/XYZ/новинки; методы редкого спроса ещё сравниваются до включения |
| Управление ассортиментом после перехода в КА | В `1С КА` переносим утвержденную ассортиментную матрицу, товарные категории, статусы, ввод/вывод из ассортимента, квоты и форматы магазинов |
| Период классификации жизненного статуса | Ранние ступени - вся доступная история заказов и карго; ступени по спросу - окна `30/90/180` дней плюс даты первой и последней продажи |

### Целевая цепочка

```text
1С / помощник закупок / продажи / остатки / заказы поставщику / план / потребности магазинов / рынок / WeChat / Disk
-> разбор правил из видео 37976/37992
-> анализ 6 месяцев заказов поставщику по дисплеям
-> анализ 3 лет продаж, сезонности и качества ассортимента
-> паспорт ассортимента: папка / предмет / категория / бренд / модель / качество / характеристики / ценовой сегмент / жизненный статус / коммерческие признаки
-> выбор расчетной единицы: SKU / аналог / предмет+tag / свойства / поставщик / потребность магазина
-> выбор метода спроса: средняя / сезонность / BRT / потребность / ручная проверка
-> расчет потребности по расчетной единице закупки
-> проверка поставщика, цены, документов и рисков
-> очередь решений в приложении Формирование заказа
-> подтверждение итогового количества ответственным
-> непроведенный черновик ЗаказПоставщику в 1С
-> контроль оплаты, логистики, приемки и закрытия в смарт-процессе Закупка/Заказ
```

Важно про границу: все, что до появления документа в `1С`, живет в приложении
`Формирование заказа`. Робот сам создаёт здесь внутренние проекты, а человек
проверяет и корректирует их. Непроведённый черновик `ЗаказПоставщику` в 1С
создаётся только после отдельного ручного действия пользователя. Smart-process
до этого не используется; после появления документа он может вести оплату,
логистику и приёмку. Автоматическая передача и проведение документа запрещены.

### Что должно получиться в MVP

1. По выбранной папке номенклатуры система собирает остатки, продажи, открытые
   заказы поставщику, сигналы помощника закупок и признаки 1С.
2. Внутри папки система выбирает расчетную единицу закупки: SKU, группу
   аналогов, `предмет + tag`, группу свойств, поставщика, потребность магазина
   или ручной профиль.
3. Система учитывает 3 года сезонности, качество ассортимента, план/прогноз
   продаж и потребности магазинов.
4. Система выбирает метод спроса по профилю: обычная средняя, сезонная средняя,
   BRT для редких реальных продаж, потребность магазина или ручная проверка.
5. По дисплеям жизненный статус считается так: ранние ступени - по первому
   заказу поставщику и передаче его в карго, дальше - по спросу за окна
   `30/90/180` дней с учетом дней, когда товар реально был на полке. Для
   закупочного ритма отдельно смотрим последние 6 месяцев заказов поставщику.
6. Система формирует короткий список к действию: купить, переместить, не
   покупать, проверить данные.
7. Для каждой строки есть простое объяснение: почему такое количество, что в
   пути, какой поставщик, какая цена, какие риски.
8. Строки без надежного поставщика, цены, договора, документов или нормальных
   данных не становятся заказом, а уходят на ручную проверку.
9. После подтверждения сотрудником закупки, который открыл и обработал проект,
   создается непроведенный черновик заказа поставщику в 1С через файловый обмен.
10. В Bitrix остается след процесса: кто подтвердил, что изменил, какие файлы
   приложены и где заказ сейчас.

### Интеграция с 1С

1С остается источником торгового факта: номенклатура, продажи, возвраты,
остатки, заказы поставщику, карго и поступления читаются только на чтение.
`pricing-service` считает статус и потребность и хранит результат у себя.

Обратно в 1С уходит ровно одно: непроведенный черновик `ЗаказПоставщику` после
подтверждения количества ответственным. Прямой SQL-write в 1С запрещен,
автоматическое проведение документа запрещено.

Чего в 1С больше не отправляем (решение `2026-08-05`): жизненный статус
ассортимента, причину статуса, дату изменения, источник расчета, утвердившего,
профиль закупочного поведения и ручной минимальный остаток. Запрет закреплен в
коде обмена: такие строки не проходят валидацию. Ранее подготовленные пакеты
статусов помещены в карантин и не применялись.

### Первый пилот

Первый пилот делаем на дисплеях в общей очереди допущенных сотрудников закупки.
АКБ не смешиваем с первым запуском: это отдельная ветка из-за документов и
перевозки.

| Папка | Зачем брать в пилот | Главный риск |
| --- | --- | --- |
| `дисплеи` | Проверить расчет количества, свойства, флагманы, новинки, старые позиции, неликвид, pipeline | Ошибка в спросе, средней продаже, цене или выборе поставщика |
| `АКБ` | Следующий отдельный пилот после дисплеев | Документы, перевозимость, ВЭД/сертификаты, опасная автоматизация |

## 1. Простые термины

Правило: сложное или "понтовое" слово не убираем. Оставляем его рядом в
скобках, но перед ним всегда пишем простую расшифровку, чтобы команда постепенно
привыкала к терминам и одновременно понимала смысл.

- Подтверждение человеком (`approval`) - человек нажал "можно создавать
  черновик" после проверки.
- Доказательство (`evidence`) - файл, скрин, запись, ссылка на WeChat/Disk,
  цена от поставщика или счет.
- Короткий список к действию (`shortlist`) - строки, с которыми закупке нужно
  работать сейчас.
- Срок до поступления (`lead time`) - сколько дней пройдет от решения купить
  до товара на складе.
- Товарная позиция (`SKU`) - конкретная номенклатура/артикул.
- Классы товара (`ABC/XYZ`) - ABC показывает важность по деньгам/продажам,
  XYZ показывает стабильность спроса.
- Карточка поставщика (`CRM`) - где хранится поставщик, контакт, ответственный
  и история общения.
- Умная карточка процесса (`smart-process`) - карточка Bitrix со стадиями,
  полями, ответственными и файлами.
- Ручная проверка (`review`) - строка не идет в заказ, пока человек не разберет
  причину.
- Документальная остановка (`document gate`) - дальше нельзя двигаться, пока
  не приложены обязательные документы.
- Минимальное количество заказа (`MOQ`) - меньше этого поставщик не отгружает.
- Сезонный коэффициент (`seasonality factor`) - насколько в этот период обычно
  растет или падает спрос по группе.
- Качество ассортимента - сколько товаров группы реально продается, а сколько
  только раздувает остаток и мешает расчету.
- Ассортиментная матрица - утвержденный список товаров, которые мы хотим держать
  в работе для конкретной категории, магазина, формата или периода.
- Статус ассортимента - управленческий ярлык товара: матричный, рабочий,
  новинка, тест, под заказ, неликвид, снят, не закупать.
- Ценовой сегмент - место товара внутри категории по цене/себестоимости: топ,
  средний, эконом или более точная внутренняя шкала.
- БКГ-матрица по-русски - сравнение товара по двум внутренним осям: доля в
  наших продажах и динамика наших продаж, без попытки оценивать весь рынок.
- План/прогноз продаж - план это цель бизнеса, прогноз это расчет ожидания по
  истории, сезонности и текущим условиям.
- Потребность магазина - заявка точки, например `Потребности Савелова`; ее
  нужно учитывать отдельно от факта продаж.
- Расчетная единица закупки (`procurement calculation unit`) - уровень, на
  котором программа реально считает потребность: SKU, группа аналогов,
  `предмет + tag`, группа свойств, поставщик, потребность магазина или ручной
  профиль.
- Метод спроса (`demand method`) - способ посчитать будущий спрос для расчетной
  единицы: средняя по доступным дням, сезонная средняя, BRT, потребность
  магазина или ручная проверка.
- BRT - метод для редкого, но реального спроса: программа смотрит историю
  интервалами и выбирает количество под целевой уровень наличия. BRT не
  применяется к разовой продаже одному клиенту и не отменяет стоп-сигналы.

## 2. Границы систем

| Система | Роль |
| --- | --- |
| `1С` | Учетный факт: номенклатура, контрагент, договор, валюта, склад, заказ, поступление, себестоимость |
| `1С` | Признаки для решения: дефицит, сверхнорматив, неликвид, ABC/XYZ, глубина остатка, планы |
| `Мегапрайс / помощник закупок` | Текущая логика авторасчета, `К ЗАКАЗУ`, прайсы, история заказов и поступлений |
| `WeChat` | Переговоры с поставщиками: цены, сроки, счета, обещания, изменения |
| `Disk` | Записи, скрины, файлы и подтверждения по пилоту |
| `Bitrix` | Рабочее место: приложение `Формирование заказа` до документа 1С и смарт-процесс `Закупка/Заказ` после него. Не аналитическая база |
| `pricing-service / аналитический слой` | Расчет, правила, история цен, безопасные проверки, API/интеграции |
| `1С КА после перехода` | Нормативная ассортиментная матрица: категории, статусы, ввод/вывод, квоты, форматы магазинов, коллекции/сезоны |

Важно: внешний контур не пишет напрямую в SQL 1С и не проводит документы.
Максимум первой версии - непроведенный черновик через файловый обмен после
подтверждения человеком.

## 3. Карточка решения по строке заказа

Каждая строка рекомендации должна иметь не только количество, но и объяснение.
Это основной контракт между программой и закупкой.

| Поле | Простое значение |
| --- | --- |
| `folder` | Папка номенклатуры: АКБ, дисплеи, стекла и т.д. |

| `sku` | Товарная позиция |
| `profile` | Профиль товара: дорогой быстрый, дорогой медленный, дешевый флагман, новинка, юный, неликвид и т.д. |
| `demand_method` | Метод спроса: средняя, сезонная средняя, BRT, потребность магазина, ручная проверка |
| `display_properties` | Для дисплеев: качество/бренд, рамка, площадка под IC, верификация |
| `do_not_order` | Есть ли запрет закупки: дубль, снятый, замена, ручной запрет |
| `warehouse_scope` | Какие склады участвовали в расчете |
| `avg_sales` | Средняя продажа, без искажения центральным/транзитными складами |
| `demand_spread` | Спрос широкий по магазинам/клиентам или разовый одному клиенту |
| `seasonality_factor` | Сезонная поправка по 3 годам |
| `active_sku_count` | Сколько товаров группы было активно в периоде |
| `sales_per_active_sku` | Продажи на одну активную позицию |
| `sales_plan_qty` | План продаж |
| `sales_forecast_qty` | Прогноз продаж |
| `store_need_qty` | Потребности магазинов из РММЗ |
| `stock_now` | Текущий общий остаток |
| `stock_in_sales_points` | Остаток в активных торговых точках |
| `stock_central_and_transit` | Остаток центрального, транзитных и складов перемещений |
| `incoming_qty` | Что уже едет или заказано |
| `pipeline` | Где товар в цепочке: в компании, через 10 дней, через 20 дней, сдан в cargo, у поставщика |
| `coverage_before` | На сколько хватит до рекомендации |

## 4. Настройки по папкам, расчетным единицам и профилям

Стартовая матрица по папкам нужна как рамка управления и ответственности. Но
для автоматического расчета этого мало: внутри папки нужно выбрать расчетную
единицу закупки и метод спроса.

| Папка | Расчет | График | Особые проверки | Подтверждение |
| --- | --- | --- | --- | --- |
| `дисплеи` | Спрос, флагманы, новинки, неликвид, цена | Отдельный график папки | Новинки, дорогие товары, старые позиции, скачок цены | Любой допущенный сотрудник закупки перед черновиком 1С |
| `АКБ` | Спрос плюс документы | Отдельный график АКБ | `АКБ без документов` означает: нет доказательств, что аккумулятор можно безопасно и законно купить, перевезти и растаможить; нужны MSDS, UN38.3, сертификат/ДС, ТН ВЭД, invoice, packing list и страна происхождения | Любой допущенный сотрудник закупки, плюс документальная остановка |
| `шлейфы/стекла/прочее` | Обычный расчет спроса и остатка | Свой график папки | MOQ, кратность, цена, поставщик | По правилам папки |
| `новинки` | Осторожное тестирование спроса | Частый контроль, например раз в 5 дней | Не масштабировать после первой продажи | Ручная проверка |
| `неликвид/стареющие` | Не закупать автоматически | Контроль остатка и цены | До 3 продаж за 180 дней, нет цен бронза/серебро/золото | Ручная проверка |

Внутри папки нужен второй уровень - профиль закупочного поведения: товар может
ехать общей партией папки, долго готовиться, долго ехать, быть дорогим и быстрым,
дорогим и медленным, дешевым ходовым, с высоким MOQ, документальным, хрупким,
новым или неликвидным. Этот профиль лучше брать из свойств номенклатуры, истории
продаж, себестоимости, маржи, поставщика и логистики.

Рабочая расчетная единица может быть ниже или выше SKU:

- SKU, если товар уникален и имеет свою историю;
- группа аналогов, если товары взаимозаменяемы;
- `предмет + tag`, если в карточках уже есть рабочие признаки ассортимента;
- группа свойств/характеристик, если свойства реально управляют поставщиком,
  спросом или риском;
- поставщик + группа свойств, если заказ должен дробиться по поставщикам;
- потребность магазина, если это отдельный клиентский или точечный сигнал;
- ручной профиль, если данных еще мало или товар рискованный.

Метод спроса выбираем после расчетной единицы:

| Ситуация | Метод |
| --- | --- |
| Стабильный широкий спрос | Средняя по доступным дням + сезонность |
| Редкий, но подтвержденный спрос | BRT, если это не разовая продажа одному клиенту |
| Сезонная группа | Сезонная средняя по 3 годам |
| Потребность магазина | Отдельный сигнал спроса, не замена факта продаж |
| Новинка | Тестовая партия и ручной лимит |
| Неликвид/старый товар | Не закупать автоматически |
| Данные спорят друг с другом | Ручная проверка |

Для дисплеев профиль строим не только по папке, а по признакам из видео и
карточек товара:

- качество/бренд: InCell, GX, ORIG100, FSENERGY, Soft OLED, Hard OLED, ZY,
  MINK/MMK и другие заполненные свойства;
- рамка/без рамки, площадка под IC, проверка/верификация;
- цена/себестоимость: 4 ценовые группы;
- ширина спроса: продажи по разным магазинам/клиентам или разовая покупка;
- жизненный статус: новый, юный, обычный, старый, неликвид;
- стопы: `дубль`, `снятый`, замена, ручной флаг `не закупать`.

## 5. Контур управления ассортиментом и переход в 1С КА

Управление ассортиментом нужно делать отдельным контуром рядом с закупками. Его
задача - не только посчитать количество к заказу, а решить, должен ли товар
вообще жить в ассортименте, в каком статусе и по каким правилам закупаться.

### Архитектурное решение

Сейчас в `УТ 10.3` и SQL-реплике 1С уже достаточно признаков для старта:
`Предмет`, `Вид номенклатуры`, `Категория`, совместимость, бренд, качество и
часть характеристик. Поэтому сначала не дорабатываем карточку 1С тяжелыми
реквизитами, а строим read-only витрину ассортимента в `pricing-service`.

После перехода на `1С КА` утвержденные результаты этой витрины должны лечь в
типовой контур управления ассортиментом:

- товарные категории и дополнительные классификаторы;
- статус ассортимента;
- ввод и вывод товара из ассортимента;
- ассортиментная матрица по магазинам, форматам, категориям и периодам;
- квоты и ограничения по количеству SKU в категории;
- коллекции/сезоны, если для части ассортимента это нужно.

`pricing-service` при этом остается расчетным и рекомендательным слоем: он
считает BRT, ABC/XYZ, БКГ-по-русски, новинки, ценовые сегменты, неликвид,
каннибализацию, риск раздутого ассортимента и предлагает изменения. `1С КА`
хранит утвержденную политику и документы изменения ассортимента.

### Подходы, которые берем в методику

| Подход | Как использовать у нас | Где живет результат |
| --- | --- | --- |
| Ассортиментная матрица | Решить, какие SKU должны быть в работе по категории/магазину/формату/периоду | Утвержденная матрица в `1С КА`, рекомендации в `pricing-service` |
| Статусы ассортимента | Действующая лестница: `Рассматриваем`, `Заказали`, `Завезли`, `Пошли продажи`, `Растим`, `Поддерживаем` плюс ручные `Матричный`, `Под заказ`, `Кандидат на замену`, `Допродаем`, `Выводим`, `Не закупать` | Расчет, причины и текущее значение - `pricing-service`; после перехода на `1С КА` туда переносится утвержденная политика, но не ежедневный расчет |
| Коммерческие признаки | `эксклюзив`, `собственная марка`, `редкий товар`, `флагман`, `только у нас` | Отдельный слой для сайта, рекламы, цены и контроля продаж; не затирает жизненный статус |
| БКГ-по-русски | Доля товара в наших продажах + динамика наших продаж: растет/падает, важен/не важен | Аналитика и рекомендации в `pricing-service` |
| ABC/XYZ | Не один показатель, а набор: штуки, выручка, валовая прибыль, маржа, стабильность, дефицит | Аналитика в `pricing-service`, итоговый статус - `1С КА` |
| Контроль новинок | Новинка получает цель: оставить или вывести; дорогие новинки обязательны к ручному контролю | `pricing-service` готовит решение, `1С КА` фиксирует ввод/вывод |
| Ценовые сегменты | Внутри категории видеть, где не хватает среднего/эконом/топ сегмента и где товары пожирают друг друга | Классификация в `pricing-service`, устойчивый сегмент можно перенести в `1С КА` |
| BRT | Только кандидат для редкого, но реального спроса; не для разовых продаж и не для всего каталога | Запланирован для backtest и теневого сравнения с Croston/SBA/TSB и профильным min/max; в рабочем расчёте ещё не действует |

### Действующая лестница статусов

Полные формулы и пороги - в `docs/specs/assortment-lifecycle-policy.md`. Здесь
только смысл для человека. Машинные коды не менялись, поменялись названия и то,
что двигает товар по лестнице.

```text
Рассматриваем -> Заказали -> Завезли -> Пошли продажи -> Растим <-> Поддерживаем
                                                          далее ручное решение:
                                                          Допродаем -> Выводим

[Добираем] - отдельная очередь потребности, статус карточки не меняет
```

| Статус | Код | Прежнее название | Смысл | Влияние на закупку |
| --- | --- | --- | --- | --- |
| `Рассматриваем` | `fruit` | `Плод` | Карточка создана, подтвержденного первого закупочного действия еще нет | Собирать сигналы, автозаказ не создавать |
| `Заказали` | `newborn` | `Новорожденный` | Создан первый заказ поставщику | Контроль первого движения товара |
| `Завезли` | `new_item` | `Новинка` | Первый заказ передан в карго | Частый контроль, товар еще не продавался |
| `Пошли продажи` | `sales_start` | `СП / Старт продаж` | Есть первая недавняя продажа, но спрос ниже порога | Осторожный заказ, спрос еще не доказан |
| `Растим` | `sale` | `ПРОДАЖА` | Спрос подтвержден или растет | Заправлять магазин полностью, допустим обоснованный излишек |
| `Поддерживаем` | `working` | `Рабочий` | Пик роста пройден или спрос угасает | Закрывать спрос без дополнительного запаса |
| `Допродаем` | `pension` | `Пенсия` | Ручное решение вывести товар из работы | Автозаказ выключен, остаток продается до нуля |
| `Выводим` | `nonliquid` | `Кандидат на неликвид` | Ручное решение о выводе из ассортимента | Не закупать |
| `Матричный` | `matrix` | без изменений | Должен быть в ассортименте | Ручной режим поверх лестницы |
| `Под заказ` | `on_demand` | без изменений | Под подтвержденную потребность | Общего автозаказа нет |
| `Кандидат на замену` | `replace_candidate` | без изменений | Есть риск замены или дубля | Ручная проверка перед закупкой |
| `Не закупать` | `do_not_order` | без изменений | Жесткий запрет закупки | Исключить до формулы, нужна причина |

Что двигает товар по лестнице:

- ранние ступени - закупочные события: создан первый заказ поставщику, затем он
  передан в карго;
- `Пошли продажи` начинается от факта первой продажи, а не от второго заказа и
  не от очередного поступления;
- `Растим` - когда продано не меньше `12` штук за `180` дней; условия по дням
  наличия для входа нет, чтобы дефицитный ходовой товар не застревал внизу;
- обратно в `Растим` товар возвращается при росте: скорость за `30` дней выше
  скорости за `90` дней минимум на `20%`;
- в `Поддерживаем` товар уходит только при угасании по трем окнам подряд
  (`30` против `90`, `90` против `180`, каждый раз минимум на `20%`) и только
  если товар реально был на полке хотя бы `15` дней из последних `90`;
- если дней наличия не знаем - понижать статус нельзя: это дефицит, а не спад
  спроса;
- правило `5 поступлений за 180 дней` и обязательное подтверждение
  ответственного отменены `2026-08-05`.

Кандидаты на ручное решение: `Родился мертвым` - карточке год и не было ни
заказа, ни продажи, ни подтвержденной потребности; `Допродаем` - последней
продаже больше `548` дней и свежих поступлений не было. Оба только предлагаются,
решение принимает человек.

`Добираем` - не статус, а отдельная очередь. Она открывается, когда после
первого заказа появился дополнительный подтвержденный спрос: сайт, клиент,
менеджер, магазин или звонок. Продажа в 1С для этого не нужна. Карточка при этом
остается там, где была. Старый код `newborn_need` встречается в исторических
данных, но новым карточкам больше не присваивается.

`Эксклюзив` не заменяет жизненный статус: это отдельный коммерческий признак.
Товар может быть одновременно `Растим + Эксклюзив` или `Под заказ + Эксклюзив`.

Все менеджеры видят новинки и могут внести персональный сигнал потребности;
текущий ежедневный документ по подразделению сохраняется, а персональные сигналы
собираются отдельным документом для будущего проекта ЗП/KPI.

### Коммерческие признаки для старта

| Признак | Код | Смысл | Влияние |
| --- | --- | --- |
| `Эксклюзив` | `exclusive` | Товар есть у компании, а у конкурентов или в стране его нет | Бейдж/фильтр на сайте, отдельная реклама, контроль цены, ручной минимальный остаток, пересмотр раз в 30 дней |
| `Собственная марка` | `own_brand` | Собственная марка или ожидаемая собственная марка | Отдельный контроль закупки, качества, сайта и продвижения |
| `Редкий товар` | `rare_market_item` | Товар сложно найти на рынке | Не путать с обычным дефицитом; показывать менеджерам и в витрине |
| `Флагман` | `flagship` | Флагман внутри категории | Отдельный контроль наличия, денег и риска заморозки |

Для `exclusive` нужно хранить тип эксклюзивности: `only_in_country`,
`only_among_competitors`, `own_import`, `supplier_agreement`, `own_brand`.
Также нужны дата проверки, источник проверки и доказательство: парсер
конкурентов, ручной поиск, поставщик, WeChat/Disk, скрин или ссылка.

### Где живет статус: решение 2026-08-05

Раньше планировалось вести `Статус ассортимента` прямо в свойствах номенклатуры
`УТ 10.3` и обновлять их файловым обменом. Этот сценарий отменен.

Как сейчас:

1. `pricing-service` считает жизненный статус, причину, блокеры и хранит их у
   себя; там же лежит история прогонов и предыдущее значение статуса.
2. Ручные решения закупщика (`Матричный`, `Под заказ`, `Кандидат на замену`,
   `Допродаем`, `Не закупать`) вводятся в приложении `Формирование заказа` с
   обязательной причиной и автором.
3. Коммерческие признаки, включая `Эксклюзив`, ведутся отдельно и не затирают
   жизненный статус.
4. В `УТ 10.3` статусы не передаются вообще. Обмен свойствами номенклатуры
   существует для других задач, но восемь служебных полей статуса запрещены на
   уровне кода и не пройдут проверку.
5. Единственный исходящий документ в 1С - непроведенный черновик
   `ЗаказПоставщику` после подтверждения количества человеком.

Почему так: два места хранения статуса неизбежно расходятся, и тогда непонятно,
какому верить. Пока идет обычная работа, достаточно одного места - расчетного
слоя, а 1С получает только результат в виде документа закупки.

## 6. Расчет заказа

Расчет должен идти в несколько шагов.

1. Выбрать папку номенклатуры и ее настройки.
2. Выбрать расчетную единицу закупки: SKU, аналог, `предмет + tag`, группу
   свойств, поставщика, потребность магазина или ручной профиль.
3. Выбрать метод спроса: средняя по доступным дням, сезонная средняя, BRT,
   потребность магазина или ручная проверка.
4. Посчитать продажи только по системным точкам продаж: все продающие склады,
   кроме центрального склада, брака и несистемных продаж.
5. По каждой номенклатурной группе поднять 3 года истории: продажи, количество
   активных SKU, долю продающихся SKU, сезонность и провалы наличия.
6. Учесть план продаж, прогноз продаж и потребности магазинов из РММЗ,
   включая поля вида `Потребности Савелова`.
7. Посчитать остатки шире: активные точки продаж, центральный склад, транзитные
   склады и склады перемещений.
8. Не давать центральному и транзитным складам искажать среднюю продажу: их
   остаток учитывать можно, но их дни наличия нельзя считать как дни наличия
   обычного магазина.
9. Вычесть будущий приход из открытых заказов поставщику, но не одной кучей:
   отдельно видеть товар в компании, через 10 дней, через 20 дней, сданный в
   cargo и еще находящийся у поставщика.
10. Сначала предложить перемещение, если дефицит точки можно закрыть сетевым
    остатком. Продажа сразу после перемещения подтверждает спрос точки, но не
    доказывает прежний дефицит сети. В закупку передаётся только остаточная
    потребность, которую нельзя закрыть перемещением.
11. Для нормальных товаров считать не одной короткой формулой, а слоями:

```text
базовая_скорость = продажи / длина_окна
дни_без_товара = длина_окна - дни_наличия
виртуальные_продажи = дни_без_товара * базовая_скорость
скорость_с_поправкой = (продажи + виртуальные_продажи) / длина_окна

горизонт_покрытия =
срок_подготовки_товара + срок_логистики
+ период_между_заказами + буфер_задержки + буфер_приемки

спрос_на_горизонт =
скорость_с_поправкой
* горизонт_покрытия
* сезонность_по_3_годам
* план_и_прогноз_продаж
* потребности_магазинов
* качество_ассортимента
* распределение_спроса_по_магазинам_и_клиентам

целевой_остаток =
спрос_на_горизонт + страховой_запас + минимум_для_нормального_наличия

доступный_товар =
свободный_остаток_в_торговых_точках
+ перемещаемый_свободный_остаток_центрального/транзитных_складов
+ товар_в_компании_готовый_к_распределению
+ товар_который_придет_примерно_за_10_дней
+ товар_который_придет_примерно_за_20_дней
+ товар_сданный_в_cargo
+ товар_в_обработке_у_поставщика_с_надежной_датой
- остаток_который_нельзя_использовать

сырая_потребность = целевой_остаток - доступный_товар
потребность_к_закупке = max(0, сырая_потребность)
```

Про дни без товара простыми словами: если товара не было на полке, продаж не
было не потому, что он не нужен, а потому что его нечего было продавать. Вопрос
закрыт решением `2026-08-09`, правило из трех частей:

- рабочий товар (`Растим` / `Поддерживаем`) - недостающие дни добираются мягко,
  по средней за весь период; больше чем вдвое скорость от этого вырасти не может;
- жесткий вариант (продажи делятся строго на дни наличия) не используется: на
  пилоте он поднимал дневной заказ в разы; полная дорисовка допустима в будущем
  только как отдельная подсказка человеку для оценки потенциала новинки, не как
  автозаказ;
- предохранитель: если товар был на полке меньше `15` дней за окно, по такой
  базе о скорости не судим - ничего не дорисовываем, а строку с положительным
  заказом отдаем человеку на проверку.

10. Для 1С различать свободный остаток и фактический остаток. Для заказа считать
   свободный остаток, а фактический использовать для контроля и объяснения.
11. Округлить количество по `MOQ`, кратности упаковки, минимальной сумме заказа,
   валюте, условиям оплаты и сроку производства.
12. Если округление поставщика раздувает закупку выше разумного запаса, строка
   уходит на ручную проверку, а не в автозаказ.
13. Min/max запас считать по профилю товара: в днях, штуках, деньгах или
    смешанно.
14. Флагманы определять не одним признаком, а по продажам в штуках, сумме
    продаж, валовой прибыли, рентабельности и себестоимости.
15. Добавить риски трехлетней закупки: сезон не успели закрыть, был дефицит,
    ассортимент раздут, потребности магазинов повторялись, план расходился с
    фактом.
16. Посчитать уверенность (`confidence score`): насколько программе можно
    доверять по строке.
17. Проверить стоп-сигналы.
18. Решить действие: автозаказ, ручная проверка, перемещение или не покупать.
19. Показать человеку строку с причиной и доказательствами.

## 7. Специальные правила расчета

### `К ЗАКАЗУ` из помощника закупок

`К ЗАКАЗУ` - это очередь внимания, а не разрешение закупать. Сначала смотрим
строки с большим количеством, потом применяем стопы:

- `дубль`;
- `снятый`;
- есть замена или ожидается собственная марка;
- ручной флаг `не закупать`;
- нет надежного поставщика/цены/договора;
- спрос похож на разовую покупку одним клиентом.

### Трехлетняя сезонность и ассортимент

Сезонность нельзя считать только по общей сумме продаж. Нужно смотреть, сколько
товаров было активно в группе в каждом периоде.

Пример простым языком: если продажи группы выросли на 20%, но количество SKU
выросло в 2 раза, закупка может быть слабее, а не сильнее. Значит формула должна
увидеть продажи на одну активную позицию, долю SKU с продажами и концентрацию
на флагманах.

Сильная закупка за 3 года:

- сезон закрыт до начала пика;
- мало потерянных продаж из-за отсутствия;
- после сезона нет лишнего дорогого остатка;
- потребности магазинов закрывались вовремя;
- продающихся SKU становится больше, а не просто растет каталог.

Слабая закупка за 3 года:

- сезон регулярно начинается раньше прихода товара;
- топовые позиции заканчиваются, слабые лежат;
- потребности магазинов повторяются и не закрываются;
- план продаж выше прогноза, но закупка не готовит запас;
- срочная логистика часто заменяет нормальный график.

Эти выводы должны становиться рисками в карточке строки и влиять на
`confidence score` - простыми словами, на доверие к автозаказу.

### Ширина спроса

Программа должна смотреть, где именно продался товар:

- 4 штуки по разным магазинам и клиентам - хороший сигнал спроса;
- 4 штуки одному клиенту или в одном заказе - слабый/разовый сигнал;
- если товар был только на центральном складе, это не нормальные дни продаж
  магазина.

Это защищает от ошибки, когда разовая покупка превращается в крупный автозаказ.

### BRT для редкого спроса

BRT рассматривается не вместо всей формулы, а как кандидат на отдельный метод
спроса для товаров, которые продаются редко, но по реальному рыночному спросу.
Обычная средняя по таким товарам часто дает слишком маленькое количество или
ноль.

Фактический статус на `2026-08-10`: BRT в рабочем расчёте не реализован. Сейчас
действует временный структурный пол `13`: он только позволяет медленной карточке
не быть безусловно занулённой и перейти к обычной формуле
`цель − свободный остаток − товар в пути`; это не правило «заказать до 13».
Структурный пол не расширяем. BRT, Croston/SBA/TSB и профильный min/max сначала
нужно сравнить на истории и в теневом режиме, после чего выбранный метод отдельным
решением заменит либо явно уточнит временный предохранитель.

BRT можно применять, если:

- товар не новый и не неликвидный;
- продажи не сводятся к одному клиенту или одному заказу;
- были доступные дни продаж, а не только дни без товара;
- есть понятный горизонт поставки;
- нет стопов `дубль`, `снятый`, замена, `не закупать`;
- поставщик, цена, MOQ и pipeline потом все равно проверяются обычными
  правилами.

BRT нельзя использовать как оправдание автоматического заказа. Он дает только
оценку спроса. Решение об автозаказе все равно принимает `confidence score`,
стоп-сигналы, поставщик, цена, документы и подтверждение человека.

### 1С

Признаки 1С нужно использовать как входные данные, а не спорить с ними
без причины:

- дефицит;
- сверхнорматив;
- супернеликвид;
- ABC/XYZ;
- глубина остатка;
- планы и исключения;
- потребности магазинов, если они ведутся в 1С/РММЗ.

### Флагманы

Флагманы нельзя считать одним правилом.

- Дорогие товары делим только на `Дорогой быстрый` и `Дорогой медленный`.
  Быстрый - до 7 дней включительно, медленный - дольше 7 дней или срок еще не
  подтвержден. Страховой запас задает ответственный за папку до сдачи в cargo.
- Дешевые флагманы можно закупать реже и большим объемом, если цена и спрос
  стабильны. Для них можно проверять покрытие до 80-90 дней, но только если нет
  риска неликвида и цена не прыгает.
- Любой флагман со скачком цены больше/меньше 10% уходит на ручную проверку.

### Pipeline поставки

`В пути` нужно разложить на этапы:

- товар уже в компании и может быть распределен;
- ожидается примерно через 10 дней;
- ожидается примерно через 20 дней;
- сдан в cargo;
- еще в обработке у поставщика.

Если дата прихода ненадежная, программа не должна вычитать этот товар из
потребности как полностью надежный приход. Она снижает уверенность и показывает
строку человеку.

### Новинки

Если `ДатаМин = ДатаМакс`, это первое поступление товара. Новинку нельзя сразу
масштабировать по обычной формуле после первой продажи. Ее нужно выводить в
отдельный контроль, например раз в 5 дней, и ждать следующего периода продаж
перед крупным заказом.

### Старые позиции и неликвид

Товар с продажей не больше 3 штук за 180 дней считается кандидатом в неликвид.
Для него программа должна создать задачу на пересмотр цены/остатка, а не
автоматически увеличивать закупку.

Отдельно нужно подсвечивать товары без назначенных цен по типам `бронза`,
`серебро`, `золото`.

### Запрет закупки

Признак `не закупать` ставит отдел закупки. У признака должны быть:

- причина;
- автор;
- дата;
- срок действия или условие пересмотра.

Такие позиции исключаются из автоматического заказа до расчета.

### Скачок цены поставщика

Базовое правило: если цена поставщика стала больше или меньше на `10%` в
течение двух заказов, строка идет на ручную проверку.

Окно проверки зависит от графика папки. Для АКБ может быть одно окно, для
дисплеев другое. Поэтому правило хранится в настройках папки, а не в одном
общем параметре.

## 8. Поставщик и автоподстановка

Основной поставщик из `РММЗ` или карточки номенклатуры - это хороший кандидат,
но не гарантия автозаказа.

Автоподстановка поставщика разрешена только если одновременно выполнены условия:

- найден ровно один основной поставщик по товару или папке;
- поставщик связан с CRM-компанией Bitrix и контрагентом 1С без дублей;
- договор, валюта, склад прихода и условия оплаты определены однозначно;
- есть свежая подтвержденная цена;
- нет скачка цены больше/меньше 10% по правилу папки;
- поставщик разрешен для этой папки номенклатуры;
- нет блокера по качеству, документам или спорной истории поставки;
- группа товара не требует отдельного ручного решения, например АКБ/ВЭД без
  полного пакета документов.

Если хотя бы одно условие не выполнено, программа не выбирает поставщика сама.
Строка уходит на ручную проверку отдела закупки.

## 9. Хранение цены, условий и доказательств (`evidence`)

Доказательства (`evidence`) - это простыми словами "чем подтверждена цена,
срок, документ или обещание поставщика". Термин не убираем, потому что он нужен
для разработки, но рядом всегда пишем понятную расшифровку.

Лучший вариант - хранить в два слоя.

| Где хранить | Что хранить | Зачем |
| --- | --- | --- |
| Bitrix-карточка закупки | Последняя подтвержденная цена, валюта, дата, кто подтвердил, ссылка на файл/скрин/запись | Удобно людям, видно в процессе |
| Таблица сервиса/аналитики | История `SKU x поставщик x дата x валюта x количество x evidence` | Нужно программе для скачков цены, последних двух заказов и истории |

WeChat-контекст нужно переводить в доказательство:

- файл или скрин;
- структурированная строка: цена, количество, дата, условие;
- автор и дата подтверждения;
- ссылка на исходный Disk/чат, если доступна.

## 10. Контуры закупки

До появления документа в 1С работа идет в приложении `Формирование заказа`.
После создания `ЗаказПоставщику` в 1С заказ ведется в смарт-процессе
(`smart-process`, простыми словами - умная карточка процесса) `Закупка/Заказ`.

| Контур | Когда использовать | Что контролировать |
| --- | --- | --- |
| `Обычный` | Закупка без cargo/ВЭД-цепочки | Потребность, условия, заказ, ожидание поставки, приемка |
| `Cargo` | Закупка через cargo-логистику | Цена, оплата, чек поставщику, отправка, сдача в cargo, путь, приемка |
| `ВЭД импорт` | Белый импорт с документами и таможней | Документы, поставщик, брокер, платежный агент, таможня, ГТД, приемка |

В `1С УТ 10.3` для постоянного процесса нужен реквизит
`ЗаказПоставщику.КонтурЗакупки`. До полной установки реквизита пилот можно вести
по allowlist, но постоянная автоматизация не должна угадывать ВЭД по валюте,
складу, ТН ВЭД или будущей ГТД.
Исключение для миграции старых заказов: если `КонтурЗакупки` пустой, но в
`ЗаказПоставщику` уже заполнена дата `Сдача в карго`, заказ автоматически
попадает в контур `Карго`; явно заполненный контур при этом не перетирается.

## 11. Стоп-сигналы

Если есть стоп-сигнал, программа всё равно создаёт внутренний проект и показывает
проблемную строку в приложении для ручной проверки. Такой проект нельзя передать
в 1С, пока блокер не устранён либо строка не исправлена или не исключена.

- нет однозначного поставщика;
- нет свежей подтвержденной цены;
- скачок цены больше/меньше 10% по правилу папки;
- нет договора, валюты, склада прихода или условий оплаты;
- позиция отмечена `не закупать`;
- товар новый и еще нет нормального периода продаж;
- товар старый/неликвидный;
- центральный или транзитный склад может исказить среднюю продажу;
- дефицит можно закрыть перемещением;
- `АКБ без документов`: нет полного подтверждения, что аккумулятор можно
  безопасно и законно купить, перевезти и растаможить. Минимально нужны MSDS,
  UN38.3, сертификат/ДС, ТН ВЭД, invoice, packing list, страна происхождения и
  понятные условия перевозки;
- есть претензии по качеству, браку, недопоставке или спорной поставке;
- данные противоречат друг другу: остаток, приход, продажи, цена или поставщик.

## 12. Что видит закупщик

Рабочее место - приложение `Формирование заказа`: `Витрина` показывает товары по
статусам и очередь переходов, `Помощник` - строки к проверке перед сборкой
заказа, `Заказы` - заказы на подтверждении и передачу черновика в 1С, `Свойства`
- ручные решения по статусу, `История` - журнал действий.

Закупщик должен видеть очередь решений, а не просто таблицу.

По каждой строке:

- что купить;
- сколько купить;
- почему система это предлагает;
- что уже в пути;
- какой поставщик выбран и почему;
- какая цена подтверждена;
- есть ли скачок цены;
- какие документы нужны;
- что заблокировано и почему;
- чем строка закрывается: покупкой, перемещением, запретом или ручной проверкой.

Доступные действия:

- подтвердить;
- изменить количество;
- выбрать другого поставщика;
- отправить в переговоры;
- отложить;
- запретить закупку;
- отправить строку на разбор данных.

## 13. Данные из пилотных записей

Пилотные записи Disk из запроса повторно разобраны по экрану, OCR и черновому
распознаванию звука:

- `objectId=37976` - `Запись экрана 2026-06-22 в 13.39.46.mov`, примерно
  25:53. Тема: как программа предлагает количество к заказу, какие товары
  исключать, как задавать поставщиков по свойствам, почему `К ЗАКАЗУ` не равно
  автоматическому заказу, почему среднюю продажу нужно считать по магазинам
  отдельно, как отличать новинки, старые позиции и неликвид.
- `objectId=37992` - `Запись экрана 2026-06-22 в 14.16.09.mov`, примерно
  16:16. Тема: разные подходы к флагманам, дорогим/дешевым позициям, pipeline
  заказа в 3-4 этапа, неликвиду, ABC по количеству/сумме/рентабельности, цене
  товара и скачкам цены поставщика.

Что принято в контур из видео:

- `дубль`, `снятый`, замена и `не закупать` блокируют автозаказ до формулы;
- свойства дисплеев могут дробить расчет и поставщика: качество, рамка,
  площадка под IC, верификация;
- спрос проверяется по магазинам и клиентам, а не только по общей штуке;
- новый товар не масштабируется по первой продаже, юный товар считается
  осторожно;
- дорогие товары пересматриваются чаще и меньшими партиями;
- дешевые флагманы можно рассматривать на больший запас при стабильном спросе;
- pipeline поставки хранится этапами, а не одним числом `в пути`;
- сильное изменение цены после ответа поставщика отправляет строку на ручную
  проверку.

Рабочие артефакты распознавания лежат локально в
`pricing-service/build/procurement_disk_recognition/`:

- `37976_transcript_tiny.md`;
- `37992_transcript_tiny.md`;
- `snapshots_37976_ocr.txt`;
- `snapshots_37992_ocr.txt`.

Это черновое распознавание, но его достаточно, чтобы извлечь бизнес-правила для
MVP. Если нужен почти дословный протокол, надо отдельно запускать более тяжелое
распознавание и вычитывать спорные места человеком.

## 13a. Что решено и что реально работает

Правило, записанное в документе или в конфигурации, не означает, что оно
исполняется. Полная карта - в
`docs/specs/assortment-status-legacy-rule-inventory.md`. Коротко на `2026-08-10`:

| Блок | Принятое правило | Реализация на `2026-08-10` |
| --- | --- | --- |
| Расчет статусов по всей папке `дисплеи` | Используется единая лестница жизненных статусов | Работает: `2729` карточек получили статус; технический источник результата ещё восстанавливается |
| Приложение `Формирование заказа` | Внутренние проекты являются штатным результатом расчёта; передача в 1С только вручную | Интерфейс и внутренние проекты работают; обе записи наружу выключены флагами |
| Очередь закупщиков | Общая для пользователей с действующим доступом; отдельного назначения и замещения нет | Используется текущий список доступа приложения; фактический пользователь действия сохраняется в истории |
| Лимиты суммы и количества | На текущем этапе отсутствуют; показывается полная потребность | `max_order_qty=null`; профильные `yellow`-лимиты не требуются |
| Витрина дней наличия из 1С | Наличие считается по объединению интервалов точек | Построена и обновляется ночью; расчёт заказа использует дни, когда товар был хотя бы в одной точке |
| Скорость и потребность по каждой точке отдельно | Требование принято, но текущий пилот не блокирует | Не сделано: расчёт по-прежнему один на товар по всей сети |
| Разделение спроса по каналам | Каналы должны быть различимы и не искажать спрос | Есть отдельный отчёт; формула заказа его пока не использует |
| Сначала перемещение, потом закупка | Закупается только остаточная потребность сети | Не завершено: остаток центрального склада виден, но ещё не вычитается из закупки |
| Блокеры дневной партии | Проблемные строки сохраняются; блокируется только передача конкретного проекта в 1С | Не завершено: cron с `--fail-on-blockers` может отменить сохранение всей партии |
| Ручные правки при пересчёте | Количество и цена защищаются построчно, новая рекомендация показывается как расхождение | Построчный merge ещё не реализован |
| Брак, поставщик и уверенность | Пороги брака, прозрачная лестница поставщика и `green/yellow/red` утверждены | Реализация частичная: exact-supplier блокер работает; аварийный сигнал не охватывает все ранние статусы; общей `confidence_category` ещё нет |
| Отмена консолидации аналогов | Каждая карточка считается самостоятельно | Выполнено: код удалён `2026-07-31`, сверка количества пройдена |
| Всё после `Поддерживаем`: `Допродаём`, вывод из ассортимента | Отдельный будущий контур | Работа не начиналась и внутренний автозаказ не блокирует |

## 14. Не входит в первый шаг

- автопроведение `ЗаказПоставщику`;
- прямой SQL-write в 1С;
- автоматическое списание денег;
- автоматический выбор спорного поставщика;
- заказ без подтвержденной цены, договора, валюты и склада;
- ВЭД/АКБ без документальной остановки;
- HTTP-запись в 1С как первый канал;
- полноценная WeChat-интеграция за один шаг.

Сначала нужен слой доказательств, затем парсер/API WeChat, если технически и
юридически это можно сделать.

## 15. Критерии приемки MVP

MVP можно считать полезным, если за 30 дней:

- по выбранной папке система стабильно формирует короткий список к действию;
- у каждой строки есть расчетная единица: SKU, аналог, `предмет + tag`, группа
  свойств, поставщик, потребность магазина или ручной профиль;
- у каждой строки есть метод спроса: средняя, сезонная средняя, BRT,
  потребность магазина или ручная проверка;
- у каждой строки есть понятное объяснение и источник данных;
- по дисплеям разобраны 6 месяцев заказов поставщику и фактические сроки `заказ
  -> cargo -> склад`;
- `дубль`, `снятый`, замена и `не закупать` блокируют автозаказ до формулы;
- спрос проверяется по магазинам/клиентам, чтобы разовая продажа не стала
  крупным заказом;
- pipeline поставки виден этапами, а не одним числом `в пути`;
- у пилотной папки есть анализ 3 лет: сезонность, активные SKU, продажи на SKU,
  план/прогноз и потребности магазинов;
- не меньше 90% строк имеют корректный статус: купить, переместить, не
  покупать, проверить;
- все строки без цены/поставщика/документов блокируются до ручной проверки;
- скачки цены больше/меньше 10% подсвечиваются;
- черновик `ЗаказПоставщику` создается в 1С только после подтверждения;
- в Bitrix виден полный след: кто подтвердил, почему, какие файлы приложены,
  где заказ сейчас;
- закупка может показать хотя бы 5 примеров, где система предотвратила ошибку:
  лишнюю закупку, неправильного поставщика, цену, отсутствие документов или
  искаженную среднюю продажу.

## 16. Статус решений и будущие исследования

### Решения текущего этапа закрыты

1. ~~Как считать спрос за дни без товара?~~ Решено `2026-08-09`: мягкая
   дорисовка для рабочего товара, предохранитель `15` дней, полная дорисовка -
   только будущая подсказка по новинкам (см. раздел 6).
2. ~~Подтверждаем ли окончательную отмену консолидации аналогов?~~ Решено:
   отмена окончательна, код удален `2026-07-31`, каждая карточка заказывается
   сама.
3. ~~С какого уровня уверенности расчета можно готовить заказ без ручного
   разбора: `80`, `85` или `90`?~~ Решено `2026-08-10`: числового порога нет;
   используются объяснимые `green/yellow/red`, жёлтая требует решения перед 1С
   без автоматического обнуления.
4. ~~Какие пороги процента брака считаем нормой, наблюдением и высоким риском?~~
   Решено `2026-08-10`: exact-supplier `>10%` при базе `≥100` и аварийная партия
   `≥5`/`≥40%` блокируют строку; неизвестная связь требует ручного решения,
   база `<30` остаётся информационной, `30–99` — предупреждение и проверка без
   автоматического обнуления.
5. ~~Какие лимиты останавливают автоматику: сумма заказа, количество, поставщик,
   дневной бюджет?~~ Решено `2026-08-10`: на текущем этапе лимитов суммы и
   количества нет. Приложение показывает полную рассчитанную потребность и её
   стоимость; крупное значение само по себе не создаёт `yellow`, не обрезает и
   не обнуляет заказ. Бюджетный контроль откладывается до утверждения бюджетной
   модели.
6. ~~Кто замещает Омара, если очередь решений не разобрана в день расчета?~~
   Решено `2026-08-10`: отдельное замещение не требуется. Очередь общая для
   сотрудников закупки с действующим доступом; кто открыл проект и взял его в
   работу, тот его обрабатывает. Назначение основного менеджера, резервная роль
   и переключение через день отменены как избыточные.

### Будущие исследования, не блокирующие внутренний автозаказ

Следующие темы нельзя решать догадками. Сначала нужны данные или теневое
сравнение; до этого они не мешают создавать и показывать текущие проекты «К
заказу»:

7. Какие свойства номенклатуры в 1С заполнены достаточно, чтобы строить по ним
   профиль закупочного поведения, и где надежны `предмет`, `tag`, характеристики?
8. Для каких профилей редкого спроса BRT разрешен, а для каких запрещен?
9. Какие свойства дисплеев должны дробить заказ по поставщикам: качество, рамка,
   площадка под IC, верификация?
10. Какой min/max запас ставим по профилям: в днях, штуках, деньгах или смешанно?
11. Где точный источник плана и прогноза продаж и какие потребности магазинов из
   РММЗ считать активными?
12. Какой шаг сезонности брать по папкам: месяц, неделя или оба варианта?
13. Какие профили требуют обязательной ручной проверки любым допущенным
   сотрудником закупки: дорогие товары, новинки, высокий MOQ, неликвид?

## 17. Следующий шаг: реализовать уже принятые правила

Ближайшие шаги контура на `2026-08-10`:

1. Убрать общий отказ сохранения дневной партии из-за `--fail-on-blockers`:
   проблемные строки должны быть видны, а блокироваться должна только передача
   конкретного проекта в 1С.
2. Защитить ручные количество и цену от следующего автопересчёта; новую
   рекомендацию показывать как расхождение для явного принятия.
3. Проверить оба исправления и включить ежедневное сохранение внутренних
   проектов без дополнительного гейта сверки количества с человеком.
4. Продолжить теневые сравнения формул и доведение фактов, не блокируя ими
   появление текущих проектов «К заказу».
5. После трёх успешных рабочих дней внутреннего автозаказа передать в 1С один
   небольшой проверенный проект без блокеров. Проверить реквизиты,
   непроведённость документа и отсутствие дубля; только затем отдельно решать,
   разрешать ли ручную передачу остальных проектов.
