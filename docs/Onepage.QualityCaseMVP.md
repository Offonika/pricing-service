Onepage v0.1 — «Контур брака / качества MVP»

1. Цель
После реализации `expertise_case` расширить модель кейсов до более широкого контура брака и качества, не ломая уже работающий контур экспертиз и не углубляясь в тяжелую доработку старой `1С УТ 10.3`.

Решение:
- оставить `1С` системой учета документов, качеств и остатков;
- вынести управленческий lifecycle дефектов и спорных случаев во внешний backend-контур;
- использовать `Bitrix24` как кейсовый и обзорный слой;
- сохранить `expertise_case` как первый уже реализованный частный кейс;
- ввести более широкий доменный слой `quality_case` как следующий типовой контур;
- сразу зафиксировать границы контура, чтобы не смешивать в одну очередь:
  - физический брак / качество;
  - пересорт;
  - реальные дубли номенклатуры;
  - архивные / выведенные позиции.

2. Что меняется
`1С` продолжает вести:
- физическое качество товара:
  - `Новый`
  - `Брак`
  - `Некондиция`
- документы:
  - `Корректировка качества`
  - `Возврат от покупателя`
  - `Экспертиза`
  - `Перемещение`
  - `Возврат поставщику`
  - `Списание`
- номенклатуру, склады, подразделения, контрагентов;
- учетные связи между документами;
- остатки и учетное движение товара.

Новый внешний сервис начинает вести:
- единый `quality_case` как карточку кейса качества;
- `case_type` и операционный сценарий;
- owner и SLA;
- текущий операционный статус кейса;
- историю этапов;
- классификацию причины дефекта;
- фото, видео и служебные данные;
- audit trail по всем действиям;
- признаки, нужные для аналитики и контроля злоупотреблений.

Отдельно, но рядом с этим контуром, должны существовать связанные сценарии:
- `mis_sort_case`:
  - пересорт и повторные пересорты;
- `catalog_duplicate_case`:
  - реальные дубли номенклатуры, которые нужно объединять;
- `archived_sku_case`:
  - возвраты и движения по архивным / выведенным позициям.

Важно:
- не каждый проблемный возврат = `quality_case`;
- `quality_case` отвечает за физическое качество и решение по товару;
- пересорт, дубль и архивная позиция могут быть связанными причинами или соседними контурами, но не должны растворяться внутри брака.

`Bitrix24` используется для:
- очереди кейсов;
- контроля просрочки;
- обзора по owner, подразделениям и источникам дефектов;
- производных задач только там, где реально нужно действие;
- эскалаций и будильников по срокам.

Связь с уже реализованным контуром:

- [TechDesign.ExpertiseCaseMVP.md](/opt/MM/pricing-service/docs/TechDesign.ExpertiseCaseMVP.md)

3. Как это работает
Базовый поток MVP:
- в `1С` возникает событие качества или спорный кейс;
- backend создает или обновляет `quality_case`;
- кейс получает `case_type`, owner, SLA и статус;
- если кейс требует экспертизы, он связывается с уже существующим `expertise_case` или становится его источником;
- дальнейшие этапы фиксируются как события во внешнем контуре.

Ключевая идея:
- не все кейсы качества являются экспертизами;
- экспертиза становится одним из частных сценариев внутри более широкого контура качества.

Ключевое уточнение по протоколу звонка `№3705`:
- нельзя лечить одним и тем же процессом:
  - брак;
  - пересорт;
  - дубль;
  - архивную позицию;
- если это один и тот же товар под разными карточками, нужен контур объединения номенклатуры, а не кейс брака;
- если позиция архивная или выведенная, нужен отдельный сценарий возврата и ограничения на использование;
- если проблема в повторяющемся пересорте, нужен отдельный признак риска и контроль возвратов по истории позиции.

Подробный onepage по соседнему контуру:
- [Onepage.MisSortCaseMVP.md](/opt/MM/pricing-service/docs/Onepage.MisSortCaseMVP.md)

Минимальные типы кейсов `Wave 1`:
- `expertise`
- `defect_internal`
- `customer_return_defect`
- `quality_change_review`

Следующий тип, который логично подключать потом:
- `discount_candidate`

4. Что получает бизнес
- единый реестр кейсов качества;
- прозрачный owner по каждому кейсу;
- контроль SLA по проверке и принятию решения;
- понятные статусы вместо чатов и ручных договоренностей;
- нормальную статистику по браку;
- различение:
  - скрытого дефекта;
  - дефекта, пропущенного на приемке;
  - клиентского возврата с дефектом;
  - спорного кейса, ушедшего в экспертизу;
- отделение брака от:
  - пересорта;
  - дубля номенклатуры;
  - архивной / выведенной позиции;
- основу для контура уценки;
- контроль злоупотреблений по смене качества;
- основу для аналитики по поставщикам, подразделениям и сотрудникам.

5. Что видит руководитель
По каждому кейсу:
- тип кейса;
- дата создания;
- подразделение;
- номенклатура;
- количество;
- текущее качество;
- причина / классификация дефекта;
- текущий статус;
- дедлайн;
- ответственный;
- решение;
- история событий;
- link на связанные документы `1С`;
- link на `expertise_case`, если кейс ушел в экспертизу.

Отдельно:
- список открытых кейсов;
- список просроченных кейсов;
- очередь по owner;
- аналитика по `Новый -> Брак`;
- аналитика по `Брак -> Новый`;
- статистика по причинам дефектов;
- статистика по подразделениям и приемщикам;
- список кейсов, ушедших в уценку.
- список возвратов по архивным позициям;
- список возвратов по позициям с историей критичного пересорта;
- список кейсов, где товар ошибочно пытались увести в брак вместо другого сценария.

6. Что нужно от 1С
Минимум, без глубокой переделки:
- read-only доступ к документам качества и возвратов;
- стабильные идентификаторы документов;
- физическое качество товара;
- дату и автора изменения качества;
- подразделение / склад;
- номенклатуру;
- количество;
- цену / сумму, если они важны для последующего решения;
- причину возврата или причину отказа, если она есть в документе;
- решение по строке / документу, если оно фиксируется;
- links на связанные документы:
  - `Реализация`
  - `Заказ покупателя`
  - `Возврат от покупателя`
  - `Экспертиза`
  - `Возврат поставщику`
  - `Списание`

Важно:
- `1 учетное событие качества в 1С` не всегда равно одному бизнес-кейсу;
- backend должен нормализовать несколько документов в один `quality_case`, если они относятся к одному управленческому случаю;
- внешний backend не должен угадывать семантику документа, нужен явный source contract по каждому типу события.

Что важно учесть по звонку `№3705`:
- если в `1С` есть штатная обработка объединения дублей, ее лучше использовать как основной путь для реальных дублей;
- архивные позиции нельзя лечить простым переименованием в духе `дубль`, для них нужен явный архивный статус / контур;
- возвраты по старому наименованию после уже исправленного пересорта должны детектироваться как отдельный риск, а не как обычный возврат.

7. Что пока не делаем
- тяжелую доработку форм и логики старой `1С УТ 10.3`;
- расширение справочника качеств под каждый вид дефекта;
- обратную запись lifecycle кейса в `1С`;
- полную автоматическую классификацию причин дефекта;
- Telegram UX;
- сложную матрицу уценки;
- сквозной barcode/QR для всего контура качества.

8. MVP-периметр
В первую очередь запускаем:
- backend-модель `quality_case`;
- историю событий `append-only`;
- sync событий качества из `1С`/адаптера;
- list/get/history API;
- структурированную фиксацию доказательств по кейсу:
  - фото;
  - комментарий;
  - подразделение;
  - кто отправил;
  - когда отправил;
- действия:
  - `take-in-work`
  - `send-to-okk`
  - `send-to-expertise`
  - `record-decision`
  - `mark-written-off`
  - `mark-returned-to-supplier`
  - `mark-converted-to-discount`
  - `close-case`
- два автоматических фильтра на возврате:
  - `archived_sku_return_filter`
  - `critical_mis_sort_return_filter`

Не входит в MVP:
- UI в Telegram;
- глубокая синхронизация с `Bitrix24`;
- полноценный контур уценки;
- автоматическое решение по всем типам кейсов;
- роботизация всех переходов внутри `1С`.

9. Основной архитектурный принцип
Рекомендуемый путь:
- не переписывать уже реализованный `expertise_case`;
- не тащить весь lifecycle качества обратно в старую `1С`;
- использовать внешний backend как anti-corruption layer между `1С` и `Bitrix24`;
- строить `quality_case` как следующий слой над уже работающим case-паттерном.

То есть:
- `1С` = система учета документа и физического качества;
- backend = источник истины для кейса, owner, SLA, классификации причины и event history;
- `Bitrix24` = слой обзора, координации и производных задач.

10. Что нужно согласовать до боевой интеграции
Нужно зафиксировать:
- какие именно события считать триггерами для создания `quality_case`:
  - `Новый -> Брак`
  - `Брак -> Новый`
  - возврат клиента с дефектом
  - скрытый дефект после проверки
  - спорный кейс, уходящий в экспертизу
- какую сущность считать главным ключом кейса:
  - документ качества
  - связанный заказ / реализацию
  - группу связанных документов
- какие поля обязательны для создания кейса;
- как классифицировать причину:
  - `hidden_factory_defect`
  - `acceptance_negligence`
  - `damage_in_internal_handling`
  - `customer_return_defect`
  - `pending_expertise`
  - `confirmed_ok_after_check`
- кто owner по типам кейсов;
- какие изменения должны приводить к sync update, а какие нет;
- в какой момент кейс качества превращается в `discount_candidate`.
- где проходит граница между:
  - `quality_case`
  - `mis_sort_case`
  - `catalog_duplicate_case`
  - `archived_sku_case`;
- как именно помечать `опасный пересорт`, чтобы потом срабатывал фильтр на возврате;
- какой архивный признак позиции можно reliably читать из `1С` или сервисной БД;
- нужно ли блокировать оформление возврата до разбора кейса или достаточно предупреждения / задачи;
- какой канал фиксации фото считается целевым:
  - чат по подразделению;
  - форма / backend;
  - карточка кейса в `Bitrix24`.

Что уже решено концептуально:
- экспертиза не исчезает, а остается отдельным частным кейсом;
- `quality_case` должен расширять, а не ломать реализованный контур экспертиз;
- уценка должна быть исходом кейса качества, а не отдельным независимым миром;
- качество товара в `1С` должно оставаться простым, а не превращаться в каталог дефектов.
- реальные дубли номенклатуры не надо маскировать под брак, для них правильнее идти через объединение;
- архивные позиции не надо лечить только переименованием, им нужен отдельный сценарий ограничения использования;
- повторный пересорт после возврата должен считаться не обычной ошибкой, а контролируемым риском.

11. Минимальные артефакты для согласования
Перед следующей волной нужно собрать:
- 10-20 реальных примеров кейсов:
  - внутренний дефект до продажи;
  - возврат клиента с дефектом;
  - скрытый брак;
  - спорный кейс, ушедший в экспертизу;
  - кейс со сменой `Брак -> Новый`;
  - возврат по архивной позиции;
  - возврат после исправленного пересорта;
  - реальный дубль номенклатуры;
  - ложный `брак`, который на деле оказался пересортом;
- список документов `1С`, из которых строится кейс;
- mapping `1С -> quality_case`;
- классификатор причин дефекта;
- матрицу решений:
  - `экспертиза`
  - `возврат поставщику`
  - `списание`
  - `уценка`
  - `подтвердить как новый`
- правила owner и ответственности по этапам;
- правила эскалации по просрочке;
- правила аналитики по злоупотреблениям.
- описание штатной обработки объединения дублей в старой `1С`:
  - что она реально умеет;
  - какие ограничения есть;
  - какие последствия для истории документов и возвратов;
- признак архивной / выведенной позиции и место его хранения;
- критерии, по которым пересорт считается `опасным` для будущих возвратов.

12. Управленческое решение
Рекомендуемый путь:
- утвердить `quality_case` как следующий bounded context после `expertise_case`;
- считать `expertise_case` первым реализованным частным кейсом этой модели;
- не стартовать широкую автоматизацию качества, пока не зафиксирован source contract по событиям `1С`;
- после согласования запускать следующую волну:
  - адаптер событий качества из `1С`;
  - точный mapping полей;
  - классификатор причин;
  - фильтры возврата для архивных позиций и опасного пересорта;
  - структурированную фиксацию фото и фактов по подразделениям;
  - правила решений и закрытия;
  - затем `Bitrix24`-слой и производные задачи.

Это дает эволюционное развитие уже реализованной case-модели, не ломает старую `1С` и позволяет последовательно подключить:
- брак / качество;
- пересорт как отдельный связанный контур;
- работу с дублями и архивными позициями без маскировки под брак;
- уценку;
- аналитику по злоупотреблениям;
- статистику по поставщикам и подразделениям.

13. Что добавил протокол звонка №3705 в архитектуру
Протокол усиливает уже выбранный курс, но добавляет важные ограничения.

Что теперь важно зафиксировать явно:
- `quality_case` не должен стать общей свалкой всех товарных проблем;
- нужно архитектурно развести минимум четыре сценария:
  - физический дефект;
  - пересорт;
  - дубль номенклатуры;
  - архивная / выведенная позиция;
- общий чат с фото по браку не подходит как system of record.

Предлагаемая целевая схема:
- `1С`:
  - учет остатков, качества, документов, архивности и штатных обработок;
- backend / service DB:
  - `quality_case`
  - `mis_sort_case`
  - risk flags по номенклатуре / возвратам
  - event history и evidence registry;
- `Bitrix24`:
  - очереди, owner, SLA, задачи, эскалации;
- фото / фиксация:
  - либо структурированный канал по подразделению,
  - либо форма/карточка, которая сразу пишет вложения в кейс.

Минимальные предложения по реализации:
- для брака на приемке:
  - обязательное фото + причина + подразделение + отправитель;
- для возврата:
  - перед подтверждением проверять:
    - архивная ли позиция;
    - есть ли у позиции история критичного пересорта;
- для дублей:
  - запускать не `quality_case`, а сценарий проверки на объединение;
- для системного пересорта:
  - хранить признак `critical_mis_sort` и поднимать связанный кейс при возврате;
- для обучения приемке:
  - использовать реестр ложного брака как материал для управленческой обратной связи.
