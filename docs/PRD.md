# **PRD v0.3**

**Проект:** Умное ценообразование Master Mobile  
 **База:** 1С \+ парсер конкурентов \+ OpenAI \+ 1С \+ Telegram-бот

Связанный регламент по присвоению SKU: `docs/sku_policy.md`.

---

## **1\. Зачем мы это делаем**

### **1.1. Текущая ситуация**

Сейчас цены на запчасти выставляются в основном вручную:

* коммерческий директор и закупщики смотрят прайсы конкурентов;

* сравнивают с нашими закупочными/розничными ценами;

* руками правят цены в 1С;

* редко учитывают курс, остатки, браки, статусы запаса и т.п.

Проблемы:

* много рутинного труда и человеческого фактора;

* медленная реакция на изменение цен и наличия у конкурентов;

* теряем маржу на эксклюзивах и новинках, где могли бы зарабатывать больше;

* 1С умно управляет запасами, но цены живут отдельно.

### **1.2. Цель проекта**

Сделать **отдельный сервис ценообразования**, который:

* автоматически собирает данные:

  * из 1С (выгрузки DBF и/или его БД),

  * из данных по конкурентам:

    * либо из внешнего парсера (ZennoPoster → файлы),

    * либо из встроенного модуля парсинга внутри сервиса (HTTP-парсер через Proxy API / прокси-сервера),

  * из 1С (через те же выгрузки, что идут в 1С);

* с помощью правил и ИИ (OpenAI) **сопоставляет** наши товары с товарами конкурентов;

* **рассчитывает рекомендованные цены** по прозрачным стратегиям;

* отдаёт результат в виде:

  * файлов для 1С («Установка цен номенклатуры»),

  * списков на ручное утверждение,

  * отчётов для руководства и закупки;

* работает в той же философии, что и **1С**:

   роботы считают и контролируют, люди принимают решения по стратегии и исключениям.

### **1.3. Ключевые эффекты**

Через 3–6 месяцев после запуска:

* **Сократить время** на выставление и обновление цен по пилотной тысяче позиций в разы.

* **Быстрее реагировать** на рынок (ежедневный мониторинг конкурентов).

* **Увеличить маржу**:

  * грамотная работа с эксклюзивами, флагманами, новинками;

  * исключение демпинга ниже минимальной маржи.

* **Привязать цену к запасам**:

  * сверхнормативы и супернеликвиды — распродавать по правилам;

  * дефицитные и хитовые позиции — не “сливать” в ноль.

## **2\. Scope и MVP**

### **2.1. Пилот (MVP)**

* Ассортимент первой волны: **≈1000 позиций**:

  * дисплеи (Apple, Samsung, Xiaomi и др.),

  * потом аккумуляторы,

  * потом шлейфы, стёкла, далее по приоритету.

* Конкуренты: **4–5 основных** (Моба, GreenPark, UltraDetail, MEMS и др. — финальный список согласовать).

* Частота:

  * парсер конкурентов — ежедневно (1 раз в день);

  * расчёт цен и отчётов — минимум 1 раз в неделю, целевая частота — ежедневно.

### **2.2. В объём MVP входит**

* Чтение исходных данных из:

  * выгрузок 1С (DBF / MySQL),

  * данных конкурентов, полученных:

    * либо из файлов внешнего парсера (ZennoPoster),

    * либо из встроенного модуля парсинга в сервисе (HTTP-парсер с Proxy API / прокси).

* Сопоставление номенклатуры с помощью правил \+ OpenAI.

* Классификация товаров для целей ценообразования.

* Конструктор стратегий ценообразования (первый простой вариант).

* Расчёт рекомендованных цен по пилотным группам.

* Формирование файлов для 1С и списков на ручное утверждение.

* Базовые отчёты «до/после».

* Telegram-бот с базовыми командами и уведомлениями.

## **3\. Пользователи и роли**

1. **Коммерческий директор**

   * задаёт стратегии ценообразования по группам/классам;

   * утверждает спорные и дорогие изменения;

   * получает дайджесты и ключевые сигналы в Telegram.

2. **Закупщик / категорийный менеджер**

   * получает сигналы:

     * флагманы рынка, где мы проигрываем;

     * эксклюзивы;

     * дефицит/сверхнорматив;

   * корректирует матрицу, закупки и даёт предложения по стратегиям.

3. **Финансовый директор / собственник**

   * смотрит агрегированные отчёты:

     * маржа до/после;

     * оборачиваемость;

     * доля неликвидов и сверхнормативов;

   * получает укороченный “дашборд владельца” в Telegram.

4. **ИТ / аналитик**

   * настраивает обмен файлами (1С → сервис → 1С);

   * следит за статусом сервиса;

   * помогает с отчётами и параметрами.

## **4\. Источники данных и интеграция**

### **4.1. Выгрузки 1С (DBF / БД)**

Основной источник:

* `Tovar.DBF` — справочник номенклатуры:

  * `KODTOV` — код номенклатуры (ключ);

  * `IDTOV` — UUID;

  * `TOVAR` — наименование;

  * `ARTIKUL` — артикул;

  * `VID` — Товар/Услуга;

  * `GRUPPA`, `URTOV1…URTOV7` — иерархия групп:  
     «ОБЩИЙ КАТАЛОГ → Запчасти для телефонов → Дисплеи/Аккумуляторы/Шлейфы/…».

* Таблицы с ценами:

  * закупочная/себестоимость;

  * розничная базовая (тип цены, выбранный как опорный).

* `Sales.DBF` — продажи:

  * для расчёта средних продаж, флагманов, анализа спроса.

* `Nost.DBF` — остатки:

  * для дефицита, сверхнормативов, глубины остатка.

* `Zakpost.DBF` и др. — закупки:

  * закупочные цены по поставщикам.

* Статусы и анализ из 1С:

  * статусы товара: Новинка, Нет продаж;

  * статусы запаса: Сверхнорматив, Супернеликвид;

  * классы ABC/XYZ;

  * глубина остатка (если есть, иначе считаем так же, как в 1С).

**Принцип:** не пересчитываем ABC/XYZ и статусы, а **используем результаты 1С** как входные признаки.

### **4.2. Данные из 1С**

При необходимости:

* свойства товаров:
  - бренд, модель;
  - тип дисплея (матрица): LCD (IPS), LCD (TFT), OLED, AMOLED, Super AMOLED, Dynamic AMOLED, LTPS LCD, LTPO AMOLED;
  - класс дисплея (качество замены): Original, Original Refurbished, OEM, Copy High, Copy Medium, Copy Low;
  - конструкция: In-Cell, On-Cell, COF, COG;
  - частота обновления (опционально): 60 / 90 / 120 / 144 Hz;
  - цвет и т.д.;
  - рекомендуется хранить тип/класс/конструкцию/частоту отдельными реквизитами, чтобы не смешивать признаки.

* процент брака (по отчётам/регистрам), когда будет выбрано удобное место для выгрузки.

На старте можно опираться на те поля, что уже попадают в выгрузку для 1С.

### **4.3. Данные от конкурентов (режимы ZennoPoster / встроенный парсер)**

Текущий список конкурентов для пилота:  
- moba.ru  
- green-spark.ru  
- ultra-details.ru  
- memstech.ru

**Два режима получения данных:**

* **Режим A — ZennoPoster (внешний парсер → файлы):**

  * внешний парсер (ZennoPoster/ZenLogs) собирает данные по конкурентам;

  * отдает сервису файлы CSV/Excel с данными;

  * pricing-service читает эти файлы как вход.

  * Для пилотных конкурентов (moba.ru, green-spark.ru, amigo и др.) ZenLogs ежедневно (1 раз в день после публикации выгрузки) отдаёт XLSX-файлы по HTTPS с одинаковой структурой (`group`, `sku`, `name`, `price_opt`, `link`, `stock`, опционально `price_roz`). Импорт приводит эти значения к формату «товар конкурента» (competitor, external_id, name, category, price_opt/price_roz, availability, url, scraped_at) и апсертит их в каталог конкурентов и историю цен/наличия. Список источников задаётся через конфиг, поэтому при добавлении нового конкурента достаточно указать пару `имя:url`.

* **Режим B — Встроенный парсер (HTTP через Proxy API):**

  * модуль внутри pricing-service сам ходит по сайтам конкурентов;

  * все запросы идут через Proxy API / HTTP-прокси, чтобы не светить основной IP;

  * данные приводятся к целевому формату и пишутся напрямую в БД сервиса.

**Единый формат данных (независимо от режима источника):**

* `id` — ID/внешний код в источнике;

* `name` — наименование товара;

* `price_roz` — розничная цена;

* `price_opt` — оптовая цена (если есть);

* `quantity / "Есть в наличии"` — остаток/наличие;

* `url` — ссылка на товар;

* `category` — раздел/категория (если доступно);

* дата съёма (в имени файла или в поле).

Сервис хранит историю цен и остатков конкурентов для анализа флагманов и динамики, вне зависимости от выбранного режима.

#### Конфигурация источника данных конкурентов

* Переключатель на уровне окружения: `COMPETITOR_SOURCE_MODE` (финальное имя будет зафиксировано в конфиге/README).

  * `zenno` — сервис ждёт файлы от внешнего парсера (ZennoPoster/ZenLogs). Переменные `ZENLOGS_IMPORT_ENABLED`, `ZENLOGS_SOURCES` (`name:url` через запятую), `ZENLOGS_MOBA_URL` (fallback), `ZENLOGS_HTTP_TIMEOUT_SEC`, `ZENLOGS_VERIFY_SSL` управляют списком источников и параметрами загрузки.

  * `internal` — сервис использует встроенный HTTP-парсер через Proxy API и пишет данные сразу в БД.

### **4.4. Рынок смартфонов и поисковый спрос на запчасти**

Цель: раньше видеть появление новых моделей смартфонов и спрос на запчасти (дисплеи/экраны/тач/стекло), чтобы учитывать это в матрице и ценообразовании.

**Источник и поток данных:**

1. **Агент новостей/пресс-релизов (ChatGPT/Codex):**
   - регулярно сканирует конфигурируемый список сайтов брендов (Apple, Samsung, Xiaomi и др.);
   - вытаскивает из пресс-релизов нормализованные данные: бренд, модель, вариант (Pro/Ultra/Plus), даты анонса/старта продаж, параметры экрана (при наличии);
   - не хранит данные локально, а вызывает backend-инструмент (например, `POST /devices/models`) и пишет в БД таблицу вроде `phone_models`;
   - пример структуры:
```json
{
  "brand": "Samsung",
  "model": "Galaxy S26",
  "variant": "Ultra",
  "announce_date": "2026-02-10",
  "release_date": "2026-03-01",
  "screen": {
    "size_inch": 6.8,
    "technology": "AMOLED",
    "refresh_rate_hz": 120
  }
}
```
2. **Генератор ключевых фраз под запчасти** (бекенд или отдельный агент):
   - на вход получает модель телефона (`phone_models`), на выход — набор фраз по шаблонам «дисплей/экран/тач/стекло <brand> <model> купить/замена/...».
   - пример результата:
```json
{
  "model_id": "uuid-or-internal-id",
  "brand": "Apple",
  "model": "iPhone 17",
  "phrases": [
    "дисплей iphone 17",
    "экран iphone 17 купить",
    "замена дисплея iphone 17",
    "модуль экрана iphone 17 оригинал"
  ]
}
```
   - фразы сохраняются в таблицу наподобие `keywords`, привязываются к модели телефона.
3. **Интеграция с официальным Wordstat API в Yandex Search API**:
   - внутренний модуль хранит API-ключ сервисного аккаунта и `folderId` только в окружении, принимает список фраз и регион;
   - отправляет ограниченные read-only запросы в Wordstat API и возвращает число поисковых запросов за последние 30 дней;
   - для воспроизводимых исторических shadow/backtest допускается месячная динамика через `/v2/wordstat/dynamics`; ответ сохраняется в content-addressed локальный кеш без API-ключа и `folderId`, а на дату решения видны только завершённые уже доступные периоды;
   - сигнал используется для сравнения интереса и динамики, но не переводится напрямую в продажи или количество закупки;
   - потенциально пересекающиеся фразы не суммируются; поисковый сигнал не меняет стадии ассортимента и сам по себе не переводит товар между режимами расчёта;
   - API Яндекс.Директа остаётся отдельным fallback-провайдером и не делит секреты с Wordstat API;
   - сохраняет результат в `demand_stats` (или аналог) с привязкой к фразе, дате, региону;
   - внешний мир (агенты/ядро pricing-service) дергает абстрактный метод вида `get_yandex_stats(phrases[], region) → [{phrase, impressions, clicks, date, ...}]`.

**Использование в pricing-service:**

- цепочка «пресс-релизы → модели → фразы → Wordstat API → спрос в БД» позволяет заранее видеть поисковый интерес к запчастям для новых моделей;
- данные из `phone_models`, `keywords`, `demand_stats` становятся признаками в стратегиях (например, приоритет закупки дисплеев для новых флагманов);
- расписание:
  - агент пресс-релизов — по cron/планировщику;
  - генератор фраз и запрос к Wordstat API — по появлению/изменению моделей или ограниченными батчами.

**Мониторинг новинок смартфонов (MVP отдельного модуля):**

- цель — хранить подтверждённые анонсы новых смартфонов в таблице `smartphone_releases` и давать сигнал аналитике/стратегиям;
- вход: один внешний новостной API (конфиг через `.env`: `SMARTPHONE_NEWS_API_BASE_URL`, `SMARTPHONE_NEWS_API_KEY`, `SMARTPHONE_NEWS_LANGUAGE`, `SMARTPHONE_NEWS_QUERY`, `SMARTPHONE_NEWS_DAYS_BACK`);
- обработка: фонова́я job по расписанию (`./.venv/bin/python -m tasks.update_smartphone_releases`) берёт свежие материалы, LLM-фильтром отделяет обзоры от анонсов, извлекает brand/model/announcement_date/status (`rumor/announced/released`);
- вывод: upsert в `smartphone_releases` с полями brand/model/full_name/announcement_date/release_status/source_name/source_url/summary/raw_payload, уникальные индексы по источнику и brand+model+дате;
- ограничения MVP: один источник, периодичность — раз в сутки или реже, пока без прямого влияния на расчёт цен (только «факт появления модели»).

## **5\. Функциональность сервиса**

### **5.1. Сопоставление номенклатуры (matching)**

**Задача:** понять, какой товар конкурента соответствует какой нашей позиции.

Подход:

1. **Правила (baseline):**

   * фильтрация по группе/подгруппе (`URTOV1…URTOV7`);

   * бренд/модель (из свойств 1С);

   * тип товара (дисплей, аккумулятор, шлейф, стекло и т.п.);

   * ключевые слова и артикулы в названии.

2. **Дополнение через OpenAI:**

   * ИИ получает пары «наш товар — товар конкурента» с описаниями;

   * даёт:

     * совпадает или нет;

     * степень уверенности;

     * при необходимости — короткое пояснение (для логов).

3. **Результат:**

   * таблица сопоставлений:

     * наш `KODTOV`;

     * конкурент;

     * ID и название товара конкурента;

     * уровень уверенности;

     * признаки совпадения.

4. **Формируем 3 списка:**

   * **Совпадения** — товары с найденными матчами;

   * **Есть у конкурентов, нет у нас** — для анализа матрицы;

   * **Есть у нас, нет у конкурентов** — база для эксклюзивов.

В интерфейсе (web или Excel/таблица):

* просмотр и ручная корректировка сопоставлений:

  * подтверждать, отклонять, привязывать вручную.

### **5.2. Классификация товаров для ценообразования**

Каждой позиции присваиваем набор признаков:

* Группа/подгруппа: дисплеи, аккумуляторы, шлейфы, стёкла и т.п.

* Бренд/модель: Apple iPhone 11, Samsung Galaxy и т.д.

* Статусы из 1С:

  * Новинка / Нет продаж;

  * Сверхнорматив / Супернеликвид;

  * класс ABC/XYZ.

* Наши спец-метки:

  * **Эксклюзив** (есть у нас, нет ни у одного конкурента);

  * **Флагман** (по конкурентам продажи высокие, по нам слабые);

  * **Дорогой товар** (цена \> заданного порога, например 15–20 тыс.);

  * **Дефицитный** (остаток ниже нормы при хороших средних продажах).

* Дополнительно (при наличии):

  * высокий процент брака (может влиять на минимальную маржу).

Эти признаки используются в стратегиях ценообразования и фильтрах.

---

### **5.3. Конструктор стратегий цен**

**Цель:** дать возможность задавать правила вида «Если… то…» без доработки кода.

Примеры условий (Если):

* группа \= Дисплеи;

* бренд \= Apple;

* класс ABC \= A;

* статус товара ≠ Новинка;

* статус запаса ≠ Сверхнорматив/Супернеликвид;

* не эксклюзив;

* цена \> X руб.;

* дефицит \= нет.

Примеры действий (То):

* ориентироваться на:

  * минимальную/среднюю цену среди выбранных конкурентов,

  * либо цену одного конкретного конкурента;

* задать ограничение по марже:

  * не ниже закупки \+ N%;

  * не выше рынка \+ M%;

* выбрать режим:

  * «Применить автоматически»;

  * «Отправить на ручное утверждение».

Типовые стратегии:

1. **Дисплеи (основные модели)**  
    Держать цену на уровне минимальной цены среди ключевых конкурентов \+ ограничение по минимальной марже.

2. **Аккумуляторы премиум**  
    Привязка к конкретному конкуренту (лидеру по этой группе).

3. **Стёкла / распродажа неликвидов**  
    Для сверхнормативов и супернеликвидов — ступенчатое снижение:

   * 3 шт: −X%;

   * 5 шт: −Y%;

   * 10 шт: −Z%, и т.д.

4. **Эксклюзивы**  
    Повышенная маржа; ежедневная проверка появления конкурентов; при появлении конкурента — уведомление.

5. **Новинки**  
    Повышенная маржа; всегда ручное утверждение.

6. **Дорогие товары**  
    Всегда ручное утверждение, даже если стратегия рассчитала цену.

7. **Дефицитные**  
    Не понижаем цену, возможна небольшая надбавка.

В будущем конструктор можно сделать с UI: выпадающие списки, чекбоксы, а на старте — конфиг/таблица с правилами.

---

### **5.4. Учёт курсов валют**

* В настройках задаётся:

  * способ получения курса (ручной / API),

  * порог изменения (например, 1% за день).

* Если курс изменился больше порога:

  * сервис пересчитывает группу цен по заданной формуле (курс \+ коэффициент логистики/комиссии);

  * формируется отдельный отчёт и Telegram-уведомление.

---

### **5.5. Расчёт и выдача цен**

Процесс:

1. По расписанию (ежедневно/еженедельно) сервис:

   * обновляет данные из 1С и парсера;

   * пересчитывает признаки (ABC/XYZ, статусы, флагманы, эксклюзивы и т.д.);

   * применяет стратегии и считает рекомендуемые цены по пилотному набору.

2. Результат:

* таблица:

  * `KODTOV`;

  * старая цена;

  * рекомендуемая цена;

  * цены конкурентов (мин/сред/макс или по ключевым);

  * закупочная/себестоимость;

  * маржа до/после;

  * стратегия;

  * режим: авто/ручное.

3. Экспорт в 1С:

* сервис формирует файл (CSV/Excel или другой согласованный формат), содержащий:

  * `KODTOV`;

  * тип цены;

  * новая цена;

  * комментарий/стратегия.

* Обработка в 1С (МегаПрайс или отдельная) читает файл и создаёт документ «Установка цен номенклатуры».

4. Позиции с ручным режимом:

* попадают в отдельный список (web-интерфейс \+ выгрузка);

* на них приходят уведомления в Telegram.

---

### **5.6. Отчёты**

MVP:

1. **Сводка по пилоту**:

   * число позиций в пилоте;

   * сколько сопоставлено с конкурентами;

   * сколько эксклюзивов;

   * сколько рекомендуемых изменений;

   * оценка эффекта по марже (грубо).

2. **Флагманы и проблемные позиции**:

   * где конкуренты продают хорошо, а мы — мало/дороже.

3. **Эксклюзивы и новинки**:

   * список наших эксклюзивов;

   * список новинок.

4. **Неликвиды и сверхнормативы**:

   * с рекомендованными скидками.

5. **Журнал изменений цен**:

   * дата/время;

   * пользователь (если было ручное утверждение);

   * стратегия;

   * старая/новая цена.

## **6\. Уведомления и Telegram-бот**

### **6.1. Общая идея**

Создаётся **внутренний Telegram-бот сервиса ценообразования**.  
 Он:

* рассылает уведомления (комдир, закупка, владельцу, IT);

* показывает короткие сводки и даёт ссылки/ID на списки в сервисе;

* в будущем может принимать действия (утверждение цен).

### **6.2. Базовые команды бота**

Общие:

* `/start` — привязка пользователя и выбор роли (коммерческий, закупка, владелец, IT).

* `/help` — список команд и пояснения.

* `/today` — сводка за сегодня:

  * пересчитанные позиции,

  * сколько авто, сколько вручную,

  * кнопки на ключевые списки.

* `/week` — краткий отчёт за неделю.

Для **коммерческого директора**:

* `/approve` — «Требуют утверждения»:

  * список групп/товаров, где режим «ручное утверждение»;

  * кнопки:

    * `✅ Одобрить группу`,

    * `❌ Отклонить`,

    * `👀 Открыть список`.

* `/strategies` — список активных стратегий (читаемый текст, позже — ссылка в web).

* `/alerts` — основные сигналы (флагманы, странные цены, отрицательная маржа).

Для **закупки**:

* `/flags` — флагманы рынка:

  * товары с высокими продажами у конкурентов и слабой динамикой у нас.

* `/exclusives` — эксклюзивы и новинки:

  * эксклюзивы (есть у нас, нет у конкурентов);

  * новинки (по статусу 1С).

* `/stock` — дефицит / неликвид:

  * дефицитные и сверхнормативные позиции.

Для **владельца/финдира**:

* `/owner` — “дашборд владельца”:

  * маржа до/после (грубо, по пилоту),

  * количество проблемных позиций,

  * количество эксклюзивов/флагманов в работе.

Для **IT**:

* `/status` — статус сервиса:

  * дата последнего расчёта;

  * состояние выгрузок.

* `/errors` — ошибки за последние 24 часа.

### **6.3. Типы уведомлений**

Бот отправляет:

1. **Ежедневный/еженедельный дайджест** (комдир, закупка, при необходимости владелец):

   * общая статистика изменений;

   * кнопки:

     * `📌 Цены к утверждению`,

     * `🏆 Флагманы`,

     * `⭐ Эксклюзивы`,

     * `📦 Неликвид`,

     * `💱 Курс и пересчёты`.

2. **Эксклюзивы:**

   * появление конкурента по ранее эксклюзивной позиции:

     * «⚠️ Наш эксклюзив больше не эксклюзив. Товар…, конкурент…, цена…».

   * новые эксклюзивы (раз в день/неделю списком).

3. **Флагманы и проблемы с ценой:**

   * товары, где у конкурентов явный хит, а мы дороже/не продаём.

4. **Дефицит / сверхнорматив:**

   * ключевые сигналы по дефициту и крупным неликвидам, где сервис предложил изменения.

5. **Курс валют:**

   * сообщение при сильном изменении курса и массовом пересчёте цен.

6. **Технические сбои (для IT):**

   * отсутсвие файлов,

   * сбой парсера,

   * ошибки OpenAI и т.п.

Инлайн-кнопки в уведомлениях **пока могут быть только “навигаторами”** (ведут к спискам / web), в следующих версиях — подтверждение/отклонение цен прямо из Telegram.

## **7\. Использование OpenAI**

Проект изначально **рассчитывает на активное использование OpenAI**:

* для сопоставления товаров с конкурентами;

* для более “умного” поиска по названиям (рус/англ, сокращения, разные форматы);

* в будущем — для объяснений решений и диалогового интерфейса («чат с роботом по ценам»).

Технически:

* весь трафик к OpenAI идёт через backend сервиса;

* сохраняются только те данные, которые нужны для работы;

* при необходимости поставщик ИИ может быть заменён.

## **8\. Нефункциональные требования**

* **Производительность**:

  * пилот: 1000 позиций × 4–5 конкурентов — расчёт в пределах минут;

  * масштабирование до десятков тысяч позиций.

* **Надёжность**:

  * устойчивость к отсутствующим или повреждённым файлам;

  * логирование всех этапов.

* **Парсинг конкурентов и Proxy API**:

  * режим prod — обязательное использование Proxy API / HTTP-прокси для встроенного парсера; в dev допускается прямое подключение;

  * ограничения по запросам: соблюдаем лимиты RPS/тайм-ауты при обходе сайтов конкурентов;

  * при недоступности Proxy API или блокировках — логирование и алерты, сервис не падает фатально.

* **Прозрачность**:

  * для каждой цены должна быть видна:

    * закупка/себестоимость;

    * цены конкурентов;

    * стратегия;

    * ограничения по марже.

## **9\. Открытые вопросы**

1. Окончательно выбрать типы цен (из 1С) для:

   * закупочной базы,

   * базовой розничной.

2. Формат файлов конкурентов (CSV/Excel, поля, кодировки) и требования к парсеру.

3. Пороги:

   * для «дорогих» товаров,

   * для дефицита/сверхнорматива,

   * для минимальной маржи.

4. Стандартные периоды анализа продаж (30/60/90 дней).

5. Формат файла для 1С (CSV/Excel/DBF) для интеграции с МегаПрайсом.

6. Детали по учёту процента брака (источник, период, влияние на стратегию).
