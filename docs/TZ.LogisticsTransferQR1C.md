# Дополнение К Заявке 1С №21202: QR-Коды Для Логистики

Статус: `superseded` для текущего пилота с 2026-08-28. Документ сохранен как
проект следующего этапа и не является основанием менять или перепечатывать
действующие формы 1С без отдельного решения.

## 1. Цель

Уточнить уже заведенную заявку 1С №21202
`Доработка ПФ Перемещение и РТУ (QR-коды) УТ 10.3`.

Будущая доработка после отдельного возобновления должна добавить корпоративные
QR-коды на печатные формы документов 1С:

- `Документ.ПеремещениеТоваров`;
- `Документ.РеализацияТоваровУслуг` (`РТУ`).

В текущем пилоте сотрудники сканируют уже напечатанный QR/штрихкод документа во
встроенном приложении Bitrix24; Telegram и web fallback остаются резервом той же
state machine. Существующие формы перепечатывать не требуется.

Если этот следующий этап будет возобновлен, новый QR нужен только для внешнего
логистического сервиса. 1С остается системой учета, Bitrix24 — основным UX,
Telegram и web fallback — резервными интерфейсами, backend хранит внутреннее
логистическое состояние.

## 2. Где Добавить

Печатная форма перемещения:

- объект: `Документ.ПеремещениеТоваров`;
- макет: `Накладная`;
- файл в выгрузке конфигурации:
  `Документ.ПеремещениеТоваров.Макет.Накладная.Макет.mxl`;
- функция печати:
  `Документ.ПеремещениеТоваров.МодульОбъекта.txt`,
  `ПечатьПеремещениеТоваров()`.

Печатная форма РТУ:

- объект: `Документ.РеализацияТоваровУслуг`;
- печатная форма расходной накладной / РТУ;
- точный макет и функцию печати нужно подтвердить в конфигурации перед
  разработкой.

По исходной заявке нужно вывести по два QR на каждой форме:

- один QR в левом верхнем углу;
- второй QR в правом верхнем углу.

QR должны быть компактными, быстро сканироваться и не перекрывать реквизиты
формы. Если текущий линейный штрихкод действительно заменяется QR по заявке
№21202, перед заменой нужно подтвердить, что старый штрихкод не нужен другим
складским сценариям. Если есть риск, безопаснее оставить старый штрихкод и
добавить QR рядом.

## 3. Формат QR Для Перемещения

Зарезервированный формат следующего этапа:

```text
MMLOG1|transfer|<1c_document_ref>
```

Где:

- `MMLOG1` - версия формата;
- `transfer` - тип документа-источника;
- `<1c_document_ref>` - стабильная ссылка 1С на документ
  `ПеремещениеТоваров`.

Предпочтительный вариант `<1c_document_ref>` - внутреннее значение ссылки
документа, соответствующее `_Document178._IDRRef`, в стабильном строковом виде,
который backend сможет получить из MSSQL sync.

Короткий номер с формы, например `34486`, использовать нельзя: он может быть
неуникален и может отличаться от полного номера документа в SQL.

Оба QR на форме перемещения должны содержать одинаковое значение.

## 4. Формат QR Для РТУ

Зарезервированный формат следующего этапа:

```text
MMLOG1|rtu|<1c_document_ref>
```

Где:

- `MMLOG1` - версия формата;
- `rtu` - тип документа-источника;
- `<1c_document_ref>` - стабильная ссылка 1С на документ
  `РеализацияТоваровУслуг`, соответствующая `_Document203._IDRRef`.

Оба QR на форме РТУ должны содержать одинаковое значение.

## 5. Будущий Fallback

Если технически сложно быстро вывести ссылку 1С в QR, допустим временный формат
для перемещения:

```text
MMLOG1|transfer-number|<full_document_number>|<document_date_yyyyMMdd>
```

Пример:

```text
MMLOG1|transfer-number|РБГУ0034486|20260428
```

Fallback можно использовать только после проверки уникальности пары:

- полный номер документа 1С;
- дата документа.

Значение вида `34486` без префикса и даты не подходит.

Для РТУ fallback:

```text
MMLOG1|rtu-number|<full_rtu_number>|<document_date_yyyyMMdd>
```

Fallback можно использовать только после проверки уникальности пары:

- полный номер документа 1С;
- дата документа.

## 6. Требования К Будущей Печатной Форме

- QR должен печататься на форме `Накладная на перемещение` и на форме РТУ.
- На каждой форме должно быть два одинаковых QR: слева сверху и справа сверху.
- Рядом с QR вывести короткую подпись:
  `Для логистики`.
- Под QR вывести человекочитаемую строку формата или последние значимые символы
  lookup-кода, чтобы можно было сверить печать глазами.
- QR разместить в свободной зоне шапки формы так, чтобы он не перекрывал
  реквизиты и таблицу товаров.
- Размер QR должен уверенно считываться обычным телефоном и ручным сканером с
  распечатки.
- QR payload не должен зависеть от канала: тот же код должен читаться в
  Bitrix24, Telegram, web fallback и ручным сканером в режиме клавиатуры.

## 7. Что Не Нужно Делать В 1С

- Не менять учет остатков.
- Не менять проведение документа.
- Не записывать логистическое состояние в 1С.
- Не интегрироваться напрямую с Telegram или backend из 1С в рамках этой задачи.
- Не зашивать в QR товары, склады, количество, водителя, статус или другие
  бизнес-данные: backend подтянет их из 1С по идентификатору документа.

## 8. Acceptance Criteria После Отдельного Возобновления

Будущая задача считается выполненной, если:

1. На печатной форме `ПеремещениеТоваров` есть два QR: слева сверху и справа
   сверху.
2. На печатной форме РТУ есть два QR: слева сверху и справа сверху.
3. QR перемещения возвращает строку вида `MMLOG1|transfer|...` или согласованный
   fallback `MMLOG1|transfer-number|...`.
4. QR РТУ возвращает строку вида `MMLOG1|rtu|...` или согласованный fallback
   `MMLOG1|rtu-number|...`.
5. Значение QR не пустое для проведенного документа.
6. Значение QR стабильно при повторной печати того же документа.
7. Значение QR однозначно сопоставляется с одним документом в backend sync.
8. QR читается с бумажной распечатки минимум на 3-5 тестовых документах каждого
   типа.
9. Одна и та же строка QR принимается Bitrix24, Telegram и web fallback без
   изменения формата.

## 9. Тестовые Кейсы

Проверить минимум для перемещения:

- документ с номером вида `РБГУ...`;
- документ, где на форме отображается короткий номер без префикса;
- документ со складом-получателем `Транзит  для Москвы`;
- документ, который проходит readiness gate логистики;
- повторную печать одного и того же документа.

Проверить минимум для РТУ:

- РТУ с номером вида `РБГУ...`;
- РТУ, связанная с заказом сайта;
- РТУ самовывоза;
- повторную печать одного и того же документа.

Для каждого кейса сохранить:

- номер документа на форме;
- значение, которое вернул сканер;
- подтверждение, что backend/sync находит ровно один документ.

## 10. Backend-Согласование

На стороне backend поле `lookup_code` уже существует как внутренний технический
идентификатор; legacy-поле `barcode` сохраняется для совместимости старых scan
endpoints. Пользовательский корпоративный lookup-код в текущем пилоте не
внедряется.

Backend должен распознавать префикс:

```text
MMLOG1|
```

и валидировать:

- тип источника;
- непустой идентификатор;
- уникальное сопоставление с одной логистической единицей.

Если QR не найден или найдено несколько документов, интерфейс должен показать
ошибку скана и не создавать логистическое событие.
