# Tech Design: Bitrix24 Expertise Smart Process MVP

Дата фиксации: `2026-04-03`

Статус: `working draft / MVP`

## 1. Цель

Спроектировать минимальный smart-process `Экспертиза` в `Bitrix24`, который:

- показывает очередь экспертиз;
- дает руководителям и owner'ам понятный статус кейса;
- усиливает контроль `ОКК` за временем проведения экспертиз и сроком принятия решения;
- автоматически информирует сотрудников подразделения-инициатора о результате и необходимости уведомить клиента;
- контролирует обязательный шаг `клиент оповещен`;
- максимально роботизирует сценарий, сводя ручное участие к подтверждению фактов;
- не дублирует логику `1С`;
- не становится источником истины по lifecycle кейса.

Главный принцип:

- `1С` = система учета документа;
- backend = источник истины по статусу, owner, SLA и history;
- `due_at` в карточке = дедлайн текущего этапа, а не общий срок по кейсу;
- `Bitrix24 smart process` = операционный обзор и координация.
- в `Wave 1` у кейса один `owner`; отдельную роль `ОКК` в карточке не вводим.

## 3. Роль smart-process

Smart-process `Экспертиза` нужен как внешний рабочий реестр.

Он должен решать такие задачи:

- показать все открытые экспертизы в одном месте;
- показывать текущий derived status из backend;
- показывать owner и дедлайн текущего этапа;
- показывать решение и факт уведомления клиента;
- давать руководителю очередь просроченных и спорных кейсов;
- запускать служебные задачи и напоминания без ручного движения карточки по стадиям;
- автоматически доводить результат экспертизы до подразделения-инициатора.

Он не должен:

- быть источником истины по статусам;
- хранить единственную версию данных кейса;
- напрямую определять бизнес-переходы вместо backend;
- заменять документ `Экспертиза` в `1С`.

## 4. Минимальная модель записи в Bitrix24

Одна запись smart-process = один `expertise_case`.

Даже если в документе `1С` несколько строк товара, для Wave 1 в `Bitrix24` это все равно одна карточка.

## 5. Поля smart-process MVP

Ниже рекомендуемый минимальный состав полей.

### 5.1. Идентификация

- `TITLE`
  - формат: `Экспертиза {номер} / {подразделение} / {клиент}`
- `UF_CRM_25_EXPERTISEREF`
  - технический `onec_expertise_ref`
  - в operator UI не используем как основной идентификатор
- `UF_CRM_25_EXPERTISENUMBER`
  - код / номер экспертизы из `1С` вида `РБ...` или `РБГУ...`
  - основной пользовательский идентификатор в списке и карточке
- `UF_CRM_25_SALENUMBER`
  - код реализации из `1С` вида `РБ...` или `РБГУ...`
- `UF_CRM_25_ORDERNUMBER`
  - код заказа покупателя из `1С`
- `UF_CRM_25_CASEID`
  - внутренний `expertise_case.id`

### 5.2. Связи

- `UF_CRM_25_SALEREF`
  - ссылка на исходную `Реализацию`
- `UF_CRM_25_ORDERREF`
  - ссылка на связанный `Заказ покупателя`

### 5.3. Бизнес-поля

- `UF_CRM_25_STORE`
  - подразделение / магазин
- `UF_CRM_25_CUSTOMER`
  - клиент / контрагент
- `UF_CRM_25_PHONE`
  - телефон клиента
- `UF_CRM_25_PROBLEM`
  - краткое описание проблемы
- `UF_CRM_25_DECISIONCODE`
  - `approved` / `rejected`
- `UF_CRM_25_DECISIONLABEL`
  - человекочитаемое значение из `1С`
- `UF_CRM_25_DECISIONCOMMENT`
  - комментарий решения

### 5.4. Управление процессом

- `UF_CRM_25_STATUS`
  - текущий derived status из backend
- `UF_CRM_25_OWNEREXT`
  - внешний id owner
- `UF_CRM_25_OWNERNAME`
  - имя owner для отображения
- `UF_CRM_25_DUEAT`
  - дедлайн текущего этапа:
    - доставка до `ОКК`,
    - работа `ОКК`,
    - уведомление клиента
- `UF_CRM_25_OVERDUE`
  - да / нет
- `UF_CRM_25_CLIENTNOTIFIED`
  - да / нет

### 5.5. Технические поля

- `UF_CRM_25_SYNCAT`
  - время последнего sync из backend
- `UF_CRM_25_SOURCE`
  - фиксированное значение `pricing-service`

## 6. Стадии smart-process

Для MVP рекомендую не изобретать отдельную сложную воронку в `Bitrix24`, а отразить воронкой те же статусы, что уже считаются в backend.

Базовые стадии:

- `CREATED`
- `RECEIVED_BY_OKK`
- `UNDER_REVIEW`
- `DECISION_READY`
- `CLIENT_NOTIFIED`
- `RETURNED_TO_STORE`
- `MANUAL_REVIEW`

Рекомендация для Wave 1:

- считать stage в `Bitrix24` отражением backend status;
- не позволять людям свободно двигать запись по стадиям вручную;
- ручные действия делать через backend / API / будущий Telegram UX.
- отдельную стадию `В пути в ОКК` не вводить; до нормативного поступления кейс остается в `Создано`.

## 7. Mapping backend -> Bitrix24

Минимальный mapping:

- `expertise_case.id` -> `UF_CRM_25_CASEID`
- `onec_expertise_ref` -> `UF_CRM_25_EXPERTISEREF`
- `onec_expertise_number` -> `UF_CRM_25_EXPERTISENUMBER`
- `linked_sale_number` -> `UF_CRM_25_SALENUMBER`
- `store_name` -> `UF_CRM_25_STORE`
- `customer_name` -> `UF_CRM_25_CUSTOMER`
- `customer_phone` -> `UF_CRM_25_PHONE`
- `problem_summary` -> `UF_CRM_25_PROBLEM`
- `current_status` -> `UF_CRM_25_STATUS`
- `decision_code` -> `UF_CRM_25_DECISIONCODE`
- `decision_label` -> `UF_CRM_25_DECISIONLABEL`
- `decision_comment` -> `UF_CRM_25_DECISIONCOMMENT`
- `client_notified` -> `UF_CRM_25_CLIENTNOTIFIED`
- `due_at` -> `UF_CRM_25_DUEAT`
- `overdue` (derived) -> `UF_CRM_25_OVERDUE`
- `owner_user_external_id` -> `UF_CRM_25_OWNEREXT`
- `linked_sale_ref` -> `UF_CRM_25_SALEREF`
- `linked_customer_order_ref` -> `UF_CRM_25_ORDERREF`
- `linked_customer_order_number` -> `UF_CRM_25_ORDERNUMBER`
- `updated_at` / sync timestamp -> `UF_CRM_25_SYNCAT`

Практическое уточнение по `Wave 1`:

- в backend как отдельные top-level поля живут `organization_ref`, `contract_ref`, `linked_sale_ref`;
- в минимальный `Bitrix24` mapping обязательно тащим `linked_sale_ref`;
- `organization_ref` и `contract_ref` можно оставить в backend/payload и не делать обязательными полями карточки `Wave 1`, если не нужен отдельный операторский UX по ним.

Техническое правило для ссылочных полей `1С`:

- в карточку `Bitrix24` передаем строковые `hex`-значения `0x...`, а не `raw binary`;
- `GUID-like` преобразование для `Wave 1` не используем.

## 8. Правила синхронизации

Рекомендуемый режим:

- backend создает запись smart-process при первом появлении кейса;
- backend обновляет запись при каждом значимом sync или action;
- отдельный внешний ручной слой для создания карточек в `Bitrix24` не нужен;
- если потребуется техническое разделение, Bitrix-вызовы оформляются как интеграционный адаптер внутри backend-контура;
- `Bitrix24` не меняет status обратно в backend напрямую;
- человек в `Bitrix24` видит статус, но не является владельцем status machine.

Операционный фильтр `Wave 1`:

- в `Bitrix24` синхронизируем не всю историю экспертиз из `1С`, а только кейсы `в работе`;
- исторические документы нужны backend для учета и сверки, но не должны засорять операторскую очередь в smart-process;
- практическое правило для `Wave 1`:
  - если `current_status != created`, кейс считаем операционным и показываем в `Bitrix24`;
  - если кейс еще в `created`, но в `payload.posted = false`, кейс считаем операционным и показываем в `Bitrix24`;
  - если `posted` недоступен, используем fallback: кейс без `decision_label` считаем потенциально активным;
- документы с `posted = true` и без движения по backend-статусам считаем историческими и в smart-process не тащим.

Что считаем источником истины:

- статус -> backend
- owner -> backend
- дедлайн текущего этапа -> backend
- факт уведомления клиента -> backend
- документные данные `1С` -> read-only sync через backend
- бинарные вложения кейса -> связанная папка `Bitrix Disk`

Ролевая модель `Wave 1`:

- у кейса один `owner`, который отображается в backend и `Bitrix24`;
- `ОКК` в первой волне трактуется как функциональный этап процесса, а не как отдельная роль данных;
- контроль работы `ОКК` обеспечивается статусами `received_by_okk` / `under_review` / `decision_ready`, SLA и эскалациями.
- `received_by_okk` может наступать автоматически по нормативу доставки без ручного перетаскивания карточки человеком.
- для notify-task используется отдельная операционная модель:
  - постановщик задачи — система / технический пользователь;
  - основной исполнитель — руководитель подразделения-инициатора в `Bitrix24`;
  - соисполнители — остальные активные сотрудники подразделения-инициатора;
  - fallback-исполнитель — стабильный координатор `ОКК`, если у подразделения не назначен руководитель.

Практика по вложениям для Wave 1:

- backend создает карточку smart-process и связанную папку `Disk` на кейс;
- карточка smart-process хранит ссылку на папку, derived state и обзорные поля;
- основные фото, видео и сканы загружаются в папку `Disk`;
- backend хранит только `storage_ref` / `folder_id` / метаданные файлов, но не собственные копии бинарей.

## 9. Задачи и роботы

Для Wave 1 рекомендую не делать тяжелую роботизацию.

Минимум:

- создавать задачу на кейсы, где нужен action `уведомить клиента`, автоматически на всех сотрудников подразделения-инициатора;
- постановщиком задачи делать систему / технического пользователя;
- основным исполнителем делать руководителя подразделения-инициатора;
- fallback-исполнителем делать координатора `ОКК`, если у подразделения не назначен руководитель;
- запускать отдельный будильник по времени нахождения экспертизы в `ОКК` и по времени после фиксации решения;
- доставку будильников ответа `ОКК` делать из backend личными Bitrix-уведомлениями по лестнице:
  - `moscow`: `2` дня -> менеджер `ОКК`, `4` дня -> Омар / Арсен / Максим, `12` дней -> Эльдар;
  - `spb` / `other`: `13` дней -> менеджер `ОКК`, `15` дней -> Омар / Арсен / Максим, `23` дня -> Эльдар;
  - каждый уровень повторяется ежедневно, пока нет решения;
- reminder/escalation после фиксации решения отправлять координатору `ОКК` и наблюдателям, плюс комментарием в notify-task, если задача уже существует;
- можно подсвечивать просрочку через поле `UF_CRM_25_OVERDUE`;
- можно писать timeline/comment при изменении ключевых статусов;
- автоматически эскалировать кейсы, где решение принято, а `клиент оповещен` долго не подтвержден.

Не делать в Wave 1:

- сложные Bitrix robots по всем стадиям;
- бизнес-логику переходов внутри Bitrix;
- двусторонний sync status из Bitrix в backend.
- автоматическую `SMS` клиенту через `Bitrix24` как основной канал уведомления.

## 10. Что не входит в MVP

- отдельные Bitrix-формы под вложения;
- сложные dashboards внутри Bitrix;
- права по ролям и оргструктуре на уровне каждого поля;
- отдельные автоматические сценарии по `closed_approved` / `closed_rejected`;
- ручное редактирование полей, которые должны приходить из backend.

## 10.1. Операторский вид карточки

В общем виде карточки оставляем только поля, нужные для ежедневной работы:

- раздел `Основное`:
  - `STAGE_ID`
  - `TITLE`
  - `ASSIGNED_BY_ID`
- раздел `Коды 1С`:
  - `UF_CRM_25_EXPERTISENUMBER`
  - `UF_CRM_25_SALENUMBER`
  - `UF_CRM_25_ORDERNUMBER`
- раздел `Клиент и подразделение`:
  - `UF_CRM_25_STORE`
  - `UF_CRM_25_CUSTOMER`
  - `UF_CRM_25_PHONE`
  - `UF_CRM_25_PROBLEM`
- раздел `Решение и контроль`:
  - `UF_CRM_25_DECISIONLABEL`
  - `UF_CRM_25_DECISIONCOMMENT`
  - `UF_CRM_25_CLIENTNOTIFIED`
  - `UF_CRM_25_DUEAT`
  - `UF_CRM_25_OVERDUE`
- раздел `Материалы`:
  - `UF_CRM_25_FOLDERURL`

Технические поля разрешено хранить в smart-process для интеграции, но их не нужно показывать в общем операторском layout:

- `UF_CRM_25_EXPERTISEREF`
- `UF_CRM_25_CASEID`
- `UF_CRM_25_SALEREF`
- `UF_CRM_25_ORDERREF`
- `UF_CRM_25_ORGANIZATIONREF`
- `UF_CRM_25_CONTRACTREF`
- `UF_CRM_25_STATUS`
- `UF_CRM_25_OWNEREXT`
- `UF_CRM_25_OWNERNAME`
- `UF_CRM_25_SYNCAT`
- `UF_CRM_25_SOURCE`

Причина:

- эти поля нужны для idempotent sync, reconciliation и трассировки интеграции;
- оператору магазина и координатору `ОКК` они не помогают принять решение по кейсу;
- длинные `0x...` значения считаем чисто техническими и скрываем из обычной карточки.

Типы данных для UX `Wave 1`:

- `store`, `customer`, `phone`, `decision_label` — короткие строковые поля;
- `problem`, `decision_comment` — многострочный текст;
- `client_notified`, `overdue` — булевы поля;
- `due_at`, `sync_at` — дата/время;
- `folder_url` — ссылка;
- ссылочные `1С ref`-поля — строковые технические поля, скрытые из common view.

## 11. Практическая рекомендация

Для запуска Wave 1 достаточно:

- завести smart-process `Экспертиза`;
- создать минимальные поля из этого документа;
- привязать stage к backend status;
- завести связанную папку `Bitrix Disk` как каноническое место вложений по кейсу;
- использовать одну корневую папку `Экспертиза` как прямого родителя для кейсовых папок;
- при необходимости допускается перемещать саму папку `Экспертиза` под родительскую папку уровня отдела, например `Отдел контроля качества`, так как интеграция опирается на `folder_id`, а не на текстовый путь;
- дополнительную вложенность внутри `Экспертиза` по месяцам, статусам или подразделениям в `Wave 1` не вводить, потому что backend создает и ищет кейсовые папки как прямых дочерних потомков `root_folder_id`;
- писать туда только derived state и обзорные поля;
- не пытаться делать в `Bitrix24` вторую систему workflow.

## 12. Зафиксированные решения Wave 1

Перед реальной настройкой в `Bitrix24` для `Wave 1` фиксируем:

- в пользовательском UI `Bitrix24` стадии `received_by_okk` и `under_review` отображаются как одна стадия `В работе ОКК`, хотя в backend остаются раздельными для history и SLA;
- финальный набор стадий `Wave 1` разделяем на два исхода:
  - `returned_to_central_defect` -> `Возврат оформлен в центральный брак`
  - `returned_to_store` -> `Возвращено в подразделение`
- `_Fld9910` в backend и `Bitrix24` не тащим даже в сырой `payload`, так как сейчас он выглядит техническим blob без операционной ценности;
- пользовательски обязательных полей в карточке `Bitrix24` не делаем;
- все поля, приходящие из backend sync, считаем display/read-only полями;
- если в `Bitrix24` технически требуется обязательность при создании карточки, ее обеспечивает backend на своей стороне, а не ручной ввод пользователя;
- stage-specific required fields в `Bitrix24` для `Wave 1` не включаем;
- ручное подтверждение по стадии допускаем только как будущую опцию для `client_notified`, но не как обязательность UI в первой волне;
- в smart-process показываем только операционные экспертизы, а не весь исторический архив из `1С`;
- технические `1С ref` и служебные поля остаются в данных интеграции, но скрываются из общего вида карточки.
