# Tech Design: Expertise Case MVP

Дата фиксации: `2026-04-02`

Статус: `working draft / implementation context`

## 1. Цель

Собрать минимальный внешний контур для кейсов экспертизы, не дорабатывая глубоко старую `1С УТ 10.3`.

MVP должен закрыть:

- единый реестр экспертиз;
- owner и SLA по каждой экспертизе;
- понятные статусы кейса;
- хранение номера экспертизы, подразделения, клиента и телефона;
- подтверждение этапов движения через `ОКК`;
- постановку производной задачи только там, где реально нужно действие;
- audit trail и основу для дальнейшего сканирования/штрих-кодов.

Архитектура MVP должна без переделки поддержать следующий слой роботизации:

- контроль времени нахождения экспертизы в `ОКК` и времени до принятия решения через будильники и эскалации;
- автоматическое информирование сотрудников подразделения, из которого оформлена экспертиза, о результате и необходимости уведомить клиента;
- обязательный контроль шага `клиент оповещен` до фактического завершения кейса;
- сведение ручного участия в smart-process к подтверждению фактов, а не к ручному ведению workflow.

## 3. Базовое решение

Экспертиза в MVP моделируется как:

- отдельный `expertise_case` во внешнем backend-контуре;
- отдельная карточка в `Bitrix24 smart process`;
- опционально связанная задача только на действие `уведомить клиента`;
- read-only связка с документом `1С`.

Экспертиза не моделируется как:

- просто обычная задача `Bitrix24`;
- только запись в журнале `1С`;
- только бумажный бланк.

## 4. Границы ответственности

### 4.1. `1С` остается источником истины для

- документа `Экспертиза`;
- номера экспертизы;
- даты документа;
- организации;
- подразделения;
- контрагента;
- ответственного;
- договора контрагента;
- табличной части `Товары`;
- комментария менеджера;
- комментария отдела брака;
- причин `1..5`;
- учетных связей с возвратом, реализацией и другими документами;
- части результатов, если они уже живут в учетном контуре;
- печатного бланка, если он остается обязательным для операционной работы.

### 4.2. Внешний backend становится источником истины для

- текущего статуса кейса экспертизы;
- owner и SLA;
- контроля времени нахождения кейса в `ОКК` и времени до принятия решения;
- истории этапов;
- отметки `клиент оповещен`;
- связки `экспертиза -> подразделение -> клиент -> телефон`;
- производных задач, будильников и эскалаций;
- идентификатора штрих-кода/QR для сканирования этапов.

### 4.3. `Bitrix24` используется как кейсовый и оркестрационный слой для

- smart-процесса `Экспертиза`;
- обзора очереди;
- контроля просрочек;
- производных задач;
- автоматических задач на уведомление клиента сотрудникам подразделения-инициатора;
- прозрачности для руководителей и подразделений.

### 4.4. `Telegram` в MVP

В первой волне Telegram не обязателен.

Но архитектура должна позволять позже без переделки добавить:

- сканирование штрих-кода;
- подтверждение приемки в `ОКК`;
- подтверждение возврата в подразделение;
- просмотр очереди экспертиз по пользователю.

## 5. Основные бизнес-правила MVP

- `1 документ экспертизы 1С = 1 expertise_case`.
- Даже если в документе несколько строк товара, в Wave 1 это все равно один кейс.
- Кейс должен иметь owner.
- `due_at` хранит дедлайн текущего этапа, а не один общий срок на весь кейс.
- Двухэтапный SLA считается в календарных днях:
  - доставка до `ОКК`: `moscow = 2`, `spb = 8`, `other = 8`;
  - ответ `ОКК`: `moscow = 3`, `spb = 14`, `other = 14`.
- Будильники ответа `ОКК` считаются от входа в фазу `received_by_okk` / `under_review` / `manual_review` и повторяются ежедневно:
  - `moscow`: `2` дня -> менеджер `ОКК`, `4` дня -> Омар / Арсен / Максим, `12` дней -> Эльдар;
  - `spb` / `other`: `13` дней -> менеджер `ОКК`, `15` дней -> Омар / Арсен / Максим, `23` дня -> Эльдар.
- После принятия решения должен существовать отдельный шаг `клиент оповещен`.
- После перехода в `decision_ready` автоматически создается задача на уведомление клиента всем сотрудникам подразделения, из которого оформлена экспертиза.
- До подтверждения `client_notified` кейс остается под явным контролем и может эскалироваться.
- Производная задача создается только на действие, а не заменяет сам кейс.
- Номер экспертизы подтягивается автоматически из `1С`, а не вводится вручную.
- Статусы кейса должны быть явными, а цвет в UI является только их отображением.
- Smart-process должен быть максимально роботизирован; ручные действия допустимы только как фиксация фактов `received`, `decision`, `client_notified`, `returned`.
- `осиДокументОснование` использовать как главный read-only link на исходную `Реализацию`.
- Телефон клиента в первой волне читать через контактную информацию контрагента, а не искать в шапке документа:
  - базовый технический кандидат хранения уже локализован до `_InfoRg6402`.
  - рабочее правило выбора уже выглядит так:
    - `Телефон контрагента`
    - затем `Рабочий`
    - затем `Доп. телефон для переноса`
  - если телефон в `1С` отсутствует, кейс не блокируется и номер дозаполняют вручную позже
- Паспортные данные не считать частью модели `expertise_case`;
  - в текущем процессе они фактически не заполняются;
  - для MVP не делать на них никакой зависимости даже в печатном контуре backend.

## 6. Предлагаемые статусы кейса

Минимальный набор статусов:

- `created`
  - кейс создан и находится в этапе доставки до `ОКК`
- `received_by_okk`
  - нормативный срок доставки истек и кейс автоматически считается поступившим в `ОКК`; в пользовательском UI `Bitrix24` показывается как стадия `В работе ОКК`
- `under_review`
  - экспертиза в работе; в пользовательском UI `Bitrix24` показывается как та же стадия `В работе ОКК`
- `decision_ready`
  - решение принято
- `client_notified`
  - клиент уведомлен
- `returned_to_central_defect`
  - по положительному решению оформлен возврат в центральный брак
- `returned_to_store`
  - по отказному решению товар/результат вернулся в подразделение

Дополнительный технический статус для обработки ошибок:

- `manual_review`

## 8. API MVP

### 8.1. Sync API

- `POST /api/expertise/sync/cases`
  - upsert кейсов из `1С`/внешнего адаптера

Минимальный read-only source payload должен собираться из:

- `_Document9868`
- `_Document9868_VT9886`
- контактной информации контрагента
- регистр паспортных данных не включать в MVP extraction contract:
  - по текущему процессу эти данные не заполняются;
  - для core-case sync и Wave 1 они не нужны

Важно для extraction contract:

- не путать `ПричинаВозврата` строки и `Причина1..5` документа;
- `ПричинаВозврата` уже локализована в `_Fld9912RRef`;
- UI-элемент `СписокПричин` пока не подтвержден как отдельное SQL-поле строки и выглядит действием формы поверх `Причина1..5`;
- `_Fld9909RRef` уже подтвержден как link на `_Document132`, но не на `ПричинаВозврата`;
- `_Document132` теперь можно трактовать как `Заказ покупателя`;
- из-за уже существующего проектного mapping `ВозвратТоваровОтПокупателя -> _Document109` связь экспертизы с возвратом и связь экспертизы с заказом нужно разводить как два разных учётных link'а;
- `_Fld9910` пока лучше трактовать как технический blob, а не как надежный источник для `СписокПричин`;
- по контактной информации уже есть рабочая гипотеза, подтвержденная SQL-выборками:
  - `_InfoRg6402._Fld6403_RTRef/_Fld6403_RRRef` = объект-владелец КИ;
  - для контрагентов используется `RTRef = 0x00000036`;
  - `_InfoRg6402._Fld6405_RRRef` = вид КИ из `_Reference25`;
  - `_InfoRg6402._Fld6406` = представление значения;
  - `_InfoRg6402._Fld6404RRef` = enum `_Enum376`, где `order 1` используется для телефонов, а `order 0` для адресов.

## 9. Smart-process MVP в Bitrix24

Smart-process `Экспертиза` должен содержать минимум:

- номер экспертизы;
- подразделение;
- клиент;
- телефон;
- краткое описание проблемы;
- текущий статус;
- дедлайн;
- ответственный;
- `клиент оповещен`;
- решение;
- ссылка на кейс/backend;
- ссылку на связанный документ/номер `1С`.

Роботы MVP:

- при создании кейса назначить owner;
- при входе кейса в `ОКК` запускать будильник по времени до начала и завершения рассмотрения;
- если статус не закрыт и дедлайн истекает, отправить напоминание;
- если кейс просрочен, эскалировать руководителю;
- при переходе в `decision_ready` создать задачу `уведомить клиента` всем сотрудникам подразделения-инициатора;
- если после решения клиент не оповещен в целевой срок, запускать повторный будильник и эскалацию;
- при установке `клиент оповещен = да` автоматически закрыть производную задачу или перевести ее в выполненную ветку.

## 10. Переиспользование текущего кода

Уже существующий логистический контур дает хороший шаблон:

- модели в [app/models/logistics.py](/opt/MM/pricing-service/app/models/logistics.py)
- state machine и append-only события в [app/services/logistics.py](/opt/MM/pricing-service/app/services/logistics.py)
- API-контур в [app/api/logistics.py](/opt/MM/pricing-service/app/api/logistics.py)
- Telegram-бот и сканирование в [app/telegram/logistics_bot.py](/opt/MM/pricing-service/app/telegram/logistics_bot.py)

Практический вывод:

- экспертизу лучше строить как соседний bounded context по тем же паттернам;
- не смешивать ее напрямую в таблицы логистики;
- но использовать ту же идею `case + state + events + action endpoints`.

При этом интеграционный слой `1С` для экспертизы должен быть отдельным и read-only:

- не использовать бизнес-логику формы как источник истины;
- использовать конфигуратор и MSSQL только для extraction contract;
- печатные формы и UI-специфику `1С` не переносить в backend, кроме нужных для кейса данных.

## 11. Wave 1

Первая волна должна быть максимально узкой.

### Входит в Wave 1

- backend-модель `expertise_case`;
- sync API;
- read API;
- action API без Telegram;
- подготовленный source contract `1С -> backend`;
- двухэтапный SLA доставки и ответа `ОКК`;
- простая история кейса;
- боевой sync в `Bitrix24 smart-process`;
- notify-task на уведомление клиента;
- backend-будильники и эскалации.

### Не входит в Wave 1

- полноценный Telegram UX;
- печать нового бланка;
- полноценное двустороннее обновление `1С`;
- сложная barcode-логика с физическими маршрутами;
- массовые отчеты по аналитике дефектов;
- глубокая автоматизация журнала экспертиз в `1С`.

## 12. Предлагаемая последовательность реализации

1. Зафиксировать контракты `expertise_case`.
2. Зафиксировать extraction contract из `_Document9868` и `_Document9868_VT9886`.
3. Добавить SQLAlchemy-модели и Alembic-миграцию.
4. Добавить Pydantic-схемы и FastAPI endpoints.
5. Добавить сервисный слой со статусами и событиями.
6. Написать тесты API и state transitions.
7. Подключить минимальный sync-адаптер.
8. Подготовить mapping под `Bitrix24 smart process`.

## 13. Зафиксированные решения

- документ `Экспертиза` создается в `1С` и остается там системой учета;
- backend в read-only режиме читает `1С`, собирает и обновляет `expertise_case`;
- в `Wave 1` основной источник `payload` экспертизы — прямой read-only sync из `1С MSSQL`;
- backend же создает и обновляет карточку smart-process в `Bitrix24`;
- отдельный внешний ручной слой для создания smart-process не требуется;
- если Bitrix-интеграцию понадобится структурно выделить, это делается как внутренний адаптер backend, а не как отдельная система процесса.
- текущий облачный чат `Bitrix24` `Экспертиза` (`dialog_id=chat70077`) подтверждает, что фото, видео и сопроводительные материалы по экспертизе уже живут в контуре `Bitrix24`;
- в `Wave 1` бинарные вложения нужно хранить в `Bitrix24`-контуре, а backend должен хранить только `storage_ref`, метаданные и ссылки, без сохранения бинарей у себя;
- каноническое место вложений `Wave 1` — связанная папка `Bitrix Disk` по кейсу;
- карточка smart-process хранит ссылку на папку `Disk`, обзорные поля, счетчики и при необходимости ссылки на 1-2 ключевых документа, но не выступает основным бинарным архивом.
- в `Wave 1` отдельную роль `ОКК` в модели кейса не вводим: достаточно одного `owner` по кейсу;
- контроль `ОКК` в первой волне реализуется через статусы, двухэтапный SLA, будильники и эскалации, а не через отдельную role-matrix.
- основной рабочий сценарий `created -> received_by_okk` в `Wave 1` происходит автоматически по нормативу доставки, а ручные actions `receive/start-review` остаются как совместимость и override.
- каноническое внешнее представление `Ref` и ссылок `1С` в `Wave 1` — строка `hex` вида `0x...`, как результат `master.dbo.fn_varbintohexstr(...)`;
- `raw binary` остается только во внутреннем SQL/extractor-слое, а `GUID-like` сериализацию в `Wave 1` не используем.
- в `Wave 1` как отдельные top-level поля кейса выносим `organization_ref`, `contract_ref` и `linked_sale_ref`;
- `return_reason_ref` и `decision_ref` в `Wave 1` остаются на уровне строки товара в `payload.items[]`, а не поднимаются в top-level кейса;
- внешний `decision_code` для `Wave 1` фиксируем так:
  - `Принято` -> `approved`;
  - `Отказано` -> `rejected`;
  - неизвестное или пустое значение -> `null`, при этом raw `decision_label` и `decision_ref` сохраняются.
