# TechDesign: Management Control Tower

Документ описывает расширение текущего сервиса до управленческого контура для ежедневных, еженедельных и ежемесячных отчётов, задач и AI-обработки встреч.

Статус: proposal.

Важно: это расширение выходит за рамки текущего PRD по ценообразованию. Его лучше проектировать как отдельный bounded context рядом с pricing, но на общей платформе FastAPI, очередей, Telegram и BI.

## 1. Цели

Новый контур должен закрывать 4 группы задач:

1. Периодические управленческие показатели для руководителей.
2. Автоматические задачи старшим по магазинам, HR и финансам.
3. Ежедневный и периодический контроль укомплектованности персонала.
4. Полноценный контур контроля дебиторской задолженности с поиском причин, ответственных и сценариев действий.

## 2. Принципы проектирования

1. Один источник правды по каждому домену:
   - продажи и взаиморасчёты: 1С;
   - график и штат: Bitrix24;
   - сотрудники и статус занятости: HR-справочник;
   - задачи: Bitrix24;
   - оперативные уведомления: Telegram.
2. Сначала собираем события и исторические снимки, потом строим отчёты.
3. Каждый показатель имеет владельца, период, SLA обновления и правило эскалации.
4. AI не подменяет учётную систему:
   - AI расшифровывает встречи, ищет причины, формирует draft-задачи;
   - итоговые статусы и долги считаются только на данных учётных систем.
5. Для критичных кейсов используем не только отчёт, но и обязательную задачу с дедлайном.

## 2.1. Фактическая инфраструктура на март 2026

По результатам проверки текущих серверов:

- сервер `A` содержит `pricing-service` и должен остаться расчётным контуром;
- сервер `B` уже содержит рабочий `Openclaw`-контур, интеграцию с `Bitrix24`, Telegram-доставку и пайплайн транскрибации звонков/встреч;
- на `B` уже есть role-based утренние отчёты и AI-обработка звонков, поэтому дублировать этот orchestration-контур на `A` не нужно.

Практический вывод:

- `A` отвечает за данные, витрины, расчёты, audit trail и API;
- `B` отвечает за транскрибацию, сбор управленческого контекста, финальную сборку сообщений, постановку задач в `Bitrix24` и доставку в Telegram.

Такой split является целевым для внедрения Management Control Tower.

## 3. Периоды и тайм-слоты

Рекомендуемые слоты доставки:

- `06:00` — ночной расчёт витрин и контроль полноты загрузки данных.
- `08:00` — утренний операционный отчёт для руководителей.
- `09:00` — персональные задачи старшим/HR/финансам.
- `12:00` — mid-day контроль отклонений.
- `18:00` — вечерний итог дня.
- `Понедельник 08:00` — недельный обзор.
- `1-й рабочий день месяца 09:00` — месячный обзор.
- `1-й рабочий день квартала 10:00` — квартальный стратегический обзор.

## 4. Показатели по периодам

### 4.1. Ежедневно

Для строки отчёта утром и вечером стоит показывать:

- выручка за вчера / с начала дня;
- валовая прибыль и валовая маржа;
- средний чек;
- количество чеков / заказов;
- продажи по магазинам и отклонение к плану;
- новые контрагенты с дебиторкой за вчера;
- общая дебиторка, просроченная дебиторка, доля просрочки;
- топ-10 новых проблемных долгов;
- укомплектованность по магазинам и сменам: план, факт, дефицит;
- невыходы, опоздания, незакрытые смены;
- открытые критичные задачи по магазину;
- товары/категории с аномалиями: возвраты, резкое падение продаж, подозрительные операции;
- статус интеграций: 1С, B24, Telegram, очереди, AI jobs.

### 4.2. Еженедельно

- выручка, маржа, средний чек в динамике по неделям;
- выполнение недельного плана по магазинам;
- динамика дебиторки: прирост, закрытие, просрочка, aged buckets;
- топ менеджеров по созданию и закрытию дебиторки;
- контрагенты, ушедшие в просрочку на неделе;
- укомплектованность по магазинам: средняя, минимальная, дни провала;
- текучесть, вакансии, время закрытия смен;
- качество выполнения задач руководителями;
- сводка по встречам: проблемы, решения, невыполненные договорённости.

### 4.3. Ежемесячно

- выручка, валовая прибыль, маржа по магазинам и компании;
- производительность на сотрудника;
- текучесть персонала, найм, увольнения, незакрытые вакансии;
- доля смен с некомплектом;
- дебиторка на конец месяца;
- оборачиваемость дебиторки и возраст долга;
- доля долга на уволенных менеджерах;
- доля внутренней дебиторки сотрудников;
- корректировки долга за месяц и причины;
- в управленческом ОПиУ положительные корректировки задолженности показываются как
  прочий доход, списания и отрицательные корректировки — как прочий расход;
- в финансовый результат попадают только события из отдельного классифицированного
  слоя `profit_loss_debt_adjustments`; сырые движения дебиторского регистра не
  используются, потому что могут дублировать продажи и не содержат утверждённой
  причины корректировки;
- публикация месяца фиксируется источником
  `finance.profit_loss_debt_adjustments`, чтобы отличать подтверждённый ноль от
  отсутствующего отчёта;
- итог после этого блока называется `Прибыль до налогообложения`; `Чистая прибыль`
  не рассчитывается до подключения налогов. Если месячный источник корректировок
  не опубликован, витрина показывает отсутствие источника, а не нулевую сумму;
- рекомендации по изменению клиентских типов цен по регламенту Master Mobile:
  кому поставить `3.Серебряный`, кому `4.Золотой`, кого понизить до `3.Серебряный` или `2.Бронзовый`;
- список системных проблем: процессы, магазины, менеджеры, контрагенты.

### 4.4. Ежеквартально

- тренд по укомплектованности и текучести;
- тренд по просроченной дебиторке;
- эффективность правил запрета продаж без оплаты;
- качество управленческой дисциплины по задачам;
- перечень процессов, которые надо изменить регламентом.

## 5. Что отправлять старшим по магазинам

### 5.1. Ежедневно в 08:00

- магазины/смены с некомплектом на сегодня;
- сотрудники с риском невыхода или отсутствующим подтверждением смены;
- вчерашние новые контрагенты с дебиторкой;
- вчерашние просрочки по действующим клиентам;
- список задач, срок которых истекает сегодня;
- отклонения по выручке к плану за вчера;
- замечания из вчерашней встречи, если по ним назначен старший магазина.

### 5.2. Ежедневно в 12:00

- незакрытые кадровые провалы на вторую половину дня;
- неразобранные новые долги;
- клиенты, которых нужно перевести на ограничение продаж без оплаты;
- задачи с высоким риском просрочки SLA.

### 5.3. Ежедневно в 18:00

- итог дня по магазину;
- что не решено и переносится на завтра;
- кто не закрыл назначенные задачи;
- какие инциденты требуют эскалации выше.

### 5.4. Еженедельно

- рейтинг магазинов по дисциплине задач;
- рейтинг магазинов по укомплектованности;
- рейтинг по приросту дебиторки;
- список повторяющихся причин проблем.

## 6. Контур укомплектованности персонала

### 6.1. Источники

- Bitrix24: график работы, сотрудники, подразделения, роли, задачи.
- HR-справочник: статус сотрудника, дата приёма, увольнения, руководитель.
- Опционально: факт выхода из СКУД, кассы или табеля.

### 6.2. Что считать ежедневно

- плановая численность на смену;
- фактическая назначенная численность;
- подтверждённые выходы;
- невыходы;
- дефицит по ролям: продавец, старший, мастер и т.д.;
- магазины с критическим некомплектом;
- прогноз дефицита на 3/7/14 дней.

### 6.3. Автоматические действия

- если на сегодня дефицит по смене:
  - задача Эльзе;
  - уведомление старшему магазина;
  - уведомление HR, если дефицит не закрыт до контрольного времени.
- если дефицит повторяется `N` дней:
  - эскалация на старшего по продажам;
  - включение в недельный отчёт.

### 6.4. Встречи и AI-обработка записи

Если предполагается сеть встреч/созвонов с записью, лучше строить отдельный поток:

1. запись встречи попадает в файловое хранилище;
2. job транскрибирует аудио;
3. LLM извлекает:
   - проблемы;
   - решения;
   - ответственных;
   - сроки;
   - признаки кадровых рисков;
4. backend создаёт draft-задачи в B24;
5. ответственный подтверждает или корректирует задачи;
6. невыполненные договорённости попадают в следующий утренний отчёт.

Минимальный набор сущностей:

- `meeting_record`;
- `meeting_transcript`;
- `meeting_action_item`;
- `staffing_issue`;
- `staffing_snapshot`.

## 7. Контур дебиторской задолженности

### 7.1. Базовое требование

Чтобы показатель дебиторки был содержательным, недостаточно текущего сальдо. Нужна ведомость взаиморасчётов за весь период и журнал событий:

- реализация;
- оплата;
- возврат;
- корректировка долга;
- взаимозачёт;
- смена ответственного менеджера;
- статус контрагента;
- статус сотрудника.

### 7.2. Что должен уметь движок дебиторки

1. Рассчитать текущее сальдо по контрагенту.
2. Найти точку появления долга:
   - первый документ, после которого баланс стал отрицательным/дебиторским;
   - цепочку документов, которые долг нарастили.
3. Назначить ответственного менеджера на момент возникновения долга.
4. Определить текущего владельца кейса:
   - действующий менеджер;
   - уволенный менеджер;
   - внутренний сотрудник;
   - общий финансовый пул на ручную разборку.

### 7.3. Обязательные сегменты

#### 5. Дебиторка: список контрагентов на корректировку долга

В отдельный список попадут контрагенты, где:

- долг тянется слишком долго;
- ответственный менеджер уволен;
- нет активности по клиенту;
- нет реалистичного сценария взыскания;
- были ручные корректировки, но причина не зафиксирована.

#### 5.a. Действующие менеджеры

Нужен список:

- менеджер;
- контрагент;
- сумма долга;
- возраст долга;
- ссылка на документ появления;
- ссылка на документы, увеличившие долг;
- задача ответственному в B24.

#### 5.b. Контрагенты, где должником является наш сотрудник

Нужны отдельные правила:

- связка с физлицом HR;
- отношение долга к месячной зарплате;
- классификация по риску;
- обязательное соглашение/график удержаний на юридических основаниях;
- задача HR и финансовому блоку.

#### 5.c. Остальные контрагенты

Деление:

- активные;
- малоактивные;
- неактивные.

Признаки сегментации:

- давность последней реализации;
- частота оплат;
- средний оборот;
- удалённость;
- формат расчётов;
- наличие подтверждённого контакта;
- статус взаимоотношений.

#### 5.d. Неактивные контрагенты

Отдельный список для Карины:

- сумма долга;
- возраст;
- последний документ;
- причина зависания;
- рекомендация: взыскание / корректировка / заморозка.

#### 5.e. Активные контрагенты

В карточке должны быть прописаны:

- правила оплаты;
- лимит отгрузки;
- допустимый уровень дебиторки;
- удалённость и логистика;
- персональный ответственный;
- меры ограничения: стоп-отгрузка, только предоплата и т.п.

#### 5.f. Малоактивные контрагенты

Для них нужны:

- сокращённые сроки урегулирования;
- жёсткие запреты на новые продажи без оплаты;
- персональный ответственный за доведение до правил.

### 7.4. Отдельный утренний список для HR и старшего по продажам

В ежедневный отчёт выносить:

- контрагентов, у которых новая дебиторка не закрыта более 3 полных дней;
- сумму;
- документ-источник;
- ответственного менеджера;
- срок первой реакции;
- факт создания задачи.

## 8. Предлагаемая архитектура

### 8.0. Разделение ответственности между серверами

#### Сервер A: pricing-service / system of record

На `A` должны жить:

- загрузка истории взаиморасчётов из 1С;
- загрузка HR-справочников и рабочих графиков, если нужна нормализация и хранение истории;
- расчёт витрин по дебиторке;
- расчёт витрин по укомплектованности;
- расчёт ежедневных / недельных / месячных KPI;
- хранение исторических snapshots и audit trail;
- приватные API для выдачи готовых управленческих данных.

#### Сервер B: Openclaw / orchestration layer

На `B` должны жить:

- транскрибация звонков и встреч;
- AI-извлечение action items и управленческих сигналов;
- интеграция с `Bitrix24` по задачам и чатам;
- role-based сборка итогового отчёта для конкретного руководителя;
- доставка в Telegram;
- создание задач и напоминаний.

Операционное уточнение для агентов: `B/Openclaw` — это отдельный удалённый сервер.
Его cron, логи, state и каталог `/home/deploy/.openclaw` проверяются по SSH-доступу,
настроенному во внешнем окружении. Отсутствие `/home/deploy/.openclaw` на машине с
рабочей копией `pricing-service` не означает, что delivery-контур не настроен.
Не нужно искать или создавать локальный Openclaw-каталог в этом репозитории; для
боевой проверки нужно идти на сервер `B` по SSH и уже там смотреть crontab, `.env`,
логи и state.

#### Сервер B: четыре независимых подконтура

На практике `B` уже нельзя считать одним монолитным `Bitrix24`-контуром.
Нужно поддерживать 4 независимые плоскости:

- `assistant_plane`
  - личный диалог ассистента в `Bitrix Box` через `bitrix-box-app`;
  - `role_assistant`, trusted prompt по `bitrix24_id`, memory triage;
- `reporting_plane`
  - scheduled KPI/digest-отчёты;
  - основной стабильный канал на текущем этапе: `Telegram`;
- `action_plane`
  - авто-постановка задач и короткие operational alerts;
  - текущий primary-контур в миграции: `Bitrix24 Cloud`;
- `source_plane`
  - чтение management API с `A`;
  - AI follow-up digest;
  - Cloud task/chat digests до полного перехода на `Box`.

Главное архитектурное правило:

- conversational assistant и scheduled management delivery не должны смешиваться в одном runtime path.
- `bitrix-box-app` обслуживает только `assistant_reply`.
- регулярные KPI в `Box`, если понадобятся, должны идти отдельным delivery-контуром, а не через тот же чат ассистента.

#### Сервер B: dual-Bitrix migration model

На `B` уже одновременно существуют:

- legacy `Bitrix24 Cloud` как текущий рабочий контур задач и task/chat sources для management;
- новый `Bitrix Box` как messenger assistant channel через `bitrix-box-app`.

Поэтому все B-side delivery decisions должны быть contour-aware:

- `cloud_primary`
- `box_shadow`
- `box_primary`
- `cloud_fallback`

Рекомендуемый маршрут миграции:

1. не трогать уже рабочий `Bitrix Box assistant plane`;
2. оставить KPI/digest-отчёты в `Telegram`;
3. сделать task/action processors contour-aware;
4. сначала переводить в `Box` только `task/action delivery`;
5. только после стабилизации task flow решать, нужен ли отдельный `bitrix_box_delivery` для регулярных KPI.

#### Почему не переносить расчёты на B

- на `B` уже сильный workflow-контур, но не system of record по финансам;
- дебиторка требует полной истории документов и воспроизводимого расчёта;
- staffing требует исторических snapshots и строгой логики дефицита;
- смешивание финансовых расчётов с AI/workflow-контуром усложнит отладку и проверяемость.

### 8.2.1. Identity model на сервере B

Для `Openclaw`-контура на `B` одного поля `bitrix24_id` уже недостаточно.
Целевая модель сотрудника должна поддерживать одновременно:

- `telegram_id`
- `bitrix_cloud_user_id`
- `bitrix_box_user_id`
- `bitrix_box_assistant_enabled`
- `allowed_delivery_channels`

Переходная совместимость:

- legacy `bitrix24_id` сохраняется временно;
- новые task/delivery processors должны сначала искать contour-specific id;
- если contour-specific id ещё не задан, допустим fallback на `bitrix24_id`.

### 8.2.2. Delivery intent model на сервере B

Для каждого сигнала/кейса/метрики на `B` должен быть отдельный `delivery_intent`:

- `assistant_reply`
- `digest`
- `alert`
- `task`

Это нужно, чтобы не смешивать:

- живой диалог ассистента в `Bitrix Box`;
- регулярные KPI-отчёты;
- короткие уведомления;
- Bitrix24-задачи.

### 8.3. Витрины и вычисления

Нужно считать не из live-запросов, а через витрины:

- `vw_staffing_daily`
- `vw_staffing_period_summary`
- `vw_receivables_current`
- `vw_receivables_aged`
- `vw_receivables_new_daily`
- `vw_manager_receivables`
- `vw_employee_receivables`
- `vw_management_morning_digest`

Эти витрины должны строиться на сервере `A`, а сервер `B` должен читать уже готовые результаты по API, а не считать их повторно у себя.

### 8.3.1. Рекомендуемые API между A и B

Сервер `A` публикует приватные endpoint'ы для сервера `B`:

- `GET /api/management/digests/morning?date=YYYY-MM-DD&role_code=...`
- `GET /api/staffing/daily?date=YYYY-MM-DD`
- `GET /api/staffing/period-summary?date_from=...&date_to=...`
- `GET /api/receivables/new-daily?date=YYYY-MM-DD`
- `GET /api/receivables/cases?segment=...`
- `GET /api/receivables/manager-summary?date=YYYY-MM-DD`
- `GET /api/receivables/employee-cases?date=YYYY-MM-DD`

Требования к обмену:

- доступ только по приватной сети;
- авторизация service-to-service токеном;
- формат `JSON`;
- идемпотентные запросы на чтение;
- тайм-ауты и ретраи на стороне `B`.

### 8.4. Фоновые задачи

На сервере `A`:

- `sync_b24_staff_schedule`
- `sync_hr_directory`
- `sync_receivable_ledger_from_1c`
- `build_staffing_snapshots`
- `build_receivable_cases`
- `build_management_kpi_snapshots`

Для sales KPI backend публикует базовую daily-витрину `vw_bi_sales_daily_kpi` с разрезами по `manager` и `store` на основе `receivable_ledger_event` (`event_type='sale'`); weekly/monthly срезы считаются поверх daily при доставке в чат и в BI. Read-only доступ наружу даётся через `/api/bi/sales-daily-kpi` и `/api/bi/sales-weekly-kpi`.

Для руководителя розничной сети backend дополнительно публикует read-only endpoint `/api/management/retail-customer-price-type-recommendations?month=YYYY-MM`. Он считает чистые продажи клиентов по `receivable_ledger_event` (`sale` минус `return`) и применяет регламент типов цен: `Бронза` ниже `300 000 ₽`, `Серебро` от `300 000 ₽`, `Золото` от `1 200 000 ₽`. По умолчанию в отчёт попадают только контрагенты из группы 1С `ПОКУПАТЕЛИ`; в Excel выводится реальный код 1С из `_Reference54._Code` (`РБ...`), а не технический reference. Текущий тип цен берётся не из наименования договора, а из реквизита договора `_Reference37._Fld513_RRRef -> _Reference87._Description` на вкладке договора. Для каждой строки также выводятся чистые продажи предыдущего месяца, изменение продаж в рублях, процент изменения и возвраты; предыдущий месяц backend берёт напрямую из 1С-регистра продаж/возвратов, если локальная витрина закрытого месяца не содержит этот период.

На сервере `B`:

- `transcribe_meetings`
- `extract_meeting_actions`
- `pull_management_data_from_A`
- `compose_role_based_management_reports`
- `create_b24_tasks_from_rules`
- `send_telegram_management_reports`
- `retail_price_type_recommendations_from_a.py` ежемесячно 1 числа забирает endpoint с сервера `A`, формирует Excel и отправляет Арсену через Telegram-ассистента. На `B` cron делает несколько идемпотентных попыток в течение 1-го числа, чтобы пережить позднюю готовность закрытого месяца на `A`.

## 9. Правила постановки задач

Задача создаётся автоматически, если выполнено правило:

- дебиторка появилась вчера;
- дебиторка перешла порог суммы;
- долг стал просроченным;
- ответственный уволен;
- контрагент неактивен и долг старше порога;
- на смену не хватает людей;
- решение с встречи не исполнено в срок.

У каждой задачи должны быть:

- источник;
- причина;
- сумма/метрика;
- владелец;
- срок реакции;
- срок закрытия;
- ссылка на документы;
- ссылка на расшифровку встречи, если есть.

## 10. Рекомендуемая очередность внедрения

### Этап 1. Данные и витрины

- загрузить историю взаиморасчётов;
- загрузить B24-график и оргструктуру;
- сделать исторические таблицы ответственности;
- собрать ежедневные витрины на сервере `A`;
- определить приватный канал доступа `B -> A`.

### Этап 2. Ежедневные отчёты

- API выдачи утреннего management payload на сервере `A`;
- adapter на сервере `B`, который забирает эти данные;
- утренний отчёт 08:00;
- список новых долгов за вчера;
- отчёт по укомплектованности;
- персональные задачи старшим и HR.

### Этап 3. Контур дебиторки

- поиск точки возникновения долга;
- сегментация активный / малоактивный / неактивный;
- кейсы по сотрудникам;
- кейсы на корректировку.

### Этап 4. AI по встречам

- транскрибация на сервере `B`;
- извлечение action items;
- авто-постановка задач;
- контроль исполнения.

## 11. Ключевые риски

- без полной истории взаиморасчётов AI не определит истинную причину долга;
- без истории ответственных менеджеров долг будет ошибочно назначаться текущему владельцу;
- без факта выхода персонала отчёт по укомплектованности будет только плановым;
- авто-постановка задач без правил дедупликации быстро создаст шум;
- юридический контур по долгам сотрудников требует отдельного согласования с HR и юристами.
- если считать одни и те же KPI и на `A`, и на `B`, появится конфликт версий и расхождение отчётов.

## 12. Практическая рекомендация после анализа A/B

Текущая инфраструктура уже подсказывает правильный путь внедрения:

1. не переносить `Openclaw`-сценарии на сервер `A`;
2. не переносить расчёты дебиторки и staffing на сервер `B`;
3. сделать `A` вычислительным backend с витринами и API;
4. сделать `B` слоем оркестрации, доставки и `Bitrix24`-автоматизации;
5. первым делом реализовать на `A` три прикладных endpoint'а:
   - новые дебиторки за вчера;
   - staffing на сегодня;
   - сводка дебиторки по менеджерам;
6. после этого подключить их в утренние отчёты `Openclaw` на `B`.

## 12. Практическая рекомендация

Для этого репозитория разумно идти так:

1. Не смешивать новый управленческий контур с pricing-логикой напрямую.
2. Добавить его как отдельный набор модулей и API, но на общей платформе.
3. Сначала реализовать дебиторку и staffing как два независимых потока данных.
4. AI-встречи подключать только после того, как готовы справочники сотрудников, магазинов и задач.
