# OnePage: шлюз и классификатор банковских платежей для 1С Клиент-Банк

Дата обновления: `2026-05-11`

Статус: draft one-pager после разбора старой загрузки `КлиентБанк1`.

## Зачем делаем

Сейчас загрузка выписки завязана на старую обработку `1С` `КлиентБанк1`.
Она читает файл, ищет справочники, создаёт документы, заполняет договоры,
записывает документы и показывает пользователю таблицу ошибок.

Проблема в двух местах:

- старая обработка понимает не все банки и не все варианты банковских файлов;
- правила по СБП/эквайрингу, внутренним переводам, возвратам банка и зарплатным
  реестрам приходится встраивать прямо в модуль загрузки.

Цель MVP: сделать `pricing-service` шлюзом подготовки выписок для старой 1С.
Для Сбера исходная загрузка по API уже живёт в `mm-compensation`: там
обновляются raw-таблицы `finance.raw_sber_*` и строится сверка Сбер/1С.
`pricing-service` не должен поднимать второй OAuth-контур Сбера, а должен
переиспользовать уже загруженные строки, классифицировать их и отдавать в 1С
подготовленный файл `1CClientBankExchange`. 1С при этом остаётся загрузчиком и
системой учёта.

## Главный принцип

- `1С` остаётся системой учёта и владельцем документов, справочников, проводок,
  номеров, прав и ручной проверки.
- `mm-compensation` остаётся владельцем уже подключенного Sber API: OAuth,
  refresh token, загрузка `client-info` и `statement/transactions`,
  raw-хранение и сверка с 1С.
- `pricing-service` становится шлюзом подготовки выписок для 1С: берёт уже
  нормализованные строки Сбера из `mm-compensation` или fallback-файл банка,
  классифицирует платежи и формирует файл для 1С.
- Обработка `КлиентБанк1` остаётся загрузчиком внутри 1С: читает
  `1CClientBankExchange`, ищет существующие документы и записывает результат в
  1С.
- Для 1С вход должен выглядеть как обычный файл клиент-банка, даже если исходный
  банк не поддерживается старой обработкой напрямую.
- Если сервис недоступен, для уже поддерживаемых банков остаётся текущая ручная
  загрузка файла в 1С; для новых банков выписка ждёт повторной нормализации в
  сервисе.

## Как будет работать

```text
Sber API
  -> mm-compensation: scripts/load_sber_api_raw_to_postgres.py
  -> finance.raw_sber_statement_transaction
  -> pricing-service: adapter чтения нормализованных строк Сбера
  -> классификация строк
  -> экспорт 1CClientBankExchange
  -> 1С КлиентБанк1 загружает подготовленный файл
  -> 1С валидирует справочники и создаёт/перезаписывает документы
```

Fallback-поток для банков без API или аварийных случаев:

```text
банковский файл / уже готовый 1CClientBankExchange
  -> pricing-service / Bitrix Disk
  -> parser конкретного банка или pass-through 1CClientBankExchange
  -> классификация строк
  -> экспорт 1CClientBankExchange
  -> 1С КлиентБанк1 загружает подготовленный файл
  -> 1С валидирует справочники и создаёт/перезаписывает документы
```

Сервис не пишет документы напрямую в 1С. Его задача: получить выписку из банка
или принять банковский файл, привести его к формату, который умеет старая
обработка, и добавить классификацию строк.

## MVP-периметр

Входит в MVP:

- Приём банковской выписки в сервис:
  - основной вход для Сбера - уже загруженные строки
    `finance.raw_sber_statement_transaction` из `mm-compensation`;
  - fallback-вход - папка Bitrix Disk `Банковские выписки / Входящие`;
  - fallback upload файла из банка через внутренний UI/API;
  - прямое получение по API других банков - отдельный этап после решения, где
    будет жить владелец OAuth/токенов.
- Нормализация разных банковских форматов в каноническую модель строки выписки.
- Экспорт нормализованной выписки в `1CClientBankExchange` для загрузки старой
  обработкой `КлиентБанк1`.
- HTTP endpoint `POST /api/v1/bank-payments/classify` как внутренний механизм
  классификации одной строки и как fallback для сценария, где 1С уже разобрала
  файл сама.
- Правила:
  - `card_payment` - СБП/эквайринг, включая сухие назначения от банков-эквайеров;
  - `internal_transfer_out` / `internal_transfer_in` - переводы между своими
    счетами;
  - `bank_return` - возвраты и неисполненные платежи от банка;
  - `founder` - расчёты через учредителя;
  - `salary_registry` - зарплатные реестры;
  - `manual_review` - все спорные или недостаточно уверенные строки.
- Возврат `scenario`, `operation_code`, `cash_flow_article_name`,
  `contract_code`, `physical_person_name`, `skip_auto_contract_fill`,
  `skip_payment_fill`, `should_load`, `existing_document_policy`, `confidence`,
  `reasons`.
- Набор тестовых строк на анонимизированных реальных примерах выписок.
- Диагностический лог без токенов, webhook URL и полных банковских реквизитов в
  публичных логах.
- Автоматическая обработка папок Bitrix Disk как fallback-канала:
  - входящие файлы читаются из `Входящие`;
  - готовый `1CClientBankExchange` и короткий отчёт кладутся в `Готово`;
  - нераспознанные форматы и блокирующие ошибки кладутся отчётом в `Ошибки`;
  - smart-process и CRM-карточки не используются в этом MVP.

Не входит:

- Полная замена обработки `Клиент-Банк`.
- Прямое создание или проведение документов 1С из `pricing-service`.
- Автоматическое создание контрагентов, договоров и банковских счетов вне 1С.
- Изменение банковского формата `1CClientBankExchange`.

Для Сбера не создаём второй прямой API-клиент в `pricing-service`: доступы,
токены, расписание и raw-журнал уже заведены в `mm-compensation`. Для других
банков прямой API остаётся отдельным этапом.

## Контракт нормализации

На вход сервис получает один из источников:

- банковский файл в родном формате банка;
- уже готовый `1CClientBankExchange`;
- нормализованные строки `finance.raw_sber_statement_transaction`, если источник
  - Сбер API из `mm-compensation`;
- позже - ответ API другого банка, если будет принято решение делать отдельный
  владелец подключения.

На выход сервис отдаёт:

- нормализованный файл `1CClientBankExchange`, который можно загрузить старой
  обработкой `КлиентБанк1`;
- отчёт по строкам: сколько распознано, сколько ушло в `manual_review`, какие
  строки не удалось экспортировать;
- диагностический идентификатор загрузки для разбора ошибок без публикации
  полных реквизитов.

## Запрос классификации строки

Сервису нужны не ссылки 1С, а данные строки выписки и признаки, которые уже
посчитала 1С или нормализатор:

- направление платежа: `incoming` / `outgoing`;
- вид документа 1С: например, `ПлатежноеПоручениеВходящее` или
  `ПлатежноеПоручениеИсходящее`;
- дата, номер, сумма, валюта;
- плательщик, получатель, ИНН/КПП, счета и банки;
- назначение платежа, включая многострочные поля `НазначениеПлатежа1..6`;
- `payment_purpose_code` / `priority`, если они есть в файле банка;
- признаки `payer_account_is_own`, `recipient_account_is_own`,
  `existing_document_found`.

Полные номера счетов и ИНН в логах сервиса маскируются.

## Контракт ответа

Черновой ответ классификатора:

```json
{
  "scenario": "card_payment",
  "operation_code": "ПоступлениеОплатыПоПлатежнымКартам",
  "cash_flow_article_name": "Оплата от покупателя (за товар)",
  "physical_person_name": null,
  "contract_code": "РБ0022772",
  "skip_auto_contract_fill": true,
  "skip_payment_fill": false,
  "should_load": true,
  "existing_document_policy": "allow_card_payment_rewrite",
  "confidence": 0.94,
  "reasons": [
    "назначение содержит СБП",
    "плательщик похож на банк-эквайер"
  ]
}
```

1С должна воспринимать ответ как рекомендацию. Финальная проверка ссылок на
справочники остаётся в 1С: если статья ДДС, договор или счёт не найдены, строка
получает замечание и уходит на ручную проверку.

`operation_code` в ответе является символическим кодом, а не прямой ссылкой 1С:
сама 1С сопоставляет его с нужным перечислением с учётом вида документа и
направления платежа.

Флаг `skip_auto_contract_fill` означает "не запускать штатный автоподбор
договора", а не "договор запрещён всегда". Для эквайринга это важно: 1С может
пропустить обычный договор покупателя и при этом применить специальный договор
эквайринга по `contract_code`.

## Что остаётся в 1С

- Чтение подготовленного файла `1CClientBankExchange`.
- Поиск существующего документа и защита от дублей.
- Поиск счетов, контрагентов, договоров, статей ДДС и физических лиц.
- Создание, перезапись, проведение и отмена проведения документов.
- Отображение таблицы загрузки и списка ненайденных реквизитов.
- Fallback на текущую логику при ошибке API, если 1С вызывает классификацию
  построчно.
- Политика перезаписи найденных документов: для `card_payment` можно
  донастраивать вид операции/договор, для остальных сценариев найденный активный
  документ безопаснее оставить без изменений и показать замечание.

## Риски и защита

- Сервис недоступен: уже поддерживаемые старой обработкой банки можно грузить
  текущим ручным путём; неподдерживаемые банки ждут повторной нормализации.
- Банк отдал новый формат файла: сервис сохраняет исходный файл локально,
  помечает загрузку как `manual_review` и не отдаёт в 1С сомнительный импорт.
- API банка недоступен: последняя успешная выписка не переиспользуется молча,
  нужна явная ошибка загрузки.
- Правило уверено, но справочник в 1С не совпал: 1С не проводит молча, а пишет
  замечание по строке.
- Уже найден старый документ с неверным видом операции: для `card_payment` нужна
  отдельная логика перезаполнения вида операции и договора, иначе ошибка
  сохранится.
- В логах есть финансовые данные: логируем минимум, маскируем счета/ИНН при
  выносе в общие артефакты.

## Проверка по текущему `КлиентБанк1`

В текущей обработке уже есть локальные правила `MM` для тех же сценариев:

- `card_payment`: СБП/эквайринг, сухие назначения от банков-эквайеров,
  `ПоступлениеОплатыПоПлатежнымКартам`;
- `internal_transfer_out` / `internal_transfer_in`: собственные счета,
  входящее движение не загружается повторно;
- `salary_registry`: зарплатный реестр, вид операции
  `осиВыплатаЗаработнойПлаты`, физлицо `Зарплата`, статья `Оплата труда (аванс)`;
- `founder`: расчёты через учредителя;
- `bank_return`: возвраты, неверные и неисполненные платежи банка.

Первую точку встраивания внутри 1С стоит искать рядом с
`ПрименитьПравилаMasterMobileДляИмпортаВыписки`, если нужен fallback-вызов API
по уже разобранной строке. Основной путь MVP лучше делать до 1С: сервис готовит
файл `1CClientBankExchange`, а старая обработка загружает его как обычную
выписку.

## План

1. Собрать примеры файлов банков, которые старая обработка не поддерживает.
2. Реализовать в `pricing-service` file-upload, parser и экспорт в
   `1CClientBankExchange`.
3. Добавить Bitrix Disk-папки `Входящие` / `Готово` / `Ошибки` как простой
   пользовательский вход без smart-process.
4. Реализовать классификатор и тесты на анонимизированных строках.
5. Прогнать на нескольких реальных выписках: СБП, эквайринг, внутренний перевод,
   возврат банка, зарплатный реестр.
6. Добавить fallback-вызов API из `КлиентБанк1`, если после пилота останется
   польза от построчной классификации прямо внутри 1С.
7. После пилота вынести стабильный контракт нормализации и классификации в
   отдельный integration contract.
