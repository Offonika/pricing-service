# Черновик задачи Bitrix24: точка заказа для «Маржинального потока» (не опубликован)

**Адресат:** Арсений, директор по развитию
**Состояние:** черновик, в Bitrix24 не опубликован
**Основание:** решения, зафиксированные в документации 2026-08-16

## Цель

Реализовать в read-only dry-run расчёт точки заказа для карточек
**Растим (ПРОДАЖА)** группы «Маржинальный поток». Не менять production, cron,
автоматическое создание заказов и записи в 1С/Bitrix24.

## Все принятые 2026-08-16 изменения, относящиеся к этой задаче

1. Область правила ограничена одновременно тремя условиями:
   - статус только **Растим (ПРОДАЖА)**;
   - скорость продаж от `0,1` до `0,25` шт/день включительно;
   - рентабельность строго выше `31%`.
2. **Поддерживаем (Рабочий)** исключён из этого правила. Разрешение этого
   статуса в старом реестре признано ошибкой.
3. Точка заказа равна потребности на `105` дней плюс фиксированный страховой
   запас `13` штук. Число `13` добавляется ровно один раз.
4. Единственный сигнал правила — `reorder_point_reached`, то есть вся позиция
   запаса стала меньше или равна точке заказа.
5. Отдельный сигнал или тревога по условию `free_stock_qty <= 13` отменён.
   Поле/сигнал `fixed_safety_stock_breach` создавать нельзя.
6. Старая динамическая формула
   `11 + ceil(продано_за_30_дней / 2 + 2)` отменена.
7. Дополнительная надбавка `+20%` на рост отменена.
8. Существующий `STRUCTURAL_FLOOR_QTY = 13` не удалять и не переименовывать.
   Это отдельный временный предохранитель для медленных карточек: при низком
   остатке он разрешает перейти к уже существующему обычному расчёту заказа.
   Он не является тревогой и не реализует новую точку заказа.

## Точная формула

```text
fixed_safety_stock_qty = 13

demand_qty_105 =
    ceil(avg_daily_sales_qty * 80)
    + ceil(avg_daily_sales_qty * 25)

reorder_point_qty = demand_qty_105 + fixed_safety_stock_qty

inventory_position_qty =
    free_stock_qty + reliable_incoming_qty

reorder_point_reached =
    inventory_position_qty <= reorder_point_qty

recommended_order_qty = max(
    0,
    reorder_point_qty - inventory_position_qty,
)
```

Округление выполняется отдельно для горизонта `80` дней и отдельно для
горизонта `25` дней. После сложения повторного округления нет.

## Требуемое изменение кода

1. В `tasks/build_display_auto_order_dry_run.py` добавить отдельную ветку
   расчёта только для карточек, которые проходят все три условия области
   действия.
2. Проверить и зафиксировать тестом соответствие машинного значения статуса
   каноническому статусу **Растим (ПРОДАЖА)**. Не определять область правила по
   одному отображаемому тексту.
3. Для прошедших фильтр строк выводить поля:
   - `fixed_safety_stock_qty`;
   - `demand_qty_105`;
   - `reorder_point_qty`;
   - `inventory_position_qty`;
   - `reorder_point_reached`;
   - `recommended_order_qty`;
   - понятную причину применения или неприменения правила.
4. Использовать только надёжный товар в пути по действующим правилам качества
   pipeline. Недостоверное поступление не уменьшает потребность.
5. Существующие hard blockers, исключение карточек «биток», запреты закупки,
   MOQ/кратность и ограничения поставщика сохраняют действующий приоритет.
6. `STRUCTURAL_FLOOR_QTY = 13` оставить без изменений для остальных строк.
   Для строки «Маржинального потока» число `13` нельзя прибавить второй раз или
   превратить в отдельный сигнал.
7. Не добавлять `fixed_safety_stock_breach` ни как поле, ни как warning, ни как
   причину решения.

## Обязательные тесты

| Сценарий | Ожидаемый результат |
| --- | --- |
| Статус **Растим (ПРОДАЖА)**, скорость `0,1`, рентабельность `>31%` | Правило применяется |
| Статус **Растим (ПРОДАЖА)**, скорость `0,25`, рентабельность `>31%` | Правило применяется |
| Скорость ниже `0,1` или выше `0,25` | Правило не применяется |
| Рентабельность ровно `31%` | Правило не применяется |
| Статус **Поддерживаем (Рабочий)** при подходящих скорости и рентабельности | Правило не применяется |
| `free_stock_qty <= 13`, но позиция запаса выше точки заказа | Нет сигнала и нет заказа по этому правилу |
| Есть hard blocker | Заказ не формируется; действует текущий blocker-flow |
| Карточка исключена правилом «биток» | Не попадает в расчёт и отчёт |
| Не подходит под «Маржинальный поток», остаток ниже `13` | Текущий `STRUCTURAL_FLOOR_QTY` работает без изменений |

Контрольный пример РБ000032399:

```text
avg_daily_sales_qty = 0,2389
demand_qty_105 = ceil(0,2389 × 80) + ceil(0,2389 × 25) = 20 + 6 = 26
fixed_safety_stock_qty = 13
reorder_point_qty = 26 + 13 = 39
free_stock_qty = 5
reliable_incoming_qty = 10
inventory_position_qty = 5 + 10 = 15
reorder_point_reached = true
recommended_order_qty = 39 - 15 = 24
```

## Результат для проверки до rollout

Запустить только read-only dry-run и приложить qty-diff:

- количество карточек, прошедших все три условия;
- количество `reorder_point_reached = true`;
- суммарное старое и новое рекомендуемое количество;
- число строк с увеличением, уменьшением и без изменения;
- топ изменений по количеству и сумме закупки;
- отдельные проверки: `0` карточек **Поддерживаем (Рабочий)**, `0` карточек
  «биток», `0` случаев двойного добавления `13`;
- список ошибок/неполных данных по рентабельности и надёжному товару в пути.

## Продолжение безопасного эксперимента 2026-08-16

После current-snapshot diff пользователь разрешил продолжить только отдельный
read-only эксперимент. Следующий этап ограничен восстановлением versioned
historical pipeline с доказуемыми `available_at`, временем наблюдения/ревизии и
reliability evidence, а затем воспроизводимым look-ahead-free replay.

Это решение не разрешает production rollout, переключение release или cron,
создание заказов, изменение `recommended_order_qty`, сохранение internal drafts,
записи в БД приложения, 1С, Bitrix24, Telegram либо другие внешние API.
Production остаётся `NO-GO` до отдельного решения после просмотра replay.

## Не входит в задачу

- удаление или изменение `STRUCTURAL_FLOOR_QTY = 13`;
- изменение статусов карточек;
- включение cron или production;
- автоматическое создание, подтверждение или проведение заказа;
- записи в 1С или Bitrix24.

## Критерий готовности

Код и адресные тесты готовы, read-only dry-run и qty-diff приложены, все
граничные сценарии пройдены. Production допускается только отдельным решением
после просмотра результата.
