# OnePage: офлайн-запись разговоров менеджер ↔ клиент у стойки

## Зачем это нужно
Нужно организовать стабильную запись живых диалогов у стойки продаж в магазинах так, чтобы дальше можно было:
- автоматически получать файлы на центральный сервер;
- делать транскрибацию;
- сохранять результаты в PostgreSQL;
- строить отчеты и речевую аналитику по аналогии с уже работающим контуром по звонкам.

На первом этапе главная цель не аналитика, а надежное получение качественных записей.
Пилот делаем не сразу на все магазины: используем один переносной комплект и по очереди тестируем точки по неделям.

## Что показал тест
Тестовая схема:
- микрофон `Aceline AMIC-11`;
- программа записи `Snooper`;
- расстояние до говорящего примерно `30-40 см`.

Результат:
- общий смысл части диалогов распознается;
- для грубой проверки гипотезы схема подходит;
- для стабильной речевой аналитики качество недостаточное.

Основные проблемы:
- один бюджетный микрофон рядом с менеджером плохо пишет клиента;
- нет раздельной записи менеджера и клиента по каналам;
- в расшифровке теряются модели, цены, артикулы и отдельные фразы;
- в шумной рознице качество будет еще хуже.

Вывод:
- `Aceline AMIC-11 + Snooper` можно использовать только как временный черновой пилот;
- как стандартное решение для rollout на 12 магазинов этот вариант не подходит;
- для следующего этапа нужен компактный специализированный микрофон, который можно быстро переставлять между магазинами.

## Что предлагаем сделать

### 1. Как идем по этапам

#### Пилотный этап
На пилоте используем один компактный переносной комплект:
- один специализированный микрофон;
- крепление на монитор;
- подключение к ПК;
- запись на одной стойке;
- перенос комплекта между магазинами по очереди.

Этот этап нужен, чтобы:
- быстро проверить качество записи в реальных магазинах;
- не закупать сразу оборудование на все точки;
- понять, достаточно ли одного микрофона для первичной транскрибации.

#### Целевой этап rollout
Если пилот подтверждает эффект, переходим к целевой схеме:
- отдельный микрофон на менеджера;
- отдельный микрофон на клиента;
- один 2-канальный аудиоинтерфейс;
- запись в `WAV PCM 16 bit, 16 kHz, stereo`.

Где:
- левый канал = менеджер;
- правый канал = клиент.

Это даст:
- лучшее качество записи;
- более точную транскрибацию;
- возможность анализировать реплики отдельно без сложного разбора говорящих.

### 2. Рекомендации по микрофонам

#### Для пилота
Требования к микрофону:
- компактный;
- крепится на монитор;
- быстро снимается и переносится между магазинами;
- дает более качественную запись, чем бытовой настольный микрофон.

Рекомендуемый тип:
- специализированный компактный микрофон для записи разговора у стойки.

Базовый приоритет для пилота:
- `STELBERRY M-120HD` или аналогичный компактный микрофон на монитор.

Если нужен больший упор именно на запись диалога сотрудник ↔ клиент:
- рассматривать `STELBERRY M-1100HD` или аналогичный двунаправленный микрофон, но это уже менее простой в подключении вариант.

Микрофоны типа `Aceline AMIC-11`, `STELBERRY M-75` и любые одиночные дешевые настольные USB/3.5 мм микрофоны как основной стандарт не использовать.

#### Для rollout
Для менеджера:
- направленный микрофон;
- крепление на монитор или рядом с монитором;
- расстояние `30-60 см`.

Для клиента:
- в рабочей схеме начинать с `boundary`-микрофона ближе к клиенту;
- если качества не хватает, переходить на более дорогую схему с массивом/beamforming.

### 3. ПО на рабочем месте
На пилоте можно временно оставить `Snooper` только как рекордер, если он стабильно пишет файлы.
Это допустимо именно потому, что пилотный комплект будет переносным и использоваться по очереди, а не сразу на 12 точках.

Для rollout нужен свой локальный Windows-агент/служба на каждом ПК, который:
- пишет 2-канальный звук;
- режет запись на диалоги по тишине;
- хранит локальный буфер `3-7 дней`;
- автоматически отправляет файлы на сервер;
- повторяет отправку при сбоях;
- контролирует, что оба канала живы;
- шлет статус и ошибки.

## Целевая архитектура

### На ПК менеджера в пилоте
- один компактный микрофон на мониторе;
- локальный рекордер пишет файлы;
- локально хранится буфер на случай обрыва сети;
- комплект можно перевезти в другой магазин и быстро подключить заново.

### На ПК менеджера в rollout
- 2 микрофона подключены к одному 2-канальному аудиоинтерфейсу;
- локальный recorder/upload agent пишет и сегментирует диалоги;
- локально хранится буфер на случай обрыва сети.

### На центральном сервере
- принимаем файлы по `HTTPS` или `SFTP`;
- raw audio храним как файлы в storage, не в PostgreSQL;
- в PostgreSQL храним:
  - метаданные диалога;
  - статус загрузки;
  - статус транскрибации;
  - транскрипт;
  - результаты аналитики.

### На ASR-сервере
- отдельный worker выполняет транскрибацию;
- результат пишет в PostgreSQL;
- затем отдельный analysis worker строит summary, флаги и отчеты.

Рекомендуемая роль серверов:
- текущий центральный сервер: API, PostgreSQL, отчеты, orchestration;
- более мощная Windows-машина `Ryzen 7600 / 64 GB`: ASR worker;
- storage: файловое хранилище raw audio с retention.

## Что сохраняем
В PostgreSQL:
- карточку диалога;
- транскрипт;
- summary;
- quality flags;
- аналитические поля и статусы.

Raw audio:
- храним отдельно как файлы;
- рекомендуемый retention для старта: `14-30 дней`;
- после успешной транскрибации и проверки можно удалять по политике хранения.

## Какой этап делаем первым

### Этап 1. Переносной пилот
- 1 переносной комплект;
- 1 магазин за раз;
- перенос комплекта по магазинам по очереди;
- 30 тестовых диалогов суммарно;
- проверка качества записи и транскрибации в реальных условиях.

### Этап 2. Контур транскрибации и отчетов
- загрузка файлов на сервер;
- запись метаданных в PostgreSQL;
- ASR worker;
- сохранение транскриптов;
- ежедневные отчеты по аналогии со звонками.

### Этап 3. Rollout
- стандартизация оборудования;
- установка локального агента на точки;
- подключение 12 магазинов;
- контроль работоспособности и алерты.

## Минимальные проверки
- файл не пустой;
- корректная длительность;
- на пилоте есть сигнал на активном микрофоне;
- в rollout есть сигнал на обоих каналах;
- алерт, если:
  - нет новых записей более `2 часов`;
  - в rollout один канал постоянно молчит;
  - есть очередь неотправленных файлов;
  - ASR не отрабатывает в SLA.

## Что нужно согласовать
1. На первом этапе используем один переносной комплект, а не закупаем сразу все магазины.
2. Для пилота подтверждаем один компактный микрофон на монитор как временное решение.
3. `Snooper` допускается только как временное пилотное решение.
4. Для rollout планируем переход на 2-канальную схему записи.
5. Для rollout планируем собственный локальный Windows-агент.
6. Raw audio храним отдельно от PostgreSQL.
7. Retention raw audio на старте принимаем `14-30 дней`.
