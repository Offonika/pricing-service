# Пилот E2E утреннего управленческого отчёта

Дата пилота: `2026-03-20`  
Проверяемые роли: `ceo`, `cco`, `coo`

## Что вошло в пилот

- B-side prompt orchestration через `sync_morning_call_reports.py`
- management digest с сервера `A`:
  - `management_digest_from_a.py --date 2026-03-20 --role-code <role>`
- AI follow-up digest на сервере `B`:
  - `meeting_action_digest.py --date 2026-03-20 --role-code <role>`
- role config в `morning_call_reports.yaml` для:
  - `CEO`
  - `Коммерческий директор`
  - `Операционный директор`

## Подтверждённое состояние

Для ролей `ceo`, `cco`, `coo` в конфиге утренних отчётов на сервере `B` подключены оба источника:

- `management_script`
- `meeting_action_script`

По живому прогону на `2026-03-20`:

- management digest с сервера `A` отрабатывает стабильно;
- AI action digest с сервера `B` отрабатывает стабильно;
- `meeting_action_digest.py` вернул:
  - `47` новых follow-up кейсов за вчера;
  - `264` overdue open-кейса;
  - топ тем:
    - `наличие/замена=14`
    - `общее follow-up=19`
    - `цена/промокод=6`
    - `возврат/обмен=3`
    - `callback/дозвон=3`
- в top-case preview попали осмысленные кейсы:
  - возврат/обмен;
  - статус заказа;
  - цена/промокод;
  - callback.

## Оценка содержательности

### Что уже содержательно

- Блок `AI action items` даёт реальные клиентские follow-up кейсы, а не пустую заглушку.
- В отчёт попадают:
  - тема кейса;
  - owner group;
  - статус;
  - краткая суть;
  - следующий шаг.
- Для `coo` и `ceo` этого уже достаточно, чтобы видеть:
  - просроченные клиентские коммуникации;
  - точки возвратов/обменов;
  - проблемы по наличию и статусам заказов.

### Что пока неполно

- Management digest с сервера `A` остаётся `degraded`:
  - `staffing=missing/empty`
  - по дебиторке сейчас фактически виден только контур `receivable_new_daily`
- Внутри самого `management_digest_from_a.py` по-прежнему печатается старая строка:
  - `Встречи/AI: ... пока не подключены`
  Это не ломает итоговый утренний отчёт, потому что AI-блок приходит отдельным `meeting_action_script`, но формально создаёт когнитивный шум.

## Оценка шума

Основной источник шума сейчас не management API, а B-side AI follow-up блок:

- слишком большой хвост `pending_review`:
  - `334` кейса в выборке;
- слишком много `overdue`:
  - `264` кейса;
- часть кейсов попадает в тему `общее follow-up`, что снижает управленческую точность;
- часть кейсов из `retail_megafon` ещё выглядит как слабоструктурированные диалоги/автоответчики.

Практический вывод:

- для `CEO/CCO/COO` блок уже полезен;
- но в текущем виде его нужно считать `pilot-grade`, а не `final-grade`.

## Оценка SLA

Подтверждено:

- source scripts на `B` запускаются и возвращают данные быстро;
- `management_digest_from_a.py` и `meeting_action_digest.py` годятся для утреннего cron/prompt flow.

Ограничение:

- managed control plane (`sync_morning_call_reports.py --apply/--verify-only`) в момент пилота отвечал заметно дольше обычного через `managed-cron-bridge.ts`.
- Поэтому по этому пилоту подтверждено:
  - готовность source layer;
  - готовность role config;
  - готовность prompt payload;
  - но не зафиксирован финальный быстрый `verify` runtime после `apply` в рамках того же сеанса.

## Итог пилота

Пилот можно считать успешным в следующем объёме:

- для `ceo`, `cco`, `coo` собран реальный E2E-контур источников;
- management и AI follow-up данные реально готовы к включению в утренний отчёт;
- содержание для управленческого чтения уже есть;
- шум и деградация локализованы и понятны.

## Что улучшать следующим этапом

1. Убрать устаревшую заглушку про `Встречи/AI не подключены` из `management_digest_from_a.py`.
2. Снизить шум в `meeting_action_digest.py`:
   - жёстче фильтровать автоответчики;
   - отделить `retail`-шум от реально клиентских кейсов;
   - сократить `overdue` хвост через верхний лимит и приоритизацию.
3. Довести staffing source до `fresh/ready`, иначе утренний management block будет системно `degraded`.
4. После стабилизации control plane отдельно переподтвердить `apply + verify` для managed runtime job'ов.
