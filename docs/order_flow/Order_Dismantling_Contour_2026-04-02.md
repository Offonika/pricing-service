# Контур расформирования заказов сайта

Дата фиксации: `2026-04-02`

Связанные задачи Bitrix24:

- `9627` График сотрудников сайта которые занимаются расформированием заказов сайта
- `10011` Доступ - расформировать заказ
- смежно: `3966` Кнопка в ВОЗВРАТ КПП В УТ10.3
- смежно: `9751` Экспертизы

## 1. В чём проблема на самом деле

Задача `9627` снаружи выглядит как просьба “дать график сотрудников”.

Но по смыслу это не кадровый вопрос, а симптом более глубокой проблемы:

- нет закреплённого owner-контура по незабранным заказам сайта;
- нет прозрачного SLA, кто и когда обязан расформировать заказ;
- нет понятной замены, если ответственный недоступен;
- доступ на расформирование есть не у всех, кто реально должен снимать зависание;
- товар лежит в резерве и “замораживается” на несколько дней;
- параллельно растёт нагрузка на возвраты, перемещения и конфликты по наличию.

Именно поэтому `9627` напрямую связан с `10011`.

## 2. Корневая причина

Сейчас смешаны три разных слоя:

1. Кто мониторит чат/канал сайта и понимает, что заказ уже проблемный.
2. Кто имеет право в `1С` технически расформировать или снять резерв.
3. Кто несёт операционную ответственность за то, что товар снова доступен для продажи.

Пока эти роли не разведены, любой “график сотрудников” будет неполным решением.

## 3. Какой контур тут на самом деле нужен

Это отдельный операционный контур:

- `выявление зависшего заказа`
- `назначение владельца`
- `решение: удерживать / продлить / расформировать / эскалировать`
- `исполнение в 1С`
- `контроль возврата товара/резерва в доступный остаток`

То есть нужен не просто график, а контур `Order Dismantling / Release`.

## 4. Минимальное рабочее решение

### 4.1. Роли

Нужно явно развести роли:

- `Observer`
  - сотрудники сайта, кто ежедневно смотрит незабранные / проблемные заказы;
  - их график и нужен в задаче `9627`.
- `Executor`
  - сотрудники, у кого есть право расформировать заказ в `1С`;
  - это задача `10011`.
- `Escalation owner`
  - старший / COO / ответственный за интернет-заказы, если SLA сорван.

### 4.2. SLA

Минимум нужно ввести 3 окна:

- `T0`
  - заказ попал в список проблемных / незабранных;
- `T1`
  - в течение короткого окна заказ должен быть взят в разбор конкретным сотрудником;
- `T2`
  - в течение согласованного окна должен быть один из исходов:
    - продлить удержание;
    - подтвердить ожидание клиента;
    - расформировать;
    - эскалировать.

Даже без автоматизации уже нужен жёсткий регламент:

- если до конца смены owner не назначен — эскалация;
- если до дедлайна нет действия — эскалация руководителю.

### 4.3. Матрица решений

Для расформирования нужен обязательный reason code:

- `клиент не выходит на связь`
- `клиент отказался`
- `дубль заказа`
- `ошибка оплаты / интеграции`
- `частичный конфликт по наличию`
- `ожидание решения по возврату / экспертизе`
- `нельзя расформировать без решения руководителя`

Это важно, потому что без причин расформирование превращается в “чёрную дыру”.

## 5. Что сделать без доработки 1С

На первом этапе можно запустить контур почти без изменений в `1С`.

### Шаг 1. Зафиксировать owner-график

По `9627` нужен не просто список людей, а таблица:

- день недели
- время окна
- основной ответственный
- резервный ответственный
- руководитель эскалации

### Шаг 2. Дать права только исполнителям

По `10011` доступ даётся не всем подряд, а только:

- старшему подразделения;
- второму сотруднику по подразделению;
- отдельным сотрудникам сайта, кто реально исполняет расформирование.

### Шаг 3. Вести очередь кейсов в Bitrix24

Даже если действие происходит в `1С`, сам кейс лучше вести в `Bitrix24`:

- заказ / номер заказа;
- подразделение;
- кто owner;
- статус кейса;
- причина;
- дедлайн;
- факт расформирования / комментарий.

То есть:

- `1С` делает учётное действие;
- `Bitrix24` хранит процесс, ответственность и SLA.

### Шаг 4. Ежедневный контрольный реестр

Нужен простой реестр:

- новые зависшие заказы;
- в работе;
- просроченные;
- расформированы;
- ждут решения по возврату/экспертизе.

Этот реестр можно сначала собрать вручную или полуручно, потом автоматизировать.

## 6. Как это связать с другими задачами

### Связь с `10011`

`9627` без `10011` не решается.

Если есть график, но нет прав:

- сотрудник увидел проблему;
- но не может её закрыть;
- заказ снова зависает.

### Связь с `3966`

Часть зависших заказов и расформирований упирается в сложные возвраты между подразделениями.

Если возврат из другого подразделения нельзя оформить быстро:

- заказ держат “подвешенным” дольше;
- товар остаётся в спорном состоянии;
- расформирование затягивается.

### Связь с `9751`

Если причина зависания — качество / экспертиза:

- такой заказ нельзя просто расформировать без отдельного кейса;
- он должен уходить в контур экспертизы.

Поэтому расформирование должно иметь исход:

- `release`
- `return`
- `expertise`
- `manual escalation`

## 7. Целевое решение на втором этапе

После быстрого оргзапуска можно довести до полноценного контура:

- внешний backend или read-only витрина над заказами сайта;
- автоматическое выявление заказов-кандидатов на расформирование;
- автосоздание Bitrix24-кейса;
- назначение owner по графику;
- контроль SLA;
- отчёт по причинам зависаний;
- отчёт по подразделениям и сотрудникам.

## 8. Практическое решение по задаче 9627

Если отвечать предметно, то задачу `9627` надо закрывать не так:

- “вот список сотрудников”.

А так:

1. Утвердить owner-график наблюдения за незабранными заказами сайта.
2. Зафиксировать резервного сотрудника на каждое окно.
3. Связать owner-график с правами на расформирование (`10011`).
4. Ввести обязательный reason code при расформировании.
5. Вести кейсы расформирования в `Bitrix24` до факта исполнения в `1С`.

## 9. Рекомендуемая очередь действий

### Немедленно

- закрыть `9627` как owner-график, а не просто “список людей”;
- закрыть `10011` как матрицу прав по подразделениям;
- утвердить 5-7 причин расформирования.

### Следом

- завести единый Bitrix24-контур кейсов расформирования;
- связать его с возвратами и экспертизами;
- добавить ежедневный контроль просроченных кейсов.

### Потом

- автоматизировать выявление заказов-кандидатов на расформирование из `1С`/сайта.

## 10. Короткий вывод

Проблема в `9627` — это не отсутствие графика как документа.

Проблема в том, что у процесса расформирования сейчас:

- нет owner-модели;
- нет связки “наблюдает -> имеет право -> исполняет -> несёт SLA”;
- нет отдельного управляемого кейса.

Решать это нужно как отдельный операционный контур, связанный с `10011`, `3966` и `9751`.
