# Проект: классификатор причин возврата в `1С` для KPI и управленческой аналитики

## 1. Зачем нужен проект

Сейчас документ `Возврат товаров от покупателя` в `1С` содержит полезные учетные поля:

- дата и номер документа;
- ответственный;
- номенклатура;
- магазин / склад;
- количество;
- сумма возврата.

Но для признака `по вине салона / не по вине салона` этого недостаточно.

По живой базе видно:

- в шапке есть свободное текстовое поле, но оно заполнено нерегулярно;
- в строках есть короткое строковое поле, но оно тоже используется редко и без единой методики;
- структурированная ссылочная причина возврата в самом документе сейчас фактически не используется как надежный источник.

Из-за этого нельзя честно считать:

- `возвраты по вине салона`;
- `долю ошибок продажи`;
- `долю возвратов по вине точки`;
- `store_fault_return_rate` для мотивации.

Поэтому нужен отдельный проект: ввести в `1С` единый классификатор причин возврата и сделать его обязательной частью процесса.

## 2. Цель проекта

Сделать в `1С` единый и обязательный классификатор причин возврата, который:

- позволяет однозначно определить, относится ли возврат к вине салона;
- отделяет управленческую причину от бухгалтерского документа;
- подходит для расчета KPI, отчетов и разбора проблемных точек;
- не ломает текущий учетный процесс возврата;
- может быть внедрен сначала в `УТ 10.3`, а потом перенесен в новую `1С`.

## 3. Что считаем результатом проекта

Проект считается реализованным, когда:

- в `1С` есть отдельный утвержденный справочник причин возврата;
- каждая строка возврата имеет обязательную классификацию;
- у классификатора есть признак `по вине салона`;
- спорные и незавершенные кейсы выделены отдельно;
- внешняя аналитика может считать `store_fault_return_rate` без парсинга свободных комментариев;
- есть регламент, кто и в какой момент выбирает причину;
- есть контроль заполненности и отчет по незакрытым причинам.

## 4. Что именно нужно добавить в `1С`

### 4.1. Новый справочник

Нужен отдельный справочник `Классификатор причин возврата`.

Минимальные поля элемента справочника:

- `Код`
- `Наименование`
- `Группа причин`
- `Подгруппа причин`
- `Признак: по вине салона`
- `Признак: по вине поставщика / завода`
- `Признак: клиентская инициатива`
- `Признак: логистика / склад / перемещение`
- `Признак: спорный кейс`
- `Признак: требует экспертизы`
- `Активен`
- `Комментарий по применению`

### 4.2. Новый реквизит строки возврата

В табличную часть `Товары` документа `Возврат товаров от покупателя` нужно добавить обязательный реквизит:

- `КлассифицированнаяПричинаВозврата`

Тип:

- ссылка на справочник `Классификатор причин возврата`

Почему именно на уровне строки:

- один документ возврата может содержать несколько товаров;
- по разным строкам могут быть разные причины;
- KPI и аналитика должны считаться по строкам, а не по шапке документа.

### 4.3. Дополнительные реквизиты строки

Рекомендую добавить еще 2 поля:

- `КомментарийКПричине`
- `СтатусКлассификацииВозврата`

Значения `СтатусКлассификацииВозврата`:

- `не классифицирован`
- `предварительно`
- `подтверждено`
- `спорный кейс`
- `ожидает экспертизы`

Это даст возможность не смешивать:

- уже подтвержденные причины;
- временные догадки менеджера;
- кейсы, которые ждут решение качества / экспертизы.

## 5. Логика классификатора

### 5.1. Верхний уровень групп причин

Предлагаю 5 верхних групп:

1. Ошибка салона
2. Дефект товара / поставщика
3. Клиентская причина
4. Логистика / склад / внутреннее перемещение
5. Не определено / спорно / экспертиза

### 5.2. Причины, которые относятся к вине салона

Эти причины должны автоматически попадать в KPI `возвраты по вине салона`:

- продан не тот товар;
- неверная консультация по совместимости;
- неверная консультация по характеристикам;
- ошибка комплектации;
- ошибка при сборке заказа;
- товар продан в неверном качестве;
- при продаже не выявлен видимый дефект;
- неверно оформлен заказ / возврат / резерв;
- нарушены обещанные условия продажи;
- ошибка выдачи клиенту;
- расхождение при сборке;
- ошибка точки при хранении / обращении с товаром.

### 5.3. Причины, которые не относятся к вине салона

Эти причины не должны входить в KPI `по вине салона`:

- скрытый заводской дефект;
- дефект поставщика;
- повреждение при внешней доставке не по вине точки;
- клиент передумал;
- товар не подошел без ошибки консультации;
- гарантийный случай без ошибки продажи;
- возврат по решению руководства вне операционной ошибки точки;
- техническая корректировка документа;
- дубль документа;
- отмена по ошибке обмена / интеграции.

### 5.4. Спорные причины

Нужен отдельный блок причин, которые не должны сразу влиять на KPI:

- причина не установлена;
- требуется экспертиза;
- спор клиента и точки;
- ожидание решения отдела качества;
- ожидание решения поставщика;
- ручная корректировка без подтвержденной причины.

Такие строки должны попадать в:

- отдельный реестр;
- контроль заполненности;
- отчет качества;

но не в финальный денежный KPI до подтверждения.

## 6. Минимальный состав справочника для MVP

Для первой версии не нужно делать слишком большой справочник.

Достаточно 15-20 причин.

### 6.1. Группа `Ошибка салона`

- `Продан не тот товар`
- `Неверная консультация по совместимости`
- `Неверная консультация по характеристикам`
- `Ошибка комплектации`
- `Расхождение при сборке`
- `Продан товар в неверном качестве`
- `Не выявлен видимый дефект при продаже`
- `Ошибка выдачи клиенту`

### 6.2. Группа `Дефект товара / поставщика`

- `Скрытый заводской дефект`
- `Дефект поставщика`
- `Неисправность выявлена после продажи без ошибки точки`

### 6.3. Группа `Клиентская причина`

- `Клиент передумал`
- `Товар не понадобился`
- `Товар не подошел без ошибки консультации`

### 6.4. Группа `Логистика / склад`

- `Повреждение при внутреннем перемещении`
- `Ошибка упаковки / хранения вне точки продажи`
- `Ошибка доставки`

### 6.5. Группа `Спорно / экспертиза`

- `Причина не установлена`
- `Ожидает экспертизы`
- `Спорный кейс`
- `Технический возврат / дубль`

## 7. Правила заполнения в процессе

### 7.1. Кто заполняет

На первом этапе:

- менеджер / сотрудник точки выбирает предварительную причину;
- отдел качества или уполномоченный сотрудник подтверждает итоговую причину по спорным кейсам;
- для простых кейсов допускается подтверждение без отдельной экспертизы.

### 7.2. Когда заполняется

Обязательный порядок:

1. строка возврата создается;
2. причина возврата выбирается сразу;
3. если причина спорная, ставится статус `ожидает экспертизы` или `спорный кейс`;
4. после решения качества / экспертизы причина переводится в `подтверждено`.

### 7.3. Что запрещено

Нельзя:

- проводить возврат без причины;
- использовать свободный текст вместо классификатора;
- оставлять спорный статус закрытым навсегда;
- подменять причину качеством товара;
- смешивать бухгалтерскую техническую причину и управленческую причину.

## 8. Как считать KPI после внедрения

После внедрения показатель `store_fault_return_rate` считается так:

`СуммаВозвратовПоВинеСалона / ЧистыеПродажиСети`

Где `СуммаВозвратовПоВинеСалона`:

- сумма строк документа `Возврат товаров от покупателя`;
- только по строкам со статусом `подтверждено`;
- только по строкам, где у выбранной причины стоит признак `по вине салона = да`.

В KPI не включаются:

- строки со статусом `не классифицирован`;
- строки со статусом `ожидает экспертизы`;
- строки со статусом `спорный кейс`;
- строки без подтвержденной причины.

## 9. Что делать с уже существующими комментариями

Свободные комментарии в старых полях не нужно считать источником истины.

Их можно использовать только как вспомогательный материал для миграции.

Например:

- `не понадобился`
- `клиент отказался`
- `не работает`
- `расхождение при сборке`

можно использовать для полуавтоматического чернового предложения причины,

но:

- не для автоматического боевого KPI;
- не как окончательную классификацию без человека.

## 10. Этапы внедрения

### Этап 1. Утверждение модели

Нужно согласовать:

- список причин;
- группы причин;
- правило `по вине салона / не по вине салона`;
- кто подтверждает спорные кейсы;
- как считаются KPI и отчеты.

### Этап 2. Доработка `1С`

Нужно сделать:

- новый справочник;
- новый реквизит строки возврата;
- статус классификации;
- обязательность заполнения;
- форму выбора причины;
- базовые отчеты по незаполненным строкам.

### Этап 3. Переходный режим

На 1-2 месяца:

- считать старый управленческий показатель в `shadow mode`;
- параллельно контролировать заполненность классификатора;
- разбирать топ причин и ошибки классификации;
- не включать спорные кейсы в денежный KPI.

### Этап 4. Боевой запуск

После стабилизации:

- включить классификатор как основной источник;
- считать `store_fault_return_rate` из `1С`;
- использовать его в monthly KPI и отчетности.

## 11. Отчеты и контроль качества данных

Сразу после внедрения нужны 4 отчета:

1. Возвраты без классифицированной причины
2. Возвраты со спорным статусом
3. Возвраты по вине салона по точкам
4. Топ причин возвратов за период

Отдельный обязательный контроль:

- доля строк возврата без причины;
- доля строк в спорном статусе;
- средний срок подтверждения причины;
- точки и сотрудники с аномально высокой долей `по вине салона`.

## 12. Что не стоит делать

- Не пытаться решить задачу только через свободное поле комментария.
- Не использовать качество товара как замену причины возврата.
- Не считать `по вине салона` без подтвержденной классификации.
- Не добавлять сразу 100 причин.
- Не завязывать KPI на ручной разбор чатов и устных договоренностей.

## 14. Практическая рекомендация

Для `MVP` показателя `возвраты по вине салона` нужно принять такое правило:

- пока классификатор не внедрен и не стабилизирован, показатель работает только в `shadow mode`;
- в денежный KPI он включается только после утверждения справочника, обязательности заполнения и контроля спорных кейсов.
