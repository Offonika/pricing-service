# Переходный слой статусов между 1С и Bitrix24

Дата фиксации: `2026-04-02`

Статус: `working decision / interim architecture`

## 1. Контекст

На текущем этапе:

- интернет-заказы попадают в `CRM Bitrix24`;
- сделки там висят в стадии `Новый` и не двигаются;
- прямой рабочей интеграции статусов между `1С УТ 10.3` и `Bitrix24` нет;
- данные о фактическом движении заказа живут в `1С`;
- при этом сама модель процесса в `1С` устроена исторически неудобно:
  - на основании заказа рано создаётся `Реализация`;
  - затем собирается не заказ, а уже `Реализация`;
  - если клиент не забрал товар, далее идёт расформирование/перемещение уже через контур `Реализации`;
  - дополнительно кастомно доработано резервирование через `Реализацию`.

Это означает:

- использовать статусы `1С` “как есть” для честного движения CRM нельзя;
- менять сам процесс внутри старой `УТ 10.3` сейчас нецелесообразно, так как планируется переход на новую `1С КА`.

## 2. Решение

Принято временное архитектурное решение:

- не менять текущий процесс исполнения внутри `1С УТ 10.3`;
- не пытаться строить прямую синхронизацию стадий CRM из “сырых” событий `1С`;
- поверх read-only данных `1С` построить внешний backend-слой, который вычисляет операционный смысл заказа;
- именно этот вычисленный смысл использовать для:
  - обновления контекста в `Bitrix24`;
  - уведомлений клиенту;
  - контроля SLA хранения;
  - контроля расформирования;
  - эскалаций и задач.

Иными словами:

- `1С` остаётся системой учёта;
- backend становится anti-corruption layer между `1С` и `Bitrix24`;
- `Bitrix24` получает не “сырые” статусы документов `1С`, а derived operational status.

## 3. Почему это правильно

Если напрямую двигать статусы CRM по факту наличия `Реализации` в `1С`, то в `Bitrix24` повторится та же бизнес-ошибка:

- клиенту и сотрудникам будет показываться “отгружено / выполнено” раньше реального факта;
- увеличатся конфликты;
- CRM станет отражением неправильной внутренней схемы, а не реального процесса.

Переходный слой позволяет:

- не трогать старую `1С`;
- убрать ложные статусы в `Bitrix24`;
- ввести нормальный операционный контроль до перехода на `1С КА`;
- позже легче заменить источник данных, сохранив сам backend-контур.

## 4. Что именно делает внешний backend

Backend должен в read-only режиме читать данные из `1С` и вычислять для каждого заказа отдельный операционный кейс.

Условное имя сущности:

- `order_execution_case`

Минимальная задача этой сущности:

- привязать CRM-заказ / интернет-заказ / документы `1С`;
- определить фактическую стадию исполнения;
- определить, ждёт ли заказ клиента;
- определить, истёк ли срок хранения;
- определить, нужно ли расформирование;
- определить, есть ли спорный контур возврата / экспертизы / качества;
- сформировать человеко-понятный derived status.

## 5. Какие статусы считаем снаружи

Не опираемся напрямую на стадии сделки CRM и не считаем раннюю `Реализацию` фактом отгрузки.

Предварительный переходный набор derived statuses:

- `crm_new`
  - сделка/заказ создан, но операционный процесс ещё не интерпретирован.
- `in_processing`
  - заказ находится в обработке, но ещё не готов к выдаче/отгрузке.
- `ready_for_dispatch`
  - заказ реально готов к передаче клиенту / логистике по вычисленным признакам.
- `awaiting_pickup`
  - заказ ожидает клиента / выдачу.
- `storage_expired`
  - срок хранения истёк.
- `dismantling_required`
  - требуется расформирование / снятие резерва / освобождение товара.
- `dismantled`
  - заказ расформирован, товар выведен из зависшего состояния.
- `manual_review`
  - требуется ручной разбор.
- `return_or_expertise_flow`
  - заказ/товар перешёл в контур возврата, качества или экспертизы.

## 6. Как использовать это в Bitrix24

На переходном этапе не рекомендуется жёстко двигать стандартные стадии CRM по каждому изменению в `1С`.

Рекомендуемый подход:

- хранить вычисленный статус в кастомных полях сделки и/или в отдельном smart-процессе;
- писать timeline-комментарии и служебные обновления;
- создавать задачи и эскалации по SLA;
- переводить стадию сделки только по ограниченному набору устойчивых условий.

То есть:

- `Bitrix24 CRM` = визуализация и операционная координация;
- не источник истины по исполнению;
- не прямое зеркало документооборота `1С`.

## 7. Что это позволяет сделать уже сейчас

Без изменения процесса в `1С УТ 10.3` можно:

- уведомлять клиента, что заказ готов к выдаче / отгрузке;
- отслеживать срок хранения;
- контролировать заказы, зависшие без расформирования;
- назначать owner на расформирование;
- строить ежедневный реестр проблемных заказов;
- создавать кейсы в `Bitrix24` по хранению, расформированию, возвратам и экспертизам.

## 8. Что остаётся внутри 1С

Внутри `1С` пока не меняем:

- раннее создание `Реализации`;
- кастомный процесс резервирования через `Реализацию`;
- текущую логику сборки и расформирования;
- действующие документы и роли, если они критичны для текущей операционной устойчивости.

Это сознательная временная уступка до миграции на `1С КА`.

## 9. Ограничения решения

Переходный слой не делает старый процесс “правильным”.

Он только:

- изолирует неправильную внутреннюю модель;
- переводит её в пригодный для управления внешний статусный контур;
- уменьшает клиентский и операционный ущерб до внедрения новой `1С`.

Поэтому после перехода на `1С КА` этот слой должен быть:

- либо упрощён;
- либо переподключён к новой корректной модели исполнения.

## 10. Практический вывод

До перехода на `1С КА` целевой путь такой:

- `1С MSSQL (read-only)` -> `backend derived status layer` -> `Bitrix24 / уведомления / SLA / расформирование`

а не:

- `пытаться срочно чинить старую УТ 10.3`
или
- `напрямую отражать неверные документы 1С в CRM`.

Это решение считать зафиксированным как временную архитектурную основу для контуров:

- заказов сайта;
- готовности к отгрузке;
- хранения;
- расформирования;
- возвратов и экспертиз.
