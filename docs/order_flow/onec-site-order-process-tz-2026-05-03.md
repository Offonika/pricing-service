# ТЗ для 1С: исправление процесса интернет-заказов

Дата: `2026-05-03`  
Статус: `draft for 1C developer`  
Система: `1С УТ 10.3`  
Контур: `Заказ покупателя -> обеспечение -> сборка -> выдача/отправка -> РТУ -> закрытие`

## 1. Цель доработки

Исправить процесс интернет-заказов в `1С УТ 10.3`, чтобы:

- `Заказ покупателя` был основным документом жизненного цикла;
- `РТУ` создавалась только по факту выдачи клиенту или передачи в ТК/курьеру;
- способ доставки, оплата и этап исполнения хранились раздельно;
- сайт не получал из `1С` ложный факт выполнения из-за ранней `РТУ`;
- сотрудники перестали исправлять последствия процесса через возвраты,
  корректировки доставки и отрицательные остатки на складе `Сайт`.

## 2. Не входит в это ТЗ

- Доработка интерфейса интернет-магазина Bitrix.
- Доработка CRM-сделок `Bitrix24`.
- Замена механизма обмена `CommerceML` с нуля.
- Перевод всего розничного процесса на новый механизм.
- Автоматическое завершение заказа только по факту `РТУ`.

Сайт в этом ТЗ рассматривается только как:

- источник входящих свойств заказа;
- получатель безопасных статусов/реквизитов из `1С`.

## 2.1. Принцип упрощения и волны внедрения

Чтобы не усложнить старую `УТ 10.3`, внедрение разделяется на волны.

### 2.1.1. Wave 1: обязательный минимум 1С

Детальное ТЗ Wave 1 вынесено в отдельный документ:
`docs/order_flow/onec-site-order-wave1-tz-2026-05-03.md`.

В первую волну входит только то, что устраняет первопричину ранних `РТУ`:

- перестать писать способ доставки и оплату в `осиСтатус`;
- ввести чистый `СтатусИсполнения` для интернет-заказов;
- нормализовать `СпособДоставки`, сохранив raw-значение сайта;
- использовать существующий `осиТрекНомер` как трек, если он стабильно
  заполняется;
- фиксировать факт передачи в ТК/курьеру через `ДатаПередачиВТК`;
- запретить или вынести в контроль ранние `РТУ` по интернет-заказам;
- обеспечить заказ штатно через резерв/размещение/перемещение, а не через
  техническую продажу;
- сделать минимальные контрольные отчеты по ранним `РТУ`, минусам склада
  `Сайт` и смешанному `осиСтатус`.

### 2.1.2. Wave 2: автоматизация дисциплины

Во вторую волну выносится все, что полезно, но может утяжелить первый запуск:

- автоматические задачи по всем переходам;
- SMS с полным антидублем по всем событиям;
- регламентное закрытие заказов и снятие резервов;
- расширенный `СтатусДоставки`;
- интеграция клиентских статусов на сайт;
- мост в `Bitrix24` / внешний backend / логистический сервис.

Если разработчик `1С` может сделать часть Wave 2 без риска для Wave 1, это
допустимо, но приемка Wave 1 не должна зависеть от полной реализации Wave 2.

## 2.2. Соответствие смежным контурам

- `1С` остается source of truth по заказу, остаткам, резервам, `РТУ` и
  закрытию.
- Сайт Bitrix на первом этапе только создает заказ и получает безопасные
  реквизиты. Включение клиентских статусов на сайте - отдельная волна после
  стабилизации `1С`.
- `Bitrix24` не становится контуром исполнения заказа. Сделки и smart-процессы
  можно обновлять позже через внешний backend, но не напрямую по сырой `РТУ`.
- Документы логистики/Telegram, где поток интернет-заказов стартует от готовой
  `РТУ`, относятся к старой As-Is модели. После этого ТЗ нельзя создавать
  раннюю `РТУ` только ради QR, сборки или попадания в логистический сервис.
  Если логистике нужен скан до фактической отгрузки, источник QR/lookup нужно
  переносить на `Заказ покупателя`, сборочный лист или отдельное событие
  готовности.
- SMS должен иметь одного владельца по каждому триггеру. Если готовность и трек
  отправляет `1С`, то `Bitrix24`/сайт не должны дублировать те же сообщения.

## 5. Текущая проблема в 1С

### 5.1. Ранняя РТУ

Сейчас `РТУ` может создаваться до фактической выдачи/отправки. Для сайта это
выглядит как факт отгрузки, и сайт может переводить заказ в `Выполнен`.

Нужно изменить правило:

```text
РТУ = только факт выдачи или передачи в ТК/курьеру
```

### 5.2. Смешанный `осиСтатус`

Текущий `осиСтатус` содержит разные сущности:

- этапы: `Сборка товара`, `Ожидает вывоз`;
- способы доставки: `Самовывоз`, `СДЭК`, `ПОЧТА РОССИИ`, `ДОСТАВИСТА`;
- оплату/коммуникации: `Ждём оплату`, `Ждём ответа`;
- финалы: `Завершен`, `Отменен`.

Нужно перестать использовать `осиСтатус` как новый статус исполнения.

## 7. Справочники и значения

### 7.1. `СтатусИсполнения`

Создать новый справочник/перечисление.

Значения:

- `Новый`;
- `Подтвержден`;
- `На обеспечении`;
- `Сборка`;
- `Готов к выдаче`;
- `Готов к отправке`;
- `Частично выдан`;
- `Выдан`;
- `Отправлен`;
- `Отменен`;
- `Завершен`;
- `Проблема / ручной разбор`.

Правило: способ доставки, вид оплаты и ожидание оплаты не должны быть значениями
этого справочника.

### 7.2. `СпособДоставки`

Создать новый справочник/перечисление.

Минимальные значения:

- `Самовывоз`;
- `СДЭК`;
- `Почта`;
- `Курьер`;
- `Такси`;
- `Другое`.

Raw-значения сайта вроде `СДЭК (Самовывоз)` хранить отдельно в
`СпособДоставкиСайта`.

`СтатусДоставки` можно отложить до Wave 2, если для Wave 1 достаточно
`СпособДоставки`, `ДатаПередачиВТК`, `ТрекНомер` и `СтатусИсполнения`.

### 7.3. `СтатусДоставки`

Создать новый справочник/перечисление.

Минимальные значения:

- `Не отправлено`;
- `Отправлено`;
- `Возврат`;
- `Не выкуп`;
- `Проблема`.

### 7.4. `осиВидыОплат`

Нормализовать справочник без физического удаления старых значений. Сейчас там
есть карты сотрудников и удаленные значения, но старые элементы почти наверняка
имеют ссылки из исторических заказов и документов.

Что сделать:

- не удалять старые элементы и не переписывать историю на первом этапе;
- добавить признак вроде `ИспользуетсяВИнтернетЗаказах` / `Архивный` или
  отдельный справочник соответствий `СтарыйВидОплаты -> НормализованныйВидОплаты`;
- запретить выбор карточных/персональных элементов в новых интернет-заказах;
- в обмене с сайтом писать только нормализованные бизнес-виды;
- старые значения оставить для чтения и отчетности;
- перед любым физическим удалением или пометкой старых элементов отдельно
  проверить ссылки на элементы справочника.

Минимальные бизнес-значения:

- `Онлайн на сайте`;
- `CloudPayments`;
- `Наличные при получении`;
- `Наложенный платеж`;
- `Безналичный расчет`;
- `Другое`.

Карты конкретных сотрудников не должны быть видом оплаты. Если они нужны в
операционном процессе, их надо хранить отдельным реквизитом/справочником
платежных реквизитов, не в виде оплаты.

### 7.5. `осиОплачено`

Нормализовать значения:

- `Не оплачено`;
- `Оплачено / предоплата получена`;
- `Ожидается при получении`;
- `Частично оплачено`;
- `Возврат / сторно`.

Дубли `Да/Нет` и `Оплачено/Не оплачено` убрать из пользовательского сценария
или оставить только как legacy-значения без использования в новых правилах.

## 8. Изменение загрузки заказа с сайта

Доработать обработку свойств `CommerceML`.

### 8.1. Правила маппинга

| Свойство сайта | Текущая проблема | Требуемое поведение |
| --- | --- | --- |
| `Способ доставки` | пишет `осиСпособДоставки` и меняет `осиСтатус` | писать raw в `СпособДоставкиСайта`, нормализовать `СпособДоставки`, `СтатусИсполнения` не менять |
| `Подразделение` | может писать подразделение в способ доставки | писать в подразделение/точку/склад, не в доставку |
| `Адрес доставки` | добавляет `(есть доставка)` в комментарий | писать адрес, комментарий не использовать как флаг |
| `Самовывоз СДЭК` | пишет адрес без отдельной структуры | писать адрес ПВЗ/доставки |
| `Адрес самовывоза` | пишет адрес | писать адрес самовывоза/точку выдачи |
| `Метод оплаты` | может влиять на оплату и косвенно на процесс | писать только `осиВидОплаты`; исполнение не менять |
| `Дата оплаты` | ставит оплачено | писать дату оплаты и статус оплаты |
| `Признак оплаты` | ставит оплачено/не оплачено | менять только статус оплаты |
| `Комментарии клиента` | склеивается с общим комментарием | хранить отдельно; склейка только для отображения |
| `Купон` | пишет купон | оставить |

### 8.2. Начальное заполнение нового интернет-заказа

При создании заказа с сайта:

- `СтатусИсполнения = Новый`;
- `СпособДоставкиСайта = исходное значение сайта`;
- `СпособДоставки = нормализованное значение`;
- `СтатусДоставки = Не отправлено`, если доставка не самовывоз и реквизит уже
  введен;
- `осиОплачено` / нормализованный статус оплаты заполняется только по оплатным
  признакам;
- `осиСтатус` не заполняется способом доставки.

## 9. Команды и переходы статусов

### 9.1. Разрешенные переходы

| Из статуса | В статус | Кто/что переводит |
| --- | --- | --- |
| пусто / новый заказ | `Новый` | автоматическая загрузка с сайта |
| `Новый` | `Подтвержден` | менеджер |
| `Подтвержден` | `На обеспечении` | менеджер/авто при необходимости перемещения/резерва |
| `Подтвержден` / `На обеспечении` | `Сборка` | назначение сборки |
| `Сборка` | `Готов к выдаче` | подтверждение сборки для самовывоза |
| `Сборка` | `Готов к отправке` | подтверждение сборки для доставки |
| `Готов к выдаче` | `Выдан` | факт выдачи + `РТУ` |
| `Готов к отправке` | `Отправлен` | факт передачи в ТК/курьеру + `РТУ` |
| любой рабочий | `Проблема / ручной разбор` | нехватка, пересорт, ошибка перемещения |
| рабочий | `Отменен` | закрытие с причиной |
| `Выдан` / `Отправлен` | `Завершен` | закрытие заказов покупателей |

### 9.2. Автоматически не делать

Не переводить заказ в `Завершен` только по проведению `РТУ`.

Не переводить заказ в `Выдан/Отправлен`, если:

- нет факта выдачи или передачи;
- для `СДЭК` / `Почты` / ТК нет трека и нет подтвержденного исключения
  `ПереданоБезТрека`;
- `РТУ` создана технически для обеспечения.

### 9.3. Сборка без лишнего документа

В `УТ 10.3` не нужно обязательно создавать новый документ `Задание на сборку`,
если в текущей конфигурации его нет или он не используется.

Для Wave 1 достаточно одного из вариантов:

- статус `Сборка` + задача пользователю `1С`;
- существующие события формы/истории вроде `Начата сборка`, `Выставлен
  сборщик`, `Собран`, если они стабильно пишутся;
- простая кнопка/команда на форме заказа, которая переводит заказ в `Сборка` и
  затем в `Готов к выдаче` / `Готов к отправке`.

Важно: сборка не должна требовать предварительного создания `РТУ`. Если для
печати или сканирования нужен документ/лист, его нужно строить от
`Заказа покупателя`, а не от технической реализации.

## 10. Правила создания `РТУ`

### 10.1. Общий инвариант

Для интернет-заказов `РТУ` создается только на основании `Заказа покупателя` и
только по факту выдачи/передачи.

### 10.2. Блокировки

Для заказов с признаком `ЗаказСWEBСайта`:

- запретить или предупреждать с правом руководителя при создании `РТУ` без
  основания `Заказ покупателя`;
- запретить создание `РТУ`, если `СтатусИсполнения` не
  `Готов к выдаче`, `Готов к отправке` или `Частично выдан`;
- запретить проведение `РТУ` доставки без `ДатаПередачиВТК`;
- для `СДЭК`, `Почты` и ТК дополнительно запретить проведение без трека или
  подтвержденного исключения;
- логировать все обходы блокировок.

### 10.3. Самовывоз

При фактической выдаче:

1. Проверить `СпособДоставки = Самовывоз`.
2. Проверить статус `Готов к выдаче` или `Частично выдан`.
3. Создать `РТУ` на основании заказа.
4. Провести `РТУ`.
5. Если выдано полностью: `СтатусИсполнения = Выдан`.
6. Если выдано частично: `СтатусИсполнения = Частично выдан`.
7. Зафиксировать комментарий по остатку: что выдано, что ждем, до какой даты
   держим резерв.

### 10.4. Доставка

При фактической отправке:

1. Проверить `СпособДоставки != Самовывоз`.
2. Проверить статус `Готов к отправке`.
3. Заполнить `ДатаПередачиВТК`.
4. Для `СДЭК`, `Почты` и ТК заполнить `ТрекНомер` или
   `ПереданоБезТрека + ПричинаПередачиБезТрека`.
5. Для `Курьер` / `Такси`, если трека нет, зафиксировать факт передачи и
   понятную причину без трека, например `Курьерская доставка без трека`.
6. Создать `РТУ` на основании заказа.
7. Провести `РТУ`.
8. Поставить `СтатусИсполнения = Отправлен`.
9. Поставить `СтатусДоставки = Отправлено`.

## 11. Обеспечение, резервы и перемещения

До факта `РТУ` заказ обеспечивать штатными механизмами `УТ 10.3`, а не
технической продажей.

Подтвержденные механизмы:

- ручное или автоматическое резервирование на складе через колонку
  `Размещение` в табличной части заказа;
- размещение потребности в заказах поставщикам или внутренних заказах через
  колонку `Размещение`, если этот сценарий используется в текущей базе;
- корректировка схемы резервирования/размещения после проведения заказа
  документом `Резервирование товаров`;
- `Перемещение товаров` только для фактического перемещения между складами,
  когда принято решение физически передать товар;
- задача ответственному не является способом обеспечения, а используется как
  контрольное действие при нехватке, пересорте, ошибке перемещения или
  просрочке.

Примечание: в конфигурации есть объекты `Документ.ВнутреннийЗаказ`,
`Документ.ЗаказПоставщику`, `Документ.РезервированиеТоваров` и
`Документ.ПеремещениеТоваров`. Конкретную механику применения внутренних
заказов для интернет-заказов нужно подтвердить на тестовых сценариях.

Запрещено использовать `РТУ` как инструмент обеспечения.

Если корректируется или удаляется перемещение:

- заказ не должен требовать возврат от клиента, если клиент не получал товар;
- заказ переводится в `На обеспечении` или `Проблема / ручной разбор`;
- создается задача ответственному;
- случай попадает в отчет контроля.

## 12. Задачи в 1С

Создавать задачи в `1С`.

Для Wave 1 обязательный минимум задач:

- подтверждение нового интернет-заказа;
- ручной разбор при нехватке, пересорте, ошибке перемещения или минусе на
  складе `Сайт`.

Задачи по каждому переходу, SLA и эскалациям можно внедрять во Wave 2, если
штатные задачи `1С` окажутся тяжелыми для быстрого запуска. Важно не заводить
параллельные ручные задачи в `Bitrix24` без интеграции, иначе появятся два
контура ответственности.

| Событие | Задача | Завершение |
| --- | --- | --- |
| Новый заказ сайта | `Подтвердить заказ №...` | `Подтвержден` или закрытие с причиной |
| Нехватка/пересорт | `Разобрать наличие по заказу №...` | перемещение, замена, частичная выдача или закрытие |
| Назначена сборка | `Собрать заказ №...` | `Готов к выдаче` / `Готов к отправке` |
| Готов к отправке | `Отправить заказ / получить трек` | `Отправлен` |
| Истек срок хранения | `Снять резерв / закрыть заказ №...` | закрытие или продление |

При просрочке:

- уведомить руководителя/старшего;
- поставить флаг `SLA нарушен`;
- вывести в отчет.

## 13. SMS из 1С

SMS отправлять только по подтвержденным событиям.

Wave 1 может ограничиться SMS готовности самовывоза и SMS с треком для
`СДЭК`/`Почты`. Перед включением нужно проверить, что сайт или `Bitrix24` не
отправляют клиенту тот же текст по тому же событию.

### 13.1. Триггеры

| Событие | Условие | SMS |
| --- | --- | --- |
| `Готов к выдаче` | еще не отправляли SMS готовности | заказ готов, адрес, срок хранения |
| `Отправлен` | есть трек или подтвержденная передача | заказ отправлен, трек |
| `Отменен` | уведомление уместно | заказ отменен, причина |

### 13.2. Антидубли

Использовать отдельные флаги:

- `SMSГотовностьОтправлено`;
- `SMSГотовностьДата`;
- `SMSTрекОтправлено`;
- `SMSTрекДата`;
- `SMSОшибка`.

Не использовать один общий флаг SMS для всех типов сообщений, если нужно
различать готовность и отправку.

## 14. Закрытие заказов

Автоматическое пакетное закрытие и снятие резервов - Wave 2. В Wave 1
достаточно не создавать раннюю `РТУ` и иметь отчет `Отгружено 100%, но заказ не
закрыт старше N дней`, чтобы не сломать взаиморасчеты и ручные исключения.

### 14.1. Успешное закрытие

Регламентно формировать `Закрытие заказов покупателей` по отбору:

- заказ отгружен/выдан полностью;
- нет резервов и размещений;
- нет флага `НеЗакрыватьАвтоматически`;
- причина закрытия: `Успешно выполнен`.

Дебиторская задолженность сама по себе не блокирует закрытие, если
взаиморасчеты ведутся по договору.

### 14.2. Снятие резервов

Регламентно формировать `Закрытие заказов покупателей` с видом операции
`Снятие резервов и размещения` по просроченным резервам.

После снятия резерва:

- заказ переводится в ручной разбор или закрывается с причиной;
- ответственному создается задача.

## 15. Обратная выгрузка из 1С

Подготовка безопасных реквизитов нужна уже в `1С`, но включение отображения на
сайте относится к отдельной волне после стабилизации Wave 1.

Подготовить безопасные реквизиты для обратной выгрузки:

| Реквизит обмена | Источник |
| --- | --- |
| `СтатусИсполнения1С` | `СтатусИсполнения` |
| `СпособДоставки1С` | `СпособДоставки` |
| `СтатусДоставки1С` | `СтатусДоставки` |
| `ТрекНомер` | `ТрекНомер` / `осиТрекНомер` |
| `ДатаПередачиВТК` | `ДатаПередачиВТК` |
| `СрокХраненияДо` | `СрокХраненияДо` |

До завершения исправления процесса не считать `Номер отгрузки по 1С` и
`Дата отгрузки по 1С` достаточным клиентским фактом выполнения.

## 16. Контрольные отчеты

Сделать отчеты:

- `РТУ не на основании заказа`;
- `РТУ по интернет-заказу до факта выдачи/передачи`;
- `Интернет-заказы, где способ доставки записан в legacy осиСтатус`;
- `Доставки СДЭК/Почта/ТК Отправлен без трека и без исключения`;
- `Заказы с корректировкой/удалением перемещения и минусом на складе Сайт`;
- `Заказы в Проблема / ручной разбор`;
- `Просроченные задачи`;
- `Резервы и размещения старше N дней`;
- `Отгружено 100%, но заказ не закрыт старше N дней`;
- `Закрытие заказов покупателей: причины закрытия`.

## 17. Права и роли

Отдельно настроить права:

- кто подтверждает заказ;
- кто назначает сборку;
- кто переводит в готовность;
- кто может создать `РТУ`;
- кто может сделать исключение `ПереданоБезТрека`;
- кто может аварийно снять блокировку `РТУ` с обязательной причиной, без
  клиентского статуса `Выдан/Отправлен`;
- кто продлевает резерв;
- кто закрывает заказ.

Все исключения должны логироваться с пользователем, датой и причиной.

## 18. Приемочные сценарии

### 18.1. Самовывоз

1. Сайт создает заказ с `Самовывоз`.
2. В заказе `СтатусИсполнения = Новый`.
3. `СпособДоставки = Самовывоз`.
4. `осиСтатус` не получает значение `Самовывоз`.
5. До фактической выдачи `РТУ` не создается.
6. При выдаче создается `РТУ` на основании заказа.
7. Статус становится `Выдан`.

### 18.2. СДЭК с треком

1. Заказ загружен с raw-значением `СДЭК (Самовывоз)`.
2. `СпособДоставкиСайта = СДЭК (Самовывоз)`.
3. `СпособДоставки = СДЭК`.
4. Оплата меняет только статус оплаты.
5. После сборки статус `Готов к отправке`.
6. Без трека и даты передачи `РТУ` не проводится.
7. После заполнения трека и даты создается `РТУ`.
8. Статус становится `Отправлен`.

### 18.3. Доставка без трека

1. Пользователь пытается отправить заказ `СДЭК` / `Почта` / ТК без трека.
2. Система блокирует действие.
3. Пользователь с правом включает `ПереданоБезТрека`.
4. Заполняет причину.
5. Заказ отправляется.
6. Случай попадает в отчет.

### 18.4. Курьер или такси без трека

1. Заказ имеет `СпособДоставки = Курьер` или `Такси`.
2. Заказ в статусе `Готов к отправке`.
3. Пользователь фиксирует `ДатаПередачиВТК` и факт передачи курьеру.
4. `ТрекНомер` не обязателен.
5. Создается `РТУ` на основании заказа.
6. Статус становится `Отправлен`.

### 18.5. Корректировка перемещения

1. Есть заказ, обеспеченный перемещением.
2. Перемещение корректируется до выдачи.
3. Система не требует возврат от клиента.
4. Заказ переводится в `На обеспечении` или `Проблема / ручной разбор`.
5. Создается задача ответственному.
6. Нет отрицательного остатка на складе `Сайт`, вызванного технической цепочкой.

### 18.6. Частичная выдача самовывоза

1. По заказу доступна только часть товара.
2. Пользователь оформляет частичную выдачу.
3. Создается `РТУ` только на фактически выдаваемую часть.
4. Статус `Частично выдан`.
5. В комментарии/реквизитах указано, что осталось и до какой даты держать
   резерв.
6. Следующая выдача оформляется отдельным фактом.

## 19. Definition of Done

### 19.1. DoD Wave 1

Первая волна считается выполненной, если:

- минимальные реквизиты из раздела 6.3 добавлены или переиспользованы безопасно;
- загрузка `Способ доставки` больше не меняет `осиСтатус`;
- оплата не меняет `СтатусИсполнения`;
- `РТУ` интернет-заказа невозможно штатно провести до факта выдачи/отправки;
- доставка `СДЭК` / `Почта` / ТК не переводится в `Отправлен` без трека или
  подтвержденного исключения;
- курьер/такси могут отправляться без трека только с зафиксированным фактом
  передачи;
- минимальные контрольные отчеты доступны;
- приемочные сценарии 18.1-18.6 пройдены на тестовой базе;
- пилот на 10-20 заказах не создает новых отрицательных остатков на складе
  `Сайт` из-за старой технической цепочки.

### 19.2. DoD полного To-Be

Полная доработка считается выполненной, если дополнительно:

- задачи создаются по ключевым событиям;
- SMS имеют отдельные антидубли;
- регламент закрытия и снятия резервов настроен или описан для запуска;
- расширенные отчеты доступны;
- сайт и/или внешний backend принимают безопасные статусы без зависимости от
  ранней `РТУ`;
- смежный логистический контур не требует создания `РТУ` до фактической
  выдачи/передачи.
