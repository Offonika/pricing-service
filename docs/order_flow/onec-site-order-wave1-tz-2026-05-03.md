# ТЗ Wave 1 для 1С: интернет-заказы без ранней РТУ

Дата: `2026-05-03`  
Статус: `approved for Wave 1 development`  
Система: `1С УТ 10.3`  
Контур: `Заказ покупателя -> обеспечение -> сборка -> факт выдачи/отправки -> РТУ`  
Заказчик согласования: руководство / владелец процесса интернет-заказов  

## 1. Цель Wave 1

Стабилизировать исполнение интернет-заказов в `1С УТ 10.3` без полной
перестройки всех смежных контуров.

Главная цель Wave 1:

```text
РТУ = только факт выдачи клиенту или передачи в ТК/курьеру
```

Wave 1 должна убрать первопричину текущих костылей:

- ранние / технические `РТУ`;
- смешение доставки, оплаты и этапа исполнения в `осиСтатус`;
- минусы на складе `Сайт` после корректировок перемещений;
- ручные возвраты от клиента, когда клиент фактически товар не получал;
- ложный статус `Выполнен` на сайте из-за преждевременной `РТУ`.

## 2. Что согласовываем этим документом

На согласование выносится только первая волна 1С-доработки.

Утверждаем:

- минимальный набор реквизитов заказа;
- правила загрузки интернет-заказа из сайта;
- правила статусов исполнения;
- запрет / контроль ранней `РТУ`;
- правила фактической выдачи и отправки;
- минимальные отчеты контроля;
- приемочные сценарии для тестовой базы.

Не утверждаем в этом документе:

- полную автоматизацию задач по всем SLA;
- клиентские статусы на сайте;
- движение сделок `Bitrix24`;
- полную SMS-автоматизацию;
- регламентное автозакрытие заказов;
- перестройку внешнего логистического сервиса / Telegram-бота;
- полный новый процесс розницы.

## 3. Границы Wave 1

### 3.1. Входит

- Доработка `Документ.ЗаказПокупателя` для интернет-заказов.
- Доработка формы заказа, если нужна кнопка/команда смены статуса.
- Доработка загрузки свойств сайта через `CommerceML`.
- Нормализация использования `осиСтатус`, `осиВидОплаты`, `осиОплачено`.
- Ограничение создания / проведения `РТУ` по интернет-заказам.
- Минимальная фиксация факта передачи в доставку.
- Минимальные контрольные отчеты.

### 3.2. Не входит

- Физическое удаление старых значений справочников.
- Переписывание исторических заказов.
- Замена всего обмена с сайтом.
- Доработка сайта Bitrix.
- Доработка сделок `Bitrix24`.
- Полная логистика QR/Telegram.
- Автоматическое закрытие заказов по расписанию.
- Полная ролевая модель исключений.

## 4. Обязательные принципы

- `1С` остается источником истины по заказу, остаткам, резервам, перемещениям и
  `РТУ`.
- Каждый интернет-заказ начинается с `Заказа покупателя`.
- `РТУ` создается только на основании заказа и только по факту.
- До факта `РТУ` заказ обеспечивается резервом, размещением, внутренним
  заказом / заказом поставщику или фактическим перемещением.
- `Перемещение товаров` не заменяет продажу и не должно создавать необходимость
  возврата от клиента, если клиент товар не получал.
- `осиСтатус` больше не используется как чистый статус исполнения.
- Оплата не меняет этап исполнения.
- Способ доставки не меняет этап исполнения.
- Сайт и `Bitrix24` не двигаются по сырой ранней `РТУ`.

## 5. Минимальные реквизиты Wave 1

### 5.1. Обязательные реквизиты

| Реквизит | Тип | Решение для Wave 1 |
| --- | --- | --- |
| `СтатусИсполнения` | справочник | новый чистый этап заказа, значения с фиксированными кодами |
| `СпособДоставки` | справочник | нормализованный способ доставки, значения с фиксированными кодами |
| `осиСпособДоставки` | строка, представление в форме `Способ доставки с сайта` | raw-значение сайта |
| `ДатаПередачиВТК` | дата-время | факт передачи в ТК/курьеру |
| `осиТрекНомер` | строка, представление в форме `Трек-номер` | трек для `СДЭК` / `Почты` / ТК |

### 5.2. Аварийное исключение без трека

Штатная отправка `СДЭК` / `Почта` / ТК без трека в Wave 1 запрещена.

Если руководитель аварийно снимает блокировку `РТУ`, система должна записать
причину и пользователя. Технически это можно реализовать отдельными
реквизитами:

| Реквизит | Тип | Правило |
| --- | --- | --- |
| `ПереданоБезТрека` | булево | только для аварийного снятия блокировки ограниченной ролью |
| `ПричинаПередачиБезТрека` | строка | обязательна при аварийном снятии блокировки |

Эти реквизиты не должны превращаться в обычный сценарий отправки без трека.

### 5.3. Существующие реквизиты, которые не удаляем

| Реквизит | Решение |
| --- | --- |
| `осиСтатус` | оставить для совместимости, не использовать как новый статус исполнения |
| `осиВидОплаты` | оставить; нормализовать выбор для новых заказов без удаления старых значений |
| `осиОплачено` | оставить; использовать как нормализованный статус оплаты |
| `осиТрекНомер` | использовать как `ТрекНомер`; если тест покажет нестабильность, добавить отдельный строковый `ТрекНомер` как техническую корректировку |
| `осиСпособДоставки` | использовать как raw `Способ доставки с сайта` |

## 6. Значения справочников

### 6.1. `СтатусИсполнения`

Минимальный список Wave 1:

- `Новый`;
- `Подтвержден`;
- `На обеспечении`;
- `Сборка`;
- `Готов к выдаче`;
- `Готов к отправке`;
- `Частично выдан`;
- `Выдан`;
- `Отправлен`;
- `Отменен`;
- `Проблема / ручной разбор`.

`Завершен` можно оставить для будущей волны закрытия заказов, но Wave 1 не
должна автоматически ставить его по факту `РТУ`.

### 6.2. `СпособДоставки`

Минимальные значения:

- `Самовывоз`;
- `СДЭК`;
- `Почта`;
- `Курьер`;
- `Такси`;
- `Другое`.

Raw-значения сайта вроде `СДЭК (Самовывоз)` не писать в статус исполнения.
Их нужно хранить в `осиСпособДоставки` с представлением в форме
`Способ доставки с сайта`.

### 6.3. Оплата

`осиВидыОплат` не удалять и не чистить физически.

Для новых интернет-заказов разрешить только бизнес-виды оплаты:

- `Онлайн на сайте`;
- `CloudPayments`;
- `Наличные при получении`;
- `Наложенный платеж`;
- `Безналичный расчет`;
- `Другое`.

Карты сотрудников, старые удаленные значения и персональные реквизиты не должны
выбираться в новых интернет-заказах как вид оплаты. Их можно оставить для
истории и отчетности.

## 7. Загрузка заказа с сайта

При создании нового интернет-заказа:

- `СтатусИсполнения = Новый`;
- `осиСпособДоставки` / `Способ доставки с сайта` = исходное значение сайта;
- `СпособДоставки = нормализованное значение`;
- `осиОплачено` меняется только по признакам оплаты;
- `осиСтатус` не заполняется способом доставки, ожиданием оплаты или методом
  коммуникации.

Минимальный маппинг:

| Свойство сайта | Требуемое поведение |
| --- | --- |
| `Способ доставки` | писать raw в `осиСпособДоставки` / `Способ доставки с сайта`, нормализовать `СпособДоставки`, не менять `СтатусИсполнения` |
| `Метод оплаты` | писать в `осиВидОплаты`, не менять `СтатусИсполнения` |
| `Признак оплаты` / `Дата оплаты` | менять только `осиОплачено` / дату оплаты |
| `Адрес доставки` / `Адрес самовывоза` | писать в адресные поля, не использовать комментарий как управляющий флаг |
| `Комментарии клиента` | хранить как комментарий клиента, не как управляющий признак |

## 8. Сборка

Согласованное решение для Wave 1: не создавать новый отдельный документ
`Задание на сборку`, если его нет в текущей конфигурации и он не используется
операционно.

Сборку нужно перевести на `Заказ покупателя` как основание.

Повторная проверка после добавления артефакта:
`/opt/MM/mm-compensation/docs/Структура 1с/ТЗП_Новый.epf` распакован и
проанализирован. Это реальное рабочее место `ТЗП`.

Подтвержденная As-Is логика `ТЗП`:

- основная форма показывает `Реализации для сборки`;
- отдельный блок показывает `Открытые заказы` без связанной `РТУ`;
- в форме заказов по заказу без `РТУ` показывается действие
  `Создать реализацию`;
- при выборе действия обработка проверяет остаток на складе подразделения,
  делит позиции на `Наличие` и `Отсутствие`;
- форма `ФормаР` создает `Документ.РеализацияТоваровУслуг`, заполняет
  `Сделка = Заказ`, строки товаров и сразу пытается провести `РТУ`;
- после создания `РТУ` открывается форма проверки/сборки реализации;
- форма оплаты и завершения также работает от `РеализацияТоваровУслуг`.

Подробный анализ зафиксирован в
`docs/order_flow/artifacts/site-order-exchange-2026-05-03/tzp_new_epf_analysis_2026-05-03.md`.

Это означает: `ТЗП` является отдельной точкой обхода нового процесса. Если его
не доработать, ранние `РТУ` сохранятся даже после исправления формы заказа.

Минимальная механика:

- статус `Сборка` + ответственный/сборщик в заказе или форме заказа;
- существующие события формы/истории: `Начата сборка`, `Выставлен сборщик`,
  `Собран`, если они стабильно пишутся;
- кнопка/команда на форме заказа: `В сборку`, `Готов к выдаче`,
  `Готов к отправке`.

Минимальная доработка `ТЗП` для Wave 1:

- очередь сборки строить от `ЗаказПокупателя`, а не от предварительной `РТУ`;
- действие `Создать реализацию` в `ТЗП` заменить на действие сборки/готовности;
- запретить штатное создание и проведение `РТУ` из `ФормаР` на этапе сборки;
- отсутствующие позиции переводить в потребность/ручной разбор без частичной
  ранней `РТУ`;
- создание `РТУ` оставить только для фактического действия `Выдать клиенту` или
  `Передано в доставку`.

Задачу пользователю `1С` в Wave 1 создавать только для исключений и ручного
разбора, а не для каждой обычной сборки.

Лист сборки, печать, QR или список позиций для сборщика должны строиться от
`Заказа покупателя` и его табличной части.

Важно: сборка не должна требовать предварительной `РТУ`. `РТУ` появляется
только после сборки и только в момент фактической выдачи клиенту или передачи в
ТК/курьеру.

Отдельный документ `Задание на сборку` можно рассматривать в Wave 2, если после
пилота станет понятно, что статуса/задачи/событий формы недостаточно.

## 9. Правила РТУ

### 9.1. Общий запрет

Для интернет-заказов запрещено использовать `РТУ` для:

- фиксации наличия;
- запуска перемещения;
- технической передачи на склад `Сайт`;
- печати/сборки до факта;
- преждевременного статуса сайта `Выполнен`.

### 9.2. Самовывоз

`РТУ` создается только когда клиент фактически пришел и товар выдается.

Условия:

- `СпособДоставки = Самовывоз`;
- `СтатусИсполнения = Готов к выдаче` или `Частично выдан`;
- `РТУ` создается на основании `Заказа покупателя`;
- если выдано полностью: `СтатусИсполнения = Выдан`;
- если выдана часть: `СтатусИсполнения = Частично выдан`.

### 9.3. Доставка СДЭК / Почта / ТК

`РТУ` создается только при фактической передаче в ТК.

Условия:

- `СпособДоставки = СДЭК` / `Почта` / `Другое ТК`;
- `СтатусИсполнения = Готов к отправке`;
- заполнена `ДатаПередачиВТК`;
- заполнен `осиТрекНомер` / `Трек-номер`;
- отправка без трека не является штатным сценарием; аварийное снятие блокировки
  возможно только ограниченной ролью с обязательной причиной и попаданием в
  отчет;
- после проведения `РТУ`: `СтатусИсполнения = Отправлен`.

### 9.4. Курьер / Такси

Трек не обязателен, но факт передачи обязателен.

Условия:

- `СпособДоставки = Курьер` или `Такси`;
- `СтатусИсполнения = Готов к отправке`;
- заполнена `ДатаПередачиВТК` или аналогичный факт передачи курьеру;
- зафиксирована понятная причина отсутствия трека, например
  `Курьерская доставка без трека`;
- после проведения `РТУ`: `СтатусИсполнения = Отправлен`.

### 9.5. Исключения

Если руководителю нужно аварийно снять блокировку `РТУ`, система должна
записать:

- пользователя;
- дату/время;
- причину;
- заказ;
- созданную `РТУ`.

Аварийная `РТУ` не должна автоматически давать клиентский статус
`Выдан/Отправлен`, если нет факта выдачи/передачи.

## 10. Обеспечение до факта РТУ

До фактической `РТУ` использовать штатные механизмы `УТ 10.3`:

- резерв на фактическом складе через колонку `Размещение`;
- размещение потребности в заказах поставщикам / внутренних заказах, если этот
  сценарий используется в текущей базе;
- корректировка резервов и размещений документом `Резервирование товаров`;
- `Перемещение товаров` только как факт физического перемещения между складами.

Запрещено использовать раннюю `РТУ` как способ обеспечения.

Если перемещение корректируется или удаляется до выдачи:

- не создавать возврат от клиента, если клиент товар не получал;
- перевести заказ в `На обеспечении` или `Проблема / ручной разбор`;
- поставить задачу ответственному или включить заказ в отчет ручного разбора;
- проверить, что не появился минус на складе `Сайт`.

## 11. Минимальные отчеты Wave 1

Сделать или подготовить как минимум:

- `РТУ по интернет-заказу до факта выдачи/передачи`;
- `РТУ не на основании Заказа покупателя`;
- `Интернет-заказы, где способ доставки записан в осиСтатус`;
- `СДЭК/Почта/ТК Отправлен без трека и без исключения`;
- `Заказы с корректировкой/удалением перемещения и минусом на складе Сайт`;
- `Заказы в Проблема / ручной разбор`.

## 12. Приемочные сценарии

### 12.0. Сборка без РТУ

1. Сайт создает `Заказ покупателя`.
2. Пользователь переводит заказ в `Сборка`.
3. Лист сборки / рабочее место / `ТЗП` получает позиции из
   `Заказа покупателя`, а не из `РТУ`.
4. Действие `Создать реализацию` в `ТЗП` недоступно на этапе сборки.
5. До фактической выдачи или передачи в доставку `РТУ` не создается и не
   проводится.
6. После сборки заказ переводится в `Готов к выдаче` или `Готов к отправке`.

### 12.1. Самовывоз

1. Сайт создает заказ `Самовывоз`.
2. В заказе `СтатусИсполнения = Новый`.
3. `СпособДоставки = Самовывоз`.
4. `осиСтатус` не получает значение `Самовывоз`.
5. До фактической выдачи `РТУ` не создается.
6. При выдаче создается `РТУ` на основании заказа.
7. Статус становится `Выдан`.

### 12.2. СДЭК с треком

1. Заказ загружен с raw-значением `СДЭК (Самовывоз)`.
2. `осиСпособДоставки` / `Способ доставки с сайта` = `СДЭК (Самовывоз)`.
3. `СпособДоставки = СДЭК`.
4. Оплата меняет только оплатный признак.
5. После сборки статус `Готов к отправке`.
6. Без трека и даты передачи `РТУ` не проводится.
7. После заполнения трека и даты создается `РТУ`.
8. Статус становится `Отправлен`.

### 12.3. Курьер / Такси без трека

1. Заказ имеет `СпособДоставки = Курьер` или `Такси`.
2. Заказ в статусе `Готов к отправке`.
3. Пользователь фиксирует факт передачи курьеру.
4. `осиТрекНомер` / `Трек-номер` не обязателен.
5. Создается `РТУ` на основании заказа.
6. Статус становится `Отправлен`.

### 12.4. Корректировка перемещения

1. Есть заказ, обеспеченный перемещением.
2. Перемещение корректируется до выдачи.
3. Система не требует возврат от клиента.
4. Заказ переводится в `На обеспечении` или `Проблема / ручной разбор`.
5. Нет отрицательного остатка на складе `Сайт`, вызванного технической цепочкой.

### 12.5. Частичная выдача самовывоза

1. По заказу доступна только часть товара.
2. Пользователь оформляет частичную выдачу.
3. Создается `РТУ` только на фактически выдаваемую часть.
4. Статус `Частично выдан`.
5. Остаток по заказу остается в обеспечении или ручном разборе.

## 13. Definition of Done Wave 1

Wave 1 считается выполненной, если:

- минимальные реквизиты добавлены или безопасно переиспользованы;
- загрузка `Способ доставки` больше не меняет `осиСтатус`;
- оплата не меняет `СтатусИсполнения`;
- сборка, лист сборки, QR и `ТЗП` работают от `Заказа покупателя`, а не от
  предварительной `РТУ`;
- в `ТЗП` отключено/заменено штатное создание и проведение `РТУ` на этапе
  сборки;
- `РТУ` интернет-заказа невозможно штатно провести до факта выдачи/отправки;
- `СДЭК` / `Почта` / ТК штатно не переводятся в `Отправлен` без трека;
- все аварийные снятия блокировки `РТУ` без трека фиксируются с причиной,
  пользователем и попадают в отчет;
- `Курьер` / `Такси` могут отправляться без трека только с зафиксированным
  фактом передачи;
- минимальные контрольные отчеты доступны;
- приемочные сценарии 12.0-12.5 пройдены на тестовой базе;
- пилот на 10-20 интернет-заказах не создает новых отрицательных остатков на
  складе `Сайт` из-за старой технической цепочки.

## 14. Согласованные решения

Решения согласованы `2026-05-03`.

| Вопрос | Согласованное решение |
| --- | --- |
| `СтатусИсполнения` и `СпособДоставки` | делать справочниками с фиксированными кодами |
| Raw-доставка с сайта | использовать текущий `осиСпособДоставки` как `Способ доставки с сайта`; добавить новый нормализованный `СпособДоставки` |
| `СДЭК` / `Почта` / ТК без трека | штатно запретить в Wave 1; аварийное исключение только через ограниченную роль и отчет |
| Кто может снять блокировку `РТУ` | ограниченная роль: руководитель онлайн/ответственный за интернет-заказы, старший склада/остатков, администратор 1С только для технических аварий |
| Факт передачи для `Курьер` / `Такси` | только физическая передача пакета курьеру/такси, не вызов машины |
| Задачи в `1С` | в Wave 1 задачи только на исключения; обычная очередь через отчет/список по статусам |
| Тестовый набор | 15 заказов на копии базы, затем 10-20 живых заказов в контролируемый пилот |
| Сборка / `ТЗП` | не создавать отдельный документ `Задание на сборку` в Wave 1; доработать `ТЗП`: очередь сборки, лист сборки и QR должны работать от `Заказа покупателя`, а действие раннего создания/проведения `РТУ` из `ТЗП` должно быть отключено или заменено на фиксацию готовности заказа |

Ниже оставлены варианты и обоснование выбранных решений для разработчика и
будущего аудита.

### 14.1. Статусы и способы доставки: справочники или перечисления

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| Перечисления | проще код, значения жестко фиксированы | любое изменение списка требует изменения конфигурации; сложнее хранить признак активности, порядок, алиасы сайта |
| Справочники | можно добавлять/архивировать значения без изменения конфигурации; можно хранить код, порядок, активность, алиасы | нужна дисциплина прав, чтобы пользователи не плодили значения |

Рекомендация: делать `СтатусИсполнения` и `СпособДоставки` справочниками с
фиксированными кодами и закрыть редактирование для обычных пользователей.

Причина: в текущей базе уже есть кастомные справочники `осиСтатус`,
`осиВидыОплат`, `осиОплачено`; для доставки почти наверняка понадобятся алиасы
сайта и архивирование старых значений.

### 14.2. Raw-доставка с сайта

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| Использовать текущий `осиСпособДоставки` как raw-поле | меньше доработок обмена, поле уже найдено и заполняется | название поля неидеальное, нужна ясная подпись в форме |
| Добавить новый `СпособДоставкиСайта` | чище модель | больше изменений в обмене и формах; риск дублирования с текущим полем |

Рекомендация: в Wave 1 использовать текущий `осиСпособДоставки` как
`Способ доставки с сайта` и добавить новый нормализованный `СпособДоставки`.
В форме можно переименовать представление поля, не ломая хранение и обмен.

### 14.3. СДЭК / Почта / ТК без трека

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| Полный запрет без трека | максимальная дисциплина, меньше ложных отправок | редкие реальные исключения придется разбирать вручную |
| Разрешить исключение по роли | гибкость для редких случаев | высокий риск, что исключение станет новым обходным процессом |

Рекомендация: для Wave 1 ввести полный запрет штатной отправки `СДЭК` /
`Почта` / ТК без трека.

Аварийное исключение допустимо только как снятие блокировки руководителем с
обязательной причиной и попаданием в ежедневный отчет. Такое исключение не
должно автоматически давать клиентский статус `Отправлен`, если нет
подтвержденного факта передачи.

### 14.4. Кто может аварийно снять блокировку РТУ

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| Любой менеджер | быстро | почти гарантированно вернет старую практику ранних `РТУ` |
| Руководитель / старший ответственный | контроль и персональная ответственность | иногда придется ждать ответственного |
| Только администратор 1С | жестко | слишком медленно для операционных исключений |

Рекомендация: право дать только ограниченной роли:

- руководитель онлайн-магазина / ответственный за интернет-заказы;
- старший склада или ответственный за остатки как резервная роль;
- администратор 1С только для технических аварий, не как операционный обход.

Любое снятие блокировки должно писать пользователя, дату/время, причину, заказ
и номер `РТУ`, а также попадать в отчет.

### 14.5. Факт передачи для Курьер / Такси

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| Считать фактом вызов курьера/такси | просто | риск ранней `РТУ`: курьер еще не забрал товар |
| Считать фактом физическую передачу пакета | соответствует принципу `РТУ = факт` | нужно заполнить минимум данных |

Рекомендация: фактом считать только физическую передачу пакета курьеру/такси.

Минимальная фиксация:

- `ДатаПередачиВТК` / дата-время передачи;
- способ доставки `Курьер` или `Такси`;
- служба / водитель / телефон / номер заказа такси, если доступно;
- ответственный пользователь;
- комментарий `Курьерская доставка без трека`.

Вызов курьера, создание заявки или ожидание машины фактом передачи не являются.

### 14.6. Задача в 1С или отчет ручного разбора

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| Создавать задачу на каждый новый заказ | дисциплина | много шума, риск перегрузить пользователей |
| Только отчеты | быстро внедрить | слабее персональная ответственность |
| Задачи только на исключения + отчет по очереди | баланс скорости и контроля | нужна договоренность, кто смотрит отчет |

Рекомендация: для Wave 1 делать задачи только на исключения:

- `Проблема / ручной разбор`;
- нехватка / пересорт;
- ошибка или корректировка перемещения;
- минус на складе `Сайт`.

Новые заказы и обычную сборку контролировать отчетом/списком заказов по
`СтатусИсполнения`. Полный SLA-задачник оставить на Wave 2.

### 14.7. Тестовый набор для пилота

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| 10 заказов | быстрее пройти | можно не поймать редкие сценарии |
| 15 заказов | баланс скорости и покрытия | чуть больше ручной проверки |
| 20 заказов | лучше покрытие | дольше согласовывать и проводить |

Рекомендация: взять 15 заказов на копии базы, затем 10-20 живых заказов в
контролируемый пилот.

Состав теста на копии:

- 3 самовывоза, где товар уже есть на нужном складе;
- 2 самовывоза с обеспечением через перемещение;
- 3 доставки `СДЭК` / `Почта` с треком;
- 1 доставка `СДЭК` / `Почта` без трека, чтобы проверить блокировку;
- 2 доставки `Курьер` / `Такси` без трека, но с фактом передачи;
- 2 заказа с корректировкой / удалением перемещения до выдачи;
- 1 частичная выдача самовывоза;
- 1 проблемный заказ вроде `211793` как регрессионный кейс.

Критерий успешного пилота: ни один тестовый заказ не создает новую раннюю
`РТУ`, ложный статус `Отправлен/Выдан` или отрицательный остаток на складе
`Сайт` из-за старой технической цепочки.
