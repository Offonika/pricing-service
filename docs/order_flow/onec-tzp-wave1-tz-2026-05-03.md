# ТЗ Wave 1: доработка внешней обработки ТЗП

Дата: `2026-05-03`  
Статус: `reviewed for developer estimate`  
Система: `1С УТ 10.3`  
Артефакт: `ТЗП_Новый.epf`  
Связанный контур: `Заказ покупателя -> сборка -> готовность -> факт выдачи/отправки -> РТУ`

## 1. Цель

Доработать рабочее место `ТЗП` так, чтобы сборка интернет-заказов больше не
создавала раннюю `РТУ`.

Главное правило:

```text
ТЗП собирает заказ по Заказу покупателя.
РТУ создается только по факту выдачи клиенту или передачи в доставку.
```

## 3. Подтвержденная проблема As-Is

Текущая обработка `ТЗП` завязана на `РеализацияТоваровУслуг`.

Подтвержденная цепочка:

1. `ТЗП` показывает `Открытые заказы`.
2. Если по заказу нет `РТУ`, в форме заказов доступно действие
   `Создать реализацию`.
3. `ФормаР` проверяет остатки по складу подразделения.
4. По позициям в наличии создается `Документ.РеализацияТоваровУслуг`.
5. В `РТУ` ставится `Сделка = Заказ`.
6. `РТУ` сразу записывается и проводится.
7. Проверка/сканирование/оплата дальше работают от `РТУ`.

Это нарушает To-Be процесс: `РТУ` появляется до фактической выдачи или передачи
в доставку.

## 4. Границы доработки

### 4.1. Входит

- Доработка внешней обработки `ТЗП`.
- Перевод очереди сборки интернет-заказов на `ЗаказПокупателя`.
- Блокировка штатного создания и проведения `РТУ` на этапе сборки.
- Фиксация статусов сборки и готовности в `ЗаказПокупателя`.
- Минимальная поддержка старых уже созданных `РТУ` на переходный период.
- Приемочные проверки на тестовой базе.

### 4.2. Не входит

- Создание нового документа `Задание на сборку`.
- Полная перестройка оплаты.
- Доработка сайта Bitrix.
- Доработка сделок `Bitrix24`.
- Автоматическое закрытие заказов.
- Массовая перепись исторических документов.

## 5. To-Be логика ТЗП

### 5.1. Основной источник сборки

Для новых интернет-заказов источник сборки в `ТЗП`:

- `Документ.ЗаказПокупателя`;
- табличная часть `Товары`;
- склад/подразделение заказа;
- новый реквизит заказа `СтатусИсполнения`;
- нормализованный `СпособДоставки`.

`РеализацияТоваровУслуг` не должна быть источником обычной сборки нового
интернет-заказа.

### 5.2. Как определять интернет-заказ

Новая логика `ТЗП` должна применяться только к интернет-заказам. Обычные
операционные сценарии, если они используют `ТЗП`, не должны быть сломаны.

Критерий интернет-заказа должен опираться на уже существующие признаки загрузки
с сайта. Приоритет признаков:

- заказ создан обменом с сайтом / имеет внешний номер заказа сайта;
- `Подразделение = Онлайн-магазин`;
- `Склад/группа = Сайт`;
- raw-значение доставки заполнено из сайта в `осиСпособДоставки`;
- ответственный/группа ответственных относится к контуру `Сайт`, если этот
  признак сейчас используется в `ТЗП`.

Точный набор условий разработчик должен сверить на тестовой базе, но правило
для Wave 1 такое: новый запрет ранней `РТУ` обязателен для интернет-заказов и
не должен случайно блокировать несвязанные с сайтом операции.

### 5.3. Очереди в рабочем месте

Минимальные очереди:

| Очередь | Источник | Назначение |
| --- | --- | --- |
| `Новые / к подтверждению` | `ЗаказПокупателя` | заказы со статусом `Новый` / `Подтвержден` |
| `Сборка` | `ЗаказПокупателя` | заказы со статусом `Сборка` |
| `Готов к выдаче` | `ЗаказПокупателя` | самовывоз после сборки |
| `Готов к отправке` | `ЗаказПокупателя` | доставка после сборки |
| `Проблема / ручной разбор` | `ЗаказПокупателя` | нехватка, пересорт, ошибка перемещения |
| `Legacy РТУ` | `РеализацияТоваровУслуг` | старые реализации, созданные до запуска Wave 1 |

`Legacy РТУ` нужен только для переходного периода, чтобы не потерять уже
начатые старые операции. Для новых заказов после даты запуска ранняя `РТУ` из
`ТЗП` запрещена.

### 5.4. Настройка даты запуска

В доработке должна быть явно задана дата/время запуска новой логики
`ТЗП`.

Требование:

- не хардкодить дату в нескольких местах формы;
- использовать одну настройку/константу/служебный реквизит обработки;
- документы до даты запуска можно показывать как `Legacy РТУ`;
- документы после даты запуска должны идти по новой схеме от
  `ЗаказПокупателя`.

## 6. Требования по формам обработки

### 6.1. Основная форма `Форма`

Изменить логику выборок:

- очередь сборки для новых интернет-заказов строить по `ЗаказПокупателя`;
- не требовать наличия `РТУ` для появления заказа в сборке;
- старую очередь `Реализации для сборки` оставить только как переходную
  `Legacy РТУ`, если это нужно операционно;
- визуально разделить новые заказы и старые `РТУ`, чтобы пользователь не
  путал процессы.

Новые `РТУ`, созданные после даты запуска без факта выдачи/передачи, не должны
попадать в обычную очередь сборки как нормальный сценарий. Такие документы
должны попадать в контрольный отчет ранних `РТУ`.

Для нового процесса действия должны менять `СтатусИсполнения` заказа:

- `В сборку`;
- `Готов к выдаче`;
- `Готов к отправке`;
- `Проблема / ручной разбор`.

### 6.2. Форма заказов `ФормаЗаказов`

Текущее действие `Создать реализацию` по заказу без `РТУ` заменить.

Вместо него:

- `В сборку`, если заказ еще не в сборке;
- `Проверить наличие`, если нужно разложить позиции на наличие/отсутствие;
- `Готов к выдаче` для самовывоза после подтвержденной сборки;
- `Готов к отправке` для доставки после подтвержденной сборки.

Запрещено:

- создавать `РТУ` только потому, что товар есть на складе;
- проводить частичную `РТУ` по наличию, если клиент еще не получает товар;
- использовать `РТУ` как способ открыть форму проверки/сканирования.

### 6.3. Форма создания реализации `ФормаР`

Текущее поведение `ФормаР`:

```text
Наличие -> создать РТУ -> провести РТУ -> открыть проверку реализации
```

В Wave 1 это поведение нужно отключить для этапа сборки.

Допустимые варианты реализации:

1. Убрать вызов `ФормаР` из сборочного сценария.
2. Переиспользовать `ФормаР`, но изменить ее назначение: она должна фиксировать
   результат проверки наличия по заказу, а не создавать `РТУ`.

Требуемое поведение:

- позиции в наличии остаются в заказе и переводятся в сборку/готовность;
- отсутствующие позиции переводят заказ в `Проблема / ручной разбор` или
  инициируют потребность;
- если товара не хватает, ранняя частичная `РТУ` не создается;
- пользователь получает понятное сообщение, что `РТУ` будет создана только при
  выдаче или передаче в доставку.

### 6.4. Форма оплаты `ФормаОплаты`

В Wave 1 форму оплаты не нужно полностью перестраивать, но нужно исключить ее
использование как способ закрыть сборку или создать раннюю `РТУ`.

Правила:

- прием оплаты через `ТЗП` может выполняться только в фактическом сценарии
  выдачи/отправки;
- предоплата, пришедшая с сайта до выдачи, должна менять только оплатный
  признак заказа и не должна создавать `РТУ`;
- оплата не должна переводить заказ в `Выдан`, `Отправлен` или `Завершен`
  без фактической `РТУ`;
- кнопка `БезОплаты` не должна закрывать сборку через статус реализации;
- если оплата нужна до выдачи, она меняет только оплатный признак заказа.

## 7. Фактическое создание РТУ из ТЗП

В `ТЗП` можно оставить создание `РТУ`, но только как отдельное фактическое
действие.

### 7.1. Самовывоз

Кнопка/действие: `Выдать клиенту`.

Условия:

- `СтатусИсполнения = Готов к выдаче` или `Частично выдан`;
- `СпособДоставки = Самовывоз`;
- клиент фактически пришел;
- `РТУ` создается на основании `ЗаказПокупателя`;
- после проведения `РТУ` статус заказа становится `Выдан` или
  `Частично выдан`.

### 7.2. Доставка

Кнопка/действие: `Передано в доставку`.

Условия:

- `СтатусИсполнения = Готов к отправке`;
- для `СДЭК` / `Почта` / ТК / `Другое ТК` заполнен `осиТрекНомер`;
- заполнена `ДатаПередачиВТК` / дата-время передачи;
- для `Курьер` / `Такси` трек не обязателен, но факт передачи обязателен;
- `РТУ` создается на основании `ЗаказПокупателя`;
- после проведения `РТУ` статус заказа становится `Отправлен`.

Аварийная отправка `СДЭК` / `Почта` / ТК без трека допускается только по
правилам общего Wave 1 ТЗ: ограниченная роль, обязательная причина и попадание
в отчет.

### 7.3. Блокировка ранней РТУ

Если пользователь пытается создать `РТУ` из `ТЗП` до факта выдачи/передачи,
система должна заблокировать действие и показать сообщение:

```text
РТУ создается только по факту выдачи клиенту или передачи в доставку.
Переведите заказ в сборку/готовность без создания реализации.
```

## 8. Работа с отсутствующими позициями

Если при проверке заказа часть товара отсутствует:

- не создавать `РТУ` на доступную часть автоматически;
- перевести заказ в `Проблема / ручной разбор` или `На обеспечении`;
- сохранить комментарий по отсутствующим позициям;
- при необходимости создать/обновить потребность по текущей логике, но без
  фактической продажи клиенту;
- не создавать возврат от клиента, если клиент товар не получал.

Частичная выдача разрешена только для самовывоза и только в момент фактической
выдачи клиенту.

## 9. Переходный период

На дату запуска Wave 1 в базе могут быть уже созданные ранние `РТУ`.

Требования:

- не удалять и не перепроводить исторические `РТУ` автоматически;
- показать такие документы отдельно как `Legacy РТУ` или оставить в старой
  очереди с явной пометкой;
- новые интернет-заказы после даты запуска не должны идти по старой цепочке
  `Открытый заказ -> Создать реализацию -> РТУ для сборки`;
- в отчет добавить контроль новых `РТУ`, созданных из `ТЗП` до факта.

## 10. Минимальные настройки и роли

Обычный пользователь `ТЗП`:

- видит очередь заказов;
- переводит заказ в сборку/готовность;
- фиксирует проблему;
- создает фактическую `РТУ` только при выполненных условиях.

Руководитель/старший ответственный:

- может аварийно снять блокировку только по правилам общего Wave 1 ТЗ;
- причина исключения обязательна;
- исключение попадает в отчет.

Администратор `1С`:

- может выполнять технические действия в тестовой/рабочей базе;
- не используется как обычный операционный обход блокировок.

## 11. Приемочные сценарии

### 11.1. Сборка нового самовывоза

1. Сайт создает заказ `Самовывоз`.
2. В `ТЗП` заказ появляется без предварительной `РТУ`.
3. Пользователь переводит заказ в `Сборка`.
4. Проверка/лист сборки открываются по `ЗаказПокупателя`.
5. `РТУ` не создается.
6. После сборки заказ становится `Готов к выдаче`.
7. Только при фактической выдаче создается и проводится `РТУ`.
8. Заказ становится `Выдан`.

### 11.2. Сборка доставки

1. Сайт создает заказ `СДЭК` / `Почта`.
2. В `ТЗП` заказ появляется как `ЗаказПокупателя`.
3. Пользователь переводит заказ в `Сборка`.
4. После сборки заказ становится `Готов к отправке`.
5. Без трека и даты передачи `РТУ` не создается.
6. После заполнения трека и факта передачи создается `РТУ`.
7. Заказ становится `Отправлен`.

### 11.3. Нехватка товара

1. По заказу часть товара отсутствует.
2. `ТЗП` показывает отсутствующие позиции.
3. `РТУ` на доступную часть не создается автоматически.
4. Заказ переводится в `Проблема / ручной разбор` или `На обеспечении`.
5. При необходимости создается/обновляется потребность.

### 11.4. Попытка ранней РТУ

1. Заказ находится в `Новый`, `Подтвержден` или `Сборка`.
2. Пользователь пытается создать `РТУ`.
3. Система блокирует действие.
4. Пользователь видит сообщение о запрете ранней `РТУ`.
5. В базе не появляется новая `РТУ`.

### 11.5. Legacy РТУ

1. В базе есть `РТУ`, созданная до запуска Wave 1.
2. `ТЗП` не теряет этот документ из операционного контроля.
3. Документ отображается отдельно или явно помечается как старый процесс.
4. Новый заказ после даты запуска не может попасть в эту цепочку.

### 11.6. Неинтернет-заказ

1. В базе есть заказ, который не относится к интернет-магазину.
2. `ТЗП` не применяет к нему интернет-правила по ошибке.
3. Если по такому заказу есть отдельный старый операционный сценарий, он не
   ломается без отдельного согласования.

### 11.7. Предоплата не закрывает исполнение

1. Сайт создает заказ с предоплатой.
2. В заказе меняется только оплатный признак.
3. `ТЗП` не создает `РТУ` из-за факта оплаты.
4. Заказ остается в корректном статусе исполнения до сборки и факта
   выдачи/передачи.

## 12. Definition of Done

Доработка `ТЗП` считается выполненной, если:

- критерий интернет-заказа явно реализован и проверен;
- дата/время запуска новой логики задана в одном месте;
- новые интернет-заказы собираются в `ТЗП` по `ЗаказПокупателя`;
- действие `Создать реализацию` недоступно на этапе сборки;
- `ФормаР` больше не создает и не проводит `РТУ` как часть сборки;
- лист сборки/проверка/QR не требуют предварительной `РТУ`;
- фактическая `РТУ` создается только по действиям `Выдать клиенту` или
  `Передано в доставку`;
- отсутствующие позиции не приводят к ранней частичной `РТУ`;
- старые `РТУ` переходного периода не потеряны из контроля;
- новые ранние `РТУ` после даты запуска попадают в контрольный отчет;
- приемочные сценарии 11.1-11.7 пройдены на тестовой базе;
- пилотные заказы не создают ложный статус сайта `Выполнен` до факта.

## 13. Вопросы для разработчика перед оценкой

Перед оценкой работ разработчик должен проверить в тестовой базе:

1. Можно ли форма проверки/сканирования принимать `ЗаказПокупателя` вместо
   `РеализацияТоваровУслуг`.
2. Где фактически хранится и используется `осиОтветственный` в текущем `ТЗП`.
3. Можно ли безопасно переиспользовать текущую `ФормаР` под проверку наличия,
   или проще исключить ее из сборочного сценария.
4. Какие старые `РТУ` должны остаться в переходной очереди после даты запуска.
5. Какие права пользователей сейчас открывают `ТЗП` и кто сможет выполнять
   фактическое действие выдачи/передачи.
6. Какой точный набор признаков надежно отличает интернет-заказы от прочих
   заказов в текущей базе.
