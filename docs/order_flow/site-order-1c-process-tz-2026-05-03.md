# ТЗ: исправление процесса интернет-заказов в 1С УТ 10.3 и на сайте

Дата: `2026-05-03`  
Статус: `draft for developers`  
Контур: `1С УТ 10.3 + интернет-магазин Bitrix + SMS из 1С`  

## 1. Назначение

Нужно исправить процесс интернет-заказов так, чтобы `1С` снова была
источником истины по исполнению, а `РТУ` означала факт выдачи клиенту или
передачи в ТК/курьеру, а не техническое обеспечение заказа.

Сейчас из-за ранних `РТУ` и смешанного поля `осиСтатус` возникают:

- ложный статус `F = Выполнен` на сайте;
- ручные возвраты и корректировки доставки;
- отрицательные остатки на складе `Сайт`;
- путаница между способом доставки, оплатой и этапом исполнения;
- невозможность безопасно показывать клиенту честный прогресс заказа.

## 3. Scope

### 3.1. Входит в доработку 1С

- Нормализация реквизитов `Документ.ЗаказПокупателя`.
- Изменение загрузки свойств сайта из `CommerceML`.
- Разделение статуса исполнения, оплаты и доставки.
- Запрет или контроль ранних `РТУ` для интернет-заказов.
- Оформление `РТУ` только по факту выдачи/передачи в ТК.
- Задачи в `1С` для подтверждения, сборки, отправки, просрочек.
- SMS-триггеры из `1С` по корректным событиям.
- Контрольные отчеты.
- Переходная совместимость со старым `осиСтатус`.

### 3.2. Входит в доработку сайта

- Защита от ложного `F = Выполнен`, приходящего из `1С` по ранней отгрузке.
- Подготовка отображения клиентских статусов только из безопасной модели.
- Прием новых реквизитов/статусов из `1С`, когда они появятся в обмене.
- Проверка настроек `sale.1C_CHANGE_STATUS_FROM_1C` и
  `sale.1C_FINAL_STATUS_ON_DELIVERY`.

### 3.3. Не входит в первый этап

- Перенос исполнения заказов в `Bitrix24`.
- Полная замена `1С УТ 10.3`.
- Переписывание всего обмена `CommerceML` с нуля.
- Автоматическое завершение заказов по факту одной `РТУ`.
- Клиентское отображение расширенной логистики ТК, кроме базового статуса и
  трека.

## 4. Распределение ответственности систем

| Система | Роль |
| --- | --- |
| `1С УТ 10.3` | Источник истины по заказу, остаткам, резервам, перемещениям, сборке, `РТУ`, выдаче, отправке и закрытию |
| Сайт Bitrix | Создает заказ, передает свойства заказа в `1С`, показывает клиенту только безопасные статусы |
| `Bitrix24` | Пока не участвует в исполнении; сделки могут оставаться справочным слоем |
| SMS из `1С` | Уведомляет клиента только по подтвержденным событиям |

### 5.3. Значения `СтатусИсполнения`

Минимальный список:

- `Новый`;
- `Подтвержден`;
- `На обеспечении`;
- `Сборка`;
- `Готов к выдаче`;
- `Готов к отправке`;
- `Частично выдан`;
- `Выдан`;
- `Отправлен`;
- `Отменен`;
- `Завершен`;
- `Проблема / ручной разбор`.

Правило: `СпособДоставки`, `СтатусОплаты` и коммуникационные состояния не
должны попадать в `СтатусИсполнения`.

## 6. Изменения в загрузке заказа с сайта

Доработать обработку `CommerceML` в `1С`, где сейчас свойства сайта пишутся в
`Документ.ЗаказПокупателя`.

### 6.1. Маппинг свойств сайта

| Свойство сайта | Сейчас | Нужно |
| --- | --- | --- |
| `Способ доставки` | пишет `осиСпособДоставки` и меняет `осиСтатус` на `Самовывоз/СДЭК/Почта/ДОСТАВИСТА` | писать raw в `СпособДоставкиСайта`; нормализовать в `СпособДоставки`; `СтатусИсполнения` не менять |
| `подразделение` / `Подразделение` | может писать наименование подразделения в `осиСпособДоставки` | писать в подразделение/точку/склад, не в способ доставки |
| `Адрес доставки` | пишет адрес и добавляет `(есть доставка)` в комментарий | писать только адресные поля; не добавлять управляющие маркеры в комментарий |

| `Признак оплаты` | ставит `осиОплачено` | писать только `СтатусОплаты` |
| `Комментарии клиента` / `Комментарии покупателя` | пишет в `осиКомКлиента` и склеивает с `Комментарий` | хранить клиентский комментарий отдельно; склейка допустима только для отображения |
| `Купон` | пишет `осиКупон` | оставить |

### 6.2. Начальное состояние заказа

Для нового интернет-заказа:

- `СтатусИсполнения = Новый`;
- `СтатусДоставки = Не отправлено`, если доставка не самовывоз;
- `СпособДоставки` заполнен нормализованным значением;
- `СпособДоставкиСайта` заполнен исходным значением сайта;
- `осиСтатус` не заполняется типом доставки.

## 7. Правила `РТУ`

### 7.1. Инвариант

`РТУ` для интернет-заказа создается только по факту:

- самовывоз: товар фактически выдан клиенту;
- доставка: товар фактически передан в ТК/курьеру.

`РТУ` запрещено использовать для:

- фиксации наличия;
- запуска перемещения;
- технической передачи на склад `Сайт`;
- преждевременного перевода сайта в `Выполнен`.

### 7.2. Ограничения для интернет-заказов

Для заказов с категорией/признаком `ЗаказСWEBСайта`:

- `РТУ` должна создаваться только на основании `Заказа покупателя`;
- ручная `РТУ` без заказа должна блокироваться или попадать в ежедневный
  контрольный отчет;
- создание `РТУ` до статуса `Готов к выдаче` или `Готов к отправке` должно
  блокироваться, кроме роли руководителя/ответственного;
- исключение должно требовать комментарий причины.

### 7.3. Самовывоз

Условия создания `РТУ`:

- `СпособДоставки = Самовывоз`;
- заказ в статусе `Готов к выдаче` или `Частично выдан`;
- сотрудник подтверждает факт прихода клиента;
- для частичной выдачи указано, что выдано и что остается в резерве.

После проведения `РТУ`:

- если выдано все: `СтатусИсполнения = Выдан`;
- если выдана часть: `СтатусИсполнения = Частично выдан`;
- сайт не переводится в финал до подтвержденного события выдачи.

### 7.4. Доставка

Условия создания `РТУ`:

- `СпособДоставки` не `Самовывоз`;
- заказ в статусе `Готов к отправке`;
- заполнена `ДатаПередачиВТК`;
- заполнен `ТрекНомер` или включено исключение `ПереданоБезТрека` с причиной.

После проведения `РТУ`:

- `СтатусИсполнения = Отправлен`;
- `СтатусДоставки = Отправлено`;
- SMS отправляется только при наличии трека или подтвержденного факта передачи.

### 7.5. Завершение заказа

`Завершен` не ставить автоматически только по факту `РТУ`.

Финальное закрытие выполнять через документ `Закрытие заказов покупателей`:

- успешно выполнен;
- отказ клиента;
- просрочен резерв;
- отмена до выдачи;
- другая утвержденная причина.

## 8. Обеспечение, резервы и перемещения

До факта выдачи/отправки заказ должен обеспечиваться штатными механизмами
`УТ 10.3`, а не ранней `РТУ`:

- резерв на фактическом складе товара через колонку `Размещение`;
- размещение потребности в заказах поставщикам или внутренних заказах, если
  этот сценарий используется в текущей базе;
- корректировка резервов/размещений документом `Резервирование товаров`;
- перемещение только как фактическое перемещение товара между складами;
- задача ответственному как контрольное действие при нехватке или пересорте,
  а не как способ обеспечения.

Старые элементы `осиВидыОплат` не удалять и не переписывать в истории на первом
этапе: нужно ограничить выбор для новых заказов и/или сделать маппинг старых
значений в нормализованные бизнес-виды оплаты.

Не использовать склад `Сайт` как технический буфер для продажи, если это
порождает отрицательные остатки и последующие возвраты.

При корректировке или удалении перемещения:

- не должно автоматически возникать требование делать возврат от клиента, если
  клиент фактически товар не получал;
- заказ должен уходить в `Проблема / ручной разбор` или `На обеспечении`;
- ответственному создается задача с перечнем позиций и причиной.

## 9. Задачи в 1С

Задачи вести в `1С`, не в чатах и не в `Bitrix24`.

| Событие | Задача | Ответственный | Завершение |
| --- | --- | --- | --- |
| Новый интернет-заказ | `Подтвердить заказ №...` | онлайн-менеджер | `Подтвержден` или закрытие с причиной |
| Нет наличия / пересорт | `Разобрать наличие по заказу №...` | ответственный за остатки | перемещение, замена, частичная выдача или закрытие |
| Назначена сборка | `Собрать заказ №...` | склад/точка | `Готов к выдаче` или `Готов к отправке` |
| Готов к отправке | `Отправить заказ / получить трек` | склад/логистика | трек или факт передачи заполнен, статус `Отправлен` |
| Истек срок хранения | `Снять резерв / закрыть заказ №...` | ответственный | закрытие или продление по праву |

Если задача просрочена:

- уведомить руководителя/старшего;
- поставить флаг `SLA нарушен`;
- вывести в отчет.

## 10. SMS

SMS отправлять из `1С` только по подтвержденным событиям.

Минимальные триггеры:

- `Готов к выдаче` -> SMS с адресом и сроком хранения;
- `Отправлен` + `ТрекНомер` -> SMS с треком;
- `Отменен` / закрыт с причиной -> SMS, если уведомление уместно.

Антидубли:

- `SMS_Готовность_Отправлено`;
- `SMS_Готовность_Дата`;
- `SMS_Трек_Отправлено`;
- `SMS_Трек_Дата`;
- `SMS_Ошибка`.

Если текущие поля `осиСМСОтправлена` недостаточны, добавить отдельные флаги по
типам SMS.

## 11. Доработки сайта Bitrix

### 11.1. Переходная защита

Пока в `1С` возможны ранние `РТУ`, сайт не должен показывать клиенту
`Выполнен` только потому, что из `1С` пришло событие отгрузки.

Нужно реализовать один из вариантов:

1. Временно игнорировать перевод `1С -> F` для интернет-заказов, если нет
   отдельного безопасного признака `Выдан/Отправлен`.
2. Оставлять технический `STATUS_ID = F` внутри Bitrix, но в клиентском
   интерфейсе показывать derived status из новых реквизитов `1С`.

Предпочтителен вариант 1, если он не ломает оплату/личный кабинет/админские
процессы.

### 11.2. Новые клиентские статусы сайта

После стабилизации `1С` сайт должен показывать 3-4 статуса:

| Клиентский статус | Источник из 1С |
| --- | --- |
| `В обработке` | `Новый`, `Подтвержден`, `На обеспечении`, `Сборка` |
| `Готов к выдаче` / `Готов к отправке` | соответствующие статусы исполнения |
| `Отправлен` | `Отправлен` + трек или подтвержденная передача |
| `Выдан / Завершен` | `Выдан` или закрыт как успешно выполненный |

### 11.3. Настройки Bitrix

Проверить текущие настройки:

- `sale.1C_CHANGE_STATUS_FROM_1C = Y`;
- `sale.1C_FINAL_STATUS_ON_DELIVERY = F`;
- `sale.status_on_paid = P`.

Если оставить `1C_CHANGE_STATUS_FROM_1C = Y`, нужна защита от ложного `F`.
Если защиту нельзя сделать точечно, временно изменить поведение импорта так,
чтобы отгрузка из `1С` не переводила клиентский статус в `Выполнен` без
нового факта исполнения.

## 12. Обратная выгрузка из 1С на сайт

Добавить или подготовить выгрузку безопасных реквизитов:

| Реквизит CML / обмена | Источник 1С |
| --- | --- |
| `СтатусИсполнения1С` | новый `СтатусИсполнения` |
| `СпособДоставки1С` | нормализованный `СпособДоставки` |
| `СтатусДоставки1С` | `СтатусДоставки` |
| `ТрекНомер` | `ТрекНомер` / `осиТрекНомер` |

Важно: до исправления процесса нельзя использовать только `Номер отгрузки по
1С` / `Дата отгрузки по 1С` как клиентский факт, потому что сейчас `РТУ` может

## 13. Контрольные отчеты

## 15. Приемочные сценарии

### 15.1. Самовывоз, товар есть на точке

1. Сайт создает заказ.
2. В `1С`: `СтатусИсполнения = Новый`, `СпособДоставки = Самовывоз`,
   `осиСтатус` не получает `Самовывоз`.
3. Менеджер подтверждает заказ.
4. Сотрудник переводит заказ в `Готов к выдаче`.
5. До прихода клиента `РТУ` не создается.
6. Клиент пришел, сотрудник нажимает выдачу.
7. Создается `РТУ` на основании заказа.
8. `СтатусИсполнения = Выдан`.
9. Сайт показывает `Выдан / Завершен` только после факта.

### 15.2. СДЭК, предоплата, трек есть

1. Сайт создает заказ с `СДЭК (Самовывоз)`.
2. В `1С`: `СпособДоставкиСайта = СДЭК (Самовывоз)`,
   `СпособДоставки = СДЭК`, `СтатусИсполнения = Новый`.
3. Оплата меняет только `СтатусОплаты`, не `СтатусИсполнения`.
4. После сборки заказ становится `Готов к отправке`.
5. До передачи в СДЭК `РТУ` не создается.
6. После передачи заполнены `ДатаПередачиВТК` и `ТрекНомер`.
7. Создается `РТУ`, статус становится `Отправлен`.
8. SMS уходит с треком.
9. Сайт показывает `Отправлен`.

### 15.3. Доставка без трека

1. Пользователь пытается поставить `Отправлен` без трека.
2. Система блокирует действие.
3. Исключение возможно только при праве `ПереданоБезТрека`.
4. Обязательна причина исключения.
5. Случай попадает в отчет.

### 15.4. Корректировка перемещения

1. Есть заказ с обеспечением через перемещение.
2. Перемещение корректируется или удаляется до фактической выдачи.
3. Система не требует возврат от клиента, если `РТУ` фактически не было.
4. Заказ переходит в `На обеспечении` или `Проблема / ручной разбор`.
5. Создается задача ответственному.
6. На складе `Сайт` не появляется отрицательный остаток из-за технической цепочки.

### 15.5. Сайт и ложный `F`

1. Заказ создан на сайте в статусе `N` или рабочем статусе.
2. Из `1С` приходит отгрузочное событие без нового безопасного факта
   `Выдан/Отправлен`.
3. Сайт не показывает клиенту `Выполнен`.
4. После реального `Выдан/Отправлен` сайт меняет клиентский статус.

## 16. Definition of Done

Доработка считается выполненной, если:

- новые реквизиты добавлены или утверждено использование существующих;
- `Способ доставки` больше не записывается в старый `осиСтатус`;
- оплата не меняет статус исполнения;
- `РТУ` по интернет-заказу не создается до факта выдачи/передачи в ТК;
- доставка не переводится в `Отправлен` без трека или подтвержденного исключения;
- сайт не показывает `Выполнен` раньше фактического события;
- SMS уходят только по правильным триггерам и не дублируются;
- контрольные отчеты доступны ответственным;
- 5 приемочных сценариев выше пройдены на тестовой базе;
- по итогам пилота на 10-20 заказах нет новых отрицательных остатков на складе
  `Сайт`, вызванных старой технической цепочкой.
