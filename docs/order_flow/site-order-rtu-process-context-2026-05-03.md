# Контекст возврата к To-Be процессу заказов сайта

Дата фиксации: `2026-05-03`

## 1. Зачем этот документ

Документ собирает контекст по теме `Заказ покупателя -> обеспечение -> РТУ -> выдача/отправка`
для интернет-заказов `MASTER-MOBILE.RU` в связке `1С УТ 10.3 + сайт + Bitrix24`.

Ранее по этой теме уже был собран пакет As-Is / To-Be. Затем было принято
временное решение не перестраивать процесс внутри старой `1С УТ 10.3`, а
построить внешний слой вычисляемых статусов между `1С` и `Bitrix24`.

Новый операционный пример по заказу сайта `211793` показывает, что временный
компромисс не устраняет первопричину: из-за неверной цепочки документов
появляются возвраты, корректировки услуг доставки, отрицательные остатки на
складе `Сайт` и ручные задачи в `Bitrix24`.

Практический вывод: тему стоит вернуть в работу как исправление процесса в `1С`,
а не только как внешний статусный слой.

## 3. Что изменилось относительно решения от 2026-04-02

Решение от `2026-04-02` было разумным как временная архитектура:

- старая `УТ 10.3` остается системой учета;
- внешний backend вычисляет операционный смысл заказа;
- `Bitrix24` и сайт получают не сырые документы `1С`, а безопасные derived statuses.

Но новый вывод другой:

- внешний слой нужен, но он не должен узаконивать неверную механику внутри `1С`;
- если ранняя `РТУ`, автоматические перемещения на склад `Сайт` и последующие
  возвраты стали ежедневным источником ручных исправлений, надо чинить
  первичный процесс в `1С`;
- сайт и `Bitrix24` можно подключать к клиентским статусам только после того,
  как `РТУ` снова станет фактом выдачи/отправки, а не инструментом обеспечения.

## 4. Пример 211793 как симптом процесса

Заказ сайта `211793`:

- дата заказа на сайте: `2026-04-15 21:31:13`;
- состав заказа:
  - товар `[071698] Задняя крышка для Huawei Honor 400 (DNY-NX9) (черный)` -
    `790`;
  - доставка `СДЭК (Самовывоз)` - `417.45`;
  - итого `1207.45`;
- оплата прошла успешно после двух отклоненных попыток;
- в `1С` заказ связан с `Заказом покупателя РБГУ0030399`;
- далее в структуре подчиненности видны `РТУ`, перемещение, корректировка
  перемещения и последующая необходимость возврата/корректировки.

Операционная проблема из обсуждения:

- если перемещение ставится на удаление или корректируется, исходное перемещение
  удаляется/замещается;
- на основании корректировки создается новое перемещение с актуальными позициями;
- товар может автоматически попасть на склад `Сайт` минусовой позицией;
- затем сотрудникам приходится делать возврат позиции от клиента на склад `Сайт`,
  чтобы минус исчез;
- дополнительно нужно корректировать услугу доставки в первой реализации.

Это не самостоятельная проблема `возврата доставки`. Это следствие неверной
цепочки:

```text
Заказ покупателя
  -> ранняя/техническая РТУ
  -> автоматическое перемещение на склад Сайт
  -> корректировка/удаление перемещения
  -> отрицательный остаток / лишний возврат / корректировка услуги
```

Правильная логика должна быть ближе к такой:

```text
Заказ покупателя
  -> резерв/обеспечение на фактическом складе товара
  -> при необходимости перемещение как обеспечение, а не продажа
  -> сборка
  -> факт выдачи/передачи в ТК
  -> РТУ на основании заказа с фактического склада
```

## 5. Почему точечные обходы не решают проблему

Обсуждавшиеся варианты вроде:

- создавать задачу ответственному при корректировке перемещения со склада `СДЭК`
  на склад `Сайт`;
- ежедневно инвентаризировать отрицательные остатки и закрывать их возвратами;
- заставлять сайт/сайтовиков вручную разбирать последствия корректировок;

могут временно снизить ущерб, но они не устраняют причину.

Их минус:

- процесс остается построенным вокруг ранней `РТУ`;
- склад `Сайт` продолжает использоваться как технический буфер вместо понятного
  состояния заказа;
- ручные возвраты становятся штатной частью исполнения;
- сайт и `Bitrix24` по-прежнему нельзя безопасно подключить к честным статусам;
- каждый сбой перемещения превращается в цепочку `удалить -> вернуть -> поправить
  доставку -> проверить остаток`.

## 6. Обновленная To-Be позиция

Базовые инварианты:

- `1С` является источником истины по исполнению заказа.
- Каждый сценарий начинается с `Заказа покупателя`.
- `РТУ` создается только по факту:
  - самовывоз: клиент пришел, товар выдан;
  - доставка: товар передан в ТК/курьеру, трек или факт передачи зафиксирован.
- Обеспечение заказа делается штатными механизмами `УТ 10.3`: резервом и
  размещением через колонку `Размещение`, при необходимости через заказы
  поставщикам/внутренние заказы. `Перемещение товаров` используется только
  как факт физического перемещения между складами, а не как замена продаже.
- Оплата, доставка и этап исполнения ведутся раздельно.
- Тип доставки и вид оплаты должны быть справочниками/перечислениями, а не
  свободным текстом.
- Сайт получает клиентские статусы только после стабилизации 1С-процесса.

Минимальные управленческие оси:

- этап исполнения:
  - `Новый`;
  - `Подтвержден`;
  - `На обеспечении`;
  - `Сборка`;
  - `Готов к выдаче`;
  - `Готов к отправке`;
  - `Частично выдан`;
  - `Выдан / Отправлен`;
  - `Отменен`;
  - `Завершен`.
- статус оплаты:
  - `Не оплачено`;
  - `Предоплата получена`;
  - `Ожидается при получении`;
  - `Частично`;
  - `Возврат / сторно`.
- доставка:
  - тип доставки;
  - трек-номер;
  - дата отправки/передачи;
  - статус доставки.

## 7. Что нужно проверить в 1С перед проектированием

Перед изменениями важно не спорить абстрактно, а проверить механику на 5-10
реальных заказах:

- обычный самовывоз из точки, где товар уже есть;
- доставка `СДЭК`, где товар есть на одном складе;
- доставка `СДЭК`, где требуется перемещение;
- частичная выдача самовывоза;
- отмена до сборки;
- отмена после сборки, но до фактической выдачи;
- заказ вроде `211793`, где были перемещение, корректировка и возврат;
- незабранный заказ после истечения срока резерва.

Для каждого кейса нужно снять:

- какие документы созданы в структуре подчиненности;
- какой документ меняет остаток;
- где появляется резерв/размещение;
- где появляется склад `Сайт`;
- что происходит при удалении/корректировке перемещения;
- что считается фактом выдачи/отправки;
- какой документ должен закрывать заказ;
- как сейчас учитывается услуга доставки.

## 8. Рекомендуемая очередь возврата к проекту

### Этап 0. Зафиксировать правила

- Утвердить: `РТУ = факт`, а не обеспечение.
- Развести статус исполнения, оплату и доставку.
- Описать, какие действия запрещены для онлайн/доставки:
  - ручная `РТУ` без заказа;
  - техническая `РТУ` до факта выдачи/передачи;
  - автоматическое перемещение на склад `Сайт` как обязательный шаг продажи.
- Утвердить допустимый сценарий розницы: быстрый заказ + реализация одной кнопкой.

### Этап 1. Протестировать механику в УТ 10.3

- На копии/тестовом контуре пройти 5-10 кейсов.
- Проверить, можно ли собрать и реализовать заказ с фактического склада товара
  без технического перемещения на склад `Сайт`.
- Проверить документальную механику частичной выдачи самовывоза.
- Проверить, как корректно закрывать заказы через `Закрытие заказов покупателей`.

### Этап 2. Доработать 1С

- Добавить/нормализовать ось статуса исполнения.
- Добавить отдельные поля оплаты и доставки.
- Сделать кнопки/флаги для подтверждения, сборки, готовности, отправки.
- Настроить задачи в `1С`, а не вести исполнение в чатах.
- Ограничить или контролировать ранние/ручные `РТУ` для онлайн-заказов.
- Настроить регламентные задания:
  - закрытие полностью отгруженных заказов;
  - снятие резервов/размещений по просрочке.

### Этап 3. Вернуть SMS и сайт

- Включить SMS по событиям:
  - готов к выдаче;
  - отправлен + трек;
  - отмена/закрытие, если уместно.
- После стабилизации включить на сайте только безопасные клиентские статусы:
  - `В обработке`;
  - `Готов к выдаче / готов к отправке`;
  - `Отправлен`;
  - `Выдан / завершен`.

## 9. Контрольные отчеты

Минимум для запуска дисциплины:

- `РТУ не на основании заказа`;
- `РТУ создана раньше факта выдачи/передачи`;
- `Заказы с перемещением/корректировкой, после которых появился минус на складе Сайт`;
- `Заказы с услугой доставки, где была корректировка или возврат`;
- `Заказы с 100% отгрузкой, но без Закрытия заказов покупателей старше N дней`;
- `Заказы с резервами/размещениями старше N дней`;
- `Просроченные задачи подтверждения, сборки, отправки, незабранных заказов`;
- `Причины закрытия заказов покупателей`.

## 11. Предварительный разбор реквизитов заказа и обмена с сайтом

### 11.1. Есть ли в УТ 10.3 задание на сборку

По локальной выгрузке конфигурации найден `Документ.осиСборка`, но его текущий
модуль не похож на рабочее задание сборщику по клиентскому заказу. Он проводит
списание номенклатуры на упаковку и пересчитывает стоимость/цену через
`СписаниеТоваров`.

Вывод:

- использовать текущий `Документ.осиСборка` как задание на сборку интернет-заказа
  нельзя без отдельной доработки;
- на первом этапе правильнее делать рабочий лист/задание сборщику от
  `Заказа покупателя`;
- технически это может быть:
  - печатная форма заказа `Лист сборки`;
  - встроенная задача `ЗадачиПользователя`;
  - отдельный новый документ/регистр `ЗаданиеНаСборкуЗаказа`, если нужно
    хранить состав, ответственного и события сборки отдельно.

Минимально достаточно не создавать новый тяжелый документ, а добавить к
`Заказу покупателя` события/флаги:

- `Сборка назначена`;
- `В сборке`;
- `Собран`;
- `Готов к выдаче`;
- `Готов к отправке`.

### 11.3. Где сейчас смешана логика

Текущее поле `осиСтатус` фактически используется как смесь:

- этапа исполнения;
- способа доставки;
- ожидания оплаты/ответа;
- финального статуса.

В справочнике `осиСтатус` видны значения разных природ:

| Значение | Что это по смыслу |
| --- | --- |
| `Сборка товара` | этап исполнения |
| `Ожидает вывоз` | этап/ожидание клиента |
| `Завершен` | финальный статус |
| `Отменен` | финальный статус |
| `Самовывоз` | тип доставки |
| `СДЭК` | тип доставки |
| `ПОЧТА РОССИИ` | тип доставки |
| `Достависта` | тип доставки |
| `Такси` | тип доставки |
| `Ждём оплату` | статус оплаты |
| `Ждём ответа` | коммуникационный статус |
| `Возможно дозаказ` | управленческий комментарий/исключение |
| `Не отвечает / WA TG` | коммуникационный статус |

Текущая обработка обмена прямо подтверждает проблему: при получении свойства
`Способ доставки` поле `осиСпособДоставки` заполняется текстом, а затем
одновременно меняется `осиСтатус`:

- `Самовывоз` -> `осиСтатус = код 06`;
- `Почта России (Доставка в отделение)` -> `осиСтатус = код 10`;
- `СДЭК (Самовывоз)` -> `осиСтатус = код 03`;
- `Доставка курьером` -> `осиСтатус = код 09`.

То есть способ доставки сейчас записывается в отдельный реквизит, но затем
дублируется в поле статуса. Это и есть корневая "каша".

### 11.4. Как разложить реквизиты правильно

В `Заказе покупателя` нужно разделить минимум 4 блока.

#### A. Данные сайта

Эти поля приходят с сайта и не должны вручную использоваться как рабочий статус:

| Поле | Назначение |
| --- | --- |
| `НомерЗаказаСайта` | внешний номер заказа |
| `СайтИсточник` | если появится несколько сайтов |
| `ДатаЗаказаСайта` | дата создания на сайте |
| `КомментарийКлиента` | текст клиента |
| `Купон` | промокод/купон |

Текущие поля можно использовать:

- `НомерВходящегоДокументаЭлектронногоОбмена`;
- `осиКомКлиента`;
- `осиКупон`.

#### B. Доставка

Тип доставки должен быть отдельным справочником/перечислением, не текстом и не
статусом исполнения.

Рекомендуемые поля:

| Поле | Тип | Пример |
| --- | --- | --- |
| `СпособДоставки` | справочник/перечисление | `Самовывоз`, `СДЭК`, `Почта`, `Курьер`, `Такси` |
| `СпособДоставкиСайта` | строка/source value | `СДЭК (Самовывоз)` |
| `ПунктВыдачи/ПодразделениеПолучатель` | ссылка | подразделение или ПВЗ |
| `АдресДоставки` | строка | как сейчас |
| `ТрекНомер` | строка | трек ТК |
| `ДатаПередачиВТК` | дата | факт отправки |
| `СтатусДоставки` | перечисление | `Не отправлено`, `Отправлено`, `Возврат`, `Не выкуп` |

Текущее поле `осиСпособДоставки` лучше сохранить как raw/source value или
переименовать по смыслу в `СпособДоставкиСайта`. Для нормальной логики рядом
нужен нормализованный `СпособДоставки`.

#### C. Оплата

`Метод оплаты` и `Признак оплаты` нельзя смешивать.

Рекомендуемые поля:

| Поле | Тип | Пример |
| --- | --- | --- |
| `ВидОплатыСайта` | справочник | `CloudPayments`, `Наличными при получении`, `Наложенный платеж` |
| `СтатусОплаты` | перечисление/справочник | `Не оплачено`, `Оплачено`, `Частично`, `Возврат/сторно` |
| `ДатаОплаты` | дата | дата оплаты от сайта/эквайринга |
| `СуммаОплаты` | число | сумма платежа |
| `PaymentId/TransactionId` | строка | id платежа, если доступен |

Текущие поля:

- `осиВидОплаты` подходит как `ВидОплатыСайта`, но справочник нужно
  нормализовать без физического удаления старых элементов: оставить историю,
  ограничить выбор для новых заказов бизнес-видами оплаты и вынести конкретные
  реквизиты карт из вида оплаты;
- `осиОплачено` подходит как `СтатусОплаты`, если привести значения к короткому
  списку.

#### D. Исполнение заказа

Это новый чистый статусный контур, который не должен хранить тип доставки и
оплату.

Рекомендуемые значения:

- `Новый`;
- `Подтвержден`;
- `На обеспечении`;
- `В сборке`;
- `Собран`;
- `Готов к выдаче`;
- `Готов к отправке`;
- `Частично выдан`;
- `Выдан / Отправлен`;
- `Отменен`;
- `Завершен`;
- `Проблема / ручной разбор`.

Можно завести новое поле `СтатусИсполнения` и временно оставить старый
`осиСтатус` только для совместимости. В обмене с сайтом перестать писать
доставку в `осиСтатус`.

### 11.5. Что менять в обмене с сайтом

Минимальная правка логики обмена:

1. При свойстве `Способ доставки`:
   - писать исходное значение в `СпособДоставкиСайта` / текущий
     `осиСпособДоставки`;
   - нормализовать в `СпособДоставки`;
   - не менять `СтатусИсполнения`.
2. При свойстве `Метод оплаты`:
   - писать в `ВидОплатыСайта`;
   - не менять статус исполнения.
3. При `Дата оплаты` / `Признак оплаты`:
   - менять только `СтатусОплаты` и дату оплаты.
4. При адресных свойствах:
   - писать адрес/ПВЗ/подразделение получателя;
   - не ставить комментарий `(есть доставка)` как управляющий признак.
5. Начальный `СтатусИсполнения` для всех заказов сайта:
   - `Новый` или `Подтвержден`, если сайт уже присылает подтвержденный заказ.

## 12. Что подтверждено на сайте по SSH

Доступ к интернет-магазину есть по SSH. Рабочий webroot:

```text
/var/www/mm/data/www/master-mobile.ru
```

Сервер интернет-магазина: `87.242.110.232` (`server.master-mobile.ru`). Важно:
это один Bitrix-контур, на котором живет сам интернет-магазин и связанные
Bitrix/CRM-механики, а не отдельная независимая система рядом с магазином.

Собранные артефакты лежат локально:

```text
docs/order_flow/artifacts/site-order-exchange-2026-05-03/site/
```

Ключевые выводы по сайту:

- сайт работает на `Bitrix`;
- заказы сайта хранятся в `b_sale_order`;
- штатный начальный статус нового заказа Bitrix:
  - `OrderStatus::getInitialStatus()` = `N`;
  - `N` = `Принят в работу`;
- то есть сайт сам при создании заказа не обязан сразу ставить `F`;
- ранний `F` появляется после обратного импорта из `1С`.

Настройки обмена `Bitrix <-> 1С`, которые критичны для текущей проблемы:

| Настройка Bitrix | Значение | Что означает для процесса |
| --- | --- | --- |
| `sale.1C_CHANGE_STATUS_FROM_1C` | `Y` | сайт принимает изменение статуса заказа из `1С` |
| `sale.1C_FINAL_STATUS_ON_DELIVERY` | `F` | при событии доставки/отгрузки из `1С` сайт переводит заказ в `Выполнен` |
| `sale.secure_1c_exchange` | `N` | обмен с `1С` настроен без включенного secure-флага Bitrix |
| `sale.status_on_paid` | `P` | при оплате сайт ставит `Оплачен`, а не `Выполнен` |

Важно: эти параметры не отображаются на форме `1С`
`Настройки обмена с WEB-сайтом: Обмен заказами`. На форме `1С` видны адрес
обмена, пользователь, периодичность, режим выгрузки и действия с отмененными
заказами. А параметры выше - это настройки модуля интернет-магазина Bitrix на
стороне сайта, они лежат в таблице `b_option` с `MODULE_ID = sale`.

Это подтверждает старый риск: если в `1С` создана преждевременная `РТУ`, сайт
получает из `1С` событие отгрузки/документ доставки и честно переводит заказ в
`F = Выполнен`, хотя клиент еще мог ничего не получить.

### 12.1. Контрольный пример 214840

История сайта по заказу `214840`:

| Время | Событие | Пользователь | Смысл |
| --- | --- | --- | --- |
| `2026-05-03 14:30:18` | `ORDER_ADDED` | клиент сайта | заказ создан |
| `2026-05-03 14:30:18` | `SHIPMENT_ADDED` | клиент сайта | доставка `Самовывоз` |
| `2026-05-03 14:30:18` | `PAYMENT_ADDED` | клиент сайта | оплата `Наличными при получении` |
| `2026-05-03 14:51:58` | `ORDER_1C_IMPORT` | `1C Пользователь` | пришел обратный импорт из `1С` |
| `2026-05-03 14:51:58` | `ORDER_DELIVERY_ALLOWED` | `1C Пользователь` | сайт получил признак разрешенной доставки/отгрузки |
| `2026-05-03 14:51:58` | `ORDER_STATUS_CHANGED N -> F` | `1C Пользователь` | сайт перевел заказ в `Выполнен` |
| `2026-05-03 14:51:58` | `ORDER_DELIVERY_DOC_CHANGED` | `1C Пользователь` | сайт получил номер документа доставки/отгрузки из `1С` |

На самом сайте заказ `214840` после этого имеет:

- `STATUS_ID = F`;
- `PAYED = N`;
- `DELIVERY_ID = 2` (`Самовывоз`);
- `PAY_SYSTEM_ID = 14` (`Наличными при получении`).

Вывод: сайт показывает/хранит `Выполнен` не потому, что клиент оплатил или
получил товар, а потому что `1С` вернула событие отгрузки/документ доставки.

### 12.2. Контрольный пример 211793

По заказу `211793` сайт показывает аналогичную механику:

- заказ создан `2026-04-15 21:31:13`;
- доставка `СДЭК (Самовывоз)`;
- оплата `CloudPayments`;
- после оплаты сайт перевел заказ в `P = Оплачен`;
- `2026-04-16 15:45:59` пришел `ORDER_1C_IMPORT`;

- одновременно пришел документ доставки/отгрузки `РБГУ0172244`.

Это ровно та цепочка, из-за которой сайт нельзя сейчас подключать к клиентскому
статусу `Выполнен` напрямую.

### 12.4. Где на сайте считается готовность товара

В кастомном коде сайта:

- `local/php_interface/events.php` рассчитывает `AVAILABILITY_CODE` и
  `AVAILABILITY_TEXT`;
- возможные значения:
  - `ALL` -> `Готов к выдаче`;
  - `NOT_ALL` -> срок доставки;
  - `DELIVERY_REMOVE` -> будет доставлен к дате;
- эти значения завязаны на наличие товара по складам/региону, а не на факт
  выдачи клиенту;
- шаблон `local/components/sp/sale.order.ajax/templates/main/confirm.php`
  не показывает блок готовности, если `STATUS_ID = F`.

Вывод: `AVAILABILITY_*` полезны как витринная доступность/готовность к сборке,
но не являются фактом выдачи. Их нельзя смешивать с `СтатусИсполнения`.

### 12.5. Что это меняет в плане внедрения

Сайт подтверждает, что первичная точка исправления - `1С`.

Пока в `1С` ранняя `РТУ` означает не факт выдачи, а техническое обеспечение,
на сайте нельзя использовать `F = Выполнен` как клиентский факт.

Варианты стабилизации:

1. Основной путь: в `1С` перестать отправлять сайту событие отгрузки/финала до
   факта выдачи/передачи в ТК.
2. Переходная защита: на сайте или в слое обмена временно игнорировать перевод
   `1С -> F`, если нет отдельного подтвержденного факта выдачи/отправки.
3. После фикса процесса включить клиентские статусы сайта из новой чистой модели:
   `В обработке -> Готов к выдаче/отправке -> Отправлен/Выдан -> Завершен`.

Нельзя считать настройку `1C_CHANGE_STATUS_FROM_1C=Y` самостоятельной ошибкой:
она становится опасной именно потому, что в `1С` преждевременная `РТУ`
маскируется под факт.

### 12.6. Что добавила матрица реквизитов

Матрица реквизитов подтверждает не только общий вывод, но и конкретные поля:

| Блок | Текущее поле | SQL | Вывод |
| --- | --- | --- | --- |
| Оплата | `осиВидОплаты` | `_Fld9087RRef` -> `_Reference9084` | справочник загрязнен картами/персональными способами оплаты |
| Оплата | `осиОплачено` | `_Fld9088RRef` -> `_Reference9085` | есть дублирующие значения `Да/Нет` и `Оплачено/Не оплачено` |
| Доставка | `осиСпособДоставки` | `_Fld9266` | хранит raw-строку сайта и не должен менять исполнение |
| Доставка | `осиТрекНомер` | `_Fld9094` | поле есть, но регулярное заполнение не подтверждено; должно стать обязательной частью факта отправки |
| Исполнение | `осиСтатус` | `_Fld9092RRef` -> `_Reference9091` | смешивает этапы, доставку, оплату, коммуникации и финал |
| Данные сайта | `осиКупон` | `_Fld9928` | аналитика промо, не статус |
| Данные сайта | `осиКомКлиента` | `_Fld9090` | комментарий клиента, не управляющий признак |

Практическое решение для To-Be:

- старый `осиСтатус` оставить только как legacy-поле совместимости;
- добавить чистый `СтатусИсполнения`;
- `СпособДоставки`, `СтатусОплаты`, `ТрекНомер`, `ДатаПередачиВТК` вести отдельно;
- в обмене с сайтом перестать писать тип доставки в статус исполнения;
- `РТУ` делать только после факта выдачи/передачи в ТК.

## 13. Короткая формулировка для руководства

Проблема не в конкретном возврате доставки по заказу `211793`.

Проблема в том, что `РТУ` сейчас часто используется как технический инструмент
обеспечения заказа, хотя должна быть фактом выдачи или отправки. Из-за этого
любая корректировка перемещения может порождать отрицательные остатки на складе
`Сайт`, ручные возвраты, исправления доставки и конфликтные статусы для клиента.

Чтобы убрать костыли, нужно возвращаться к To-Be:

```text
Заказ покупателя -> резерв/обеспечение -> сборка -> готовность -> фактическая РТУ -> закрытие заказа
```

И только после стабилизации этого процесса включать честные статусы на сайте и в
`Bitrix24`.
