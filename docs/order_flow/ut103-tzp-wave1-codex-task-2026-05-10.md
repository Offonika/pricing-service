# Задача для Codex: доработка ТЗП под Wave 1 интернет-заказов

Дата постановки: `2026-05-10`
Основной проект: `/opt/MM/pricing-service`
Система: `1С УТ 10.3.11.4`, платформа `1С 8.2.19.130`
Артефакт: внешняя обработка `ТЗП_Новый.epf`
Рекомендуемый подход: отдельная внешняя обработка / форк `ТЗП` для сборщика,
работающая от `ЗаказПокупателя`, без нового документа метаданных.

## 1. Короткая цель

Сделать следующий этап после зеленых тестов Wave 1:

```text
ТЗП должна собирать интернет-заказ от ЗаказПокупателя.
РТУ создается только по факту выдачи клиенту или передачи в доставку.
```

Не делать новый документ `ЗаданиеНаСборку` в этой задаче. Для `УТ 10.3` это
слишком широкий Wave 2-контур: новые метаданные, отдельный жизненный цикл,
права, отмены, строки сборки, сканирование, отчеты. В текущей задаче нужен
практичный безопасный шаг: форк/новая внешняя обработка для сборщика плюс
защитная блокировка старого сценария ранней `РТУ`.

## 2. Готовый промпт для Codex на другом сервере

```text
Мы продолжаем Wave 1 интернет-заказов в 1С УТ 10.3.

Рабочий workspace: /opt/MM.
Основной проект с документацией: /opt/MM/pricing-service.
Обязательно отвечать по-русски и не раскрывать секреты.

Главное правило:
РТУ = только факт выдачи клиенту или передачи в ТК/курьеру/такси.

Текущий этап:
Wave 1 по заказам и РТУ протестирован. Нужно доработать ТЗП.

Решение по архитектуре:
Не создавать новый документ ЗаданиеНаСборку.
Сделать отдельную внешнюю обработку / форк ТЗП для сборщика интернет-заказов,
которая работает от ЗаказПокупателя. Старый сценарий ТЗП, который создает
раннюю РТУ по открытому заказу, нужно заблокировать для интернет-заказов после
даты запуска Wave 1.

Обязательные документы к прочтению:
- pricing-service/docs/order_flow/onec-tzp-wave1-tz-2026-05-03.md
- pricing-service/docs/order_flow/artifacts/site-order-exchange-2026-05-03/tzp_new_epf_analysis_2026-05-03.md
- pricing-service/docs/order_flow/onec-site-order-wave1-tz-2026-05-03.md
- pricing-service/docs/order_flow/ut103-site-order-wave1-work-report-2026-05-06.md
- pricing-service/docs/order_flow/ut103-tzp-wave1-codex-task-2026-05-10.md

Исходная обработка может лежать в одном из мест:
- /opt/MM/mm-compensation/docs/Структура 1с/ТЗП_Новый.epf
- в рабочей копии на текущем сервере разработки Wave 1
- в каталоге, который укажет владелец задачи

Перед изменениями:
1. Найди актуальный исходник ТЗП.
2. Посчитай SHA-256 исходного epf.
3. Сделай резервную копию epf с датой/временем.
4. Распакуй epf через доступный инструмент проекта, например v8unpack.
5. Работай по распакованным BSL/Form-файлам, затем собери новый epf.
6. Не меняй production-базу без явного разрешения.

Что нужно реализовать:
1. Новая обработка/форк ТЗП для сборщика интернет-заказов строит очередь от
   Документ.ЗаказПокупателя, а не от РеализацияТоваровУслуг.
2. Для интернет-заказов действие "Создать реализацию" на этапе сборки больше
   не создает и не проводит РТУ.
3. Основные действия новой обработки:
   - В сборку -> СтатусИсполнения = Сборка;
   - Готов к выдаче -> только для Самовывоз;
   - Готов к отправке -> для доставок;
   - Проблема / ручной разбор;
   - Выдать клиенту -> фактическая РТУ для Самовывоз;
   - Передано в доставку -> фактическая РТУ для СДЭК/Почта/Курьер/Такси.
4. Проверка наличия не должна создавать РТУ.
5. Для СДЭК/Почта/ТК перед фактической РТУ обязательны:
   - СтатусИсполнения = Готов к отправке;
   - ДатаПередачиВТК;
   - осиТрекНомер, кроме аварийного сценария без трека с причиной.
6. Для Курьер/Такси трек не обязателен, но ДатаПередачиВТК обязательна.
7. Для Самовывоз фактическая РТУ разрешена только из Готов к выдаче или
   Частично выдан.
8. Legacy-РТУ, созданные до даты запуска новой логики, можно оставить отдельной
   переходной очередью, чтобы не потерять уже начатые старые операции.
9. Дата запуска новой логики должна быть задана в одном месте: настройка,
   константа обработки или служебный параметр. Не хардкодить дату в нескольких
   формах.

Критерий интернет-заказа:
Использовать устойчивый набор признаков, сверив его на тестовой базе:
- заказ имеет категорию ЗаказСWEBСайта или внешний номер сайта;
- заполнен НомерВходящегоДокументаЭлектронногоОбмена;
- заполнен raw-способ доставки осиСпособДоставки;
- подразделение/склад относятся к интернет-магазину, если это актуально в базе.
Нельзя случайно заблокировать несвязанные с сайтом сценарии.

Файлы форм ТЗП, которые нужно проверить после распаковки:
- Form/Форма/Form.obj.bsl
- Form/ФормаЗаказов/Form.obj.bsl
- Form/ФормаР/Form.obj.bsl
- Form/ФормаОплаты/Form.obj.bsl

Ожидаемое поведение:
- сборщик видит интернет-заказы из ЗаказПокупателя;
- заказ можно перевести в Сборка/Готов к выдаче/Готов к отправке без РТУ;
- ранняя РТУ из ТЗП заблокирована понятным сообщением;
- РТУ создается только кнопками факта: Выдать клиенту / Передано в доставку;
- проведение РТУ дополнительно защищено общей Wave 1-проверкой документа РТУ;
- старый осиСтатус не используется как способ доставки или этап исполнения.

Приемочные сценарии:
1. Самовывоз:
   Новый -> В сборку -> Готов к выдаче -> Выдать клиенту -> РТУ -> Выдан.
   Попытка РТУ до Готов к выдаче блокируется.
2. Частичный самовывоз:
   Готов к выдаче -> выдача части -> РТУ только на фактически выданные позиции
   -> СтатусИсполнения = Частично выдан.
3. СДЭК/Почта:
   Новый -> Сборка -> Готов к отправке.
   Без ДатаПередачиВТК/трека РТУ блокируется.
   С датой и треком -> Передано в доставку -> РТУ -> Отправлен.
4. Курьер/Такси:
   Без ДатаПередачиВТК РТУ блокируется.
   С датой передачи -> РТУ разрешена без обязательного трека -> Отправлен.
5. Нет товара:
   Проверка наличия не создает частичную раннюю РТУ.
   Заказ переводится в На обеспечении или Проблема / ручной разбор.
6. Legacy:
   Старые РТУ до даты запуска видны в отдельной legacy-очереди, если это нужно
   операционно.

Что сдать:
- новый epf / форк обработки;
- распакованные измененные BSL-файлы или патч;
- резервную копию исходного epf и SHA-256 до/после;
- короткий отчет по измененным формам;
- статический тест/скрипт, который проверяет, что раннее создание РТУ из ТЗП
  для интернет-заказов заблокировано;
- результат приемочных тестов на тестовой базе.

Не делать:
- не создавать новый документ метаданных ЗаданиеНаСборку;
- не переписывать весь контур оплаты;
- не менять сайт/Bitrix24;
- не трогать боевую базу без отдельного разрешения;
- не выводить секреты из .env или строк подключения.
```

## 3. Технический план работ

### 3.1. Подготовка

1. Найти актуальный `ТЗП_Новый.epf` на сервере разработки.
2. Зафиксировать путь к исходнику и SHA-256.
3. Сделать backup исходного файла:

   ```text
   ТЗП_Новый.before-wave1-tzp-YYYYMMDD-HHMMSS.epf
   ```

4. Распаковать обработку в отдельный каталог, например:

   ```text
   build/ut103-tzp-wave1/unpacked/
   ```

5. Проверить, что структура содержит:

   - `Form/Форма/Form.obj.bsl`;
   - `Form/ФормаЗаказов/Form.obj.bsl`;
   - `Form/ФормаР/Form.obj.bsl`;
   - `Form/ФормаОплаты/Form.obj.bsl`.

### 3.2. Основная форма

В `Form/Форма/Form.obj.bsl`:

- добавить новый режим/вкладку/очередь интернет-заказов от
  `Документ.ЗаказПокупателя`;
- не использовать `РеализацияТоваровУслуг` как источник обычной сборки;
- оставить старые реализации только как `Legacy РТУ`, если это нужно
  операционно;
- показывать минимум:
  - номер и дату заказа;
  - внешний номер сайта;
  - контрагента;
  - подразделение/склад;
  - raw-доставку `осиСпособДоставки`;
  - нормализованный `СпособДоставки`;
  - `СтатусИсполнения`;
  - трек `осиТрекНомер`;
  - `ДатаПередачиВТК`;
  - комментарий клиента.

### 3.3. Форма заказов

В `Form/ФормаЗаказов/Form.obj.bsl`:

- заменить действие `Создать реализацию` для интернет-заказов после даты
  запуска;
- вместо него дать действия:
  - `В сборку`;
  - `Проверить наличие`;
  - `Готов к выдаче`;
  - `Готов к отправке`;
  - `Проблема`;
- если пользователь все же пытается создать раннюю `РТУ`, показывать:

  ```text
  РТУ создается только по факту выдачи клиенту или передачи в доставку.
  Переведите заказ в сборку/готовность без создания реализации.
  ```

### 3.4. ФормаР

В `Form/ФормаР/Form.obj.bsl`:

- отключить обычный путь `Наличие -> создать РТУ -> провести РТУ` для
  интернет-заказов после даты запуска;
- использовать форму только для проверки наличия/разбора, если ее проще
  переиспользовать;
- отсутствующие позиции не должны создавать частичную раннюю `РТУ`;
- результат проверки должен менять статус заказа на `Сборка`,
  `На обеспечении` или `Проблема / ручной разбор`.

### 3.5. ФормаОплаты

В `Form/ФормаОплаты/Form.obj.bsl`:

- исключить использование оплаты как скрытого завершения сборки;
- не переводить заказ в `Выдан`, `Отправлен` или старый `Завершен` без
  фактической `РТУ`;
- разрешить оплатные действия только в сценарии фактической выдачи/отправки или
  как оплатный признак заказа без смены `СтатусИсполнения`.

### 3.6. Фактическая РТУ

Добавить отдельные действия:

- `Выдать клиенту` для `Самовывоз`;
- `Передано в доставку` для `СДЭК`, `Почта`, `Курьер`, `Такси`.

Эти действия могут создавать `РТУ` на основании `ЗаказПокупателя`, но только
после проверки условий Wave 1. При проведении нужно полагаться также на общую
защиту в модуле `Документ.РеализацияТоваровУслуг`.

## 4. Риски и контрольные точки

| Риск | Как контролировать |
| --- | --- |
| Случайно сломать старые несайтовые сценарии `ТЗП` | Ограничить новую логику надежным признаком интернет-заказа и датой запуска |
| Пользователь продолжит делать раннюю `РТУ` через старую кнопку | Блокировать `Создать реализацию` для интернет-заказов после даты запуска |
| Частичная ранняя `РТУ` появится при нехватке товара | Проверка наличия не должна проводить `РТУ`; нехватка ведет в `На обеспечении` / `Проблема` |
| Оплата снова смешает оплату и исполнение | Оплата не меняет `СтатусИсполнения` без фактической `РТУ` |
| Новая обработка не соберется обратно в epf | После каждого крупного блока собирать epf и открывать в тестовой базе |

## 5. Definition of Done

Задача готова, если:

- новая/форкнутая обработка открывается в тестовой базе;
- очередь сборщика строится от `ЗаказПокупателя`;
- ранняя `РТУ` из `ТЗП` для интернет-заказа после даты запуска невозможна;
- статусы `Сборка`, `Готов к выдаче`, `Готов к отправке`, `Проблема` меняются в
  заказе без создания `РТУ`;
- фактические действия `Выдать клиенту` и `Передано в доставку` создают `РТУ`
  только при выполнении условий Wave 1;
- пройдены сценарии самовывоза, частичной выдачи, `СДЭК`/`Почта`,
  `Курьер`/`Такси`, нехватки товара и legacy-очереди;
- сохранены SHA-256 исходного и итогового epf;
- подготовлен короткий отчет по измененным формам и тестам;
- в репозиторий не попали секреты, реальные пароли, webhook URL или строки
  подключения.
