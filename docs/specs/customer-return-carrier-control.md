# Назначение

Спецификация задаёт технический контракт задачи Bitrix24 №3507
«[CRM][Возвраты][Доставка] Автоматизировать оформление и контроль возвратов через
перевозчиков».

Сейчас компания узнаёт о клиентском возврате только после того, как клиент
самостоятельно передаст трек-номер. В личных кабинетах перевозчиков нет единого
списка всех отправлений, идущих в адрес компании, поэтому такие возвраты могут
остаться без контроля, прибыть в пункт выдачи и уехать обратно после окончания
срока хранения.

Цель первой версии — создать в `pricing-service` единый реестр входящих
клиентских возвратов, не зависящий от перевозчика, и дать Bitrix24 надёжный
контракт для регистрации трека, контроля движения и действий сотрудников.

# Scope / Out of Scope

## Входит в первую версию

- ручная регистрация трек-номера сотрудником, клиентским интерфейсом или
  интеграцией Bitrix24;
- перевозчики `russian_post` и `cdek`;
- единая модель отправления, истории событий и нормализованных статусов;
- приём статуса перевозчика через внутренний API без привязки общей модели к
  формату конкретного API;
- идемпотентность повторной регистрации и повторной доставки одного события;
- одна рабочая задача при прибытии возврата в пункт выдачи;
- напоминания за 3 и 1 день до окончания хранения, если срок известен;
- ручное подтверждение сотрудником действия «Забрали»;
- постановка контрольного действия на сверку факта возврата в 1С;
- read-only приём подтверждения, что документ возврата найден в 1С;
- журнал действий и outbox уведомлений без выполнения внешних side effects в
  транзакции изменения статуса;
- интерфейс адаптера для последующего подключения API перевозчиков.

## Не входит в первую версию

- автоматический поиск отправления только по адресу, телефону или ФИО получателя;
- запись, создание или проведение документов в 1С;
- изменение действующего контура исходящих отправлений и внутренних перемещений;
- повторное использование его таблиц, статусов и carrier adapter как источника
  состояния клиентского возврата;
- хранение полных контактов клиента, если достаточно ссылок на Bitrix24/заказ/1С;
- включение production, создание полей или задач в Bitrix24 и реальные запросы к
  API перевозчиков без отдельного rollout и проверенных credentials;
- активная интеграция с Яндекс Доставкой в первой версии.

# Change Summary / Spec Delta

- было: трек возврата живёт в переписке или карточке сотрудника, а компания не
  имеет единого реестра и надёжного сигнала о прибытии;
- станет: один carrier-neutral реестр принимает трек и события, нормализует
  статус, дедуплицирует действия и отдаёт Bitrix24 готовые рабочие события;
- не меняется: 1С остаётся системой учёта факта товарного возврата, Bitrix24 —
  рабочим интерфейсом, а существующий логистический контур — системой исходящих
  и внутренних перемещений.

## Решения по привязке сделки Bitrix24

- вместо ручного ввода номера заказа сотрудник ищет и выбирает сделку Bitrix24;
- поиск показывает все найденные сделки, включая закрытые, с явной пометкой
  закрытого состояния;
- возврат разрешено зарегистрировать без сделки и привязать её позднее;
- после регистрации связь можно заменить или удалить; каждое изменение сохраняется
  в истории возврата с автором, прежней и новой связью;
- номер заказа, клиент и ответственный берутся backend из выбранной сделки, а не
  принимаются как доверенные данные браузера.

## Решения по связям сервисного обращения

- корневой заявкой остаётся карточка смарт-процесса Bitrix24 с
  `entityTypeId=1134`; отдельная сущность «Заявка на возврат» не создаётся;
- одно обращение может объединять несколько возвратных отправлений и несколько
  экспертиз; у отправления и экспертизы может быть не более одного обращения;
- прямой связи `отправление -> экспертиза` нет: список экспертиз определяется по
  общему `service_request_item_id`;
- трек разрешено зарегистрировать без обращения с явной меткой «Обращение не
  привязано» и связать позднее;
- создание нового сервисного обращения из раздела возвратов в этот релиз не входит;
- backend повторно читает карточку 1134 и сохраняет доверенный снимок названия,
  стадии, сделки, заказа, ответственного и времени привязки; браузер передаёт
  только ID;
- если у обращения есть сделка, она автоматически заполняет пустую сделку
  отправления; разные сделки блокируются, а удаление обращения не удаляет сделку;
- экспертиза привязывается вручную из карточки возврата; разные известные номера
  заказа блокируются, отсутствие номера допускается и отражается в аудите;
- rollout управляется `CUSTOMER_RETURN_SERVICE_LINKS_ENABLED` и списком
  `CUSTOMER_RETURN_SERVICE_LINKS_ROLES`: сначала `admin`, после smoke —
  `admin,returns`;
- rollback выполняется выключением feature flag без удаления новых полей и аудита.

# Acceptance Criteria

- [x] Повторная регистрация одной пары `carrier + tracking_number` не создаёт
  второе отправление, возвращает существующую запись и дополняет её ранее
  отсутствовавшими техническими ссылками без перезаписи уже заполненных значений.
- [x] Почта России и СДЭК используют одну модель данных и один набор
  нормализованных статусов.
- [x] Один внешний статус с тем же ключом дедупликации создаёт не более одного
  события истории.
- [x] Переход в `arrived_at_pickup_point` создаёт ровно одно действие
  `arrival_task`.
- [x] При известном сроке хранения создаются не более одного напоминания за 3 дня

- [x] Действие «Забрали» фиксирует сотрудника и время, переводит возврат в

- [x] Повторное подтверждение «Забрали» идемпотентно и не создаёт вторую сверку.
- [x] Подтверждение из read-only проверки 1С переводит запись в

  реестр и фильтры, ручную регистрацию, карточку с историей, срок хранения,
  состояние сверки 1С и действие «Забрали».
- [x] При регистрации сотрудник ищет сделку по ID, названию или номеру заказа;
  закрытые сделки доступны с явной пометкой, а регистрация без сделки остаётся

- [x] Backend повторно читает выбранную сделку и сохраняет доверенный снимок заказа,

- [x] В интерфейсе доступна встроенная справка; тестовые данные видит только
  `admin`. Карточка возврата открывается модально поверх реестра, на мобильном —
  нижней панелью; закрывается кнопкой, фоном и `Esc` с возвратом фокуса.
- [x] Bitrix24 UI использует действующую OAuth/session-схему логистического
  приложения; роль `returns` не получает складских операций, а `admin` получает
  раздел возвратов вместе с существующими возможностями.
- [x] Действующий исходящий логистический API и его таблицы не изменяют
  поведение.

# Source of Truth

Единый контур клиентских возвратов не зависит от конкретного перевозчика.
Первая версия поддерживает Почту России и СДЭК. Яндекс Доставка подключается
позже отдельным адаптером без изменения общей модели данных, статусов и
интерфейса Bitrix24.

`pricing-service` хранит реестр возвратов, историю статусов и правила
уведомлений. Bitrix24 является рабочим интерфейсом, а 1С — read-only источником
факта оформленного возврата. Действующий контур исходящих отправлений не
изменяется.

# Data Flow

```text
клиент / сотрудник / Bitrix24
            |
            v
ручная регистрация carrier + track
            |
            v
pricing-service: shipment -> event history -> normalized state
            ^                         |
            |                         v
carrier adapter / internal status API  notification outbox -> Bitrix24 worker
                                      |
                                      v
                               сотрудник: «Забрали»
                                      |
                                      v
                         read-only сверка документа возврата в 1С
```

Внешний polling/webhook-клиент перевозчика отвечает только за получение сырого
события. Адаптер нормализует трек и статус. Сервис атомарно сохраняет историю,
текущее состояние и уникальные outbox-действия. Отдельный worker выполняет
side effects в Bitrix24 и подтверждает их результат.

# API / Data Contracts

## Перевозчики

- `russian_post` — Почта России;
- `cdek` — СДЭК;
- `yandex_delivery` — зарезервирован для будущего адаптера и не принимается при
  ручной регистрации первой версии.

## Нормализованные статусы

- `registered` — трек принят, движение ещё не подтверждено;
- `in_transit` — перевозчик принял отправление или оно движется;
- `arrived_at_pickup_point` — возврат доступен для получения компанией;
- `picked_up` — сотрудник подтвердил «Забрали»;
- `onec_return_confirmed` — read-only сверка нашла оформленный возврат в 1С;
- `cancelled` — перевозка отменена или отправление возвращено клиенту;
- `exception` — статус не распознан либо требует ручного разбора.

## Внутренний API первой версии

- `POST /api/customer-returns` — зарегистрировать трек вручную или
  идемпотентно получить существующую запись;
- `GET /api/customer-returns` — получить реестр с фильтрами по перевозчику и
  нормализованному статусу;
- `GET /api/customer-returns/{shipment_id}` — получить карточку и историю;
- `POST /api/customer-returns/{shipment_id}/carrier-events` — принять сырой
  статус перевозчика с `external_event_id` либо явным `idempotency_key`;
- `POST /api/customer-returns/{shipment_id}/pickup` — подтвердить «Забрали»;
- `POST /api/customer-returns/{shipment_id}/onec-confirmation` — принять
  результат read-only сверки 1С;
- `GET /api/customer-returns/actions/due` — получить готовые к выполнению
  outbox-действия;
- `POST /api/customer-returns/actions/{action_id}/complete` — сохранить ID
  выполненного действия Bitrix24 без повторного side effect.

Встроенный интерфейс Bitrix24 вызывает session-authenticated BFF того же
приложения:

- `GET /api/bitrix/logistics/customer-returns` — реестр с фильтрами;
- `POST /api/bitrix/logistics/customer-returns` — ручная регистрация трека;
- `GET /api/bitrix/logistics/customer-returns/{shipment_id}` — карточка и история;
- `POST /api/bitrix/logistics/customer-returns/{shipment_id}/pickup` — действие
  «Забрали» от имени текущего пользователя сессии.

Следующий релиз связей добавляет:

- `GET /api/bitrix/logistics/customer-return-service-requests` — поиск обращений
  по сделке, ID, заголовку или ID тикета, включая закрытые;
- `PUT /api/bitrix/logistics/customer-returns/{shipment_id}/service-request-link`
  — установить, заменить или удалить связь; тело содержит только
  `serviceRequestItemId`;
- `GET /api/bitrix/logistics/customer-return-expertise` — связанные экспертизы
  и поиск кандидатов по номеру экспертизы или заказа;
- `PUT /api/bitrix/logistics/expertise/{case_id}/service-request-link` —
  установить или удалить связь экспертизы с обращением;
- реестр и карточка возвращают вложенные объекты `serviceRequest` и
  `expertiseCases`, сохраняя старые `bitrix_case_id` и `site_ticket_id` для
  совместимости.

Все методы используют существующую Bitrix-сессию, роль `returns`/`admin` и
backend-определение сотрудника и времени. Недоступность Bitrix24 при поиске или
чтении выбранной карточки возвращает `503` до изменения существующей связи.

BFF не принимает от браузера `created_by_bitrix_user_id`,
`picked_up_by_bitrix_user_id`, произвольный `source` или время получения:
идентификатор сотрудника и время проставляет backend из проверенной сессии.
Доступ имеют профили `logistics_user` с ролью `returns` и `admin`. Роль
`returns` не требует склада и не открывает сканер, мониторинг или разбор
внутренних перемещений.

Worker `python -m tasks.customer_return_bitrix_worker` по умолчанию работает в
read-only `dry_run`. Режим `--check` не обращается к БД и сети. Режим `--apply`
разрешён только при явном `CUSTOMER_RETURN_BITRIX_WRITES_ENABLED=true`, настроенных
webhook и ответственном. Outbox использует lease, backoff и лимит попыток;
повторные вызовы Bitrix24 защищены служебными метками задачи и комментариев.

В API не передаются обязательные телефон, адрес или ФИО клиента. Для связи
используются технические ссылки `bitrix_case_id`, `site_ticket_id`,
`onec_order_ref` и безопасный `source_ref`.

# Invariants

- уникальность отправления задаётся нормализованной парой
  `carrier + tracking_number`;
- событие и outbox-действие имеют уникальные ключи дедупликации;
- внешнее событие не может автоматически понизить `picked_up` или
  `onec_return_confirmed` до транспортного статуса;
- подтверждение «Забрали» и 1С-сверка — отдельные бизнес-события, а не статусы
  API перевозчика;
- любой исходный код статуса и безопасный payload доступны для аудита;
- операции записи в 1С отсутствуют;
- классы и таблицы нового контура имеют префикс `CustomerReturn` /
  `customer_return_` и не пересекаются с `LogisticsTransfer`.

# Errors / Edge Cases

- пустой или невалидный трек отклоняется до записи;
- один трек у разных перевозчиков считается разными отправлениями;
- конфликт `source_ref` с другой парой carrier/track возвращает `409`;
- событие без внешнего ID получает воспроизводимый dedupe key из перевозчика,
  трека, кода статуса и времени события;
- событие, пришедшее вне порядка, сохраняется в истории, но не изменяет текущий
  статус, последний статус перевозчика, дату его события и срок хранения;
- конкурентная регистрация одной пары `carrier + tracking_number` возвращает
  запись победившей транзакции и не отдаёт наружу ошибку уникального индекса;
- неизвестный carrier первой версии возвращает `422`;
- неизвестный provider status не теряется и переводит текущий транспортный
  статус в `exception`, если возврат ещё не забран;
- отсутствие срока хранения не блокирует `arrival_task`, но не создаёт
  календарные напоминания;
- падение Bitrix24 не откатывает полученный статус: outbox остаётся готовым к
  повторной обработке.
- миграция заполняет `service_request_item_id` из числового `bitrix_case_id`,
  затем через локальную пару `site_ticket_id -> site_service_request_case`;
  неразрешённые ссылки остаются пустыми;
- изменение или удаление обращения не может удалить уже привязанную сделку;
  изменить сделку на несовместимую при активном обращении нельзя;
- каждое фактическое link/relink/unlink отправления и экспертизы содержит автора,
  прежний и новый ID в истории.

# Review Notes / Risks

- API статусов Почты России и СДЭК нужно сверить с официальными контрактами до
  включения polling/webhook; текущий адаптер не должен угадывать production URL
  и credentials;
- Bitrix24 task ID сохраняется только после успешного внешнего вызова;
- сырые payload не должны содержать неограниченные персональные данные или
  секреты;
- срок хранения может меняться после прибытия: уникальные action key запрещают
  дубликат, а изменение `due_at` должно обновлять ещё не выполненное действие;
- rollout требует миграции, настройки internal token, проверки прав Bitrix24 и
  отдельного smoke без записи в 1С.

# Rollout

1. Применить миграцию при выключенных внешних polling/webhook и Bitrix worker.
2. Проверить существующий Bitrix app URL `/bitrix/logistics`; для пилотных
   сотрудников онлайн-отдела использовать роль `returns`, а действующие
   администраторы логистического пилота получают раздел через роль `admin`.
3. Проверить дедупликацию, историю и формирование outbox без внешних side effects.
4. Подключить worker Bitrix24, проверить одну тестовую задачу и напоминания.
5. Подключить read-only сверку 1С.
6. По отдельности включить официальные интеграции Почты России и СДЭК.
7. Яндекс Доставку подключить новым адаптером после отдельной приёмки контракта.

Rollback: выключить producers/workers и оставить данные реестра для аудита;
откатывать миграцию только если таблицы пусты либо данные отдельно сохранены.

Для релиза связей rollback ограничен выключением
`CUSTOMER_RETURN_SERVICE_LINKS_ENABLED`; новые поля и аудит сохраняются, downgrade
миграции в Production не выполняется. После локальной приёмки отдельной командой
выполняется production smoke: обращение со сделкой, поздняя привязка, две отправки
по одному обращению, обращение с экспертизой и конфликт разных сделок.

Следующие отдельные релизы: worker задач и напоминаний с read-only сверкой 1С;
официальные API Почты России и СДЭК; адаптер Яндекс Доставки после проверки
контракта и доступов.
