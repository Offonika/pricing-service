# Автозаказ дисплеев: краткий документ проекта

- **Статус:** рабочий brief после пилотного dry-run
- **Дата среза:** 2026-07-05
- **Контур:** закупки / дисплеи / 1С / РММЗ / TopControl / pricing-service

## Суть

Проект переводит закупку дисплеев из ручного заказа "по опыту" в управляемый автозаказ. Автозаказ здесь не значит, что программа сама покупает товар. Правильный смысл: система готовит объяснимый проект заказа, показывает причины и риски, а человек утверждает спорные места перед созданием черновика в 1С.

Карточка номенклатуры в 1С остается источником свойств товара. Но для закупки этого мало. Нужен расчетный слой, который отвечает:

- можно ли товар заказывать автоматически;
- сколько заказать и почему;
- у какого поставщика;
- какой срок поставки реально ожидать;
- не лучше ли перейти на аналог;
- нет ли ручного блокера, неликвида или мертвого спроса.

## Проблема

В одной папке "дисплеи" смешаны разные товары: ходовые позиции, новинки, старые аналоги, товары под внутреннюю потребность, мертвые позиции, товары с разными сроками поставщика и дороги. Если считать все одной формулой, заказ раздувает склад. Если все делать руками, теряется скорость и контроль.

Проект строит середину: автомат считает рутинную часть, но каждая строка заказа объяснима и проверяема.

## Принятые правила

1. `Статус ассортимента` и `Скорость автозаказа` - разные свойства. Один товар в статусе `ПРОДАЖА` может быть `super_fast`, `fast`, `normal` или `slow`.
2. `nonliquid`, `on_demand`, `do_not_order` блокируют обычный автозаказ.
3. Внутренние потребности склада видны в анализе, но не считаются обычным рыночным спросом.
4. Если товар старше 180 дней, поступал мало, не продавался и потребность не подтверждена, он уходит в ручной контур.
5. В группе аналогов заказ должен получать лучший рабочий SKU, а не исторически привычная позиция.
6. Срок поставки должен быть живым: создание заказа поставщику -> сдача в cargo -> поступление.
7. Сезонность дороги обновляется отдельно: границы, праздники и логистические сбои должны менять расчет еженедельно.
8. Первая запись в 1С - только после dry-run, Excel-проверки и ручного осмотра.

## Рабочие статусы товара

| Этап | Смысл | Автозаказ |
| --- | --- | --- |
| `Плод` | товар появился, спрос не доказан | нет |
| `Новинка` | товар тестируется | ограниченно |
| `ПРОДАЖА` | спрос доказан | да, если нет блокеров |
| `Review` | данные спорные | нет |
| `Под заказ` | только под конкретную потребность | нет общего автозаказа |
| `Неликвид` / `Не закупать` | товар блокируется | нет |
| `Пенсия` | вывод из активной работы | только ручное решение |

## Что должно жить отдельными свойствами

- `Статус ассортимента` - жизненный этап товара.
- `Скорость автозаказа` - допустимое покрытие в днях.
- `Скорость продажи` - фактический спрос в доступные дни.
- `Качество товара` - ORIG, ORIG100, OLED, In-Cell, рамка и т.д.
- `Победитель аналога` - SKU, которому отдается заказ внутри группы.
- `Уверенность срока поставки` - можно ли верить истории.
- `Ручной блокер` - причина, почему автомат не имеет права заказать.
- `Ответственный` - кто должен проверить нестандартные строки.

## Роль человека

Человек не пересчитывает весь заказ руками. Он проверяет то, что автомат еще не должен решать сам: крупные количества, спорные аналоги, нестандартного поставщика, необычный срок, низкую уверенность данных и расхождение со старым инструментом.

На текущей стадии подготовлен Excel и черновик задачи Омару Бочарову. Задача не опубликована, заказ в 1С не создан.

После подключения 2026-07-06 адаптивный расчет перестал быть только разовым
отчетом: `lead time` - срок поставки обновляется ежедневно утром, а автозаказ
строит `display-auto-order-adaptive-sync-ready.csv` как основной вход для Bitrix.
Контрольный прогон без записи в Bitrix на 2026-07-06 дал 24 строки / 624 шт.

Дополнительно подключен event trigger - запуск по событию: когда в открытом
заказе поставщику появляется новая дата `Сдача в cargo`, пересчет `lead time` -
срока поставки запускается сразу после синхронизации 1С -> Bitrix, а не ждет
только утреннего расписания.

Следующее уточнение графика: данные обновляются ежедневно, но документ
`Потребность на заказ` создается по order schedule - графику заказа. Предложение:
`super_fast` - два раза в неделю, `fast` - раз в неделю, `normal` - раз в две
недели, спорные статусы - только в manual_review - ручную проверку.

## Вопрос проекта

**Для чего существует этот проект?**

## Ответ проекта

Чтобы деньги в закупке работали быстрее и безопаснее: ходовые дисплеи были в наличии, мертвые и спорные позиции не попадали в автоматический заказ, аналоги выбирались осознанно, а каждая строка заказа имела понятную причину.

Цель проекта - не заменить закупщика, а дать ему управляемый инструмент: программа готовит расчет, показывает риски и доказательства, человек утверждает границы, а 1С получает только проверенный черновик заказа.

## Критерий развития

Следующая доработка полезна, если она увеличивает долю безопасного автозаказа без раздувания склада. Если доработка не помогает принять решение "заказать / не заказать / проверить руками", ее надо отложить или вынести в соседний контур.
