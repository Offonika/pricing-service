# Смарт-процесс Закупка/Заказ и автозаказ: исторический единый контур

Дата среза: 2026-07-05

Статус: исторический материал. Документ больше не является рабочим планом или
источником актуальной архитектуры. Его заменил
`docs/specs/assortment-status-contour-plan.md`; технический источник по рабочему
OAuth-приложению — `docs/specs/procurement-order-formation-smart-process.md`.
Окончательная судьба семи старых правил зафиксирована в
`docs/specs/assortment-status-legacy-rule-inventory.md`; наличие правила ниже не
означает, что оно исполняется текущим кодом.

Разделы `Открытые вопросы до испытания`, `Шаги до первого испытания` и `Шаги до
автономного запуска` ниже сохранены только для истории и не являются текущей
очередью работ.

## Вопрос проекта

Для чего существует проект?

## Ответ проекта

Чтобы деньги в закупке работали быстрее и безопаснее: ходовые товары были в
наличии, мертвые и спорные позиции не попадали в автоматический заказ, аналоги
выбирались осознанно, а каждая строка заказа имела понятную причину.

Проект не заменяет закупщика. Он дает закупщику рабочий инструмент: программа
готовит расчет, показывает риски и доказательства, ответственный человек
утверждает границы, а 1С получает только проверенный черновик.

## Зафиксировано на 2026-07-20

Блок собирает решения по закрытию открытых вопросов статуса `Рабочий` -
эффективное наличие, роли складов, каналы, автоматизация масштабирования. Если
между разделом «Разрез складов» выше и этим блоком есть расхождение,
использовать этот блок как актуальную договоренность. Полный разбор с
утверждёнными формулами, реальной активностью по складам за 13 месяцев и
примерами - в
`reports/assortment_lifecycle/2026-07-20/supplier-order-working-status-decisions-2026-07-20.md`.

| Тема | Что зафиксировано |
| --- | --- |
| Переход в `Рабочий` | Решение изменено: `5` поступлений за `180` дней -> автоматический переход, без ручного подтверждения ответственного за папку. Отменяет прежнее правило «оба условия одновременно» (5/180 + подтверждение Омара) из дизайн-документа и код-гейта `approve_lifecycle_transitions` - код пока не обновлен, это только решение |
| Дни эффективного наличия - формула | Принятая формула восстановления спроса: `виртуальные_продажи = дни_без_остатка × (реальные_продажи / календарные_дни)`; `скорость = (реальные + виртуальные) / календарные_дни`. Мягче, чем простое исключение дней без остатка - не переоценивает короткие всплески |
| Уровень расчета | Скорость и потребность считаются **по каждой точке продаж отдельно**, не суммарно по сети: излишек на одном складе не должен маскировать дефицит на другом. Правило дополнительно подтверждено нашей находкой про Сдэк Склад |
| Потребность точки - формула | `потребность = скорость_точки × целевые_дни_покрытия + подтвержденные_заказы - свободный_остаток_точки - товар_в_пути`. Перед тем как остаток идет в заказ поставщику, сначала закрывается перемещением между точками |
| Сдэк Склад | Реальный высокоактивный узел (184186 ед. активности за 13 мес., 1775 из 2663 SKU дисплеев) - подтвержден как настоящий центральный/распределительный склад, хотя в конфиге сейчас `is_transit`. Для формулы точек продаж его количество = `0` - не входит в свободный остаток магазинов, это отдельный канал |
| Мертвые склады | `Новый центральный` и `Онлайн склад` - `0` активности за 13 месяцев для дисплеев; `Онлайн склад`, вероятно, переименован из бывшего магазина `Люблино 1-2` (общий адрес по карточке 1С). `Оптовый склад` и `Склад Закупка` - активность практически `0` |
| Сайт и Опт | Подтверждено (источник - чат 6 июля): `Сайт` - канал спроса, не физическая точка со своим остатком; `Оптовый склад` в сценарии сайта - технический транзит под конкретный заказ, не свободный остаток и не день наличия. **Срок действия решения (2026-07-21):** это верно только пока `Сайт` создает документ `Реализация` в 1С сам. Планируется переход `Сайта` в роль онлайн-распределительного центра/точки отгрузки без собственной `Реализации` - когда это изменится, роль `Сайта` в формуле нужно пересмотреть заново, не считать текущее решение окончательным |
| Маркетплейс | Решение от 6 июля остается в силе и не меняется: пороги `10-30/30-70/70+` с готовыми действиями на каждый (см. раздел «Разрезы спроса по типу покупателя»). Пропорциональное смешение (идея закупщика) допустимо только как уточнение **внутри** зоны `30-50%` (там уже есть защита минимумом `7` продаж МП), не как замена категориям и не в крайних зонах |
| Роль склада - источник | Заведено новое свойство 1С `Роль склада` (справочник «Склады», тип «Значения свойств объектов»): `Точка продаж`, `Центральный`, `Транзит`, `Брак`, `Резерв`, `Производства`, `Транзит/Брак` (комбинированное значение для складов с двумя ролями). Старое свойство `Магазин` (Булево) признано ненадежным - заполнено на `5` из `~30` складов, с ошибкой (`Уценка`) - не использовать как правило |
| Роль склада - готовность данных | На момент фиксации решения чтение значений `Роль склада` через прямой SQL-доступ к отчетной копии базы 1С не подтверждено - возможна задержка репликации нового объекта метаданных. Требует уточнения у ответственного за 1С (Кештов) |
| Автоматическое подключение новых складов | **Уточнено (2026-07-21):** склад с активностью больше `5` поступлений и `2` расходов (качество только `Новый`), при остатке `0` до начала этой активности, автоматически помечается статусом `неопределен, ждет менеджера` - НЕ подключается сразу как учетник для остатка и НЕ входит в расчет остатка/наличия до подтверждения человеком. Еженедельная проверка по понедельникам. Автоматически создается задача в Bitrix старшему отделу закупки и коммерческому директору с явным решением подтвердить роль (согласовано пользователем: "согласен через менеджера") |
| Раннее окно триггера партийной ошибки - длина окна | **Уточнено (2026-07-21):** для карточек, уже дошедших до статуса `Рабочий` (устоявшийся товар, есть история 90-180 дней) - окно проверки `90` дней, скользящее. Для новых карточек (`Новинка`/`СП`, еще нет 90 дней истории) - окно открытое с даты первой продажи до накопления минимума `5` возвратов качества `Новый`, без фиксированной верхней границы. Причина разделения: 90 дней актуальнее многолетней истории для устоявшегося товара, но у новой карточки просто еще нет 90 дней данных, чтобы это правило имело смысл |
| Открытый риск (не решено) | Логика выбора SKU-победителя аналога не учитывает статус «маркетплейс-only» - маркетплейс-only карточка теоретически может стать победителем группы и получить магазинную потребность, которая ей не принадлежит. Требует отдельной проверки в коде, не проверено окончательно |
| Аналог-победитель - направление решения (2026-07-21) | Пользователь подтвердил направление ("так и оставим" по текущему автоматическому механизму), но указал на неточность прежнего объяснения: одна карточка не должна автоматически "забирать" всю группу аналогов - обычно замена идет 1-к-1 или 1-к-паре карточек, не группой целиком. Проверено на реальном примере "iPhone 11" (не Pro): группа из `6` карточек под настоящим корнем `ОБЩИЙ КАТАЛОГ` - РБ000075803, РБ000050728, РБ000038144, РБ000065187, РБ000043823, РБ000044904. Одобренное пользователем направление (не построено): менеджер при подтверждении явно выбирает, КАКУЮ именно карточку(и) заменяет победитель, вместо автоматического распространения на всю группу |
| Возврат ≠ брак - проверено на всей базе | На 25396 возвращённых штук дисплеев за 180 дней 82.6% возвратов имеют причину `001. Не понадобился` при качестве `Новый` - это не брак. Настоящий технический брак (`Тачскрин не работает`, `Дисплей нет изображения` и т.д.) - около 11%. Раньше формула `net_sales_qty = продажи - возвраты` (см. пункт 5 разбора статуса `Рабочий`) без разбора причины и качества занижала реальный спрос почти на порядок сильнее, чем предполагалось |
| **Спрос брутто - выбран и подтверждён на реальных данных (2026-07-21)** | Финальное решение: демонстрационная база заказа считается по всем реализациям, без вычета возвратов вообще (`gross_demand_qty = sales_qty`). Проверено на 2144 карточках дисплеев с продажами за 180 дней: сумма нового способа `155835` шт. против текущего кода (`продажи - все возвраты`) `130213` шт. - разница `+19.7%` по всей категории. Полное сравнение по каждой карточке - `reports/assortment_lifecycle/2026-07-21/display-gross-demand-vs-current-diff-2026-07-21.csv`. Это первый пункт формулы `Рабочий`, прошедший полный цикл design -> diff на реальных данных -> подтверждение пользователем - готов к реализации в коде |
| Ранний триггер партийной ошибки (пересорт/ревизия) | Правило (исправлено 21.07): если одновременно `(а)` возвратов с качеством `Новый` `>= 5` штук за окно **и** `(б)` доля этих возвратов от продаж за то же окно `>= 40%` - продажа/автозаказ карточки останавливается **немедленно**, а не «не допускается до Рабочий». Обоснование правки: триггер типично срабатывает на 20-30 день продаж, когда карточка ещё в Новинке/СП - блокировать путь к `Рабочий` бессмысленно, туда карточка и так не дошла бы так скоро; реальный вред (продажа не той версии живым покупателям) идёт в моменте и должен останавливаться сразу. Задача в Bitrix закупщику - срочная, с просьбой остановить продажу физически в точках/на сайте. Второе условие (доля, не только счётчик) отсекает ложные тревоги на ходовых товарах |

## Суть контура

| Система | Роль |
| --- | --- |
| 1С | Главный источник факта: заказы, продажи, возвраты, остатки, поставщики |
| pricing-service | Расчет потребности, рисков, сроков, аналогов и объяснения |
| Bitrix smart-process - смарт-процесс | Рабочая карточка закупщика: очередь решений, подтверждения, статусы |
| Ответственный | Принимает решение: подтвердить, изменить, запретить или отправить на разбор |

Главная логика: программа считает рутинную часть, но не должна покупать товар
вслепую. Чем выше риск, сумма, брак или неуверенность в данных, тем быстрее
строка уходит к человеку.

| Фактическая карта полей | `build/bitrix/procurement_order_mapping.json` |

Текущий смарт-процесс `Закупка/Заказ` начинается только после появления
готового `ЗаказПоставщику` в 1С. Все, что происходит до этого: расчет
потребности, проверка аналогов, матрица, ручное подтверждение и решение
создавать заказ, относится к отдельному будущему smart-process -
смарт-процессу `Формирование заказа`.

Системная стартовая стадия Bitrix `NEW` в `Закупка/Заказ` используется как
`Заказ поставщику`. Бизнес-стадии `Потребность` в этом процессе больше нет.
Если в live Bitrix остались старые карточки авто-заказа без номера 1С, это
legacy-хвост - старый хвост контура, а не новая норма процесса.

Принцип подготовки к переезду:

| Что | Как переносить |
| --- | --- |
| Правила автозаказа | Остаются в `pricing-service` и отчетах; новый Bitrix-процесс получает результат, а не становится расчетной базой |
| Товар | Главный ключ - код/идентификатор 1С товара, а не ID карточки Bitrix |
| Статус ассортимента | Переносится как управленческое поле: решение, причина, утвердил, дата, коммерческие признаки |
| `Потребность` | Переносится как набор полей доказательства: продажи, остатки, товар в пути, маркетплейс-срез, риск, причина заказа |
| Ручные исключения | Переносятся как записи в `display-manual-overrides.json` и как история решения, а не как скрытая логика в старой карточке |
| Старый `entityTypeId=1056` | Использовать только для чтения текущей упаковки до отдельного решения владельца |

До выбора нового процесса запрещено менять live-синхронизацию. Когда новый
smart-process будет назван, сначала создается новая mapping - карта полей и
выполняется dry-run - проверочный прогон без записи.

Категории:

| Категория | Для чего |
| --- | --- |
| `Обычный` | Готовый обычный заказ поставщику из 1С без отдельной cargo/ВЭД-логики |
| `Карго` | Путь от заказа поставщику до сдачи в cargo, пути, приемки и раскладки |
| `ВЭД импорт` | Импорт с документами, платежным агентом, ГТД и остановками по риску |

Cargo - карго-цепочка:

1. Заказ поставщику.
2. Товар готов к сдаче в cargo.
3. Сдано в cargo.
4. Заявка на оплату / оплата в работе.
5. Товар в пути.
6. Доставка своими силами.
7. Зона разборки.
8. Приемка товара.
9. Поступление в 1С.
10. Штрихкодирование.
11. Зона раскладки.
12. Раскладка завершена.
13. Проблема / отмена.

Важно по товару в пути: проведенный `ЗаказПоставщику` в 1С уже участвует в
расчете как pipeline - цепочка поставки, даже если дата `Сдача в cargo` еще не
стоит. В этом состоянии товар находится в ранней ветке `supplier_processing` -
сборка/подготовка поставщиком. После даты `Сдача в cargo` он переходит во
вкладку `cargo_handoff / in_transit` - сдано в cargo / в пути. Поэтому
автозаказ не ждет cargo-дату, чтобы вычесть количество из новой потребности.

Граница процессов:

| Процесс / вкладка | Готовность | Когда используется | Микро-задачи внутри |
| --- | --- | --- | --- |
| `Формирование заказа / Потребность` | Готово по правилам; нужна отдельная техническая публикация | До создания заказа поставщику: старый товар, новый SKU или новая модель | Для товара с историей: причина заказа, продажи, остатки, товар в пути, сумма, `% брака`, аналоги, решение ответственного. Для нового товара: ранние сигналы спроса, аналоги-доноры, наличие запчастей в РФ, цена, поставщик, стартовая партия |
| `Закупка/Заказ / Заказ поставщику` | Реализуется как старт старого процесса | `ЗаказПоставщику` уже создан в 1С, cargo-даты еще может не быть | Проверить поставщика, количество, сумму, валюту, цену, статус сборки, ожидаемую дату сдачи в cargo, аналоги, качество, онлайн-сопоставление и блокеры |
| `Закупка/Заказ / Карго / В пути` | Следующий процесс на разбор | Дата `Сдача в cargo` появилась | Проверить cargo-дату, оплату, маршрут, ожидаемую приемку, риск задержки, связь с open order - открытым заказом поставщику |
| `Закупка/Заказ / Приемка / Разбор / Раскладка` | Следующий процесс на разбор | Товар физически приехал | Принять, сверить количество, провести поступление, штрихкодировать, разложить, закрыть отклонения |

Как читать вкладку `Потребность` для новых товаров: у нового SKU может не быть
продаж, `% брака`, остатков и товара в пути. В этом случае вкладка не требует
эти поля как готовый факт, а показывает основание прогноза.

| Что проверяем | Товар с историей | Новый товар |
| --- | --- | --- |
| Продажи | Факт продаж из 1С за 180 дней | Продажи analog donor - аналога-донора: предыдущая модель, близкая серия или совместимая запчасть |
| Остаток | Текущий свободный остаток в 1С | Обычно 0; важно показать, что это первая закупка |
| Товар в пути | Проведенные заказы поставщику и cargo | Если заказ поставщику уже есть, показывать как `У поставщика / сборка`; если нет, поле остается пустым |
| `% брака` | Возвраты покупателя именно как брак | Proxy - заменитель показателя: брак по бренду, группе, качеству и поставщику |
| Аналоги | Реальные аналоги в ассортименте | Донорская группа: предыдущие модели телефонов, совместимые дисплеи, близкие ценовые классы |
| Количество | Расчет от продаж, остатка, пути и срока | Стартовая партия от спроса по донорам, цены, доступности в РФ и ручного подтверждения |

Источники для новой модели телефона и новой запчасти:

| Источник | Что подтягивать | Как использовать |
| --- | --- | --- |
| Существующий `Market Research / Demand` - контур рынка и спроса | `smartphone_releases`, `phone_models`, `keywords`, `keyword_demands`, weekly buyer digest - недельный обзор закупщику | Использовать как главный вход по новинкам, чтобы не создавать второй канал сбора спроса |
| Модели телефонов | дата анонса, дата выхода, статус `announced/released`, популярность, поколение, связь с прошлой моделью | Привязать прогноз к донору: продажа телефона + срок службы устройства = будущая потребность в запчасти и ремонте |
| Интернет-спрос по запчастям | показы и клики по фразам "дисплей/экран/тач/стекло + модель", витрина `vw_bi_model_demand_30d` | Поднять или понизить стартовую партию по реальному интересу к запчасти |
| 1С / РММЗ | заявки на ремонт, отказы из-за отсутствия, обращения по модели телефона | Ранний внутренний спрос |
| Сайт и внутренний поиск | поиски по модели, клики `нет в наличии`, запросы менеджерам | Сигнал интереса до появления продаж |
| История аналогов | продажи предыдущей модели, той же линейки, похожего дисплея | База для первой партии |
| Поставщики | наличие в прайсах, MOQ - минимальная партия, цена, срок сборки, качество | Проверка возможности купить и риска по сроку/цене |
| Российский рынок запчастей | наличие у конкурентов, маркетплейсы, сервисные поставщики, цены в РФ | Проверка, появилась ли запчасть в России и насколько рынок живой |

### Разрезы спроса по типу покупателя

Факт продаж нельзя смотреть только одной общей суммой. Один и тот же дисплей
может быть ликвидным для покупателей-маркетплейсов и одновременно слабым для
магазинов. Если смешать эти каналы в одну скорость продаж, автозаказ может
завести товар как магазинную матрицу, хотя реальный спрос был только под
перепродажу на маркетплейсах.

Источник типа покупателя в 1С: карточка контрагента, основной вид деятельности
`_Reference54._Fld619RRef -> _Reference23`. Для маркетплейса используем вид
деятельности `РБ0000021 Маркетплейс`.

Вкладка `Потребность` и отчеты автозаказа должны показывать не один показатель
продаж, а минимум три картины:

| Разрез | Что показывает | Как использовать |
| --- | --- | --- |
| `Весь спрос` | Общие продажи за окно, как сейчас видит автозаказ | Контроль общей активности товара |
| `Спрос без маркетплейса` | Покупки магазинов, сервисов и обычных покупателей | База для магазинной матрицы и общего автозаказа |
| `Только маркетплейс` | Покупки контрагентов с видом деятельности `Маркетплейс` | Отдельный канал спроса; не доказывает ликвидность для магазинов |

Обязательные метки для просмотра:

| Метка | Условие | Решение |
| --- | --- | --- |
| `Только маркетплейс` | Обычного спроса нет, есть только маркетплейс-спрос | Не заводить в магазинную матрицу без ручного подтверждения |
| `Маркетплейс доминирует` | Доля маркетплейса высокая, ориентир от 70% | Разбирать отдельно: товар может быть нужен маркетплейсам, но не магазинам |
| `Смешанный спрос` | Есть оба канала, ориентир 30-70% маркетплейса | Показывать две потребности: магазинную и маркетплейсную |
| `Обычный спрос` | Маркетплейса нет или он малый | Можно считать обычным основанием для автозаказа, если нет других блокеров |

Самая опасная автоматическая метка - риск неликвида при отказе
маркетплейсщика. Она нужна не для изменения количества сразу, а для
обязательного ручного просмотра.

| Метка риска | Условие | Действие |
| --- | --- | --- |
| `critical_marketplace_refusal_nonliquid_risk` | обычный спрос = 0 или маркетплейс >=70%, и есть остаток/путь/заказ | Не заказывать автоматически; решение только вручную |
| `high_marketplace_refusal_risk` | маркетплейс 50-70% и есть остаток/путь/заказ | Разделить магазинную и маркетплейсную потребность |
| `medium_channel_split_required` | маркетплейс 30-50%, минимум 7 продаж МП, и есть экспозиция или заказ | Итоговая потребность = магазинная + маркетплейсная (складываются, не выбор); менеджер подтверждает итоговое количество, как обычно; раздельный показ — только ради прозрачности риска (уточнено 2026-07-25, см. `assortment-status-legacy-rule-inventory.md`, раздел 2) |
| `watch_order_impact` | маркетплейс 10-30%, но влияет на заказ минимум на 10 шт. | Сравнить заказ по всему спросу и без маркетплейса |
| `low_marketplace_dependency` | маркетплейс не главный риск | Долю показывать справочно |

Практическое правило: маркетплейс-спрос не должен автоматически переводить товар
в статус `Матричный` для магазинов. Для матрицы нужен подтвержденный спрос без
маркетплейса или отдельное ручное решение, что товар держим именно под
маркетплейс-канал.

Единичные критические случаи не должны тормозить проект отдельной
автоматизацией. Пример на срезе 2026-07-06: `РБ000063286` оставляем в ручной
проверке с объяснением: обычный спрос без маркетплейса `0`, доля маркетплейса
`100%`, риск неликвида при отказе маркетплейсщика. Автоматический заказ и
перевод в магазинную матрицу запрещены без отдельного ручного решения.

### Разрез складов и средняя продажа по дням наличия

Среднюю продажу нельзя считать только как `продажи / 180 календарных дней`.
Для автозаказа важна не календарная скорость, а скорость в те дни, когда товар
реально был доступен покупателю в физических точках продаж.

Что показала проверка на срезе 2026-07-06:

- продажи сейчас берутся по складам `sells_systematically`;
- в этот список входят физические точки, но также `Сайт`, `Онлайн склад` и
  `Оптовый склад`;
- центральные склады `Новый центральный` и `Склад Закупка` в текущий
  `free_stock_qty` не смешиваются, они выводятся отдельно как
  `central_stock_qty`;
- `avg_daily_sales_qty` сейчас фактически считается как чистые продажи за 180
  дней, деленные на 180;
- дни реального наличия в физических точках продаж пока не считаются;
- остатки 1-2 штуки в точках сейчас считаются свободным остатком, если они не
  зарезервированы.

Это опасно для РММЗ и автозаказа: если программа при перемещениях оставляет на
точке 1-2 штуки под сайт или отдельные заказы, товар выглядит доступным, хотя
для магазина это не полноценное наличие. Тогда свободный остаток закрывает
потребность, средняя продажа занижается, а дальше занижается целевой запас и
итоговый заказ.

Правильные роли складов:

| Роль | Что входит | Как использовать |
| --- | --- | --- |
| `physical_sales_point` - физическая точка продаж | Магазины/точки, где товар реально продается покупателю | Входит в продажи, эффективные дни наличия и магазинную потребность |
| `online_site_reserve` - сайт/онлайн | `Сайт`, `Онлайн склад` | Показывать отдельно; не считать магазинным днем наличия |
| `wholesale` - опт | `Оптовый склад` | Показывать отдельным каналом; не смешивать с магазинной матрицей |
| `central_transfer_stock` - центральный/закупка/транзит | Центральные и транзитные склады | Использовать как источник перемещения, но не как день наличия в магазине |

Формулу средней продажи не переписываем целиком: меняется только источник числа
дней в знаменателе. Базовый смысл остается `продажи / дни`, но вместо
календарных 180 дней для магазинной скорости нужно передавать дни эффективного
наличия:

`store_avg_daily_sales_qty = store_net_sales_qty / effective_available_days`

Где `effective_available_days` - количество дней, когда в физических точках был
эффективный свободный остаток. Для пилота эффективным остатком считаем больше
`2` свободных штук на точке. Остаток `1-2` штуки показываем как
`technical_low_residue` - технический хвост, который не должен закрывать
магазинную потребность.

Остальные правила расчета не трогаем в этой доработке: `demand_multiplier` -
коэффициент спроса, `target_stock_qty` - целевой запас, safety stock -
страховой запас, округления, товар в пути и логика аналогов должны остаться
как есть. Меняется только подход к подсчету дней, когда товар действительно был
доступен в точках продаж.

Если дней эффективного наличия мало, строка получает низкую
`confidence score` - уверенность расчета и уходит в ручную проверку, а не в
автоматическое подтверждение.

В карточке `Потребность` нужно показывать отдельно:

| Поле | Зачем |
| --- | --- |
| Свободный остаток в физических точках | Видим реальную магазинную доступность |
| Эффективный остаток в физических точках `> 2` | База для дней наличия и покрытия |
| Остаток 1-2 штуки | Технический хвост, не полноценный запас |
| Сайт/онлайн | Отдельный резерв под сайт и онлайн-заказы |
| Опт | Отдельный канал, не магазинная матрица |
| Центральный склад | Источник перемещения, а не продажи |
| Дни эффективного наличия | Деноминатор для средней продажи |
| Средняя продажа по дням наличия | Правильная скорость спроса для заказа |

Если дефицит в магазинах можно закрыть центральным складом, система сначала
должна рекомендовать перемещение, а не закупку у поставщика.

### Сопоставление рынка и нашей номенклатуры

Для сигнала "рынок живой" не нужно всегда находить точный аналог нашего SKU.
Достаточно понять, что по этой модели телефона в РФ уже продаются дисплеи или
другие нужные запчасти. Для выбора конкретного товара в заказ точность должна
быть намного выше: совпадение только по грязному названию конкурента не
считается безопасным основанием для автозаказа.

Правильный путь - не сравнивать строку со строкой, а разбирать название на
признаки:

| Шаг | Что делаем | Пример |
| --- | --- | --- |
| `normalization` - нормализация | Убираем мусор и приводим термины к одному виду | `экран`, `дисплей`, `LCD`, `module` -> тип "дисплей" |
| `parsing` - разбор | Вытаскиваем признаки товара | бренд, модель, тип запчасти, качество, цвет, рамка |
| `alias` - словарь вариантов | Связываем разные написания одной модели | `айфон 11`, `iphone11`, `iPhone 11` |
| `compatibility` - совместимость | Понимаем, к каким моделям подходит запчасть | один дисплей может подходить к 2-5 моделям |
| `confidence score` - оценка уверенности | Ставим процент доверия и маршрут решения | 95% можно принять, 65% только ручная проверка |

Уровни использования:

| Уровень совпадения | Как использовать |
| --- | --- |
| Совпала модель телефона + тип запчасти | Только рыночный сигнал: запчасть уже появилась и рынок живой |
| Совпала модель + дисплей + качество/тип | Можно учитывать в прогнозе спроса и стартовой партии |
| Совпала модель + дисплей + качество + рамка/цвет/партномер | Можно считать кандидатом в аналог нашего товара |
| Есть сомнение или конфликт признаков | Только `manual_review` - ручная проверка, без автозаказа |

Практическое правило: слабое совпадение дает рыночный сигнал, сильное
совпадение дает кандидата в аналог, спорное совпадение уходит к человеку.
Ни один рыночный сигнал сам по себе не должен создавать заказ поставщику.

В проекте уже есть база для этого контура: `competitor_item_match` хранит
сильное сопоставление конкурентной позиции с нашим товаром, `phone_model_alias`
и `device_brand_aliases` держат варианты написания, `product_phone_model` и
`competitor_item_compatibility` связывают товары с моделями телефонов, а
`compatibility_mapping_decisions` фиксирует ручные решения по спорной
совместимости. Поэтому для автозаказа нужно переиспользовать этот слой, а не
строить отдельное сопоставление по названиям.

В проекте уже есть готовый путь для новинок: `smartphone_releases` - таблица
анонсов смартфонов, синхронизация в `phone_models`, генерация фраз в `keywords`,
сбор спроса в `keyword_demands` и BI-витрина `vw_bi_model_demand_30d`. Поэтому
автозаказ должен переиспользовать этот контур как источник сигналов, а не
создавать отдельный робот.

Логика прогноза для новой запчасти:

`продажи телефона -> installed base - парк устройств -> срок службы -> ремонты -> спрос на запчасть`

Добавляется слой `model lifecycle` - жизненный цикл модели телефона и
`part lifecycle` - жизненный цикл запчасти. Он нужен, потому что дисплей,
совместимый с несколькими моделями, может жить дольше и продаваться ровнее, чем
дисплей только под одну модель.

| Возраст модели телефона | Что смотрим | Как влияет на `Потребность` |
| --- | --- | --- |
| 0-3 месяца | Анонс, старт продаж, первые поисковые запросы | Не создавать автоматический заказ; только малая тестовая потребность и ручная проверка |
| 3-9 месяцев | Первые ремонты, рост запросов, наличие у поставщиков | Можно давать стартовую партию при подтвержденном спросе и понятном поставщике |
| 9-24 месяца | Парк устройств растет, ремонтов становится больше | Основной период роста спроса на дисплеи |
| 24-48 месяцев | Массовая ремонтная стадия | Можно держать регулярный автозаказ при стабильных продажах |
| 48+ месяцев | Модель стареет | Снижать заказ, кроме товаров с широкой совместимостью и живым спросом |

Для статуса `Плод` граница жестче, потому что это не рабочий товар, а карточка
до первого подтвержденного движения. Если модель телефона уже `48+` месяцев, она
считается старой именно для тихого `Плод`: такая карточка не должна месяцами
висеть в обычной вкладке без сигнала. `84+` месяца - порог жесткого
`РМ / Родился мертвым`, если движения нет.

| Возраст модели телефона | Максимум в тихом `Плод` без сигнала | Действие |
| --- | ---: | --- |
| `0-24` месяца | `180` дней | Обычный срок ожидания первых сигналов |
| `24-48` месяцев | `90` дней | Подсветить как ленивый `Плод` и проверить причину |
| `48-84` месяца | `45` дней | Убрать из обычной вкладки `Плод`, открыть `РМ-кандидат` / ручную проверку |
| `84+` месяца | `14` дней | Без явного источника создания - `РМ-кандидат`; при `180+` днях карточки и нуле движения - `РМ` |

Совместимость меняет картину спроса:

| Тип запчасти | Как живет спрос | Что делать |
| --- | --- | --- |
| Под одну модель | Спрос сильнее зависит от возраста этой модели | Быстрее снижать заказ при старении модели |
| Под несколько моделей | Спрос живет дольше и ровнее | Учитывать общий installed base - парк всех совместимых моделей |
| Под популярную линейку | Спрос может расти даже после старения одной модели | Смотреть не одну модель, а всю donor group - донорскую группу |

Чем популярнее модель телефона и чем больше времени прошло после выхода, тем
выше вероятность спроса на дисплей. Если модель новая, но уже активно продается
и по ней растут поисковые запросы, `Потребность` создает малую стартовую партию
и отправляет строку в ручную проверку.

Для нового товара расчет должен иметь `confidence score` - оценку уверенности.
Если уверенность низкая, строка не уходит в автоматическое подтверждение, а
попадает в ручную проверку с причиной: "новая модель, расчет по аналогам".

Если нужны более понятные названия без английского:

| Технический смысл | Человеческое название |
| --- | --- |
| `supplier_processing` | `У поставщика / сборка` |
| `cargo_handoff` | `Сдано в cargo` |
| `in_transit` | `В пути после cargo` |
| `warehouse_receiving` | `Приемка и раскладка` |

## Автозаказ дисплеев

Пилотная папка: `дисплеи`.

Ответственный: Омар Бочаров.

Автозаказ здесь означает не самостоятельную покупку, а подготовку проверяемого
проекта заказа.

Расчет отвечает:

- можно ли товар заказывать автоматически;
- сколько заказать;
- почему именно столько;
- какой товар уже в пути;
- какой срок поставки реально ожидать;
- какой аналог лучше заказать;
- где есть блокер, риск или ручная проверка.

Базовые правила на срезе:

| Правило | Значение |
| --- | --- |
| Окно продаж | 180 дней |
| Регулярность решения | 7 дней |
| Сборка поставщика | 18 дней |
| Логистика | 30 дней |
| Страховой складской запас | 25 дней |
| Минимальный заказ | если потребность больше нуля, округлять минимум до 1 |
| Верхний лимит по штукам | снят |
| Крупное округление | больше 2000 до 100, больше 1000 до 50, больше 100 до 10 |

Решение по первому пункту: adaptive lead time - адаптивный срок поставки
становится основным ежедневным расчетом автозаказа. Базовый dry-run -
проверочный расчет остается контрольным слоем, чтобы видеть расхождение и
ловить ошибки. Bitrix должен получать не дефолтный расчет 18 + 30, а
`display-auto-order-adaptive-sync-ready.csv` с живыми сроками поставщика,
дорогой, остатками и pipeline - товаром в цепочке поставки.

Подтверждение, что это уже было заложено:

- в `config/assortment/display-auto-order-policy.json` стоит daily evaluation -
  ежедневная оценка `20 9 * * *`, но отдельно указано, что размер заказа считает
  горизонт регулярной закупки;
- там же уже есть `order_cadence_days = 7` - период между закупочными решениями;
- в объяснении строки расчета уже выводится `график 7`, то есть график входит в
  формулу горизонта;
- после 2026-07-06 адаптивный `sync-ready` файл стал основным входом для Bitrix.

Разделяем два графика:

| График | Что делает | Частота |
| --- | --- | --- |
| Data refresh - обновление данных | Обновляет продажи, остатки, pipeline, lead time, cargo-даты, `% брака` | Ежедневно утром и дополнительно по новой дате `Сдача в cargo` |
| Order schedule - график заказа | Создает документ `Потребность на заказ` и очередь решений | По статусу/скорости товара, не обязательно каждый день |

Предлагаемый график создания `Потребность на заказ`:

| Статус / скорость | График документа | Почему |
| --- | --- | --- |
| `ПРОДАЖА` + `super_fast` | 2 раза в неделю: понедельник и четверг | Риск быстро потерять наличие; при критичном остатке разрешить внеплановый сигнал |
| `ПРОДАЖА` + `fast` | 1 раз в неделю | Текущий `order_cadence_days = 7` подходит как базовый график |
| `ПРОДАЖА` + `normal` | 1 раз в 2 недели | Не раздувать склад, но держать регулярную закупку |
| `Рабочий` без устойчивой скорости | 1 раз в 2 недели + manual_review - ручная проверка | Можно покупать, но автомату нужна причина и подтверждение |
| `Новинка` | Каждые 5 дней только в очередь проверки | Спрос еще не доказан, но раннюю ходовую карточку нужно поймать быстро; нужен малый тест или ручное решение |
| `Плод` | 1 раз в неделю только в очередь проверки | До первого заказа поставщику это сигнал спроса, а не доказанная продажа |
| `Review` | Еженедельная очередь Омара | Не создавать заказ без разбора причины |
| `Под заказ` | Только по клиентской/внутренней потребности | Общего автозаказа нет |
| `Неликвид` / `Не закупать` / `Пенсия` | Не создавать | Только месячный контроль, чтобы не забыть статус |

История заказов подтверждает, что единый ежедневный заказ по всем дисплеям не
нужен: по повторяемым группам в истории фактический интервал часто держится
около 9-13 дней, а текущий недельный график нужен как рабочий базовый слой для
ходовых товаров и раннего сигнала риска.

Внеплановый сигнал:

| Уровень | Когда включается | Что делать |
| --- | --- | --- |
| `warning` - предупреждение | Сборка у поставщика уже на 30% выше обычного срока, но минимум на 3 дня | Показать риск в карточке и отправить строку в manual_review - ручную проверку |
| `alarm` - тревога | Сборка у поставщика уже на 60% выше обычного срока, но минимум на 7 дней | Поднять приоритет: проверить поставщика, аналог, срочную замену или перенос закупки |
| `stockout_guard` - защита от опустошения склада | Дней свободного остатка меньше ожидаемого оставшегося срока поставки плюс 10 дней запаса | Создать внеплановую `Потребность на заказ` или ручную задачу до обычного дня графика |

Базу для 30% и 60% лучше считать не от простой средней, а от
`median / p75` - медианы или осторожного срока из `supplier_prepare_profile`.
Средняя легко портится редкими провалами, а медиана показывает нормальное
поведение поставщика. Если данных мало, берем общий дефолт 18 дней и ставим
низкую confidence score - уверенность расчета.

График с учетом себестоимости:

Анализ за 180 дней на срезе 2026-07-06 проверил 733 SKU со статусом `ПРОДАЖА`
и скоростью `super_fast / fast / normal`. В истории заказов поставщику найдено
1269 строк по 604 SKU. Подробный отчет:
`reports/assortment_lifecycle/2026-07-06/display-order-schedule-price-batch-analysis.md`.

Сырой минимум заказа часто равен 1-5 шт., поэтому его нельзя использовать как
правило партии. Для нормального минимума берем `p25` - нижний нормальный
квартиль, для целевой партии - `median / p75` - медиану или верхний осторожный
уровень.

| Скорость | `economy / mid_low` - дешевле | `mid_high / premium` - дороже |
| --- | --- | --- |
| `super_fast` | 1 раз в неделю, крупнее: партия ближе к `median / p75`; `stockout_guard` может создать внеплановый сигнал | 2 раза в неделю, меньше: партия ближе к `p25 / median`, выше `p75` - ручная проверка |
| `fast` | 1 раз в 2 недели, крупнее: партия ближе к `median / p75` | 1 раз в неделю или каждые 10 дней, партия ближе к `p25 / median` |
| `normal` | 1 раз в 3 недели, крупнее, но без раздувания склада | 1 раз в 2 недели, маленькая партия, крупная сумма - ручная проверка |

Простой смысл: дешевые позиции можно брать реже и пачкой, потому что они меньше
замораживают деньги. Дорогие позиции лучше смотреть чаще и брать меньшими
партиями, чтобы не раздувать сумму заказа и не ошибиться с аналогом/качеством.

Speed tiers - скоростные группы:

| Группа | Смысл | Поведение |
| --- | --- | --- |
| `super_fast` - супер-ходовая | высокий спрос | можно держать большее покрытие |
| `fast` - ходовая | стабильный спрос | автозаказ разрешен при отсутствии блокеров |
| `normal` - обычная | умеренный спрос | автозаказ осторожнее |
| `slow` - медленная | слабый спрос | не раздувать автоматом, отправлять на review - ручную проверку |

## Статусы товара

| Этап | Смысл | Автозаказ |
| --- | --- | --- |
| `Плод` | товар появился, спрос не доказан | нет |
| `РМ / Родился мертвым` | бывший `Плод`, который за `180+` дней не дал ни одного сигнала движения, а модель телефона уже старая | нет; скрывать из рабочей вкладки `Плод`, возвращать только через ручную проверку нового спроса |
| `Новинка` | товар тестируется | ограниченно |
| `ПРОДАЖА` | спрос доказан | да, если нет блокеров |
| `Review` | данные спорные | нет |
| `Под заказ` | только под конкретную потребность | нет общего автозаказа |
| `Неликвид` / `Не закупать` | товар блокируется | нет |
| `Пенсия` | вывод из активной работы | только ручное решение |

Важно: `Статус ассортимента` и `Скорость автозаказа` - разные свойства. Товар в
статусе `ПРОДАЖА` может быть быстрым, обычным или медленным.

## Отдельные свойства для автозаказа

| Свойство | Для чего |
| --- | --- |
| `Статус ассортимента` | Жизненный этап товара |
| `Скорость автозаказа` | Допустимое покрытие в днях |
| `Скорость продажи` | Фактический спрос в доступные дни |
| `Качество товара` | ORIG, ORIG100, OLED, In-Cell, рамка и т.д. |
| `Победитель аналога` | SKU, которому отдается заказ внутри группы |
| `Уверенность срока поставки` | Можно ли верить истории поставщика и дороги |
| `% брака` | Доля возвратов покупателя именно как "брак"; возвраты как "новый" не входят |
| `Сумма заказа по закупочной цене` | Сколько денег требуется по строке и документу потребности |
| `Риск суммы заказа` | Флаг ручной проверки для крупных сумм, даже если количество выглядит нормальным |
| `Ручной блокер` | Почему автомат не имеет права заказать |
| `Ответственный` | Кто проверяет нестандартные строки |

## Рабочее место ответственного

Основной инструмент ответственного: Bitrix smart-process - смарт-процесс
`Закупка/Заказ`.

Excel/CSV остаются как выгрузка и доказательная таблица, но не как главный
инструмент ежедневного решения.

Ответственный должен видеть:

| Блок | Что показывает |
| --- | --- |
| Очередь решений | `к заказу`, `ручная проверка`, `риск`, `запрещено` |
| Картина товара | продажи, остаток, товар в пути, сроки, аналоги, `% брака` |
| Рекомендация | сколько заказать, на какую сумму и почему |
| Риски | брак, спорный аналог, плохой срок, мало данных, крупная сумма |
| История | кто подтвердил, что изменил, почему |

Действия ответственного:

| Действие | Что значит |
| --- | --- |
| Подтвердить | Строка готова идти дальше в черновик 1С |
| Уменьшить количество | Ответственный вводит новое количество и причину |
| Заменить аналог | Выбирается другой SKU из группы аналогов |
| Сменить поставщика | Выбирается другой поставщик с учетом срока, цены и риска |
| Запретить заказ | Товар уходит в стоп с причиной |
| На разбор | Строка остается в ручной проверке |

Ручное решение по статусу ассортимента хранится в этой же Bitrix-карточке, в
секции `Статус ассортимента`. Это рабочий вход для Омара и других закупщиков,
когда товар нужно поставить в матрицу, оставить рабочим, перевести под заказ,
отметить как кандидата на замену, неликвид или `Не закупать`.

| Поле Bitrix | Для чего |
| --- | --- |
| `Статус ассортимента: решение` | Выбор управленческого статуса: `Матричный`, `Рабочий`, `Под заказ`, `Кандидат на замену`, `Неликвид`, `Не закупать` |
| `Статус ассортимента: причина` | Почему закупщик принял такое решение |
| `Статус ассортимента: утвердил` | Кто отвечает за решение |
| `Статус ассортимента: дата решения` | Когда решение принято |
| `Статус ассортимента: коммерческие признаки` | Дополнительные признаки через запятую, например `own_brand`, `exclusive`, `rare_market_item` |

Как читать это в списке `Закупка/Заказ`:

| Место | Что видно | Для чего |
| --- | --- | --- |
| Список карточек | Колонка `Статус ассортимента: решение` с одним выбранным значением по каждой карточке | Быстро увидеть и отфильтровать карточки: например только `Матричный`, `Неликвид` или `Не закупать` |
| Фильтр списка | Условие по колонке `Статус ассортимента: решение` | Получить список товаров/карточек с нужным решением |
| Карточка закупки | Вкладка `Ассортиментный статус` | Записать комментарий, причину, ответственного, дату и применить решение в правила автозаказа |

Важно: `Статус ассортимента: решение` - это поле самой карточки, а не
вложенный список товаров внутри поля. Если нужно увидеть все товары в статусе
`Матричный`, закупщик выводит эту колонку в списке и ставит фильтр
`Статус ассортимента: решение = Матричный`.

Значения поля:

| Значение | Смысл для закупщика |
| --- | --- |
| `Без изменения` | Решение еще не принято или статус менять не нужно |
| `Матричный` | Товар должен быть в постоянной матрице, например свой бренд или стратегическая позиция |
| `Рабочий` | Товар нормальный рабочий; это подтверждение, что его не надо выводить из активной работы |
| `Под заказ` | Не держать в общем автозаказе, покупать только под конкретную потребность |
| `Кандидат на замену` | Товар нужно заменить аналогом или проверить победителя группы |
| `РМ / Родился мертвым` | Карточку не удаляем, но выводим из рабочей вкладки `Плод`: модель старая, карточка не дала движения, автозаказ запрещен |
| `Неликвид` | Не заказывать автоматически, держать как стоп для общего автозаказа |
| `Не закупать` | Жесткий запрет закупки до отдельного решения |

Технический мост из Bitrix в расчет: `scripts/sync_procurement_assortment_status_decisions.py`.
По умолчанию он работает как dry-run, а с `--apply` обновляет
`config/assortment/display-manual-overrides.json`, после чего существующий
расчет статусов и UT103-экспорт используют решение закупщика штатным путем.

Для ежедневной работы в карточке есть отдельная Bitrix-вкладка
`Ассортиментный статус`: frontend route - маршрут
`/bitrix/procurement-assortment/`, backend API - серверные методы
`/api/procurement-assortment/orders/{item_id}/decision` и
`/api/procurement-assortment/orders/{item_id}/decision/sync`.

Вкладка позволяет закупщику:

- проверить текущий код 1С, название товара и выбранный статус;
- выбрать управленческий статус;
- оставить причину/комментарий;
- указать ответственного и дату решения;
- сохранить решение в Bitrix;
- применить готовое решение в `display-manual-overrides.json`, если заполнены
  обязательные поля.

## Регламент ответственного

Регламент Омара - это не отдельная бюрократия, а правила, где автомат может
действовать сам, а где обязан ждать человека.

Нужно зафиксировать:

| Вопрос | Что решить |
| --- | --- |
| Что проверяет | `manual_review`, крупные заказы, спорные аналоги, необычные сроки, риск брака |
| Когда проверяет | Например ежедневно после утреннего расчета |
| Где работает | Bitrix-карточка, Excel/CSV или отдельная задача |
| Какие лимиты стопорят автомат | Сумма, количество, поставщик, высокий `% брака`, низкая уверенность |
| Кому отправлять | Омару как ответственному и автору проекта на просмотр удобства карточки |
| Кто замещает | Кто принимает решение, если Омара нет |
| Что считается готовым | Подтвержденные строки можно передавать дальше в черновик 1С |

## Текущая готовность

| Уровень | Готовность | Решение |
| --- | ---: | --- |
| Управляемый пилот | 75-78% | Можно готовить испытание через Bitrix с ручным подтверждением |
| Автономный запуск | 58-60% | Рано: не хватает качества, оценки поставщика и регламента |

Фактические цифры по последним срезам:

| Источник | Строк к заказу | Количество | Комментарий |
| --- | ---: | ---: | --- |
| Базовый dry-run - проверочный расчет 2026-07-06 15:02 | 28 | 726 | Контрольный расчет без записи в Bitrix |
| Адаптивный расчет lead time - живых сроков 2026-07-06 15:02 | 24 | 624 | Основной файл для Bitrix после подключения живых сроков |
| Исторический адаптивный пилот 2026-07-05 | 47 | 1898 | Первый файл для проверки Омаром |
| Последний контрольный Bitrix result - результат sync 2026-07-06 | 24 | - | `dry-run`, без записи в Bitrix; вход `display-auto-order-adaptive-sync-ready.csv` |

Рекомендация: официальным входом автозаказа считать адаптивный `sync-ready`
файл, потому что он учитывает живые сроки поставщика, сборку до cargo, дорогу
после cargo и свежую сезонность маршрута. Исторический файл 47 строк / 1898 шт.
остается первым пилотным срезом, но ежедневный контур дальше пересчитывает цифры
заново по актуальным остаткам, товару в пути и срокам.

## Что уже готово

| Блок | Статус |
| --- | --- |
| Bitrix smart-process - смарт-процесс | Есть процесс, категории, стадии, поля и mapping - карта полей |
| Синхронизация 1С -> Bitrix | Открытые заказы поставщику умеют попадать в Bitrix |
| Автозаказ дисплеев | Расчет строится, учитывает продажи, остатки, товар в пути и аналоги |
| Сроки поставки | Живой `lead time` - срок поставки обновляется ежедневно утром и дополнительно при новой дате `Сдача в cargo`; автозаказ использует adaptive lead time - адаптивный срок поставки |
| Округление заказа | Правила крупного округления записаны |
| Ограничение 5 шт. | Снято |
| Ручная роль человека | Описана: человек утверждает, автомат не покупает сам |

## Что не готово

| Блок | Почему важно |
| --- | --- |
| `% брака` | Сейчас есть общий возврат, но нет отдельного расчета возврата именно как "брак" |
| supplier scoring - оценка поставщика | Поставщик еще не выбирается полноценно по цене, сроку, браку, качеству и надежности |
| confidence score - уверенность расчета | Нет порога, ниже которого автомат запрещен |
| Разрез спроса по типу покупателя в расчете | Отчет уже есть, но формула автозаказа еще не разделяет магазинный спрос и маркетплейс-спрос |
| Дни эффективного наличия в точках | Отчет уже есть, но расчет еще делит среднюю продажу на календарное окно, а не на дни фактического наличия в физических точках |
| Очередь manual_review - ручной проверки | Спорные строки пока остаются в CSV/Excel, а не в отдельной Bitrix-очереди |
| Live readback - обратная проверка Bitrix | После apply - применения нужна проверка, что карточки реально видны и заполнены |
| Регламент ответственного | Нужно утвердить сроки реакции, лимиты и замещение |

## Противоречия перед пилотом

| Важность | Что не сходится | Решение |
| --- | --- | --- |
| Высокая | Раньше root-cron мог включать `DISPLAY_AUTO_ORDER_APPLY=true`, то есть Bitrix-карточки могли обновляться автоматически | Решено: cron по умолчанию dry-run - проверочный режим; apply - применение заблокировано для старого процесса `Закупка/Заказ` |
| Высокая | В документах `% брака` обязателен, но в расчете его еще нет как отдельного признака | Подключить defect_return_rate - процент брака |
| Высокая | Было два числа заказа: базовый dry-run и адаптивный отчет | Решено: ежедневный Bitrix-вход строится из адаптивного `sync-ready` файла |
| Средняя | Документ `Потребность на заказ` еще не создается по календарю статуса/скорости | Реализовать order schedule - график заказа поверх ежедневного обновления данных |
| Средняя | После проведенного заказа поставщику нужно явно разделять `у поставщика / сборка` и `в пути после cargo` | Утвердить вкладки `Заказ поставщику / Сборка` и `Cargo / В пути` |
| Средняя | Ручные проверки не превращаются в понятную очередь работы | Решить, нужна ли отдельная Bitrix-очередь |

## Запрещено до отдельного разрешения

- Менять боевые формулы средней продажи, целевого запаса, страхового запаса,
  округления, товара в пути или аналогов без отдельного прямого вопроса и
  подтверждения владельца.
- Включать Bitrix apply - применение, менять live-сервис или деплоить вкладки в
  рабочий портал без отдельного прямого подтверждения.
- Автоматически создавать любой `ЗаказПоставщику`, включая непроведённый
  черновик. Робот автоматически готовит расчёт и кейс `Формирование заказа`, но
  передача черновика в 1С разрешена только после зафиксированного подтверждения
  количества ответственным.
- Проводить документы 1С автоматически.
- Писать напрямую в SQL 1С.
- Закупать строку с блокером качества, брака, поставщика или данных.
- Выбирать поставщика только по цене.
- Пропускать крупные позиции без лимита и подтверждения ответственного по сумме,
  количеству, MOQ и излишку. Выход за любой лимит переводит строку в `Review`.

Решение от 2026-07-16: автоматика должна самостоятельно считать потребность,
проверять спрос, покрытие, аналог, поставщика, качество, цену, рентабельность,
сумму, MOQ, кратность и лимиты, а затем создавать готовый кейс `Формирование
заказа`. Ответственный не пересчитывает формулу вручную, но подтверждает итоговое
количество. Только после этого система создаёт в 1С непроведённый черновик.
Автоматическое создание без такого подтверждения и автоматическое проведение
документа запрещены.

## Открытые вопросы до испытания

1. Когда публикуем отдельный smart-process `Формирование заказа` и его mapping -
   карту полей для авто-заказа?
2. Утверждаем ли предложенный график `Потребность на заказ`: `super_fast` 2
   раза в неделю, `fast` раз в неделю, `normal` раз в 2 недели, спорные статусы
   только в manual_review - ручную проверку?
3. Должны ли `manual_review` - ручные проверки попадать в Bitrix отдельной
   очередью и отправляться Омару плюс автору проекта на просмотр удобства?
4. Где берем точный `% брака`: 1С как главный факт и РММЗ как контроль, или
   сначала 1С-only - только 1С?
5. Какие пороги `% брака` считаем нормой, наблюдением, завышенным браком и
   высоким риском?
6. Какой `confidence score` - порог уверенности разрешает автомат после пилота:
   80, 85 или 90?
7. Какие лимиты ставим на крупные позиции: сумма, штуки, поставщик, группа
   аналогов или дневной бюджет?
8. Основной поставщик хранится в карточке товара как подсказка или итоговый
   выбор всегда делает supplier scoring - оценка поставщика?
9. Утверждаем ли названия вкладок: `Потребность`, `Заказ поставщику / Сборка`,
   `Cargo / В пути`, `Приемка / Разбор / Раскладка`?
10. Кто замещает Омара, если очередь не обработана в день расчета?
11. Подтверждаем ли для пилота порог эффективного наличия в точке `> 2` штуки,
    а 1-2 штуки считать техническим хвостом?
12. Считаем ли `Оптовый склад` отдельным каналом всегда или часть оптовых
    продаж нужна для отдельной оптовой потребности?

## Шаги до первого испытания

1. Закрепить официальный ежедневный вход: адаптивный `sync-ready` расчет.
2. Утвердить order schedule - график создания `Потребность на заказ`.
3. Подготовить read-only - только для чтения сравнение текущей средней продажи
   с расчетом по дням эффективного наличия в физических точках.
4. Подготовить read-only сравнение общего спроса, спроса без маркетплейса и
   только маркетплейс-спроса для строк к заказу.
5. На основании двух сравнений решить, какие поля показываем Омару во вкладке
   `Потребность` и какие пороги отправляют строку в ручную проверку.
6. Опубликовать отдельный `Формирование заказа` и только после этого включать
   Bitrix apply - применение для авто-заказа в новый процесс.
7. Утвердить регламент Омара: действия, лимиты, сроки реакции, замещение.
8. Добавить live readback - обратную проверку Bitrix после применения.
9. Провести 3-5 рабочих дней управляемого пилота: сначала без записи в 1С,
   затем создать тестовый непроведённый черновик только после подтверждения
   количества ответственным.

## Шаги до автономного запуска

1. Подключить `% брака` как отдельный показатель.
2. Реализовать supplier scoring - оценку поставщика.
3. Добавить confidence score - уверенность расчета.
4. Перевести `manual_review` - ручную проверку в удобную очередь Bitrix.
5. Проверить файловый обмен с 1С в режиме `draft_only` - только черновик.
6. Разрешить создание непроведённого черновика 1С только после прохождения
   машинных шлюзов и подтверждения итогового количества ответственным; спорные
   строки оставить в `Review`.

## Критерий развития

Следующая доработка полезна, если она увеличивает долю безопасного автозаказа
без раздувания склада. Если доработка не помогает принять решение "заказать /
не заказать / проверить руками", ее нужно отложить или вынести в соседний
контур.
