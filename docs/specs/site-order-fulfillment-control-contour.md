# Назначение

Создать управляемый контур исполнения интернет-заказов `MASTER-MOBILE.RU` после
создания сделки в `Bitrix24 Box` и документов в `1С УТ 10.3`.

Контур нужен для трех операционных потоков:

- самовывоз: сборка на центральном складе `Склад Сдэк`, перемещение в розничный
  магазин, хранение на точке самовывоза, выдача клиенту или расформирование;
- курьерская доставка по Санкт-Петербургу: передача курьеру, факт доставки,
  неуспешная попытка или возврат;
- внешние перевозчики (`СДЭК`, `Почта России`): ожидание оплаты, создание
  накладной, передача в доставку, вручение, отмена/возврат.

Главная цель: не считать раннюю `РТУ` и технические документы `1С` фактом
вручения клиенту. Успех сделки должен фиксироваться только по сильному
операционному доказательству.

# Scope / Out of Scope

Входит:

- append-only история событий исполнения заказа из `1С`, сайта, логистического
  сервиса, Bitrix-чатов и Bitrix24;
- парсинг сообщений из Bitrix-чатов `chat733` / `Сайт MASTER-MOBILE.RU` и
  `chat727` / `Отчет доставок СПб`;
- OCR изображений из `chat727` через существующий OpenAI OCR-подход сервиса;
- derived status заказа и правила перевода сделки в стадии `Bitrix24`;
- новые CRM-стадии для хранения самовывоза на точке и расформирования/отмены;
- SLA хранения самовывоза `3 дня`;
- правила ручного разбора при слабых или конфликтующих сигналах;
- dry-run, outbox и idempotency для любых изменений в `Bitrix24`.

Не входит:

- запись в БД `1С`;
- замена учетного процесса `РТУ`, возвратов, оплат и остатков внутри `1С`;
- хранение бизнес-состояния в Bitrix-чатах;
- автоматическое закрытие в успех по отсутствию заказа в очередном чат-отчете;
- отправка клиентских SMS без отдельного согласованного контракта.

# Текущий Контекст

На `2026-05-21` в CRM уже восстановлен базовый порядок для большинства старых
интернет-заказов:

- поля доставки и оплаты сделки заполняются;
- по СДЭК/Почте массово разнесены доставленные, переданные в доставку,
  отмененные и сделки с треками;
- `289` неоплаченных самовывозов с `РТУ` и проведенным возвратом на основании
  `РТУ` переведены в `Сделка провалена`;
- `697` неоплаченных самовывозов из `В работе` переведены в `Проверка заказа`;
- `283` неоплаченных онлайн-заказа `СДЭК`/`Почта` с неоплаченным
  `CloudPayments` переведены в `Ожидает оплаты`.

Оставшаяся проблема не в массовом backfill, а в постоянной модели управления:

- `РТУ + F` для самовывоза означает, что товар собран/готов к выдаче, но не
  означает, что клиент забрал заказ;
- факт хранения на точке самовывоза должен быть виден отдельно;
- факт расформирования должен быть виден отдельно от обычной сборки;
- факт вручения самовывоза и курьерской доставки сейчас часто есть только в
  операционных Bitrix-чатах.

Read-only срез Bitrix-чата на `2026-05-21` показал:

- `chat733` / `Сайт MASTER-MOBILE.RU`: последние `50` сообщений, `130`
  уникальных номеров заказов, `19` сообщений типа `не забрали`;
- `chat727` / `Отчет доставок СПб`: последние `100` сообщений, текстовых
  номеров заказов почти нет, найдено `55` изображений, поэтому нужен OCR.

Read-only срез production `1С` за `2026` по raw-доставке `_Document132._Fld9266`:

- `Самовывоз`;
- `СДЭК (Самовывоз)`;
- `Доставка курьером`;
- `Почта России (Доставка в отделение)`;
- один пустой raw-случай.

В тестовой Wave 1 встречались `Такси` и `Достависта`; если они, `Boxberry` или
`EMS` появятся в production/сайте, контур должен вынести их в отдельный
ежедневный dry-run отчет, а не молча применить старые правила.

Поля `1С` `_Document132._Fld9939RRef` (курьер) и `_Fld9940` (стоимость доставки)
считаются optional enrichment: в production они почти не заполнены, поэтому v1
не должен требовать их для определения стадии.

# Целевая CRM-Модель

Текущая воронка:

| Код | Название |
| --- | --- |
| `NEW` | `В работе` |
| `PREPARATION` | `Проверка заказа` |
| `PREPAYMENT_INVOICE` | `Ожидает оплаты` |
| `EXECUTING` | `Сборка / обеспечение` |
| `FINAL_INVOICE` | `Готов к отгрузке` |
| `IN_DELIVERY` | `Передан в доставку` |
| `DELIVERY_REVIEW` | `Проблема доставки / проверка` |
| `WON` | `Сделка успешна` |
| `LOSE` | `Сделка провалена` |

Read-only проверка REST на `2026-05-21` показала: категории сделок не
используются (`crm.dealcategory.list` вернул пустой список), стадии живут в
`ENTITY_ID = DEAL_STAGE`. В CRM также есть финальная failure-стадия `APOLOGY`
`Анализ причины провала` с `SORT = 110`; она не меняет основную модель заказа,
но ее нужно учитывать при скриптах, чтобы не считать `LOSE` единственной
failure-стадией.

Нужны процессные стадии:

| Семантический код | Название | Где в воронке | Назначение |
| --- | --- | --- | --- |
| `PICKUP_TRANSIT` | `В пути на точку самовывоза` | после `FINAL_INVOICE`, до `PICKUP_WAITING` | заказ передан внутреннему водителю или отправлен с центрального склада, но магазин еще не подтвердил приемку |
| `PICKUP_WAITING` | `Ожидает самовывоза` | после подтвержденной приемки магазином, до `WON`/`LOSE` | заказ готов к выдаче в магазине и ждет клиента |
| `PICKUP_STORAGE` | `Хранение в ПВЗ / отделении` | после `IN_DELIVERY`, до `WON`/`LOSE` | отправление хранится во внешнем ПВЗ/постамате/отделении |
| `DISMANTLING` | `Расформирование / отмена` | после `PICKUP_WAITING`/`PICKUP_STORAGE`, до `WON`/`LOSE` | истек срок ожидания/хранения или начат возврат/разбор заказа |

Целевой поток внутреннего самовывоза:
`FINAL_INVOICE` / `Готов к отгрузке` ->
`PICKUP_TRANSIT` / `В пути на точку самовывоза` ->
`PICKUP_WAITING` / `Ожидает самовывоза`.

## Решение по приложению и автоматическим стадиям от 2026-08-26

- Основной интерфейс пилота — встроенное приложение Bitrix24
  `/bitrix/logistics/` с пунктом `LEFT_MENU` «Логистика». Telegram и
  `/logistics/fallback` остаются резервными интерфейсами одной state machine.
- Пользователь Bitrix связывается с `logistics_user` через уникальный nullable
  `bitrix_user_id`. Браузер получает только короткую scoped-сессию BFF и не
  получает internal logistics token.
- `sender` передает только со своего склада, `receiver` принимает только на свой
  склад. `logist/admin` видят мониторинг, историю и ошибки; ручного обхода
  проверок через пользовательское приложение v1 нет.
- Сильные события `pickup_moving_to_point` и `pickup_stored_at_point` создают в
  той же DB-транзакции строки `site_order_stage_outbox`. Worker берет их строго
  по порядку одного заказа, повторно читает сделку и делает readback после записи.
- Разрешены только переходы `FINAL_INVOICE -> PICKUP_TRANSIT` и
  `PICKUP_TRANSIT -> PICKUP_WAITING`. Финальные/отмененные сделки не меняются;
  неоднозначность и конфликт живой стадии создают `logistics_manual_review`, а
  безопасно определенная конфликтная сделка переводится в `DELIVERY_REVIEW`.
- Повторное подтверждение, scan или запуск worker не создает второго перехода.
  Timeline содержит событие, склад/магазин, водителя, сотрудника, канал, время и
  идентификатор логистического события.
- Автоматические стадии ограничены pilot allowlist складов и флагом
  `LOGISTICS_STAGE_AUTOMATION_ENABLED=false` по умолчанию. Исторические 254
  спорные сделки автоматически в новый outbox не добавляются.

## SMS готовности

Будущим владельцем SMS «заказ готов к выдаче» выбран Bitrix24. Это решение не
включает production-отправку и не отменяет действующее правило «SMS готовности
отключены».

- SMS-gate заполняется только после успешного readback `PICKUP_WAITING`.
- Антидубль хранится в полях сделки: ID события приемки, статус SMS и время
  отправки. Срок хранения — три дня от первого сильного события приемки.
- Телефон берется только из одного однозначно связанного контакта. Без телефона,
  адреса точки или корректного номера заказа статус `ready` не выставляется, а в
  timeline создается предупреждение.
- Шаблон будущего робота: «Заказ №… поступил в магазин … по адресу …. Можно
  забрать до …».
- `PICKUP_READY_SMS_ENABLED=false` сохраняет shadow-режим. Одна реальная SMS
  разрешается только отдельным production-решением после проверки стадий и
  тестового номера.

Точный `STATUS_ID` нужно проверить через REST перед применением, потому что
Bitrix24 может хранить стадии default/category pipeline с внутренними префиксами.
В спецификации используются семантические коды.

Отдельная стадия `Спорные` в v1 не создается. Для конфликтных или неполных
сигналов используется существующая стадия `PREPARATION` / `Проверка заказа`.
Это дает простой принцип пилота: чистые cases вытаскиваются из проверки в
процессные стадии, а спорные остаются в текущем рабочем карантине.

Правило для `LOSE`: финальная стадия `Сделка провалена` ставится только после
устойчивого признака отмены, например проведенного `Возврата от покупателя` на
основании `РТУ` при отсутствии оплаты. Стадия `DISMANTLING` нужна для процесса
разбора до финального закрытия.

Стадия `DELIVERY_REVIEW` считается карантином, а не рабочей очередью хранения.
30-минутный quick-проход обязан разбирать ее по безопасным признакам:

- `CANCELED=Y`: если заказ уже собран, `DISMANTLING`; если не собран, `LOSE`;
- `STATUS_ID=F`: `WON` с заполнением CRM-флага оплаты, потому что это уже
  сайт-статус `Выполнен`, а не ранняя техническая `РТУ`;
- `STATUS_ID=P` и `PAYED=Y`: несобранные возвращаются в `EXECUTING`, собранные
  самовывозы в `PICKUP_WAITING`, собранные доставки в `FINAL_INVOICE`;
- `STATUS_ID=N`, `PAYED=N`, самовывоз и `Собран`: `PICKUP_WAITING`;
- `STATUS_ID=N`, `PAYED=N`, ожидание оплаты больше 7 дней: `LOSE`;
- свежие неоплаченные СДЭК/Почта: `PREPAYMENT_INVOICE`;
- свежий курьер с оплатой при получении: `EXECUTING`;
- все остальные комбинации остаются в ручном разборе.

# Derived Status

Backend хранит более детальный `derived_status`, чем CRM-стадия:

ОТМЕНЕНО (2026-08-25): прежнее сопоставление
`pickup_moving_to_point` с `FINAL_INVOICE` или `IN_DELIVERY`. После передачи
внутреннему водителю используется отдельная стадия `PICKUP_TRANSIT`.

| Derived status | CRM stage | Комментарий |
| --- | --- | --- |
| `awaiting_order_check` | `PREPARATION` | самовывоз/курьер без оплаты, заказ требует проверки |
| `awaiting_online_payment` | `PREPAYMENT_INVOICE` | онлайн-оплата выбрана, платеж не подтвержден |
| `assembling` | `EXECUTING` | заказ обеспечивается или собирается |
| `ready_for_dispatch` | `FINAL_INVOICE` | `1С`/сборка говорят, что заказ готов к передаче, но еще не у клиента/логистики |
| `pickup_moving_to_point` | `PICKUP_TRANSIT` | самовывоз передан внутреннему водителю и едет с центрального склада в магазин |
| `pickup_stored_at_point` | `PICKUP_WAITING` | магазин принял заказ, заказ ждет самовывоза |
| `pickup_storage_expired` | `DISMANTLING` | прошло `3 дня`, нет выдачи/оплаты/другого закрывающего события |
| `pickup_dismantling_started` | `DISMANTLING` | магазин/сайт сообщил о разборе, или создан возврат-кандидат |
| `pickup_dismantled` | `LOSE` | проведен возврат на основании РТУ, оплаты нет |
| `courier_spb_handed_to_courier` | `IN_DELIVERY` | пакет физически передан курьеру СПб |
| `courier_spb_delivered_payment_pending` | `IN_DELIVERY` | доставка подтверждена, но оплата еще не подтверждена |
| `courier_spb_delivered_paid` | `WON` | доставка подтверждена и заказ оплачен или OCR/`1С` подтвердили сбор оплаты |
| `carrier_ready_for_label` | `FINAL_INVOICE` | СДЭК/Почта готовы к накладной |
| `carrier_in_delivery` | `IN_DELIVERY` | есть трек/статус передачи в доставку |
| `delivered` | `WON` | сильный факт вручения/получения |
| `cancelled` | `LOSE` | сильный факт отмены |
| `manual_review` | `PREPARATION` | конфликт или слабые доказательства, без авто-закрытия |

CRM-стадия меняется только из `derived_status` с достаточной уверенностью.
Кастомные поля сделки должны хранить сам `derived_status`, дату расчета и
последний evidence, чтобы стадия не была единственным объяснением.

# Bitrix Chat Ingest

Чаты:

- `site_master_mobile` - `chat733` / `Сайт MASTER-MOBILE.RU`;
- `courier_spb` - `chat727` / `Отчет доставок СПб`.

Источник сообщений: Bitrix REST `im.dialog.messages.get`.

Для `chat733` v1 парсит текст сообщений:

- списки номеров заказов;
- фразы `не забрали`, `забрали`, `выдали`, `разобрали`, `расформирование`,
  `возврат`.

Для `chat727` v1 должен обрабатывать изображения:

- `params.FILE_ID` из сообщений;
- download через Bitrix Disk/file API;
- OCR через OpenAI Responses API по уже принятому в `pricing-service` подходу.

OCR должен возвращать JSON: номера заказов, статус доставки, сумму/оплату,
курьера/комментарий и confidence. Полный raw text/картинки не выводятся в
пользовательские ответы; наружу идет только redacted evidence.

Исторический backfill не входит в старт v1: начинаем с новых сообщений и
повторно применяем только идемпотентные события.

# Парсер Чатов

Парсер должен быть сначала детерминированным:

- извлекать номера заказов сайта, прежде всего 6-значные номера;
- учитывать строки списков, диапазоны и несколько заказов в одном сообщении;
- нормализовать адреса/точки самовывоза;
- классифицировать event type по словарю ключевых фраз;
- выставлять confidence и причину.

LLM можно использовать только как assist для ручной разметки и расширения
словарей, но не как единственный источник автоматического перевода сделки в
`WON` или `LOSE`.

Базовые события из чата `Сайт MASTER-MOBILE.RU`:

| Event type | Пример смысла | Confidence |
| --- | --- | --- |
| `pickup_moving_to_point` | заказ/РТУ перемещается в магазин | medium/strong |
| `pickup_arrived_at_point` | заказ на точке самовывоза | strong при явном тексте или совпадении с логистическим receipt |
| `pickup_unclaimed_reported` | заказ числится незабранным | medium |
| `pickup_client_received` | клиент забрал/выдали заказ | strong только при явном сообщении |
| `pickup_dismantling_started` | начат разбор/возврат | medium |
| `pickup_dismantled` | заказ разобран/возврат оформлен | strong только при подтверждении `1С` или явном регламентном сообщении |

Базовые события из курьерского чата Санкт-Петербурга:

| Event type | Пример смысла | Confidence |
| --- | --- | --- |
| `courier_spb_assigned` | заказ назначен курьеру | medium |
| `courier_spb_handed_to_courier` | пакет физически передан курьеру | strong при явной передаче |
| `courier_spb_delivered_payment_pending` | доставлено, но оплата не подтверждена | medium/strong, CRM stage только `IN_DELIVERY` |
| `courier_spb_delivered_paid` | доставлено и оплачено/оплата собрана курьером | strong, можно рекомендовать `WON` |
| `courier_spb_failed` | не доставлено, перенос/отказ | medium/strong |
| `courier_spb_returned` | пакет вернулся/нужен возврат | strong при явном возврате или подтверждении `1С` |

ОТМЕНЕНО (2026-08-26): прежнее абсолютное правило, по которому отсутствие
заказа в очередном списке незабранных никогда не являлось фактом выдачи.

Для исторического разбора заказ считается выданным и переводится в `WON`, если
он подтвержденно поступил на конкретную точку, в более позднем подтвержденном
остатке этой точки отсутствует, возврата в `1С` нет и отсутствует более новое
противоречащее событие. Простое отсутствие без подтвержденного поступления либо
без последующего подтвержденного состояния по-прежнему создает `manual_review`.

# Правила Самовывоза

## Готовность

`РТУ` и событие `Собран` означают:

- товар собран/готов;
- сделку можно перевести в `Готов к отгрузке`;
- для самовывоза и курьера оплата может произойти при получении, поэтому
  отсутствие оплаты не блокирует готовность.

`РТУ + F` не означает выдачу клиенту.

## Перемещение на точку

Подтвержденная передача внутреннему водителю или отправка с центрального склада
создает событие `pickup_moving_to_point` и переводит сделку в
`PICKUP_TRANSIT` / `В пути на точку самовывоза`.

Эта стадия означает только физическое движение между складами. Она не запускает
SMS готовности, срок хранения или SLA клиента. Сделка остается в
`PICKUP_TRANSIT`, пока магазин не подтвердит приемку заказа.

## Хранение на точке

Сделка переходит в `PICKUP_WAITING`, если есть сильный факт, что внутренний
самовывоз находится в магазине и ждет клиента. `PICKUP_STORAGE` оставляем для
внешних ПВЗ/постаматов/почтовых отделений:

- логистический сервис зафиксировал приемку РТУ/пакета на складе магазина;
- или чат `Сайт MASTER-MOBILE.RU` явно сообщает, что заказ пришел/лежит на
  конкретной точке;
- или другой согласованный источник дает тот же факт.

`storage_started_at` берется из первого сильного события нахождения на точке.
`storage_deadline_at = storage_started_at + 3 дня`, если не согласован другой
SLA.

## Успех

Самовывоз закрывается в `WON` только при сильном доказательстве:

- явное чат-сообщение `pickup_client_received`;
- или история связанной `РТУ` в `1С` содержит оба действия `Распечатан` и
  `Отсканирован` для внутреннего самовывоза: в текущем production-процессе это
  считается фактом выдачи клиенту;
- или связанный платеж/чек/приход оплаты, который в правилах утвержден как
  достаточный факт выдачи;
- или будущий логистический event `accepted_by_customer`.

До появления такого доказательства заказ остается в `PICKUP_WAITING` или в
ручном разборе.

## Расформирование / Отмена

Сделка переходит в `DISMANTLING`, если:

- срок хранения истек;
- или чат/оператор сообщает, что заказ надо разобрать;
- или есть конфликт, который требует возврата товара из лотка.

Сделка переходит в `LOSE`, если:

- на основании `РТУ` есть проведенный `Возврат от покупателя`;
- оплаты нет;
- нет более сильного факта выдачи клиенту.

В `Bitrix24` нужно фиксировать loss reason/комментарий:
`Расформирован: самовывоз не забран, возврат от покупателя на основании РТУ`.

`DISMANTLING` не используется как карантин для неопределенных заказов. Для
разового исправления ошибочного пакета от 2026-08-24 утверждено следующее
правило: сделка из `DISMANTLING` переводится в `WON` только после повторного
readback номера заказа и живой стадии, если проведенного возврата по связанной
`РТУ` нет и имеется либо связка `Распечатан + Отсканирован`, либо статус сайта
`F / Выполнен`. Исправление выполняется пакетами не более 20 сделок с
append-only журналом и итоговым readback. Меняется только стадия; CRM-маркер
оплаты этим историческим исправлением не заполняется. Сделки с возвратом,
отменой или конфликтом остаются без движения для ручной проверки.

Для подтвержденного пакета от 2026-08-26 шесть самовывозов из `DISMANTLING`
закрыты в `LOSE`: по каждому имеется проведенный полный возврат на сумму `РТУ`,
отсутствуют скан выдачи и фактическая оплата, а номер заказа и живая стадия
повторно проверены перед записью. Седьмой исходный кандидат исключен после
обнаружения платежа в `1С`, несмотря на признак `PAYED=N` на сайте. Поле оплаты
в CRM при закрытии пакета не изменялось; оплаченные и иные противоречивые случаи
остаются в `DISMANTLING` до ручного разрешения конфликта.

# Правила Курьера Санкт-Петербурга

Курьерский чат СПб должен давать такой же evidence-layer, как чат самовывоза.

Правила:

- вызов курьера или назначение заказа не является фактом передачи;
- `courier_spb_handed_to_courier` переводит сделку в `IN_DELIVERY`;
- факт доставки без оплаты создает `courier_spb_delivered_payment_pending` и
  оставляет сделку не выше `IN_DELIVERY`;
- `courier_spb_delivered_paid` переводит сделку в `WON` только при
  подтверждении доставки и оплаты;
- `courier_spb_failed` не закрывает сделку, а создает `manual_review` или
  повторную доставку;
- `courier_spb_returned` с подтверждением `1С`/возврата и отсутствием оплаты
  переводит в `LOSE`.

Для MVP отдельную CRM-стадию `Курьер СПб` не вводим: визуально достаточно
`Передан в доставку`, а тип маршрута хранится в derived status/полях. Если
операционно понадобится отдельная доска курьеров, лучше сделать smart-process
или фильтр, а не дробить основную воронку сделок.

# Правила СДЭК / Почты

Для внешних перевозчиков остаются текущие правила:

- онлайн-оплата выбрана и не оплачена: `PREPAYMENT_INVOICE`;
- заказ собран и готов к накладной: `FINAL_INVOICE`;
- есть трек/статус передачи перевозчику: `IN_DELIVERY`;
- `вручен`/`получен`: `WON`;
- отмена/возврат: `LOSE`.

СДЭК и Почта не должны закрываться по `РТУ` без статуса доставки.

## Automation Ownership

Центр принятия решений находится на стороне `pricing-service`, а не в роботах
Bitrix24. Сервер собирает события из `1С`, сайта, Bitrix-чатов, OCR,
СДЭК/Почты и других источников, хранит историю, рассчитывает `derived_status`,
строит review/outbox CSV и только после проверки применяет изменения через REST.

Bitrix-роботы в этой модели остаются UX-слоем:

- уведомить ответственного;
- поставить дело или напоминание;
- создать задачу на проверку или разбор;
- показать timeline-комментарий с безопасным evidence.

Bitrix-роботы не должны самостоятельно решать те же stage transitions, которыми
управляет сервер. Иначе появятся конкурирующие правила, циклы и переходы без
единого audit trail.

## Bitrix outbox

Любое изменение CRM идет через outbox:

- `target_type = bitrix_deal`;
- `target_id = deal id`;
- `operation = update_stage | update_fields | timeline_comment | smart_process_upsert`;
- `idempotency_key`;
- `dry_run_payload`;
- `applied_at`;
- `error`.

Прямые массовые REST-изменения без предварительного CSV/dry-run запрещены.
Первый серверный outbox для пилота формируется в CSV через
`scripts/build_order_fulfillment_stage_outbox.py`: он включает только строки
`update_stage`, блокирует целевые стадии, которых еще нет в CRM, и не выполняет
REST-изменения.
Применение outbox выполняется отдельным скриптом
`scripts/apply_order_fulfillment_stage_outbox.py`: dry-run по умолчанию,
реальная запись только с `--apply`, перед `crm.deal.update` live-проверяются
номер заказа, текущая стадия и отсутствие финальной стадии.

## Регулярный Cron-Контур

`infra/cron/order_fulfillment_sync.py` — единая точка регулярного dry-run
контроля:

- `--mode quick`: каждые 15/30 минут строит review/outbox для простых сделок в
  `NEW`, `PREPARATION`, `PREPAYMENT_INVOICE`, `EXECUTING` и
  `DELIVERY_REVIEW`, делает dry-run/apply stage apply и пишет операционный
  мониторинг;
- `--mode chat`: каждый час загружает `chat733` и `chat727`, сохраняет события,
  строит review/outbox по чатовым кейсам и делает dry-run stage apply
  (`ORDER_FULFILLMENT_SYNC_REVIEW_LIMIT`, по умолчанию `100`);
- `--mode daily`: утром формирует отчет неизвестных raw-доставок и сводку по
  стадиям интернет-заказов.

Shell-обвязка `infra/cron/order_fulfillment_sync.sh` по умолчанию не передает
`--apply`. Auto-apply включается только явным env
`ORDER_FULFILLMENT_SYNC_APPLY=true` после приемки нескольких дней dry-run.

С 2026-08-26 включен production `quick` auto-apply для строгих переходов.
Перед записью повторно проверяются номер заказа, текущая стадия и
отсутствие финального статуса. Chat auto-apply, SMS, SLA, inventory/WON и
спорные pickup-переходы остаются выключенными.

Quick-проход всегда пишет отдельные артефакты:

- `quick-stage-summary-*.csv`: счетчики интернет-заказов по рабочим стадиям;
- `quick-operational-monitoring-*.csv`: сигналы по `NEW`, `PREPARATION`,
  `DELIVERY_REVIEW`, просроченному ожиданию оплаты, ошибкам outbox/apply;
- `executing-rtu-without-assembled-*.csv`: сделки в `EXECUTING`, где в `1С`
  есть проведенная `РТУ`, но нет события `Собран`.

Стадия `PICKUP_WAITING` также попадает в quick-проход. Заказы самовывоза
закрываются в `WON` автоматически только если сайт уже `F / Выполнен` и есть
сильное подтверждение оплаты/выдачи:

- оплата подтверждена в CRM/сайте;
- или `1С` показывает проведенную `РТУ` и отсутствие долга по заказу;
- или `1С` показывает полную оплату/ПКО/эквайринговую оплату на сумму
  проведенной `РТУ`.

`PAYED=N` на сайте для наличного самовывоза не является блокером само по себе:
сайт часто не получает обратный флаг оплаты после выдачи на точке. Если сайт
`F`, но CRM/сайт и `1С` не подтверждают оплату или отсутствие долга,
quick-проход не закрывает сделку, а пишет сигнал
`самовывоз можно проверить на закрытие`: нужно сверить оплату/долг в `1С` и
закрыть вручную или добить факт оплаты.

Если уведомления включены, новые операционные сигналы отправляются в Bitrix
в групповой диалог сайта `MASTER-MOBILE.RU` через
`ORDER_FULFILLMENT_NOTIFY_SITE_DIALOG_ID` (по умолчанию берется
`ORDER_FULFILLMENT_SITE_CHAT_DIALOG_ID`) и, если настроены, получателям
`ORDER_FULFILLMENT_NOTIFY_BUSINESS_USER_IDS` и
`ORDER_FULFILLMENT_NOTIFY_TECH_USER_IDS`; state-файл не дает спамить тем же
ключом сигнала повторно. Для отключения публикации в групповой диалог при
сохранении персональных уведомлений можно задать
`ORDER_FULFILLMENT_NOTIFY_SITE_DIALOG_ID=-`.

Штатные quick- и chat-проходы продолжают выполняться каждые 30 и 60 минут, но
запускаются с `ORDER_FULFILLMENT_NOTIFY_ENABLED=false` и не отправляют сообщения
в рабочий чат. Накопительная сводка формируется отдельным запуском `mode=all`
ежедневно в `11:00 Europe/Moscow`. Для текущего процесса непроведенный документ
заказа в `1С` и отсутствие `РТУ` не исключают заказ из контроля: автоматически
загруженный неотмененный заказ сайта считается актуальным, а ранняя `РТУ` не
используется как признак подтверждения заказа.

При этом просроченный неоплаченный заказ без проведенной `РТУ` не считается
однозначным основанием для автоматического закрытия сделки и не публикуется как
операционный сигнал `требуется действие`. Он остается в техническом review до
появления подтвержденного учетного факта или решения менеджера.

Групповой диалог получает только понятные операционные сигналы: номер
заказа/сделки, бизнес-причину, ожидаемое действие и владельца. Внутренние пути к
CSV/JSON, технические коды (`manual_review`, `terminal_crm_stage`) и состояние
dry-run/apply в групповой чат не выводятся. Ручной разбор доставляется только
персональным business-получателям, технический разбор — только tech-получателям;
ежедневная сводка также отправляется только персональным business-получателям и
не публикуется в групповом диалоге;
пустые примеры без номера заказа и сделки не публикуются.

Отчет неизвестных доставок использует общий нормализатор:

- `СДЭК*` и `Почта России*` считаются внешним перевозчиком;
- `Курьер*`, `Доставка курьером*`, `Dostavista/Достависта`, `Такси` считаются
  курьерской доставкой;
- `Самовывоз*`, названия магазинов и центрального склада считаются внутренним
  самовывозом;
- пустые или нераспознанные raw-значения остаются в unknown/watch отчете.

# Bitrix24 Поля И Smart-Process

Минимальные поля сделки:

- `derived_status`;
- `derived_status_at`;
- `derived_status_confidence`;
- `execution_evidence`;
- `pickup_point`;
- `storage_started_at`;
- `storage_deadline_at`;
- `delivered_at`;
- `cancelled_at`.

На первом этапе поля можно создать как `UF_CRM_*` в сделке. Для SLA и ручного
разбора лучше завести отдельный smart-process `Контроль интернет-заказа`, где
одна карточка соответствует одному `site_order_execution_case`.

Smart-process полезен для:

- очереди `manual_review`;
- просрочек хранения;
- конфликтов оплаты/возврата/чата;
- ручного подтверждения спорной выдачи;
- аудита парсинга чатов без засорения карточки сделки.

# Invariants

- Не закрывать самовывоз в `WON` по факту `РТУ + F`.
- Не закрывать самовывоз в `WON` по исчезновению из списка незабранных.
- `PAYED=N` на сайте не блокирует закрытие наличного самовывоза, если `1С`
  подтверждает отсутствие долга или полную оплату по проведенной `РТУ`.
- Не закрывать курьерскую доставку в `WON` по назначению курьера или вызову
  машины.
- Не закрывать `Доставка курьером` в `WON` только по факту доставки, если заказ
  неоплачен.
- Не закрывать СДЭК/Почту в `WON` без статуса вручения/получения.
- Не переводить в `LOSE`, если есть подтвержденная оплата или сильный факт
  выдачи.
- Любой авто-переход должен иметь сохраненный evidence event.
- Все Bitrix-chat события дедуплицируются по `chat_id + message_id + order +
  event_type`.
- `1С` и сайт остаются source of truth по документам, оплатам и заказу.

# Errors / Edge Cases

- Сообщение содержит несколько заказов и одну фразу статуса: событие создается
  на каждый заказ, evidence сохраняет общий текст.
- В сообщении есть номер телефона/сумма/адрес: в Bitrix timeline выводить
  только минимальный evidence, raw хранить ограниченно.
- Один номер заказа найден в нескольких сделках: `manual_review`, без
  авто-перехода.
- Чат сообщает `выдан`, но в `1С` уже есть возврат: `manual_review`.
- Есть оплата, но чат сообщает расформирование: `manual_review`.
- Есть возврат на основании РТУ, но чат сообщает выдачу: `manual_review`, пока
  не решит ответственный.
- Bitrix REST недоступен или вернул неполный ответ: ingest job должен
  фиксировать ошибку, не делать выводы из отсутствия событий.
- Исторический backfill из Bitrix-чата не должен повторно применять уже
  обработанные события.

# Tests

Unit:

- regex/parser извлекает один и несколько номеров заказов;
- parser отличает `незабран`, `выдан`, `разобран`, `передан курьеру`,
  `доставлен`, `не дозвонились`;
- parser не считает простое отсутствие заказа в списке фактом выдачи без
  подтвержденного поступления, последующего состояния точки и проверки возврата;
- OCR-классификатор `chat727` отличает `доставлено`, `не доставлено`,
  `перенос`, `оплата получена`;
- state machine не закрывает неоплаченный курьерский заказ в `WON`;
- state machine не закрывает самовывоз по `РТУ + F`;
- state machine закрывает самовывоз в `WON`, если сайт `F`, CRM/сайт не
  подтверждают оплату, но `1С` показывает отсутствие долга или полную оплату;
- state machine переводит `pickup_stored_at_point` в `PICKUP_WAITING`;
- state machine переводит `pickup_dismantled` в `LOSE` только при отсутствии
  оплаты и наличии возврата.

Integration:

- ingest Bitrix message -> parsed mentions -> execution events -> dry-run
  recommendation;
- duplicate message does not create duplicate event;
- conflicting evidence creates `manual_review`;
- Bitrix outbox builds update payload without direct side effects in dry-run.

Smoke:

- 10-20 живых заказов: самовывоз, курьер СПб, СДЭК, Почта;
- сверить stage recommendation с карточками сделок;
- проверить timeline comments на отсутствие секретов и лишних персональных
  данных.

- Утвердить новые CRM-стадии: `В пути на точку самовывоза`,
  `Ожидает самовывоза`,
  `Хранение в ПВЗ / отделении` и
  `Расформирование / отмена`.
- Проверить через REST текущий `STATUS_ID` воронки интернет-заказов.
- Согласовать доступ REST/webhook к `chat733`, `chat727` и Bitrix Disk/file API.

## Wave 1. Read-only ingest и dry-run

- Добавить таблицы `site_order_execution_case`,
  `site_order_execution_event`, `bitrix_chat_message`,
  `bitrix_chat_mention`.
- Подключить ingest новых сообщений из двух чатов.
- Сделать parser v1 и dry-run рекомендации без изменений CRM.
- Сравнить рекомендации с 122 оставшимися сделками в `В работе` и свежими
  заказами.

### Исторический карантин самовывоза 2026-08-25

- В исходном read-only срезе в `PICKUP_WAITING` находилось 269 сделок: 15 имели
  подтвержденный актуальный остаток или факт приемки магазином, 254 не имели
  подтверждения приемки либо передачи внутреннему водителю.
- Подтвержденные 15 сделок остаются в `PICKUP_WAITING`.
- Сделки без подтвержденной приемки и без события `pickup_moving_to_point`
  переводятся в `DELIVERY_REVIEW` / `Проблема доставки / проверка` как
  исторический карантин. Применение выполняется пакетами с повторной проверкой
  живой стадии и доказательств перед каждым обновлением.
- `PICKUP_TRANSIT` запрещено ставить только по наличию сборки или проведенной
  `РТУ`: нужен отдельный факт передачи внутреннему водителю или отправки с
  центрального склада.
- Если заказ подтвержденно поступил на точку, затем отсутствует в более позднем
  подтвержденном остатке этой точки и возврата в `1С` нет, он считается выданным
  и переводится в `WON` при отсутствии более нового противоречащего события.
- Исходящие запросы сотрудникам в рабочие чаты разрешены только после отдельного
  согласования; read-only анализ и подготовка текста не являются разрешением на
  публикацию.

## Wave 2. Bitrix fields и timeline

- Создать поля сделки для derived status и evidence.
- Писать кастомные поля и timeline-комментарии через outbox.
- Стадии пока менять только вручную или по малому allowlist.

## Wave 3. Авто-стадии с ограниченными правилами

- Включить авто-переходы:
  - `pickup_moving_to_point` -> `PICKUP_TRANSIT`;
  - `pickup_stored_at_point` -> `PICKUP_WAITING`;
  - `pickup_dismantled` -> `LOSE`;
  - `courier_spb_handed_to_courier` -> `IN_DELIVERY`;
  - `courier_spb_delivered_payment_pending` -> `IN_DELIVERY`;
  - `courier_spb_delivered_paid` -> `WON`.
- Все переходы запускаются сначала на `--dry-run`, затем на ограниченном окне
  заказов.

## Wave 4. SLA и smart-process

- Завести smart-process `Контроль интернет-заказа`.
- Создавать карточки для просроченного хранения, ручного разбора и конфликтов.
- Добавить ежедневный отчет по заказам на точках самовывоза и курьеру СПб.
